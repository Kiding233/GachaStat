为什么先分类

右栏排版参考页（rightcol_showcase.html）比的是「同一份内容怎么排」，结论是方案 A 最好。 但那只解决了一半：不同分析方法的主元素根本不是同一种东西。A 的骨架是「图为主」的 （眉题 → 标题 → 导语 → 主图 → 数据带 → 正文 → 表 → 脚注），把它直接套在「结果就是一张表」 或「结果就是一个数字」的方法上，主位会空着，读者不知道该看哪。

下面是 gui/analysis_panel.py 里实际产出的图形类型统计，不是凭印象分的：

type出现次数对应方法

scatter4GDR 时间序列、2D 瀑布、抽卡数 vs 达成率、转变分析

两处容易忽略的事实：

  • 多数项是「表 + 图」成对出现的（最差情形 = 统计量表 + 分布直方图），不是单一元素。 骨架必须给这对关系一个明确的主次，而不是把两张都平铺。
  • 过程分析 5 项全是表（事件统计、成败统计、事件→成败、成败→事件、轨迹详情）， 一条曲线都没有。给它们套「主图」骨架是错的。

六型（按「主位是谁」+「重要信息在哪」切）

判据只有两条：主位是读者第一眼该看到的东西；重要信息是这次分析真正要回答的问题。 骨架的变形只做一件事：把主位让给对的东西，把重要信息放到标注层与数据带里。

两处不套 A 骨架的特殊情形

脆弱性分析：结果块数是 2 + 2×池数，3 池 8 块、24 池 50 块。它不套 A， 走「总览常驻 + 逐项下钻」（见 docs/00-meta/UI设计体系/工作区交互形态.md §5.9）。 原因是 A 的前提是「一次分析产出一块结论」，而它一次产出几十块。
3D 瀑布图：3D 图在 868px 的框里不可读（透视会让近处的柱子遮住远处的，且无法精确读刻度）。 两条路：给它更大的框并允许全屏，或者降级成 2D 压缩瀑布图（waterfall_2d 本来就存在， 且已有散点实现）。倾向前者只在用户主动展开时提供，默认走 2D。

把六型压成一句规则

骨架不变，只换三件事：主位让给谁（图 / 表 / 数 / 矩阵）、数据带放什么（分位数 / 位置点 / 极值 / 取消）、 标注层标什么（尾部 / 拐点 / 最差项 / 极值格 / 异常行）。其余（眉题、标题、导语、图注体系、口径脚注、行长控制） 六型共用，这也是 A 能被选中的原因：它的骨架本来就是把「读者先看什么、后看什么」写死了， 换主位不破坏这个次序。

这一页没有解决的事

  • 型与方法的对应还没接进代码。本页的映射是读 analysis_panel.py 的 ChartSpec 现推的， 要落地需要在 AnalysisSpec 上显式声明「结果形态」（P86 §3.2 的注册表里加一个字段）， 否则前端只能靠猜。
  • 型 3 的池数上限没定。池数到几十个时横轴会挤，是横向滚动、排序截断、还是分组折叠，需要按真实配置量再定。
  • 型 5 与型 1/2 的混血没试。最差情形是「表 + 分布图」，本页把它归到型 1（图为主、表为佐证）， 但也可以反过来（表为主、图为佐证），取决于读者是「看形状」还是「读数字」，这个取向还没裁决。
  • 本页只做版面，不碰数据。所有数字都是固定的假值，用来撑起字阶与对齐，不追求统计自洽。
