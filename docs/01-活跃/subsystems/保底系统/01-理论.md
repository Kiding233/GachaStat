## 一、核心假设

### 1.1 概率调整的可加性假设

多保底管道假设**保底效果可叠加**：保底 A 调整概率分布后，保底 B 在 A 的结果上继续调整。

> **2026-09-15 复核勘误（2026-10-13 状态更新）**：本文件原称「P55 通过 `_resolve_order(behaviors, rarity_rank)` 控制执行顺序」，当时的代码实况是排序结果只写入 `self._behavior_list`、概率管道走 `spec.pity_names`（TOML 定义顺序），故**排序未接入管道**。该缺口已由 **P82-1**（并入 P64）接通：`PityEngine._pool_order` 承载排序结果，三个调度入口经 `get_behaviors_for_pool()` 消费。详见 §2.1。

**隐含假设**：
1. **调整方向一致性**：所有保底增加同一方向（提高高稀有度概率）。
2. **单调性保持**：概率调整后所有值的和为 1.0（归一化不变）。
3. **顺序依赖**：管道的最终概率分布依赖于保底的应用顺序。该顺序**自 P82-1 起为 `_resolve_order()` 的排序结果**（排序键 `(稀有度 rank, -priority, _BTYPE_ORDER, name)`，经 `PityEngine._pool_order` 进入管道）；`spec.pity_names` 仅保留 TOML 定义顺序供 `banner.draw_pity_names` 生成输出串，不再决定执行顺序。

### 1.2 目标定向机制

P55 通过 `target_featured` + `scope` + `featured_slots` 槽位分离实现定向提升。`compute_scope_mappings(pool)` 将 featured SSR 拆分为独立槽位 `ssr_featured`，概率提升仅作用于该槽位：standard SSR 保持基础概率不变。等价于旧系统的 `target_distribution` + `resolved_targets`，但通过声明式槽位系统替代运行时解析。

### 1.3 软保底概率递增模型（P55：RLE deltas）

P55 用 RLE（游程编码）deltas 统一替代旧三种 `func_type`：

```
deltas = ((起始段抽数, 每抽增量%), ...)
例：((80, 0.0), (10, 10.0)) → 前80抽0%→后10抽每抽+10%→第90抽到达100%
```

`soft_interval` / `soft_additive` 的语法糖在 preset 工厂内经 `_soft_deltas_of(pdef)` 展开为 deltas，统一由 `SoftModifier`（`core/pity_modifier.py`）消费（P64 前由 `SoftStepBehavior` 承担）。仅 `linear` 被保留：`exp` / `step` 函数已移除，含 `func` 键的条目被 `_check_pity_format()` 判为旧格式并硬拒。

### 1.4 重置条件

| 条件 | 含义 | 行为 |
|------|------|------|
| `featured` | 仅 featured SSR 重置计数器 | 提升仅对 featured 槽位，标准 SSR 保持基线概率 |
| `ssr` | 任何 SSR 出卡后重置 | 标准 gacha 行为 |
| （默认） | 未设置时回退为 scope 值 | 与 scope 同名的稀有度出卡时重置 |

重置条件由 `PityDef.reset` 承载，P64 起落到 `CounterTracker` 的 `reset_on` 形参（`core/pity_tracker.py`；`reset_on='never'` 即 G16 的「出金不重置」，无需特殊分支；`reset_on='on_effective'` 即「保底触发时归零」，判据是本抽该保底真的改动了分布，2026-10-15 新增）。`reset` 与 `target_featured` 正交：支持「仅提升 featured 但任意 SSR 重置」等灵活组合。合法取值集合见 `config_toml.legal_reset_values()`（空串 / `featured` / 稀有度名 / `never` / `on_effective`，未知值抛 `ConfigError`）；其中 `on_effective` 另有**类型面**白名单（只放阈值触发型 `hard` / `hard_exclude_owned_*`，其余 type 由 `create_behavior` 抛 `ConfigError`）。

## 二、多保底管道优先级（P82-1 已接线；2026-10-13 回写）

### 2.1 执行顺序：`_resolve_order()` 已接入概率管道

`_resolve_order(behaviors, rarity_rank)`（`core/pity.py`）按以下键排序：

1. **稀有度层级优先**：高稀有度（rank 值小）先执行
2. **`priority` 次之**：排序键取 `-priority`，即 **`PityDef.priority` 数值大者先执行**（P64 S6b 定，2026-10-13 回写）。注意方向：`core/notifier.py` 的 `Notifier.subscribe(priority=...)` 是**数值小者先执行**，两者同名反向、互不影响
3. **btype 分类再次**：`_BTYPE_ORDER` 的取值（`soft_interval`/`soft_additive`/`soft_step` = 0 → `hard` = 1 → `rotating_soft`/`rotating_cr`/`rotating_cr_soft` = 2 → `rotating`/`rotating_inverse`/`targeted`/`targeted_soft` = 3）
4. **name 字母序兜底**：同优先级按 name 确定性排序

**该排序结果已作用于概率计算（P82-1）**：`PityEngine.__init__` 预计算 `self._pool_order`（全局排序在池成员上的子序），三个调度入口（`get_probabilities` / `before_draw` / `after_draw`）经 `get_behaviors_for_pool(pool_id)` 消费它。「谁先执行」与「TOML 怎么写」自此解耦。

`PoolPitySpec.pity_names` **保持 TOML 定义顺序不动**：它兼有第二职责，`banner.draw_pity_names` 用 `','.join(pity_names)` 生成输出串，字面顺序会进 golden 快照，故不随排序改动。

> **2026-10-13 状态**：原「排序未接入管道、实际执行顺序为 TOML 定义顺序」的结论**已失效**（该缺口由 P82 承接、随 P64 落地接通）。`priority` 全为 0 时 `-0 == 0`，排序结果与接线前的默认序逐位相同，故接线不引入回归。
> **方向依据（P64 S6b）**：字段名直译即「优先级」，手册 3.4 节把该需求写作「福利保底和常规保底的优先级交互」，期望 `hard` 先于 `targeted`，即优先级高者先执行。

**尚未实施（M2 的 S8）**：`_apply_delta` 归一化到 `Σp = 1` 的**增量形式**，以及**卡级管道**（S8 起 `Modifier.apply` 的默认实现改调 `compute_delta`，内层零件只写 `compute_delta`）。M1 期各 Modifier 自实现 `apply`，按槽位级绝对赋值/因子形式工作，验收口径为「与旧类逐场一致」。

### 2.2 配置层安全网：`_validate_behaviors()`（已生效）

`_validate_behaviors()`（`core/pity.py`，定义于 `_resolve_order()` 之后）在 `PityEngine` 构造期执行，四条规则：
- name 重名 → `ValueError`
- 同 scope 两个硬保底 → `ConfigError`
- 同 scope 两个事件驱动型 → `ConfigError`
- 同 scope 同 type 两个软保底 → `ConfigError`

非法配置在构造期即被拒绝，比运行期告警强。

注意其**未覆盖**的范围：同 scope 的「一软一硬」是合法配置，混合触发时的覆盖不受此校验保护。

### 2.3 管道语义

保底按 `spec.pity_names` 的顺序依次调整概率，**后应用的保底覆盖前者的调整**。

该覆盖不止发生在「配置非法」时：`HardModifier.apply`（P64 前为 `HardPityBehavior._compute_probabilities`）触发时会以 `result = {k: 0.0 for k in dist}` 重建分布，把此前软保底的调整整体覆盖（更高稀有度槽位按 M1 形态豁免、原值保留）。

## 三、P55 概率调整的数学分析

> **2026-10-13 口径标注（P64 S7c）**：本节的两个小标题原名 `SoftStepBehavior._compute_probabilities()` / `HardPityBehavior._compute_probabilities()`，两个类已随 P64 从注册表与公共导出面退役，承载者改为 `SoftModifier.apply` / `HardModifier.apply`（`core/pity_modifier.py`）。**下面的公式描述是 P55 期形态，与当前实现有两处实质差异**，本节未按新形态重写，须以代码为准：① soft 的转移量现为**百分点绝对量** `t = min(boost_pct/100, p(Q))`（`steal = pool × boost_pct/100` 是旧式，两者差一个因子 `p(Q) ≈ 1`，爬升后段才拉开）；② soft 的分配权重现取**当前分布** `dist`（因子形式 `k_t = (p(A)+t)/p(A)`），而非下文写的**基础权重** `base(t)`。hard 侧的「重建分布 + 目标集按声明权重回填 100%」与下文一致，但**下文漏列 M1 形态的第三个组成**「**更高稀有度豁免、原值保留**」（`pity_modifier.py:212-214`，`Σ > 1` 的来源），故 hard 侧亦非逐项一致。

### 槽位模型

P55 起，概率调整以**槽位**（slot）为单位而非卡片。一个稀有度可拆成两个槽位：`ssr`（standard）与 `ssr_featured`（限定）。这层映射由 `compute_scope_mappings()` 预计算。

### SoftModifier.apply()（原 SoftStepBehavior._compute_probabilities()）

四步算法：

1. **累计 boost**：`_cumulative_boost(counter)` 遍历 deltas RLE，累加各段的「段长 × 每抽增量」，上限钳至 100
2. **定目标槽位**：取 `scope_slots[self._scope]`；`target_featured=True` 时收窄为 `featured_slots[self._scope]`
3. **定概率池**：`non_target = 所有槽位 − 目标槽位 − 更高稀有度槽位`（排除更高稀有度是层级保护，SSR 软保底不得窃取更稀有槽位的概率）
4. **重分配**：

```
pool   = Σ 非目标槽位概率
steal  = pool × boost_pct / 100
ratio  = 1 − boost_pct / 100

非目标槽位 s:  p'(s) = p(s) × ratio
目标槽位 t:    p'(t) = p(t) + steal × base(t) / Σ base(目标槽位)
```

**数学性质**：
- 归一化保持：`Σ p' = Σ p`（steal 的增量与 ratio 的削减量严格相等）
- 权重比例保持：目标槽位之间按**基础概率**比例分配，而非均分（均分会破坏 featured/standard 的内部比例）
- 兜底：所有目标槽位基础权重为 0 时退化为均分
- `boost_pct = 0` 时不调整；`boost_pct = 100` 时目标槽位独占全部池概率
- 早退：`scope_slots` 为空、`non_target` 为空、`pool <= 0` 三种情况均原样返回

### HardModifier.apply()（原 HardPityBehavior._compute_probabilities()）

`counter >= threshold` 时以 `result = {k: 0.0 for k in ctx.current}` 重建分布，仅按基础权重把目标槽位回填为 1.0。
