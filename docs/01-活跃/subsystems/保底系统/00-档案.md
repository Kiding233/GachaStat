## 业务问题

抽卡游戏的核心机制之一：随着玩家连续未抽到高稀有度卡片，系统逐渐提高高稀有度的出率，直到玩家「保底」获得高稀有度卡。保底机制深刻影响玩家的抽卡策略（何时该抽、何时该等）以及模拟结果的统计分布。

需要一个**多池多保底引擎**，能够：

1. 建模软保底（概率从某抽起逐渐递增）与硬保底（达到阈值时 100% 触发）
2. 支持一个池适用多个保底机制（如同时存在 SSR 软保底和限定硬保底）
3. 支持**事件驱动型**保底：大小保底轮换、定轨、捕获明光（P56）
4. 按配置顺序叠加应用多个保底
5. 支持多种重置条件（按稀有度 / 仅 featured / 多种组合）
6. 正确处理保底目标的概率分配：把提升的概率精确投向特定卡片（槽位系统）

## 设计意图

### 类层次（P64：Tracker + Modifier + Lifecycle 三元组）

```
PityBehavior (ABC)                     # 保底行为基类
└── Pity                               # 统一骨架（core/pity.py）
    ├── trackers:  List[Tracker]        # core/pity_tracker.py
    │   ├── CounterTracker              # 每抽 +1，出金按 reset_on 重置
    │   ├── FlagTracker                 # 二态标志翻转（hit / miss）
    │   ├── StreakTracker               # 连歪计数 + prepare 相位掷骰（捕获明光）
    │   ├── FateTracker                 # 命定值累积（定轨）
    │   └── NamespaceTracker            # 只声明命名空间（X_soft 的 _active 载体）
    ├── modifiers: List[Modifier]       # core/pity_modifier.py
    │   ├── HardModifier                # counter >= τ → 目标集 100%
    │   ├── SoftModifier                # boost 个百分点搬给 scope
    │   ├── RotatingModifier            # guaranteed → 非 featured 整组搬给 featured
    │   ├── NonFeaturedModifier         # 反向（G1 rotating_inverse）
    │   ├── SelectedModifier            # 定轨目标集
    │   └── NotOwnedModifier            # 排除已拥有（G3，S9 用）
    └── lifecycle: Lifecycle            # core/pity_tracker.py
        ├── AlwaysActive                # 常驻
        ├── FiniteActive                # max_triggers 用尽即退役
        ├── DependentActive             # depends_on 驱动
        └── DependentFiniteActive       # 两维复合
```

**一个保底 = 一组 Tracker + 一组 Modifier + 一个 Lifecycle**，由 preset 工厂（`_preset_<btype>(pdef) -> dict`）按 `PityDef` 字段组装。11 个 btype 全部 preset 化（`BEHAVIOR_REGISTRY` 条目一律 `class: None` + `preset`），故不再分「counter 驱动 / 事件驱动」两条继承链：分类只是 `btype` 经 `_SOFT_TYPES` / `_HARD_TYPES` / `_EVENT_DRIVEN_TYPES` 推导出的三个标志。

**旧行为类族的去向**：10 个旧类（`CounterBasedBehavior` / `SoftStepBehavior` / `HardPityBehavior` / `RotatingBehavior` / `RotatingCRBehavior` / `RotatingSoftBehavior` / `RotatingCRSoftBehavior` / `TargetedBehavior` / `TargetedSoftBehavior` 与 `SoftPityMixin`）的**类本体仍在 `pity.py` 内**，但已从 `BEHAVIOR_REGISTRY` 与 `core/__init__.py` 的公共导出面双双退役（2026-10-13 实测）。其删除归「发布前一次性移除旧类」那个 commit（P64 GATE-5 末条）；`create_behavior` 的旧类兼容分支同样保留到那时。

### 核心抽象

| 类 | 职责 | 关键方法 |
|----|------|---------|
| `PityBehavior (ABC)` | 保底行为基类 | `before_draw(ctx, readonly)` / `after_draw(ctx)` / `did_fire(ctx)` / `_rebind_state(state)` |
| `Pity` | **统一骨架**：消费 Tracker / Modifier / Lifecycle 三族零件 | `before_draw` 的 N1 三段（`advance` → `prepare` → Modifier 链）+ `after_draw` 的「退役先于 `commit`」；`_view_for(part)` 按零件命名空间取 view |
| `Tracker`（协议） | 状态推进与声明 | `rebind` / `advance` / `prepare` / `commit` / `did_reset` / `state_keys()` |
| `Modifier`（协议） | 概率分布改写 | `rebind` / `state_keys()` / `apply(ctx, view, dist, readonly)`（返回 `None` 表示不改动） |
| `Lifecycle`（协议） | 激活与退役判定 | `initialize` / `is_active` / `should_deactivate` / `deactivate` / `rebind` / `state_keys()` |
| `PityEngine` | 多池多保底引擎：三个调度入口 + 状态重绑定 | `get_probabilities()` / `before_draw()` / `after_draw()`；`get_behaviors_for_pool()`；查询类 `get_counter()` / `is_guaranteed()` / `is_active()` / `get_state_summary()` |
| `PityState` | 单次模拟的保底状态：三层嵌套 namespace | `get(name, key, default)` / `set()` / `incr()` / `clone()` / `to_dict()` / `from_dict()` |
| `PoolPitySpec` | 单个池的保底配置 | `pity_names`（TOML 顺序）+ `featured_ids`/`ssr_ids` + 五个槽位映射字段 |
| `DrawInfo`（frozen） | 本次抽卡的**静态事实**：贯穿管道的不可变部分 | `pool_id` / `reward_rarity` / `is_featured` / 五个槽位映射 / `rarity_rank` |
| `PityContext` | 管道中流转的**可变载体** | `draw: DrawInfo` + `current: Dict[str, float]` + `state: PityState` |
| `Counter` / `Flag` | `PityState` 的遥控器：记住地址、封装操作 | `Counter.incr()` / `.reset()` / `.value()` / `.reached()`；`Flag.set()` / `.clear()` / `.is_set()` |
| `LifecycleConfig`（frozen） | 跨 type 共享的生命周期参数 | `deactivate_on_early_hit` / `depends_on` 两个字段 |

`Counter`/`Flag` 的价值在于：behavior 不用每次拼字符串键名去读写状态，且 P75 的 `_rebind_state()` 只需重建这两个遥控器对象即可完成 state 切换。

### 11 种保底类型

下表按 GUI 下拉顺序（= `BEHAVIOR_REGISTRY` 字典书写顺序）排列，「零件组合」列即该 preset 产出的 Tracker / Modifier。

| # | btype | 显示名 | 零件组合 | 参数 |
|---|-------|--------|----------|------|
| 1 | `soft_interval` | 区间软保底 | `CounterTracker` + `SoftModifier` | `start`(80) / `end`(90) / `func`(linear) |
| 2 | `soft_additive` | 累加软保底 | 同上 | `start`(74) / `increment`(6.0%) |
| 3 | `soft_step` | 分段软保底 | 同上 | `deltas`（RLE 分段表） |
| 4 | `hard` | 硬保底 | `CounterTracker` + `HardModifier` | `threshold`(90) |
| 5 | `rotating` | 轮换保底 | `FlagTracker` + `RotatingModifier` | 无（guaranteed 二态翻转） |
| 6 | `rotating_inverse` | 反向轮换保底（连中必歪） | `FlagTracker` + `NonFeaturedModifier` | 无（G1，S6a 新增） |
| 7 | `rotating_soft` | 轮换+软保底 | `CounterTracker` + `FlagTracker` + `NamespaceTracker` + `SoftModifier` + `RotatingModifier` | 软保底 `start`/`increment` |
| 8 | `rotating_cr` | 轮换+捕获明光 | `StreakTracker` + `FlagTracker` + `RotatingModifier` | `cr_counter_threshold`(3) / `cr_base_rate`(5.0%) |
| 9 | `rotating_cr_soft` | 轮换+捕获明光+软保底 | 第 7、8 行两组零件的并集 | CR 两参数 + 软保底两参数 |
| 10 | `targeted` | 定轨保底 | `FateTracker` + `SelectedModifier` | `fate_threshold`(1) / `switch_allowed` / `switch_resets_progress` |
| 11 | `targeted_soft` | 定轨+软保底 | `FateTracker` + `CounterTracker` + `NamespaceTracker` + `SelectedModifier` + `SoftModifier` | 定轨三参数 + 软保底两参数 |

`soft_interval` / `soft_additive` 是 `soft_step` 的语法糖，三条共用同一个 preset 工厂（`_preset_soft_step`），差异只在 deltas 的来路（`_soft_deltas_of(pdef)` 三分支归一）；deltas 由 `SoftModifier` 消费。

语义：`rotating` 实现大小保底轮换（小保底沿用基础分布比例，大保底 featured 100%）；`rotating_inverse` 是它的对偶（出 UP 后下一次必非 UP）；`rotating_cr` 在 `rotating` 之上叠加捕获明光；`targeted` 实现定轨：锁定的目标卡（`selected_card`）与命定值累积（`fate_points`），支持中途切换及切换是否清零进度（后两者是策略层 `NonDrawAction` 的判定输入，由 `pity_engine.get_pity_def()` 直读 `PityDef`）。

> **`targeted` 的 `switch_allowed` / `switch_resets_progress` 不进 preset**：它们是 `GachaService` 策略层的判定输入，零件侧不消费。

### 保底管道机制

一个池可能适用多个保底（如 SSR 软保底提升概率 + 限定硬保底确保特定卡）。这些保底构成一条**管道**：前一个保底调整后的概率分布传入下一个继续调整，最终概率为管道末端输出。

管道载体是 `PityContext`：`current` 字段逐跳被覆写，`draw` 字段全程只读。

**管道顺序的现状（P82-1 已接线）**：由 `_resolve_order()` 的排序结果决定，排序键为 `(稀有度 rank, -priority, _BTYPE_ORDER, name)`（`priority` **数值大者先执行**，P64 S6b 定）。`PityEngine.__init__` 预计算 `self._pool_order`（全局排序在池成员上的子序），三个调度入口经 `get_behaviors_for_pool()` 消费它。`PoolPitySpec.pity_names` **保持 TOML 书写顺序不动**（`banner.draw_pity_names` 用它生成输出串，字面顺序会进 golden 快照），故「谁先执行」与「TOML 怎么写」自此解耦。

### P16 修复：查询/修改分离（含 P75 补充）

P16 修复之前，`get_probabilities()` 内部会隐式修改保底计数器，导致所有调用者（包括只做概率查询的策略）都产生副作用。修复后三个入口职责分离：

| 入口 | 计数器 | 用途 |
|------|--------|------|
| `get_probabilities()` | 只读（不递增） | 策略查询「按现在的保底状态，下一抽的概率是多少」 |
| `before_draw()` | 递增 | 实际抽卡前取调整后概率 |
| `after_draw()` | 按 `_should_reset()` 重置 | 抽卡后结算 |

**P75 补充**：以上三者的首行均为 `self._rebind_state(state)`，把 behaviors 的 `Counter`/`Flag` 重绑到本次调用传入的 `PityState` 实例（纯重定向、不复制旧值）。因此 `get_probabilities()` 不再是 P55 归档定义的无副作用纯查询：它仍**不写计数器**，但会改绑 behavior 的内部引用。这个重绑必须先于 `spec is None` 的早退，否则计数器会写入错账本。

## 技术实现

### 调用链

```
GachaService 每步决策:
  1. strategy.select_action(ctx)         # 策略可经 ctx.get_pity_probabilities() 只读查询
  2. pity_engine.before_draw(pool_id, state, base_probs)   # 递增计数器 + 管道调整概率
  3. 按调整后概率执行抽卡（banner.py 完成抽卡 + after_draw 调度）
  4. pity_engine.after_draw(pool_id, state, reward_id)     # 按重置条件结算
```
