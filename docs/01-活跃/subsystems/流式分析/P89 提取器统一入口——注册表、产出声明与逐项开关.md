# P89 提取器统一入口——注册表、产出声明与逐项开关

> 日期：2026-10-08 | 状态：设计中，实施未启动
> 触发：用户在「删除完整序列」专题讨论中提出「流式分析应该是统一唯一入口，不同的项目产出不同的数据，每个项目单独开关，下游分析读这些数据」
> 关系：与本子系统相关的 P86 §3.9（时间演化类图表重做与完整序列删除）是**一般与特例**的关系。§3.9 删掉其中一个提取器，本计划规范全部提取器；§3.9 的实施应是本计划的一次应用，不是并行的一件独立工作
> 前置：**分两阶段，依赖不同**（见 §四）。阶段 1 无任何依赖，**可立即开工**且与 P64 并行不冲突；阶段 2（逐项开关）须等 P86 / P87 的接口定型

## 一、问题

### 1.1 四套提取机制并存，只有两套在生产

`core/streaming.py` 里有四套做同一件事（从 `CompactResult` 提取派生数据）的机制：

| 机制 | 用在哪 | 形态 |
|---|---|---|
| `WorkerLocalExtractor` + `merge_extraction_packets` | **生产**：批量并行路径（`batch_simulator.py:414` 装配，`:559` 调用） | worker 侧每样本出一份轻量包，父进程合并 |
| `SharedResultCollector` + `extract_aggregate` | **生产**：仅 `core/worst_impact.py:132` 一处 | 父进程内的通用收集器（`add_extractor(name, func)`） |
| `DrawSequenceExtractor` | **仅测试**（`tests/core/test_transition.py`、`tests/gui/test_p72_key_repairs.py`） | 单进程、内部累积 |
| `StreamingAnalyzer` ABC + `StreamingSuccessCounter` | **仅测试** | 抽象基类与一个具体实现 |

`DrawSequenceExtractor` 是 `WorkerLocalExtractor` 的**单进程等价物**，两者的归约逻辑必须手工保持同步。`tests/gui/test_p72_key_repairs.py:253` 起那个测试就是为此存在的（对照两条路径的累积快照是否一致）。

**这是 P86 要消灭的「同一件事两份实现」的同一种病，只是发生在 core 内部。** 与 GUI/WebUI 那两份不同之处在于：这里的第二份没有消费者，只被测试维持着。

### 1.2 产出键没有声明，「数据集里有什么」靠读代码

现在产出是一组平铺的键：`aggregates` / `kept_sequences` / `cumulative_snapshots` / `transition_flags` / `heatmap_ach` / `heatmap_res` / `n_results`。它们由 `WorkerLocalExtractor.process` 的返回字典与 `merge_extraction_packets` 的返回字典两处**各自写死**，没有一处声明「这个提取器产出哪些键」。

后果：下游分析拿数据集时无法在运行前判断「这个分析能不能跑」，只能运行到中途发现字段为空（`gui/analysis_panel.py:1343` 的「转变分析需要池结束时间数据，但当前为空，已跳过」就是这种形态）。

### 1.3 跑一次就把全部提取器都跑了

现在没有开关。用户要一张 GDR 分布图，系统仍然会算热力图、累积快照、转变标记、完整序列。

这一层的产物现在全部落进数据集。P86 §3.9 已查明：单是完整序列一项就有 1.8 MB 量级，而其 6 个键中只有 1 个有消费点。不需要的提取器既费时又占体积。

### 1.4 一个已验证的性能缺陷（本次讨论中查出并已修）

`_build_merged_draw_arrays` 在逐抽循环里对 `bonus_events` 做线性扫描，复杂度 O(T×B)。实测 T=395 抽、B≈40 事件时每样本 15750 次徒劳比较。

2026-10-08 已按「先按 `draw_index` 建一次索引」修正，实测 707.7 → 325.6 µs/样本（2.17 倍），9 个平行数组逐元素等价（60 样本验证）。**该修正已落地**，本计划只需把它纳入「共享预处理」的设计（见 §3.2）。

## 二、目标

1. **一套机制**：`DrawSequenceExtractor` 与仅测试用的那套收掉，生产路径的两套统一为「注册表 + 声明」。
2. **产出可声明**：「数据集里有哪些键」由提取器的声明决定，不再由两处字典字面量决定。
3. **逐项开关**：开关是**运行参数**，不需要的提取器不跑。
4. **可判定**：给定「本次启用的提取器集合」与「某个分析项声明的依赖」，能在运行前判定该分析项能不能跑，缺什么报什么。
5. **顺带**：共享预处理只算一次（现在 `WorkerLocalExtractor.process` 一次，单进程路径的三个 `_update_*` 各一次，共 4 次）。

## 三、方案

### 3.1 提取器声明

复刻本项目已有的同构模式（P69 的 `@register_strategy`、P86 的 `@register_analysis`），做 `@register_extractor`：

```python
@dataclass(frozen=True)
class ExtractorSpec:
    key: str                      # 'heatmap'
    display_name: str             # '时间-档位热力图'
    produces: Tuple[str, ...]     # 产出的数据键（契约，见 §3.7）
    merge: str                    # 'extend' | 'sum' | 'extend_by_key'（父进程合并规则，见 §3.3）
    required: bool = False        # 见 §3.6
    fn: Callable[[Compact, SharedPrep], dict]   # 每样本归约
```

### 3.2 共享预处理归入口，不进提取器

`_build_merged_draw_arrays` 的产物（9 个平行数组）是所有提取器的公共输入。它应当是**入口的固定职责**：每样本算一次，传给同一批提取器。

这同时落实目标 5（现在是 4 次：`on_result` 一次加三个 `_update_*` 各一次）。

**提取器之间保持无依赖。** 现在确实没有依赖，不要引入。将来若真出现（如某提取器消费另一提取器的中间结果），用 `depends_on` 表达，项目已有先例（`[[banner.lifecycle]]` 的 `depends_on`）。

### 3.3 产出必须可合并

提取器跑在 worker 进程里，结果 pickle 回父进程合并（`merge_extraction_packets`）。**这决定了哪些提取器能存在**：产出必须满足可合并性。

| 合并规则 | 适用 | 现有产出 |
|---|---|---|
| `extend` | 每样本一条记录，顺序拼接 | `aggregates`、`transition_flags` |
| `sum` | 逐元素相加（直方图） | `heatmap_ach`、`heatmap_res` |
| `extend_by_key` | 按 key 分组后拼接 | `cumulative_snapshots`（按 banner 分组） |

**`kept_sequences` 是唯一不合群的**：它要「全局排序取前 K」，而每个 worker 只能看到自己那份，各自截断后再合并得不到正确结果（实测：`-w` 从 1 变到 8，保留数 22→176，**且留下的是哪些样本也变**）。这是 P86 §3.9 决定删它的理由之一。

**判据**：新增提取器时先问「它的产出能不能由各 worker 独立算完、再由父进程无损合并」。不能的，不应做成提取器。

### 3.4 与 P86 的接口：`requires ⊆ ∪ produces(已启用)`

**供方**：提取器声明 `produces`。
**需方**：分析项声明 `requires`（P86 §3.6 精化二已定）。

两侧用**同一套键名**，判定是静态的：

```
某分析项可跑  <=>  AnalysisSpec.requires ⊆ ⋃ produces(本次运行启用的提取器)
```

不满足时**报「本数据集缺 X，请用同一配置重跑并启用 X」**，不是静默空图。

**这正是「让用户知道」的机制**（用户 2026-10-05 指出：删掉某个提取器后，原有分析项在旧数据集上取不到数据，这本身没问题，但要能告知用户）。没有这套声明，开关设计会退化成静默失效。

### 3.5 与 P87 的接口：开关集合进统一元信息

**开关集合必须落进数据集的统一元信息**（P87 §3.5）。

理由：同一个配置跑三次（热力图开/关、累计开/关）会得到三个**外观完全相同**的节点，用户分辨不出哪个能画什么。缺了这条，整套开关设计不成立。

产出的键集合可由开关集合推出，不必另存。

### 3.6 必须有不可关的最小集

`aggregates`（每样本的 compact 摘要）**不能是可选的**：`compute_from_compact` 是几乎全部 GDR 的主路径，关掉它数据集就废了。

所以形态是「**一个必需产出 + N 个可选产出**」，不是「全部可关」。否则用户能关出一个空数据集。

`ExtractorSpec.required` 表达这件事；注册表导入期校验「至少有一个 `required` 提取器产出 `aggregates`」。

### 3.7 纪律：改语义必须换键名

键名是**跨层契约**（提取器的 `produces` 与 P86 的 `requires` 两侧写死同一套）。由此：

- **加键、删键不必升 `format_version`**（否则每加一个提取器都要升）
- **改语义必须换键名**。若某键的含义变了而不改名，下游会静默算错

这条与 P87 §3.11 H 是同一条纪律，本计划是它在 core 侧的落点。

### 3.8 开关的粒度与默认

建议粗粒度四个（对齐现有机制，不细到热力图的每个通道）：

| 开关 | 覆盖 | 产出键 |
|---|---|---|
| `aggregates` | 每样本摘要 | `aggregates`（**必需，不可关**） |
| `heatmap` | 时间-档位热力图 | `heatmap_ach`、`heatmap_res` |
| `cumulative` | 累积快照 | `cumulative_snapshots` |
| `transitions` | 转变标记 | `transition_flags` |

**默认全开**，现有行为不变。

**`transitions` 建议直接删除而不做成开关**：它是 `cumulative` 的纯函数（`core/per_pool_analysis.py` 的 `compute_transition_flags_from_gdr`），且现在有一个真实缺陷：`gui/analysis_panel.py:1357` 与 `webui/analysis_service.py:907` 都**无条件优先使用它**，不看用户选的 `success_criteria`，而它本身是硬编码的 `all_targets` 口径（`core/streaming.py:392` 的 `_check_success_draw_only`）。

删掉同时消掉冗余与那个静默口径错误，代价是每次分析重算一次 O(N·P)，可忽略。删掉之后提取器只剩 `aggregates`（必需）+ `heatmap` + `cumulative`，开关粒度小、契约面小。

## 四、实施阶段

**两阶段，依赖不同**（2026-10-08 拆）。原先是「实施未启动」一个整块，但其中「逐项开关」有外部依赖而其余没有。不拆会让人以为整份计划都要等接口定型，从而把可立即开工的那半也一起搁置。

| 阶段 | 内容 | 依赖 | 可否立即开始 |
|---|---|---|---|
| **1 收成一机制 + 产出声明** | `ExtractorSpec` / `@register_extractor` / `EXTRACTOR_REGISTRY` + 导入期校验；`WorkerLocalExtractor` 按注册表装配；合并规则由 `merge` 驱动；共享预处理归入口（每样本一次）；删 `DrawSequenceExtractor`、`StreamingAnalyzer` ABC、`StreamingSuccessCounter` | **无** | **是** |
| **2 逐项开关** | 开关做成运行参数并接到装配处；`requires ⊆ ∪ produces` 的静态判定与「缺 X，请重跑并启用 X」的提示；开关集合进 P87 的统一元信息 | P87 §3.5（元信息字段）+ P86 §3.6（`requires` 声明） | 否，须等两处接口定型 |

### 4.1 阶段 1 的边界：排除 `SharedResultCollector` 那一支

`SharedResultCollector` 被 `core/worst_impact.py:132` **生产使用**，而最差影响的改造属 **P87 阶段 3**（拆三段 + 保留 `analyze()` 为过渡外壳）。若阶段 1 一并收编它，就要同时改 `worst_impact.py`，等于把 P87 的活提前做了。

**排除之后，阶段 1 完全不碰 `worst_impact.py`**，只处理 `core/streaming.py` 里那三套：`WorkerLocalExtractor`（生产保留，改为按注册表装配）、`DrawSequenceExtractor` 与 `StreamingAnalyzer` ABC / `StreamingSuccessCounter`（删除）。

阶段 1 结束时 `streaming.py` 的形态是「**一套注册表 + 一个历史遗留的通用收集器**」。这是可接受的中间态（后者只有一处消费者），等 P87 阶段 3 落地后随最差影响一起收掉。

### 4.2 与 P64 / P87 / P86 的顺序

```
P64 ──────────────┐
                  ├─→ P87 ─→ P86 ─→ P89 阶段 2
P89 阶段 1 ───────┘
```

**阶段 1 与 P64 可并行。** 查证依据：P64 波及 `core/pity.py` 与两个新建文件（`pity_primitives.py` / `pity_condition.py`）为主，加上 `service/batch_simulator.py` 的**保底配置透传段**（`:218-243`、`:1161-1186`）；阶段 1 触及同一文件的**提取器装配段**（`:414`、`:559`、`:828-831`）。**同文件、不同区域**，与「P87 等 P64」的理由（两者改 `config_panel.py` / `config_toml.py` 的同一批行）不同。

**阶段 2 必须等 P87 与 P86。** 理由不是技术耦合，是**没有元信息字段时开关会制造混乱**：同一个配置跑三次（热力图开/关、累计开/关）会得到三个**外观完全相同**的节点，用户分辨不出哪个能画什么。同理，「缺 X，请重跑并启用 X」要等 P86 的 `requires`。

**阶段 1 不阻塞任何东西**，所以它不插到 P64 前面，而是与 P64 并行。

| 风险 | 等级 | 缓解 |
|---|---|---|
| `SharedResultCollector` 被 `worst_impact.py` 生产使用 | 🟢 低 | **已由 §4.1 排除出阶段 1**，两阶段都不动它；待 P87 阶段 3 改造最差影响时一并收掉 |

## 七、验收标准

**阶段 1**（前六条至「新增一个提取器只需写一处」）与**阶段 2**（其后的开关与元信息条目、等价性对照）分别验收；阶段 1 完成即有可用产物。


- [ ] `EXTRACTOR_REGISTRY` 建成，每个提取器声明 `produces` / `merge` / `required`；导入期校验通过
- [ ] `core/streaming.py` 只剩一套提取机制；`DrawSequenceExtractor` / `StreamingAnalyzer` / `StreamingSuccessCounter` 已删，全仓无残留
- [ ] 共享预处理 `_build_merged_draw_arrays` 每样本只调一次（计数或计时可验）
- [ ] 开关可关：关掉 `heatmap` 后数据集不含 `heatmap_ach` / `heatmap_res`
- [ ] 必需产出不可关：试图关掉 `aggregates` 被拒绝并给出原因
- [ ] `requires ⊆ ∪ produces` 可静态判定；不满足时报「缺 X，请重跑并启用 X」，不静默空图
- [ ] 数据集元信息记录本次启用的提取器集合
- [ ] 新增一个提取器只需写一处（注册表中的一条记录），`WorkerLocalExtractor` 与合并逻辑不改
- [ ] 同配置、同种子、同参数下，开关全开时的产出与改动前逐字段一致（等价性对照）
- [ ] `pytest` 全过；`benchmarks/` 中涉及提取产出的契约断言同步

## 八、边界与不做的事

| 不做 | 理由 | 触发条件 |
|---|---|---|
| 提取器之间声明依赖 | 现在没有依赖，不引入 | 出现真实依赖（某提取器消费另一提取器的中间结果） |
| 细粒度开关（热力图每个通道各一个） | 粒度小则契约面小，先粗后细 | 出现「只想开其中一个通道」的真实需求 |
| 提取器插件化（第三方扩展） | 与 `@register_strategy` 的插件体系不同，无证据 | 出现外部扩展需求 |
| `transitions` 做成开关 | 见 §3.8，建议直接删 | 若保留，需先修口径不一致（`success_criteria` 被忽略） |
