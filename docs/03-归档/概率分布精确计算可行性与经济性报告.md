# 池子配置概率分布精确计算 · 可行性与经济性报告

> 日期：2026-06-14 | 状态：草案 | 作者：AI 分析

---

## 摘要

本文评估将池子配置文件（`pools/*.txt`）中定义的概率分布从 IEEE 754 浮点数切换为精确有理数计算的可行性与经济性。结论：**全链路 Fraction 方案经济性不可接受**（保底热路径 ~10× 减速）；**推荐混合方案：配置解析层 Fraction 精确化 + 运行时浮点归一化**——零热路径开销、最小代码改动（~30 行）、保证概率分布总和恒精确为 1.0。

---

## 1. 现状分析

### 1.1 概率配置格式

池子分布文件（如 [`character_pool.txt`](../gacha_simulator/config/pools/character_pool.txt)）使用 bracket 语法定义三层结构：

```ini
[1]:0.004           # 稀有度层概率（绝对）
[1]=[featured,offrate]  # 嵌套子分布
[featured]:0.5      # 子分布内权重（相对）
[offrate]:0.5
[featured]=ssr      # 叶子 → 卡片绑定
```

### 1.2 解析 → 抽卡数据流

```
pools/*.txt (文本) 
  → parse_distribution_file() [pool_config.py:203]  ← float() 入口
    → resolve_leaves() [pool_config.py:255]         ← 嵌套概率乘法
    → _expand_binding() [pool_config.py:289]        ← 多卡权重切分
  → Pool.__post_init__() [pool.py:190]              ← 累积权重 float 求和
  → PityEngine.get_probabilities() [pity.py:205]    ← 保底概率重分配
  → Pool.draw() [pool.py:218]                       ← random.random() * total
```

**关键发现**：浮点转换发生在 `parse_distribution_file()` 的第 230 行——`float(prob_match.group(2))`。自此之后，全部运算均为 IEEE 754 双精度。

### 1.3 当前实际精度

```
池子模板          浮点和    偏差
──────────────────────────────────
character_pool   1.0       0.00e+00
standard_pool    1.0       0.00e+00
weapon_pool      1.0       0.00e+00
```

现配置恰好和为 1.0——因为 0.004 + 0.051 + 0.945 的二进制近似误差相互抵消。**这纯属巧合，不具备稳定性**。若用户将 `[3]:0.945` 改为 `[3]:0.944` 并新增 `[4]:0.001`，浮点和可能偏离 1.0。

### 1.4 偏差的下游影响

`Pool.draw()` 使用 `random.random() * self._total_weight` 配合 `bisect` 查找。若 `_total_weight = 0.9999999999999999`，则有效随机区间为 `[0, 0.999…9)` 而非 `[0, 1.0)`，最后一段奖励的概率微幅缩水约 1e-16。

**实际影响**：模拟 10^9 次抽卡，期望偏差 < 1 次。对统计推断无实质影响，但**理论严格性受损**。

## 2. 四种精确方案

### 2.1 方案 A：全链路 `fractions.Fraction`

**原理**：所有概率用 Python 标准库 `Fraction`（任意精度有理数）表示。`Fraction(numerator, denominator)` 存储为两个任意大整数，四则运算保持精确。

**可行性**：✅ 完全可行。Python 3.10+ 内置，无需额外依赖。所有保底运算（加法、乘法、min）在有理数域闭合。

**保底兼容性**：✅ 天然兼容。`SoftPityBehavior` 的 `progress` = `Fraction(counter - start, end - start)` 精确。`_apply_targeted` 中 `new_target = current_target + progress * other` 精确。

**性能基准**（100,000 次运算）：

```
场景                 float       Fraction      倍率
─────────────────────────────────────────────────
配置解析 (乘+加)    0.0058s     0.4440s      77×
保底重分配 (20卡)   0.1620s     1.5323s       9.5×
累积权重构造        0.1014s     1.3481s      13.3×
```

**经济性**：❌ 不可接受。保底热路径 10× 减速意味着 N=10^6 模拟额外耗时 ~13s。若启用多 worker 并行，Fraction 对象不可 pickle 跨进程传输（需序列化为 `(numerator, denominator)` 对后在子进程重建），进一步增加开销。

**此外**：保底操作中的连续乘法会导致分母膨胀。每步 `Fraction * Fraction` 约使分母位数翻倍。深度 100 次保底应用后分母可达 ~300 位，单次运算从 0.4ns 退化至 ~10ns（25× 膨胀）。

### 2.2 方案 B：全链路 `decimal.Decimal`

**原理**：用 `Decimal`（可控精度十进制浮点）替代 `float`。`Decimal('0.004')` 精确存储十进制小数，无二进制近似误差。

**可行性**：✅ 可行。Python 标准库，支持四则运算、比较、min/max。

**保底兼容性**：⚠️ 有条件兼容。需设置上下文精度（`getcontext().prec = 28`）。`progress = Decimal(counter - start) / Decimal(end - start)` 可能产生无限小数（如 1/3），被上下文精度截断——本质上仍是近似计算，只是近似在十进制而非二进制。

**性能**：~10× 慢于 float（场景 1 中 9.6×），较 Fraction 快约 8×。

**经济性**：⚠️ 中等。性能损失可接受（N=10^6 额外 ~3s），且 Decimal 可 pickle 跨进程。但**并未实现真正「精确」**——1/3 等非十进制有理数仍被截断。

### 2.3 方案 C：整数权重（配置格式改造）

**原理**：废除十进制小数配置格式，改为整数权重。例如：

```ini
# 当前 (浮点)
[1]:0.004

# 改造后 (整数权重)
[1]:4/1000
# 或采用隐式分母
[TOTAL]:1000000
[1]:4000
```

所有内部概率以整数计数表示，概率 = 权重 / 总和。

**可行性**：✅ 数学完美，但需改造配置格式 + 解析器 + 所有下游读取方。

**保底兼容性**：⚠️ 保底操作涉及乘法缩放 (`prob * scale`)，缩放因子为有理数（如 `new_other_prob / other_prob`）。整数权重 × 有理缩放 = 有理数，需取整——取整引入可控误差（< 1/total_weight）。

**经济性**：❌ 不经济。改动面过大——需修改 3 个模板文件、`parse_distribution_file`、`_expand_binding`、`Pool.__post_init__`、`PityEngine`、`ConfigStore` 序列化、JSON 导出/导入，以及 4 个面板的数据显示路径。约 200+ 行改动，且破坏现有配置文件兼容性。

### 2.4 方案 D：混合方案（解析层 Fraction + 运行时归一化浮点）★ 推荐

**原理**：

```
配置解析阶段 (冷路径，仅一次)
  ┌─────────────────────────────────────────┐
  │ 文本 "0.004"                             │
  │   → Fraction('0.004')  = 4/1000          │
  │ 构建概率树（Fraction 精确乘除）            │
  │   → ["limited_ssr_1": 1/500, ...]        │
  │ 归一化 → 确保 Σ = 1                     │
  │   → 转为 float 存入 Pool.rewards        │
  └─────────────────────────────────────────┘

运行时阶段 (热路径)
  ┌─────────────────────────────────────────┐
  │ Pool.__post_init__: 累积权重 → float      │
  │ PityEngine.get_probabilities: float 运算  │
  │ Pool.draw: random.random() * total       │
  │   — 与现状完全相同，零性能退化             │
  └─────────────────────────────────────────┘
```

**可行性**：✅ 完全可行。

- `Fraction(str)` 可从十进制字符串精确构造（`Fraction('0.004')` = `Fraction(1, 250)`）
- 嵌套概率树构建用 Fraction 乘法——精确
- 多卡权重切分用 Fraction——精确
- 最终归一化：`sum(probs) == 1` 恒成立（在有理数域）
- 转为 float 后虽仍受 IEEE 754 限制，但**归一化保证 Σ_f = 1.0**

**关键洞察**：浮点 `sum(probs) != 1.0` 的根因不是单个值的表示误差，而是**未归一化**。只要将分布显式归一化到 1.0，即使每个值有 ±1e-16 的表示误差，累积权重终点确实为 1.0。这是 IEEE 754 的基本性质：`x / x == 1.0`（当 x > 0）。

**保底兼容性**：✅ 完全兼容。运行时概率为归一化 float，保底介入后可能再次偏离 1.0（误差 < 1e-15），但每次 `Pool._apply_probabilities()` 调用后可通过归一化恢复。

**代码改动量**：~30 行，集中在 `parse_distribution_file()` 和 `Pool.__post_init__()`。

**性能**：配置解析增加 ~0.4ms（一次），运行时零性能退化。

## 4. 推荐方案实施路径

### Phase 1：配置解析精确化（核心，~20 行）

修改 `parse_distribution_file()` [pool_config.py:203-286](..\gacha_simulator\core\pool_config.py#L203-L286)：

1. **第 230 行** — `prob = float(prob_match.group(2))` → `prob = Fraction(prob_match.group(2))`
2. **`resolve_leaves()` 内部** — 所有乘除改用 Fraction 运算
3. **返回前** — Fraction 归一化 + 转 float：

```python
# 在 parse_distribution_file() 末尾，rewards 构建之后
total = Fraction(0, 1)
frac_rewards = []
for reward, prob in rewards:
    f_prob = Fraction(prob) if not isinstance(prob, Fraction) else prob
    frac_rewards.append((reward, f_prob))
    total += f_prob

normalized = []
for reward, f_prob in frac_rewards:
    normalized.append((reward, float(f_prob / total)))
return normalized
```

### Phase 2：保底后归一化（加固，~10 行）

修改 `Pool._apply_probabilities()` [pool.py:208-216](..\gacha_simulator\core\pool.py#L208-L216)：

```python
def _apply_probabilities(self, probabilities: Dict[str, float]):
    total = sum(probabilities.values())
    if total > 0 and abs(total - 1.0) > 1e-15:
        # 保底介入后归一化，确保累积权重终点 = 1.0
        probabilities = {k: v / total for k, v in probabilities.items()}
    # ... 原有逻辑
```

### Phase 3：配置验证（可选，~5 行）

在 `Pool.__post_init__()` 末尾添加断言/日志：

```python
if abs(self._total_weight - 1.0) > 1e-12:
    logger.warning("Pool %s total_weight=%.15f deviates from 1.0", 
                   self.id, self._total_weight)
```

### 总改动量

- `pool_config.py`：~20 行（解析链路 Fraction 化）
- `pool.py`：~10 行（`__post_init__` 归一化守卫 + `_apply_probabilities` 归一化）
- 不涉及：pity.py、strategy.py、config_io.py、任何 gui/ 文件、任何 config/ 文件

## 5. 未解决的理论问题

### 5.1 保底介入后的误差传播

即使配置解析完全精确，`SoftPityBehavior._apply_targeted()` 中：

```python
new_target_prob = min(current_target_prob + progress * other_prob, 1.0)
new_other_prob = 1.0 - new_target_prob
scale = new_other_prob / other_prob
result[rid] = prob * scale
```

经过一次保底调整后，`sum(result.values()) = 1.0` 在实数域成立，但在浮点域可能有 ~1e-16 误差。**Phase 2 的归一化守卫可修复此问题**。

### 5.2 `random.random()` 的固有浮点性

即使内部概率完全精确，`random.random()` 返回 IEEE 754 `[0, 1)` 浮点数。这意味着抽卡决议本身精度上限为 2^-53 ≈ 1.1e-16。对概率分布中极小值（如 1e-15 级别的概率），可能永远抽不到。当前配置最小概率 ~1/6000 ≈ 1.7e-4，远高于此阈值，不构成实际问题。

### 5.3 权重绑定的精度

`_expand_binding()` [pool_config.py:289](..\gacha_simulator\core\pool_config.py#L289) 中的多卡权重切分：

```python
results.append((cid, prob * (w / total_weight)))
```

当 `w / total_weight` 为无限小数（如绑定 3 张卡权重均等 → 1/3），浮点表示有误差。**Phase 1 的 Fraction 化可解决**——Fraction(1, 3) 为精确有理数，只在最终转 float 时引入一次近似，而非每步累积。

## 6. 结论

| 问题 | 答案 |
|------|------|
| 能否实现精确计算？ | ✅ 可以——混合方案在配置层用 Fraction，保证解析阶段绝对精确 |
| 能否兼容保底机制？ | ✅ 完全兼容——保底 + 归一化守卫保证运行时 Σ=1 |
| 经济性如何？ | ✅ 优秀——~30 行改动，零热路径性能退化，不破坏兼容性 |
| 推荐方案 | **方案 D：配置解析 Fraction 精确化 + 运行时归一化** |

全链路 Fraction/Decimal 在学术界有理论吸引力，但在工程上不经济——10× 热路径减速 + 跨进程序列化开销，换取的仅是 10^-16 级别的精度提升，而该精度差异对统计推断无实质影响。混合方案以最小代价达成「配置概率和恒为 1」的核心目标，是当前架构下的帕累托最优解。
