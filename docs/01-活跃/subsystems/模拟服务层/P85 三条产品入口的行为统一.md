# P85 三条产品入口的行为统一

> 日期：2026-09-30 | 状态：设计中
> 触发：用户质疑「为什么两条路径行为不同，不应该是只是调用核心引擎的入口的问题吗」
> 前置报告：[独立分析-入口行为统一-2026-09-29](../04-收件箱/独立分析-入口行为统一-2026-09-29.md)（独立子 agent 产出，22 处差异清单 + 三套方案，均为实测或代码取证）
> **历史脉络**：本计划是 **P54（CLI/GUI 统一化重构，2026-06-15 归档）的下一层**。P54 解决的是「入口不共用引擎」（CLI 当时自写 55 行 `run_single_sim()` 独立于 `run_batch_parallel()`），已经完成。本计划解决的是它没覆盖的那一层：**共用引擎之后，行为仍然不一致**。

## 一、问题

### 1.1 现状：调用点已统一，胶水没有

三条产品入口（GUI `gui/gacha_panel.py`、WebUI `webui/api.py`、CLI `cli.py`）**确实都在调用同一个核心函数** `run_batch_parallel`（`service/batch_simulator.py`），而且实参表逐项几乎相同（唯一差异是 CLI 多传一个性能采集开关，那是 P83 测量通道，已有裁决）。

但行为仍不一致，因为差异全部落在**两段胶水**上：

1. **调用之前**：各自往 `env`（模拟环境对象）上写不同的字段；
2. **调用之后**：各自用不同方式消费返回值。

这类差异不会在「看调用点」时暴露，只会在「看用户看到的数字」时暴露。

### 1.2 根因：调用态被塞进了配置态

`env`（`SimulationEnv`）承载的是「这个世界长什么样」（池子、保底引擎、初始资源），它会被序列化送给每个 worker，是**共享的配置态**。

而 `return_compact`（worker 要不要把每次模拟的完整明细回传父进程）、`n_heatmap_bins`（热力图分箱数）这类字段，表达的是「**这一次调用我要什么输出**」，是**调用态**。把它们放在 `env` 上，等于让每个入口各自去改一个共享对象：谁忘了改，谁就静默漂移。

CLI 正是在 `return_compact` 这一项上忘了改（GUI 与 WebUI 各自设了假），后果是同一个核心函数、同一份配置，CLI 的进程内存是 GUI 的约 2.7 倍。

### 1.3 差异清单（22 处，按性质分类）

完整清单与逐条实测见前置报告 §2、§3。摘要：

| 性质 | 条目 | 说明 |
|---|---|---|
| **用户可见的不一致** | E1、E2、F1、C2 | 见下 |
| **缺陷级（功能整体失效）** | G2（**已修**）、G1、H1 | 见下 |
| **契约与卫生** | B1、B2、B4、D1、H2 | `return_compact` / `n_heatmap_bins` 三条不一致、字段未声明、核心函数回写调用方对象、缺省值重复 5 次 |
| **无害的写法漂移** | A3、B5、B6、D2、D3、E3 | 结果等价，仅写法不同，建议顺手收敛 |
| **本就应该不同** | A1、A2（回调形态）、B3、F2 | 界面形态或测量通道决定，**不属于要统一的范畴** |

**四条用户可见的不一致**：

- **E1｜同一个名字「SSR 数量」在两个入口指不同的量**：CLI 用目标卡编号（`cli.py:417`），GUI 用全部 SSR 编号含常驻（`gacha_panel.py:399`）。实测同种子同次数：**4.75 对 5.10**。
- **E2｜没有配置目标卡时口径分岔**：CLI 有兜底（拼 `_ssr`），GUI 与 WebUI 无兜底，报 0。
- **F1｜配置校验闸门不一致**：GUI 会拦下「Banner/池子标识重复」这类错误（该错误会导致保底串池），WebUI 只在**保存配置时**校验、模拟入口不校验，CLI 完全不校验。实测：重复 Banner 标识的配置在 CLI 上**正常运行、退出码 0**。
- **C2｜不抽卡基线的异常处理不同**：CLI 打印告警，GUI 与 WebUI 是 `except Exception: pass` 静默吞掉。

**三条缺陷级**：

- **G2｜插件策略在并行进程数大于 1 时整批静默失败**（**2026-09-30 已修，commit `38962ab`**）：三条入口的插件注册都在**函数体内**，而 Windows spawn 的子进程只执行主模块的模块级代码，父进程那份注册传不过去。
- **G1｜并行路径的失败次数无人计数**：调用方不传流式回调时，失败既不入结果列表也不计数，三条入口在并行路径下都拿不到失败数。
- **H1｜WebUI 进程从不加载插件策略**：`webui/` 全目录无任何 `load_plugin_strategies()` 调用，插件管理页形同虚设。**已登记进 P74**（见该计划 §八）。

### 1.4 另外两条独立缺陷（本次调查中新发现，一并登记）

- **I1｜模拟结果依赖运行日期，破坏可复现性**：`ConfigStore.sim_start_date` 默认取 `date.today()`（`core/config_store.py:295`），而 `monthly_day` 类收入规则按这个起始日期展开调度表（`core/resource_gain.py:168` 起）。对照实验（只改这一个字段）：起始日期 2026-09-29 / 09-30 / 10-15 → 最终资源 `exchange_currency` 为 **300 / 250 / 300**。**后果**：同一份配置、同一个种子，今天跑与明天跑结果不同；「同种子同结果」这一被当作回归判据的前提在跨天时不成立（影响 P83 的基线回归体系）。
- **I2｜`sim_start_date` 不落盘**：`core/config_toml.py` **完全不读写**该字段，所以 GUI 配置面板里的「模拟起始日期」控件（`config_panel.py:5178`）改了也存不住，每次加载配置都重置为今天。这两条是同一个字段的两面。

### 1.5 相邻调查：影响 GUI 路径的问题（17 条，其中 5 条高危）

针对「有没有其他影响 GUI 路径的问题」另派了一次独立只读排查，**结论是有，且不在少数**。
完整报告：[独立调查-GUI路径问题-2026-09-30](../04-收件箱/独立调查-GUI路径问题-2026-09-30.md)。

**五条高危（全部为 GUI 独有）**：

| # | 问题 | 关键证据 |
|---|---|---|
| 1 | **模拟完成后的主线程后处理没有异常兜底，一旦抛错整个 GUI 进程静默消失** | 实测：槽内抛 `RuntimeError` → `returncode 3221226505`（abort），stdout/stderr 皆空，连 traceback 都没有。`main_window.py:342-508` 与 `gacha_panel.py:339-370` 全程无 try/except |
| 2 | **模拟运行期间配置仍可编辑，完成回调读「此刻」的 store，落库指纹与实际运行不一致** | `start_simulation` 只禁用了自己那颗按钮（`gacha_panel.py:317`），无运行中标志；完成回调在 `main_window.py:387-456` 读 `self._store`。污染 `compare_fingerprints`（`core/result_store.py:334-350`） |
| 3 | **未知策略键在 GUI 被静默替换成 smart，CLI 则报错** | `config_panel.py:7495` 的 else 分支回落到 `'按需追卡'`（= smart 的显示名），`:7197-7198` 再反向写回 `store.strategy_key` |
| 4 | **`BatchResult.warnings` 三条入口都没有消费者** | 全仓 grep 只命中 `batch_simulator.py` 自身与 `gacha_service.py`。通道里装的是「路径降级」与「零进度」告警，而路径降级影响的正是 GUI/WebUI 的默认路径 |
| 5 | **并行路径下失败计数永不累加，`n_failed` 对 GUI 恒为 0** | `batch_simulator.py:848-854` 的 `elif compact is not None` 分支。GUI/WebUI 设了 `return_compact=False` 且不传 `on_result`，两条合起来结构性不触发；**CLI 因不设该字段而幸免** |

另有中危 8 条（`QThread.finished` 被同名信号遮蔽、用 `terminate()` 强杀正在跑进程池的线程、状态栏消息被覆盖、`setCurrentIndex(2)` 魔数、`seed=-1` 的指纹、`n_heatmap_bins` 未声明字段、dict 引用共享、目标达成率语义）、依赖关系问题 4 条（`benchmarks/` 反向依赖 GUI 内部并对源码做文本断言、GUI 调 core 私有函数与跨面板私有方法、`gui/batch_simulator.py` 是 0 字节同名空文件）。

**范围界定**：其中与「入口统一」直接相关的（第 4、5 条，以及中危里的 `n_heatmap_bins`、dict 引用共享、SSR 口径）**归本计划**；第 1、2、3 条与中危的多数条目属于 **GUI 自身的健壮性问题**，与本计划同源（都是「胶水分散」的后果）但修复面不同，**是否并入本计划待定**，或另立计划。

## 二、目标

1. **把「选择」定义在一处**：三条入口只负责「收集用户参数」与「把结果渲染成自己界面的样子」，中间那段（校验、构造环境、设置隐含字段、跑主模拟、跑不抽卡基线、组装统一结果）由共享层负责。
2. **用户可见的指标一致**：E1、E2、F1 消除。
3. **新增入口不再复制胶水**：这是「结构性统一」而非「三处对齐维持」的判据。
4. **可复现性成立**：I1、I2 消除（起始日期要么固定进配置、要么显式排除出可复现性声明）。

## 三、方案

**用户已表态：偏好方案乙（入口薄壳化），但具体方案之后再讨论。** 故本节只登记三套方案的轮廓，实施细节待专门讨论。

### 方案甲：最小对齐（不改核心函数签名）

只修「用户看得到或会致错」的项：E1 口径、E2 兜底、F1 校验下沉、C2 异常处理、G1 失败计数、H1 插件加载、B2 字段声明。

- 工程量约 1 天（不含测试）
- **局限**：B1、B4、D1 仍在，三条入口仍各自维护一段胶水

### 方案乙：入口薄壳化（用户偏好）

新增一层共享编排，输入是配置来源、模拟次数、进程数、种子、策略，以及三项运行开关；内部按固定顺序做完全部流程；三条入口退化为「组参数、调用、渲染」。

- **收益**：C2、D1、D2、D3、B1、B2、B3、B6、A3 这一整类「三处各写一遍」的差异从结构上消失
- **风险**：GUI 的编排必须留在 Qt 线程内，共享层不得持有任何 Qt 对象
- 工程量约 2 到 3 天

### 方案丙：核心函数契约显式化（只做部分）

把「读 env 上的隐式字段」改成显式参数，成败计数无条件化，`n_heatmap_bins` 与 `metrics_dir` 声明为字段。

- **不建议做的一条**：翻转 `return_compact` 的默认值。独立调查查明三处依赖方（`core/retreat_search.py:207-217` 依赖明细做广义出率判定、`core/worst_impact.py:140-152` 与 `scripts/profile_sim.py:85-92` 通过流式回调拿明细），且它还是 P83 跨路径比对的**可比性维度**（`benchmarks/perf/record.py:13,24-26`），翻转会让这些静默失效。

### 建议顺序

甲的 1、3、5、6 四条（口径、校验闸门、失败计数、插件）→ 乙 → 丙的第 2、3 条。

## 五、风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 翻转 `return_compact` 默认值的爆炸半径（撤退搜索 / 最差影响 / 三个脚本 / P83 基线体系） | 🔴 高 | **本计划不做这一条**；若要动，须先解耦「真失败」与「未回传结果」的表示，并登记为「改动产品默认行为」 |
| 共享编排层退化成「按入口类型分支」的新胶水 | 🟡 中 | 把三处合理差异（进度回调、是否需要明细、是否持久化）写成显式参数 |
| GUI 编排必须留在 Qt 线程内 | 🟡 中 | 共享层设计时写死「不持有任何 Qt 对象」 |
| E1 改动会改变 CLI 既有输出数字 | 🟢 低 | 属语义修正，`RELEASED=False` 阶段做代价最低；须在测试里固化新口径 |
| 合约测试需同步 | 🟡 中 | `tests/benchmarks/` 有一批断言「适配器申报值与实际驱动方式一致」的用例，凡改调用形状都要同步 |

## 六、验收标准

- [ ] E1、E2、F1、C2 四项用户可见的不一致消除，且各有测试固化
- [ ] G1 失败计数在并行路径可见（请求数 / 成功数 / 失败数进入批结果容器）
- [ ] **三入口等价比对**：同一配置、同一模拟次数、进程数、种子、策略下，三条入口产出的「每次模拟聚合数据集合」逐项相等。**注意并行到达顺序不保证一致，必须按种子排序后再比**，该比对固化为自动化测试
- [ ] 插件策略在单进程与多进程下均产出全部结果（G2 的回归测试固化）
- [ ] I1 消除：同配置同种子在任意运行日期产出相同结果（或以显式声明的方式排除该依赖）
- [ ] I2 消除：`sim_start_date` 可经 `config.toml` 读写
- [ ] 新增一条入口时，无需复制任何胶水（由方案乙的实现结构保证）
