## 二、缺陷详解与改进方案

### 2.1 缺陷 12：策略不满足贝尔曼最优性（严重，设计澄清）

**现状**：策略均为一阶前瞻（或零阶），检查当前条件，立即行动，不递归评估未来状态的期望价值。（原记载「7 种策略」，P69 后为 8 种。）

**具体后果**：
- 没有策略能权衡「现在花费资源抽此池」vs「等待更好的池子」
- 没有策略能预测保底计数器在未来池子中的价值
- `future_schedules` 已传入 `StrategyContext` 但**没有任何策略使用它**

**理论立场**（来自审查 §2.4 理论澄清）：

> 策略系统采用**基于规则的启发式**而非期望效用最大化，这一选择本身是合理的：抽卡游戏的最优策略通常是 NP-hard 的（多池多保底多资源多目标的随机动态规划），实际游戏中玩家也使用启发式。理论审查的重点不是要求实现贝尔曼最优，而是**明确文档化这一设计决策**。

**推荐方案**：
1. **文档化设计决策**：在 `strategy.py` 模块级 docstring 中明确说明启发式性质
2. **UI 标注**：在策略选择下拉框、策略比较面板中添加 Tooltip 说明启发式性质
3. **future_schedules 使用或移除**：要么让至少一个策略使用它，要么标注为「预留字段，当前未被任何策略使用」
4. **可选：贝尔曼基准**：对极简化场景用动态规划求解真正最优策略，作为评估启发式质量的基准，属研究级增强，非工程必需

**文献**：Simon (1956), *Psychological Review*（满意原则）；Bellman (1957), *Dynamic Programming*

> **处置决定**（2026-06-13）：关于页面「策略行为说明」tab 已覆盖用户核心需求：告知每个策略的决策逻辑、适用场景和局限。原推荐方案 1–4 经评估后不予实施：
> - 推荐 1（docstring）：不实施，用户不读源码 docstring，关于页面是正确位置
> - 推荐 2（UI Tooltip）：不实施，关于页面已覆盖，额外 Tooltip 冗余
> - 推荐 3（future_schedules）：不实施，字段后续需求明确时再启用
> - 推荐 4（贝尔曼基准）：不实施，属研究级增强，无用户需求

**最终状态**：✅ 已处置。两点实测补充（2026-09-15）。
- 关于页面 tab（`gui/about_dialog.py:361-435`）逐项说明 **7 个策略**（smart / pool_quota / pity_reserve / stop_on_target / target_hunting / fixed_count / no_draw），**未含第 8 个 `draw_target`**（internal，最差影响分析专用）。同文件「关于」tab `:68` 另写「6 种策略（按需追卡、指定池配额、保底预留、目标即停、指定池追卡、固定次数）」，与注册表实际 8 个（6 公开 + 2 internal）不符：属该 tab 自身的陈旧表述，非本计划的处置范围。
- 四个未来信息字段（`future_schedules` / `future_resource_gains` / `inter_pool_pity_links` / `time_discount`）至今无策略消费。

### 2.2 缺陷 13：策略间无统一效用函数（中等）→ 已由 P19 覆盖

> **处置**：2026-06-13 标记。元目标选择器已在 P19 Phase 3 #3「L5 偏好排序」中规划（λ 滑块 + CARA/CRRA 效用函数），本条不再由 P30 追踪。

**现状**：各策略服务于不同的隐式目标（成功率最大化 / 资源最小化 / 风险规避），无共同度量标准。「策略 A 优于策略 B」的断言在不指定元目标时无定义。

**推荐方案**：
1. **策略比较面板文档**：在比较结果中明确说明比较的维度（如「在给定 GDR 阈值下的成功率」），避免暗示存在绝对优劣
2. **多维比较**：展示多维雷达图（成功率 / 平均资源消耗 / 最差资源消耗 / 目标卡收集率），而非单一排名
3. **元目标选择器**：允许用户选择比较维度（「按成功率」「按资源效率」「按稳健性（最差情形）」），不同元目标下策略排名可能不同

**最终状态**（2026-09-15 复核）：⏸ 已委托。P19 Phase 3 八项整体**暂缓**（🟠），#3 的暂缓理由为「需要 λ 滑块 UI 调节效率/风险权重 + CARA/CRRA 效用函数，用户群体不熟悉」。P19 清单另拆出 **3a「极简前置」**（策略比较面板 L1 表上方一行说明文字，零新功能，来源即本条），**经裁决暂不实施**（2026-09-14），该条仍挂在 P19 清单中。

### 2.3 缺陷 14：StrategyContext 信息不完备（中等）

**原记载现状**：`StrategyContext` 不提供：
- 未来资源收入预测（每日任务奖励）
- 未来池子的奖励分布（只有 pool_id 和时间）
- 时间贴现因子
- 池间保底链接关系

**推荐方案**：
1. **文档化当前局限**：在 `StrategyContext` docstring 中列出「当前未提供但可能相关的信息」
2. **增量补充**（低风险）：
   - `future_resource_gains`：从 `schedule_mgr` 计算未来每日资源收入，已有全部数据，仅需聚合并传入
   - `inter_pool_pity_links`：从 `PityEngine` 的保底配置中提取跨池保底继承关系
3. **暂不补充**（需设计讨论）：
   - 未来池子的奖励分布：需要完整的未来卡池数据，超出当前配置范围
   - 时间贴现因子：需用户研究确定有意义的默认值

**归档时的记载**（P69 阶段 2）：推荐 1、2 已落地，`time_discount` 字段也一并加入。三者由 `build_strategy_context()` 统一计算，均带默认值。

> **复核勘误**（2026-09-15）：上述记载只对了一半。**字段与计算分支确实存在，但在实际模拟中三者恒为默认常量**：
>
> | 字段 | 恒定的原因 |
> |------|-----------|
> | `future_resource_gains` | 计算受 `if resource_gain is not None and lookahead` 门控（`strategy_context_builder.py:86`）。`lookahead` 取自 `gacha_service.py:335` 的 `self.strategy.lookahead`，而 8 个内置策略**全部**为 `None`（5 个显式声明 `lookahead = None`，其余 3 个继承基类默认）→ 恒为 `{}`。`future_schedules` 同理恒为 `[]` |
> | `inter_pool_pity_links` | 提取分支要求 behavior 具备长度 > 1 的 `pools` 或 `_pools` 属性（`strategy_context_builder.py:95`）。`create_behavior()` 构造 behavior 时从不传 `pools`（`PityDef.pools` 未被消费），behavior 类也无 `_pools` 赋值点 → 恒为 `{}` |
> | `time_discount` | 唯一调用点 `gacha_service.py:422-441` 未传该参数，全库无其它传值处 → 恒为 `1.0` |
>
> 因此本缺陷的准确状态是：**基础设施已就位，但未接通数据源**。`future_resource_gains` 的原始设计更有一处数据源错配：早期实现从 `schedule_mgr` 取资源日程，而后者只管理池子开放窗口、不含资源信息（勘误见 `docs/02-待办/Ps01`），后改为 `resource_gain.compute()`，但仍受 `lookahead` 门控。

**最终状态**：⚠️ **部分落地**：字段定义、计算分支、默认值齐备，但运行中恒为常量（上表三个原因）。**无任何策略消费**这一点属实。**未来池子的奖励分布**仍未提供（需完整未来卡池数据，超出当前配置范围）。

### 2.4 缺陷 11：多保底管道无优先级逻辑（中等）

**现状**：保底按定义顺序依次调整概率分布。当软保底和硬保底同时触发且目标集不同时，后处理的行为可能覆盖前者的调整。无冲突解决机制。

**推荐方案**：
1. **文档化当前行为**：在 `pity.py` 模块 docstring 中说明管道顺序语义
2. **冲突检测**：在 `PityEngine.__init__()` 中增加检测：若两个保底适用同一池且目标集部分重叠，发出 `warnings.warn()` 提示潜在冲突
3. **长期方向（方案 A）**：支持显式优先级字段，新增可选的 `priority` 列，数值越小优先级越高
4. **长期方向（方案 B）**：取最高概率，当多个保底同时作用于同一抽时，取它们给出的 SSR 概率的最大值

**依赖**：此缺陷与 P16（保底缺陷修复，已完成）互补。P16 修复了计数器和归一化的代码 bug，本缺陷处理的是保底交互的语义定义。

**归档时的记载**（P55/P56）：由两道机制在原方案之上更强地解决：`_resolve_order()` 给出确定性排序键 `(稀有度 rank, btype 顺序, name)`；`_validate_behaviors()` 把 `warnings.warn()` 升级为硬性 `ConfigError`。

> **复核勘误**（2026-09-15）：两条机制**只有一条真正生效**，且生效的那条并未触及缺陷原文所指的问题。
>
> **① 冲突检测：✅ 确实生效。** `_validate_behaviors()`（`pity.py:1001-1053`）在 `PityEngine` 构造期执行，四条规则与归档记载逐字一致：name 重名 → `ValueError`；同 scope 两个硬保底 / 同 scope 两个事件驱动型 / 同 scope 同 btype 两个软保底 → `ConfigError`。这比原方案的 `warnings.warn()` 强，配置错误在构造期即被拒绝。
>
> **② 顺序确定性：❌ 未接通，缺陷原文所述问题依然存在。** `_resolve_order()`（`pity.py:984-998`）确实存在、排序键也确实是 `(rank, order, name)`，但其输出**只赋给 `self._behavior_list`**（`pity.py:1260`），而概率管道三个入口（`get_probabilities` / `before_draw` / `after_draw`）走的是另一条路：
>
> ```
> get_behaviors_for_pool(pool_id)          # pity.py:1271
>   → for pname in spec.pity_names          # pity.py:1277
> ```
>
> `spec.pity_names` 由 `batch_simulator.py:172-176` 按 `pity_defs_list` 的**TOML 定义顺序**逐个 append 生成（`worst_impact.py:540` 同一写法，全库仅此两处构造 `PoolPitySpec`，无任何再排序）。`_behavior_list` 的全部消费点只有 `_rebind_state` 的重绑定循环（`pity.py:1329`）与 `strategy_context_builder.py:93` 的跨池链接提取：**都与顺序无关**。
>
> 结论：`_resolve_order()` 目前是「算了但没人按顺序用」。缺陷原文「顺序由定义顺序决定」在代码上**仍然成立**。这是一个**真实的功能缺口**（可能是有意留待后续，也可能是遗漏），需要单独立项判定，不在本计划处置范围内。
>
> **③「覆盖场景不可能发生」的表述过强。** 四条校验只禁止「同 scope 两个硬保底」「同 scope 两个事件驱动型」「同 scope 同 btype 两个软保底」三类；同 scope 的**「一软一硬」是合法配置**，而该场景下覆盖确实发生：`SoftStepBehavior._compute_probabilities` 重分配概率后，`HardPityBehavior._compute_probabilities` 触发时以 `result = {k: 0.0 for k in ctx.current}` 重建分布，软保底的调整被整体覆盖。跨稀有度场景由排序键的稀有度优先级保护，但同 scope 内的覆盖未被防住。
>
> **④ 未实施方案 A / B**：显式 `priority` 字段与「取最高概率」均未实施，这一点属实（全库无 `priority` 字段，管道为后写覆盖）。

**最终状态**：⚠️ **部分解决**：推荐方案 2（冲突检测）已以更强形式落地；推荐方案 1（顺序语义文档化）与 3/4（方案 A/B）未实施；缺陷原文所述「顺序由定义顺序决定」的问题**未被解决**，`_resolve_order()` 未接入概率管道。
