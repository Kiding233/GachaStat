# P41 目标卡实例权重架构改造——可行性分析

> 日期：2026-06-12 | 更新：2026-07-29 | 状态：分析中 | 优先级：低
> 来源：用户需求——同名目标卡 ≥2 张时支持按实例（副本）区分权重
> 设计方向：**分离架构**——目标卡与权重独立升级，两棵独立的树
> 涉及层：config → core → service → gui
> 
> **优先级说明：** 分离架构下 P41 与所有活跃计划（P55/P56/P57/P58）零依赖——不阻碍任何计划，也不被任何计划简化。当前架构已覆盖 90%+ 用例。待活跃计划收敛后再排期。
> **P70 前置完成：** `config_panel.py` 的「目标卡」Tab 已独立（`_setup_target_tab()`）——P41 恢复时目标卡 UI 改动仅需操作此方法，不受策略段影响。

## 1. 目标

**现状：** 两套独立结构——`target_cards: List[TargetCardEntry]` 管抽卡目标，`card_weights: Dict[str, CardWeightEntry]` 管权重。后者以 `card_id` 为键，同名卡的所有副本共享同一权重值。

**问题：**
1. `Dict[str, CardWeightEntry]` ——同一 `card_id` 只有一个条目，无法区分「第 1 张」和「第 2 张」
2. 权重仅绑定到目标卡——`card_value_weights.get(cid, 0.0)` 对非目标卡静默返回 0.0（`_gdr_total_card_value`），无法表达「歪到它值钱但不会特意追」
3. 不支持动态表达式

**目标：**
1. 同名卡 ≥2 张时，每个副本（实例）可有独立权重
2. 权重独立于目标——非目标卡也可以有权重
3. 支持 `ExpressionWeight` 动态求值
4. 架构上支持未来新增权重类型

**设计决策：分离而非合并。** 原草案将目标卡与权重合并为 `TargetInstance`，但强行绑定了「有权重的卡=目标卡」。分离架构保持两棵独立的树——`target_cards` 定义「追什么」，`card_weights` 定义「值多少」——各自独立升级。

## 2. 核心数据结构变更

### 2.1 TargetCardEntry —— 不变

```python
@dataclass
class TargetCardEntry:
    card_id: str
    quantity: int = 1
    pool_ids: List[str] = field(default_factory=list)
```

目标卡定义完全不变——只回答「抽哪些卡、各几张、在哪些池子」。不携带任何权重。

### 2.2 CardWeightEntry —— 升级

```python
WeightValue = Union[float, 'ExpressionWeight']


@dataclass
class CardWeightEntry:
    """一张卡的一个实例（副本）的权重。

    同一 card_id 可出现多次——每条对应该卡的一个副本。
    card_id 无需在 target_cards 中出现——非目标卡也能有权重。

    instance_index 不显式存储——该 card_id 在 card_weights 列表中
    第 N 次出现 = 第 N 张副本（0-based）。
    """
    card_id: str                              # ← 新增，替代旧 Dict 的键
    desire_weight: WeightValue = 1.0
    miss_cost_weight: WeightValue = 1.0
    card_value: WeightValue = 1.0
    add_order: float = 1.0
    remove_order: float = 1.0
```

### 2.3 ConfigStore 变更

```python
# 旧
card_weights: Dict[str, CardWeightEntry]   # {card_id: 权重}

# 新
card_weights: List[CardWeightEntry]        # 有序列表，同 card_id 可多次出现
```

权重查找函数：

```python
def resolve_instance_weight(
    weights: List[CardWeightEntry],
    card_id: str,
    instance_index: int,
    key: str,            # "desire_weight" | "miss_cost_weight" | "card_value" | ...
    ctx: WeightEvalContext,
    default: float = 1.0,          # ← 调用方指定默认值
) -> float:
    """查 (card_id, instance_index) 的权重，无匹配 → 返回 default。

    尾条兜底：instance_index 超出条目数时复用最后一条。

    default 参数由调用方按语义设置：
    - desire / miss_cost → 1.0（目标卡的满足/错失默认等权）
    - card_value → 取决于是否目标卡（见 total_card_value 实现）
    """
    entries = [w for w in weights if w.card_id == card_id]
    if not entries:
        return default
    if instance_index < len(entries):
        entry = entries[instance_index]
    else:
        entry = entries[-1]
    return _resolve_weight(getattr(entry, key), ctx)
```

### 2.4 示例

```python
target_cards = [
    TargetCardEntry("limited_ssr_1", quantity=2, pool_ids=["pool_c1"]),  # 目标：抽 2 张
    TargetCardEntry("limited_ssr_2", quantity=1, pool_ids=["pool_c1"]),  # 目标：抽 1 张
]

card_weights = [
    # ssr_1 第 1 张：高权重
    CardWeightEntry("limited_ssr_1", desire_weight=2.0, miss_cost_weight=3.0),
    # ssr_1 第 2 张：低权重
    CardWeightEntry("limited_ssr_1", desire_weight=0.5, miss_cost_weight=0.8),
    # ssr_2 动态表达式——有了 ssr_1 后 desire 降为 0.1
    CardWeightEntry("limited_ssr_2",
        desire_weight=ExpressionWeight(
            "0.1 if acquired.get('limited_ssr_1', 0) > 0 else 2.0")),
    # 非目标卡——歪到值 5.0 分
    CardWeightEntry("limited_ssr_x", card_value=5.0),
]
```

### 2.5 与合并架构（原草案）的对比

```
合并架构（已废弃）：
  TargetInstance(card_id, quantity, pool_ids, weights)
  → 一张卡 ×2 = 两行 TargetInstance，各行 quantity=1
  → 有权重 = 必然是目标卡

分离架构（当前）：
  TargetCardEntry(card_id, quantity, pool_ids)     ← 不变
  CardWeightEntry(card_id, desire, miss, ...)      ← 升级为列表
  → 一张卡 ×2 = 一行 TargetCardEntry(quantity=2) + 两行 CardWeightEntry
  → 非目标卡可仅有 CardWeightEntry
```

## 3. 权重系统设计（两层）

`instance_index` 不单独存储——已在 `WeightEvalContext` 中，表达式可以直接用。类型层次仅两层：

```python
WeightValue = Union[float, 'ExpressionWeight']
# float  = 静态值。同名卡不同权重 = 多条权重条目
# ExpressionWeight = 任意 Python 表达式，覆盖动态/跨卡/参数化/按实例索引


class ExpressionWeight:
    """可序列化的权重表达式——编译为受限 callable。"""
    expression: str

    def compile(self) -> Callable[['WeightEvalContext'], float]:
        code = compile(self.expression, '<weight_expr>', 'eval')
        def evaluator(ctx: WeightEvalContext) -> float:
            return eval(code, {'__builtins__': {}}, ctx.to_namespace())
        return evaluator
```

无 `InstanceWeight`、无 `is_static()`、无中间地带。

### 3.1 求值上下文

```python
@dataclass
class WeightEvalContext:
    # ── 实例身份 ──
    card_id: str                          # 当前卡 ID
    instance_index: int                   # 该同名卡中的序号 (0-based)

    # ── 模拟状态 ──
    acquired: Dict[str, int]              # {card_id: 已抽到累计数量}
    draw_number: int                      # 当前总抽数 (1-based)
    simulation_day: int                   # 当前模拟日
    active_pool_id: str                   # 当前活动池
    resources: Dict[str, float]           # 当前剩余资源

    # ── 用户扩展 ──
    extra: Dict[str, Any]                 # 用户自定义参数

    def to_namespace(self) -> Dict[str, Any]:
        return {
            'card_id': self.card_id,
            'instance_index': self.instance_index,
            'acquired': self.acquired,
            'draw_number': self.draw_number,
            'simulation_day': self.simulation_day,
            'active_pool_id': self.active_pool_id,
            'resources': self.resources,
            'extra': self.extra,
        }
```

### 3.2 实例消耗语义（顺序模型）

抽到第 k 张该卡 → `instance_index = k` → 权重求值。

```
card_A ×2: desire_weight = $[2.0, 0.5][instance_index] if instance_index < 2 else 1.0$
  抽到 0 张 → 全部缺失
  抽到 1 张 → instance_index=0 → desire=2.0   ✓
  抽到 2 张 → instance_index=1 → desire=0.5   ✓

更简洁等价写法：$2.0 / (instance_index + 1)$
```

**`instance_index` 的推导：** 运行时从 `state.acquired[card_id]`（抽前值）推导——`instance_index = state.acquired.get(card_id, 0)`。事后 GDR 从 `card_counts` 出发，迭代时维护局部计数器。P58 就绪后两处统一读 `state.acquired`——单一真相源。

### 3.3 方案搜索的边界

排序键（`add_order` / `remove_order`）必须在模拟前确定全序。只接受 `float`，拒绝 `ExpressionWeight`：

```python
def validate_search_weight(spec: WeightValue, key_name: str) -> float:
    """add_order / remove_order：float 通过，ExpressionWeight 拒绝。"""
    if isinstance(spec, (int, float)):
        return float(spec)
    raise SearchWeightError(
        f"{key_name} 不接受表达式: {spec.expression}。"
        f"同名卡不同排序权重请用多条权重条目（每行不同 float）。"
    )
```

## 4. 配置格式

### 4.1 TOML：两个独立节

`[[targets]]` 不变，`[[weights]]` 从 Dict 升级为 List（同 card_id 允许多条目）：

```toml
# ═══ [[targets]] —— 只管抽卡目标，不变 ═══
[[targets]]
card_id = "limited_ssr_1"
quantity = 2
pool_ids = ["pool_c1", "pool_c7"]

[[targets]]
card_id = "limited_ssr_2"
quantity = 1
pool_ids = ["pool_c2"]

# ═══ [[weights]] —— 独立权重，可选，同名卡可多条 ═══
# 权重值语法：
#   2.0                  → 静态 float
#   "$expr$"             → ExpressionWeight（$ 分隔符内的 Python 表达式，TOML 中需加引号）

# 第 1 张 ssr_1：高权重
[[weights]]
card_id = "limited_ssr_1"
desire_weight = 2.0
miss_cost_weight = 3.0
card_value = 1.0

# 第 2 张 ssr_1：低权重
[[weights]]
card_id = "limited_ssr_1"
desire_weight = 0.5
miss_cost_weight = 0.8

# 非目标卡——只在 [[weights]] 中，不在 [[targets]] 中
# 「歪到它值 5.0 分，但不会特意去追」
[[weights]]
card_id = "limited_ssr_x"
card_value = 5.0

# 动态表达式——有了 ssr_1 后 desire 降为 0.1
[[weights]]
card_id = "limited_ssr_2"
desire_weight = "$0.1 if acquired.get('limited_ssr_1', 0) > 0 else 2.0$"
```

### 4.2 字段定义

| 字段 | 类型 | 默认值 | 说明 | UI 编辑入口 |
|------|------|--------|------|-----------|
| `card_id` | str | — | 必填。可对应目标卡或任意池内卡牌 | 权重面板 |
| `desire_weight` | WeightValue | 1.0 | 抽取意愿（→ weighted_satisfaction） | 权重面板 |
| `miss_cost_weight` | WeightValue | 1.0 | 错失代价（→ 未完成目标的惩罚） | 权重面板 |
| `card_value` | WeightValue | 1.0 | 卡牌价值（→ total_card_value） | 权重面板 |
| `add_order` | float | 1.0 | 前进法加入优先级（高→先加入） | **方案搜索面板** |
| `remove_order` | float | 1.0 | 后退法移除优先级（低→先移除） | **方案搜索面板** |

`add_order` / `remove_order` 仅接受 `float`，编辑入口在方案搜索面板。

### 4.3 表达式语法

- `"$...$"` 包裹的是 Python 表达式，求值时命名空间 = `WeightEvalContext.to_namespace()` 的所有字段
- 可用变量：`instance_index`, `acquired`, `draw_number`, `simulation_day`, `active_pool_id`, `resources`, `extra`
- 安全性：`eval()` 关闭 `__builtins__`，只能做纯计算
- `add_order` / `remove_order` 禁用表达式（方案搜索需静态全序）
- 预编译校验：`ExpressionWeight` 构造时即 `compile()`——语法错误在加载配置时暴露

### 4.4 扩展性

新增权重列 = 在 `CardWeightEntry` 加一个字段 + 在 TOML `[[weights]]` 中加一个可选键。未知字段忽略（向前兼容）。

## 5. GDR 计算改造

### 5.1 核心原则：不同指标用不同驱动源

| GDR 指标 | 迭代驱动 | 用到的权重 |
|---------|---------|-----------|
| `target_achievement` | `target_cards` | 无（纯计数） |
| `target_collection` | `target_cards` | 无 |
| `all_targets` | `target_cards` | 无 |
| `weighted_satisfaction` | **`target_cards`** | desire + miss_cost |
| `total_card_value` | **`card_counts`**（所有抽到的卡） | card_value |
| `extra_target` | `target_cards` | 无 |
| `resource_efficiency` | `target_cards` | 无 |
| `target_card_draws` | `target_cards` | 无 |

### 5.2 weighted_satisfaction —— 由 target_cards 驱动

与当前 `_gdr_weighted_satisfaction`（`gdr.py:395-409`）语义完全等价，仅权重寻址方式从 `Dict[card_id]` 变为 `resolve_weight(weights, card_id, instance_index)`：

```python
def _gdr_weighted_satisfaction_v2(compact, target_cards, card_weights, **kwargs):
    """由 target_cards 驱动迭代，权重从独立的 card_weights 列表查找。"""
    card_counts = compact.get('card_counts', {})
    satisfaction = 0.0

    for tc in target_cards:
        actual = card_counts.get(tc.card_id, 0)
        for i in range(tc.quantity):
            desire = resolve_weight(card_weights, tc.card_id, i, 'desire_weight', ctx)
            miss   = resolve_weight(card_weights, tc.card_id, i, 'miss_cost_weight', ctx)
            if i < actual:
                satisfaction += desire
            else:
                satisfaction -= miss              # ← miss_cost 逻辑完全保留
    return satisfaction
```

示例——`ssr_1 × 2`、实际抽到 1 张：

```
旧：got=1 → +desire["ssr_1"], missed=1 → -miss_cost["ssr_1"]
新：i=0 < actual → +desire[ssr_1, 0],  i=1 ≥ actual → -miss_cost[ssr_1, 1]
→ 结果相同，唯一区别是第 1、2 张可取不同权重
```

### 5.3 total_card_value —— 由 card_counts 驱动

```python
def _gdr_total_card_value_v2(compact, target_cards, card_weights, **kwargs):
    """由 card_counts 驱动——所有抽到的卡都计值，包括非目标卡。"""
    card_counts = compact.get('card_counts', {})
    target_ids = {tc.card_id for tc in target_cards}
    total = 0.0
    for card_id, cnt in card_counts.items():
        # 目标卡默认 1.0，非目标卡默认 0.0（向后兼容旧行为）
        default_val = 1.0 if card_id in target_ids else 0.0
        for i in range(cnt):
            total += resolve_weight(card_weights, card_id, i, 'card_value', ctx,
                                    default=default_val)
    return total
```

与旧逻辑的精确对应：

| 场景 | 旧 `_gdr_total_card_value` | 新 `_gdr_total_card_value_v2` |
|------|--------------------------|-----------------------------|
| 目标卡，有 weight 条目 | `card_value_weights[cid]` | `card_weights` 对应条目的 card_value |
| 目标卡，无 weight 条目 | `{cid: 1.0 for cid in target_specs}` → 1.0 | `default=1.0`（因 card_id in target_ids） |
| 非目标卡，有 weight 条目 | `card_value_weights.get(cid, 0.0)` → **0.0**（Dict 中不存在） | `card_weights` 对应条目 → 用户配置的值 ✅ |
| 非目标卡，无 weight 条目 | `0.0` | `default=0.0`（因 card_id ∉ target_ids） |

**关键改进：** 旧架构中非目标卡即使配置了 `card_value` 也被忽略（`card_value_weights` Dict 只含目标卡）。新架构中配置了就能生效——这正是分离架构的核心价值。

### 5.4 权重条目多于/少于 quantity

```
target:  ssr_1 × 2
weights: ssr_1 有 3 条（[0]=desire=2.0, [1]=desire=0.5, [2]=desire=0.3）
实际:    抽到 3 张

weighted_satisfaction:
  i=0 → desire[0]=2.0  (抽到了)
  i=1 → desire[1]=0.5  (抽到了)
  → 迭代结束（quantity=2），[2]条不被问到——目标只要求 2 张

total_card_value:
  i=0 → card_value[0]  (第1张)
  i=1 → card_value[1]  (第2张)
  i=2 → card_value[2]  (第3张，超出目标但仍计值)
  → 迭代到 card_counts=3

如果 quantity=3 但 weights 只有 2 条：
  i=2 → resolve_weight 命中尾条兜底 → entries[-1]
```

### 5.5 无权重函数 + history-based 路径

以下 GDR 函数不涉及权重，仅需遍历 `target_cards` 展开 quantity——逻辑比旧架构更简单（统一了遍历模式）：

| 函数 | 改造 |
|------|------|
| `_gdr_target_achievement` | 遍历 `target_cards`，累计 `min(card_counts[cid], tc.quantity)` |
| `_gdr_target_collection` | 同上 |
| `_gdr_all_targets` | 同上 |
| `_gdr_extra_target` | 同上 |
| `_gdr_resource_efficiency` | 同上 |
| `_gdr_target_card_draws` | 同上 |

history-based 路径（`compute_all_gdr`，`gdr.py:770-815`）中 `weighted_satisfaction(history, ctx, get_weight, miss_cost_func)` 同样适配——`get_weight` / `miss_cost_func` callable 内部切换至 `resolve_instance_weight`。适配方式与 compact 路径一致（`card_weights` 优先，旧 Dict fallback）。

### 5.6 GDRCalculator / make_gdr_calculator 过渡

当前 `GDRCalculator` 存储 `desire_weights` / `miss_cost_weights` / `card_value_weights` 三个独立 Dict。新参数追加，旧参数保留（过渡期并存）：

```python
class GDRCalculator:

                 card_value_weights=None,

        self.target_cards = target_cards or []
        self.card_weights = card_weights or []

        self.miss_cost_weights = miss_cost_weights

    def compute_gdr(self, compact):

            compact,
            target_specs=self.target_specs,

            desire_weights=self.desire_weights,       # 旧路径仍可用
            card_weights=self.card_weights,            # 新路径
            target_cards=self.target_cards,            # 新路径
            ...

```

`compute_gdr_from_compact` 将 `card_weights` / `target_cards` 透传至各 GDR 函数（通过 `**kwargs`）。各函数优先使用 `card_weights`（新路径），fallback 到旧 Dict：

```python
def _gdr_weighted_satisfaction(compact, target_specs, desire_weights=None,
                                miss_cost_weights=None, card_weights=None,
                                target_cards=None, **kwargs):
    if card_weights is not None and target_cards is not None:
        return _gdr_weighted_satisfaction_v2(compact, target_cards, card_weights, **kwargs)
    # 旧路径不变
    ...
```

`make_gdr_calculator` 同步传递新参数：

```python
def make_gdr_calculator(store, target_specs, gdr_key, *, ...):
```

`ConfigStore` 便捷属性（`desire_weights` 等）标记 deprecated 但保留——旧调用方不受影响。过渡期后（Phase F）移除旧 Dict 路径。

## 6. 非目标卡权重的语义边界

分离架构下，一张卡可以只在 `[[weights]]` 中而不在 `[[targets]]` 中。各权重的适用性由 GDR 函数的迭代驱动源自判——无需 `is_target` 标记：

| 权重键 | 非目标卡 | 原因 |
|--------|---------|------|
| `card_value` | ✅ 适用 | `total_card_value` 由 `card_counts` 驱动，所有抽到的卡都参与 |
| `desire_weight` | ❌ 不适用 | `weighted_satisfaction` 由 `target_cards` 驱动——没有目标就没有「满足」 |

## 8. 方案搜索改造

核心原则：**数据的消费者拥有数据的编辑权。** `add_order` / `remove_order` 的唯一消费者是方案搜索——编辑界面迁入方案搜索面板。

### 8.1 从 CardWeightEntry 提取排序键

```python
def get_sorted_instances(
    weights: List[CardWeightEntry],
    target_cards: List[TargetCardEntry],
    key: str,          # "add_order" | "remove_order"
    reverse: bool,
) -> List[Tuple[float, int, str]]:
    """返回按权重排序的 (score, instance_index, card_id) 列表。"""
    scored = []
    for tc in target_cards:
        entries = [w for w in weights if w.card_id == tc.card_id]
        for i in range(tc.quantity):
            if i < len(entries):
                score = validate_search_weight(getattr(entries[i], key), key)
            else:
                score = 1.0
            scored.append((score, i, tc.card_id))
    scored.sort(key=lambda x: x[0], reverse=reverse)
    return scored
```

### 8.2 GUI：方案搜索面板接管 add/remove 编辑

## 14. 判定

**可行。** 分离架构相比合并架构有三项优势：

1. **改动面减半**——`target_cards` 签名不变，~15 个仅引用 `target_specs` 的文件完全不受影响
2. **语义清晰**——目标卡回答「追什么」，权重回答「值多少」；两棵独立的树，互不绑架
3. **非目标卡权重**——`[[weights]]` 中的 card_id 无需在 `[[targets]]` 中，天然支持「歪到值钱但不追」

建议先做 Phase A+B 原型——定义 `ExpressionWeight` → 升级 `CardWeightEntry` → 4 行 TOML（含表达式 + 非目标卡权重）→ 验证 `resolve_instance_weight` + GDR 双输入管道贯通。
