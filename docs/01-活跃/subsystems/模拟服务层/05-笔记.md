### 二、G1 的根因不是漏写 `else`，是判据选错

并行路径的失败计数恒为 0。看上去像「收集分支少写了一个 else」，实际是**判据选错了**：

worker 的失败出口返回 `(None, None, ...)`，但 `return_compact=False` 时（GUI 抽卡面板与
WebUI 跑主模拟前的默认）**成功也不回传 compact**，所以单看 `compact is None` 会把每一次
成功都记成失败；单看 `ext_pkt is None` 又会误伤「抽取器自身抛错」的形态。正确判据是
「两者同时为空」。另两条路径（进程内 / mp_failed 兜底）本就无条件计数，本次令并行路径
与它们同形，不是新设计。

**同一个坑在 P83 会话里已被记过一次**（见性能分析 05-笔记：「`return_compact=False` 与
`on_result` 组合会让父进程把每次模拟都误判为失败」）。本次从另一侧（漏计）再撞一次，
说明这条判据的歧义是**双向**的：既会多计也会漏计，取决于 `on_result` 在不在。

### 三、E2：一个「看起来在工作」的兜底

原描述是「CLI 有兜底、GUI/WebUI 报 0」。复核发现 CLI 的兜底合成 `{banner_id}_ssr`，
而仓库那份 `config.toml` 的 banner 叫 `pool_cN`、卡叫 `limited_ssr_N`，**合成 id 不是
任何真实卡**（不在 `card_defs`，也无卡以它为前缀）。两边其实都是 0，只是路径不同。
真正的问题是「兜底静默失效且失效时无任何提示」，而不是「口径分岔」。

**记一条**：兜底逻辑若依赖命名约定，就该有一条「约定不成立时喊出来」的断言；否则它会
长期以「我以为它在工作」的形态躺着。仓库里那条测试（原 `TestCliFallbackTarget`）用的是
**符合约定**的合成配置，所以一直是绿的。

### 四、告警通道：接上之后才发现要限流

`BatchResult.warnings` 建好了但三个入口都没接。接的过程中实测：1000 次同类告警会原样
进列表（一次 1000 次模拟各产一条），接上界面即刷屏。故新增按内容去重 + 20 条上限。
**先接消费端才暴露了这个问题**，只做生产端时它不可见。

### 六、配置身份为什么会漏七项：一个「每个调用点都要记得」的纪律

`compute_config_hash` 有十来个成分参数，两个生产调用点各自拼装。实测结果：**七项
影响模拟结果的配置一个都没进去**，包括收入规则（把 60 改成 600、乃至删光，哈希不变）。

修法不是「把七项补上」就完事，而是加一层 `compute_config_hash_for_store(store, ...)`
作为**生产代码的唯一入口**——把「该取哪些字段」收在一处，完整性就从「每个调用点都要
记得」变成结构上的事。**只补字段不加这层，下次加配置项时会以同样的方式再漏一次。**

顺带删掉恒空的 `schedules_config` 形参：它处理的三项已被 BannerEntry 分支覆盖，生产
调用从来只传空列表（`ConfigStore` 没有 `schedules` 属性）。**一个恒空的形参比不写更
危险**，读代码的人会以为排期已被覆盖。

覆盖面以「`SimulationEnvBuilder.from_config_store` 会读的字段」为准：该函数是配置
进入 worker 的唯一通道，它不读的字段（`auto_wait` / `resource_defs` / `select_vouchers`
等）不影响模拟结果，故不纳入。**注意 `auto_wait` 是个死字段**——声明了、GUI 有复选框、
能存能改，但全仓无任何消费者。

### 七、一次过程失误：探针本身写错了

复测 `rarity_rank` 时显示「仍不变」，差点当成实现没生效。实际是**探针写错了**：
该配置的键是大写 `SSR`，我用了小写 `ssr`，等于没改。

这与 P83 会话记录的那条是同族问题（「探针的测量对象必须自己核对」）：**当结论是
「改动没生效」时，先怀疑探针，再怀疑实现。** 本次还撞到同一族的第二种形态：用
`, None, [])` 做无差别字符串替换时，误伤了另一个无关调用
（`test_startup_timeline.py` 的 `_startup_segments(observed, None, [])`）。
**批量替换要按行内容限缩范围，不能只按键序列的字面形状。**
