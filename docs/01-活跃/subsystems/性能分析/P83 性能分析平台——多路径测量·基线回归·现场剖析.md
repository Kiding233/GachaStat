# P83 性能分析平台——多路径测量·基线回归·现场剖析

> 日期：2026-09-17 | 状态：设计中
> 触发：用户提问「本项目性能分析相关工作有哪些」→ 查证发现三份 profile 脚本全部失效、全仓无性能基线、无任何剖析工具链 → 用户提出重建一条工作流
> 六文件：`subsystems/性能分析/`（2026-09-17 首次建档）
> 前置实证：offscreen Qt 可用、`py-spy --subprocesses` 可采到子进程（2026-09-17 实测，详见 `01-理论.md` §6）

---

## 一、问题

GachaStat 的性能目前只能靠人记得住。五项均已查证到代码级或实跑级证据。

**1. 无性能基线。** 全仓没有任何地方记录「同配置同种子上次跑出来是多少毫秒」，因此「这次改动有没有变慢」无法回答。

**2. 三份测量脚本全部失效且从未入库。**
- `scripts/profile_sim.py:51` 读 `config_store.strategy_name`，该属性已改名 `strategy_key`，实跑抛 `AttributeError`
- `scripts/profile_gui.py:43` 从 `gacha_simulator.gui.batch_simulator` 导入，而该文件是 **0 字节空文件**（2026-06-12 commit `e3b49c3` 清空，`git ls-files` 确认仍被跟踪），实跑抛 `ImportError`
- 三份脚本均被 `.gitignore:28,30`（`benchmark_chart.py` / `profile_*.py`，无目录限定）覆盖，从未入库，因此无 CI、无测试、无引用者，失效后无任何机制报警

**3. 唯一的自动化性能判据只管「失控」不管「变慢」。** `tests/test_p79_stop_condition_matrix.py` 的 8.4 闸门共 4 个用例（实跑 `4 passed`），判据是迭代数上界 1000 与耗时阈值 0.5s，用途是防止 `WaitAction(duration=0)` 空转复现。

**4. 剖析位置错了就测不到东西。** 模拟的真实计算跑在 `multiprocessing.Pool` 子进程里，2026-09-17 实测在主进程挂剖析器时，父进程主线程空等在 `multiprocessing/pool.py:861`。

**5. 无任何剖析工具链。** 全仓 `cProfile` / `pstats` / `py-spy` / `yappi` / `line_profiler` 零命中；`pyproject.toml` 的 dev 依赖只有 `pytest` / `pytest-cov` / `pytest-timeout`。

**为什么不能靠「有 P12 就够了」**：P12 是**优化方案**（Phase 2 Numba / Phase 3 共享内存尚未启动），不是**测量设施**。P12 当年定位到核心瓶颈靠的是分阶段计时，而这个能力当前以失效脚本的形态存在，且零回归保护。

## 二、目标

建立一套按「粒度 × 路径 × 因子」三轴正交组织的性能测量、基线登记与现场剖析平台，使性能成为**可回答的问题**而非记忆。

| # | 目标 | 判据 |
|---|------|------|
| G1 | 回答「这次改动有没有变慢」 | 一条命令产出「配置 X 在路径 P 上对比基线 B 的比值」 |
| G2 | 覆盖用户真实走的四条路径 | `cli` / `gui-qt` / `webui` / `inline` 各有适配器，`gui-qt` 可在无显示器环境（含 CI）运行 |
| G3 | 函数级定位到热点 | `function` 档产出 `(name, ncalls, tottime, cumtime)`，可在 worker 侧采集 |
| G4 | 回答「用户现场为什么卡」 | `py-spy` 可 attach 到运行中的真实进程（含 `--subprocesses`）并产出可读剖面 |
| G5 | 平台自身不再腐烂 | 全部产物入库；有测试；安全协议写入 `README.md` 并作为硬规则 |

**非目标**（明确划出，防止范围蔓延）：
- 跨路径结果等价对照（属测试体系的事）
- 参数扫描 / 通用实验编排（不是性能问题）
- P68 的独立参考实现对照
- `gui/` 与 `webui/` 两套平行编排的收敛（属 P74 换头计划）
- 具体性能优化本身（仍由 P12 Phase 2/3 等承载）

## 三、方案

### 3.1 三层架构

**① 测量内核**（`benchmarks/perf/`，无 Qt 依赖）：管「测什么、怎么算」。含 `Plan` / 阶段计时 / `cProfile` 采集与聚合 / `py-spy` 调用与解析 / 序列化与比对。它不知道自己在哪条路径上跑。

**② 路径适配器**（每条一个，薄）：实现同一契约 `name` / `is_user_path` / `available()` / `run(plan) → RunResult`。四条：`cli` / `gui-qt` / `webui` / `inline`。

**③ 调用面**（薄壳）：命令入口，最后做。

### 3.2 硬约束（本平台的核心纪律）

**约束 A：适配器不得新写驱动，只能修复或包装已有入口。**

正例：`gui-qt` 适配器 import `gacha_panel` 现有的 `SimulationThread`（签名仅需 `ConfigStore`，实测可独立构造），用 offscreen `QApplication` 驱动它，被测代码一行不改；`inline` 适配器就是修好后的 `profile_sim.py` 驱动逻辑。
反例：为「方便测量」新写脚本去跑模拟。
判别式：**任何适配器如果需要「先写个脚本来跑」，说明它设计错了。**

理由：自己写驱动，测出来的是驱动而不是产品。2026-09-17 已有一起实证事故，详见 §3.4。

**约束 B：测量覆盖 ≠ 代码收敛。** 让 GUI 路径可测不需要重构 `gacha_panel`；收敛 `gui/` 与 `webui/` 的平行编排属 P74。P74 落地时 `gui-qt` 适配器随之删除，内核不动。

**约束 C：路径是一等维度。** 每条 `RunResult` 带路径标识；`inline` 强制 `is_user_path=False`。

### 3.3 三轴模型

**粒度 grain**（逐级叠加，默认 `stage`）：

| 档位 | 产出 | 相对成本 |
|------|------|---------|
| `batch` | 仅总墙钟 | 最低 |
| `stage` | 阶段分解：配置加载 / env 构建 / 进程池启动 / 模拟 / extractor / 分发 | 低（默认） |
| `single` | 追加单次模拟分布 | 中 |
| `function` | 追加 `cProfile` 调用次数与自耗时 | 高（2-5x），N 需下调 |

资源计数（序列化字节数、RSS 峰值）任何档位都采集。

**路径 path**（五条真实入口，见 `01-理论.md` §5.2）：`cli` / `gui-qt` / `webui` / `inline`，加 `run_batch_parallel` 内部单进程与多进程细分（由 `workers` 因子覆盖）。

**因子 factors**：`n` / `workers` / `chunksize` / `strategy_key` / `config` / `seed`。一个 plan 展开为笛卡尔积，每格一条记录。

### 3.4 安全协议（硬规则，来自 2026-09-17 事故）

事故：验证 `py-spy` 时手写探针以 `num_simulations=60000` 无收集器驱动 `run_batch_parallel`，父进程堆积 60000 份 `CompactResult`，用户机器（15.3 GB）内存耗尽崩溃。根因在 `service/batch_simulator.py:415` / `:441` / `:452` 坐实。

| # | 规则 | 违反后果 |
|---|------|---------|
| 1 | 必须传 `on_result` 流式收集器，禁止无收集器裸跑大批量 | 全部结果堆在父进程，必 OOM |
| 2 | 主模块必须有 `if __name__ == '__main__':` 守卫 | Windows spawn 下级联起进程池 |
| 3 | 杀进程必须带 `/T`（`taskkill /PID <pid> /T /F`） | Windows 杀父不杀子，孤儿 worker 残留 |
| 4 | 设 N 上限，且先小规模试跑验证进程模型 | 首次就跑大批量，出错即全量代价 |
| 5 | 启动前检查可用内存，低于阈值直接拒绝 | 在用户正在使用的机器上打满内存 |

规则 1、2 特别值得记录：**现有脚本里本来就有这两份防护**（`profile_sim.py:116` 主模块守卫、`:32-33,53` 流式收集器），手写驱动把它们同时丢掉。

### 3.5 回归判据

- **比值不用绝对毫秒**：绝对耗时受频率 / 负载 / 调度影响，跨时间跨机器不可比
- **序列化用字节数不用耗时**：同配置同种子下字节数完全确定、零噪声。已知近似：它是代理指标，不等于真实传输开销；`CompactResult` 有 `to_dict()` / `from_dict()` 暗示跨进程传 dict，故「`len(pickle.dumps(...))` 估算是否符合真实路径」需实施时核对
- **`repeats` 默认 3 取中位数**：预估墙钟超 30 秒降为 1 并记录 `repeats_downgraded`；建基线时强制 ≥3。原始各次值保留在 `wall_samples`
- **基线按机器类别分组**（核数区间 + OS 版本）：同组内比比值，跨组只比阶段占比。若只有一台基准机则在基线文件中显式写明适用范围

### 3.6 存储切分

| 目录 | 入库 | 理由 |
|------|------|------|
| `benchmarks/runs/` | 否 | 过程数据，体积与数量不可控 |
| `benchmarks/baselines/` | 是 | 被选择、少量、必须跨时间可追溯 |

`.gitignore` 新增 `benchmarks/runs/`。同时按 P81 既有建议，把 `.gitignore:28,30` 的无目录限定规则收紧为 `scripts/profile_*.py` 形式。

### 3.7 阶段划分

| 阶段 | 内容 | 交付判据 |
|------|------|---------|
| 1 | 内核 + `cli` 适配器 + 基线登记与比对闭环 | 能回答「cli 路径这次比基线慢了多少」（G1） |
| 2 | `inline` 适配器（接管修复后的 `profile_sim.py` 逻辑）+ 修复 `04-问题.md` P1 的失效脚本 | 纯计算基线可复现 |
| 3 | `gui-qt` 适配器（offscreen）+ 阶段口径对齐 `profile_gui.py` 分段 | GUI 路径可进自动化（G2） |
| 4 | `webui` 适配器 + `py-spy` 采集层与 speedscope 解析 | 四路径齐备，现场勘查可用（G4） |
| 5 | `function` 档：`cProfile` 在 worker 侧注入与合并 | 函数级判据可进基线（G3） |

阶段 5 单列的原因：它是唯一需要触碰被测量代码（`_wk_init` / `_wk_run_single` 调用形态）的阶段，风险高于其余。

**不拆为多个 P 计划的理由**：内核无适配器则无用，适配器无内核则无从落地，各阶段不是独立可交付物。按阶段逐项 commit、逐项验收。

| 风险 | 缓解 |
|------|------|
| 平台自身腐烂（重蹈三份脚本的覆辙） | 全部入库 + tests + `README.md` 硬规则；G5 作为验收项 |

## 附二：决策记录（已定稿，实施时不得回退）

1. 路径是一等维度，不是环境细节
2. 测量覆盖 ≠ 代码收敛，适配器只驱动不重构
3. 适配器不得新写驱动
4. `cProfile` 进基线（确定性），`py-spy` 出线索（采样噪声，不进回归）
5. `py-spy` 只进开发依赖，不进发布产物
6. `benchmarks/` 放顶层（先例：`测试体系` 核心文件为 `tests/` 顶层目录）
7. 安全协议 5 条为硬规则
8. 粒度默认 `stage` 而非 `function`（P12 经验：分阶段计时投入产出比最高）
