## 二、调查发现：矛盾与不一致

### 🔴 矛盾 1：P57 的 `_collect_ssr_ids` 依赖命名约定——且与池子级 featured 设计矛盾

**位置：** [P57 §步骤1](docs/01-活跃/subsystems/模拟服务层/P57%20随机目标卡生成.md#L184-L193)

```python
def _collect_ssr_ids(store, scope):
    if scope == 'all_ssr':
        return [cd.card_id for cd in store.card_defs if cd.rarity == 'SSR']
    else:
        return [cd.card_id for cd in store.card_defs
                if cd.rarity == 'SSR'
                and cd.card_id.startswith('limited')]  # ← 命名约定
```

**问题：** `card_id.startswith('limited')` 把「限定/常驻」的判定绑在卡名上——一个标识符不应该承载业务语义。

**P55/P56 已确定的方向：** `featured` 是**池子维度的属性**——每个池子声明自己的 `featured_card_ids`。P56 进一步强化了这一点：`[[pool]].epitomizable_cards`（可定轨卡列表）也是池子级配置，不从 featured 推导、不从卡名推导。

P57 作为最下游的消费者，应该统一从池子配置读取——`store.get_cards_by_rarity('SSR', limited_only=True)`，其中 `limited_only` 判断的是「这张卡是否至少在某个池子是 featured」。

### ✅ 非矛盾：P41 `TargetInstance.weights` 与 P55 `PoolPitySpec.resolved_targets`

> **经审查确认：两者不是同一类东西，不存在冲突。**

| | `PoolPitySpec.resolved_targets` | `TargetInstance.weights` |
|---|---|---|
| **职责** | 保底触发时「概率增量分配给哪些卡」——概率引擎的**机制配置** | 玩家「有多想要这张卡」——GDR 评分 / 方案搜索的**偏好权重** |
| **数据源** | `[[pity]]` 节中的 `target_distribution` | `[[targets]]` 节中的权重列 |
| **消费者** | `SoftPityBehavior.apply()` / `HardPityBehavior.apply()` | `_gdr_weighted_satisfaction()` / `retreat_search.py` |
| **语义** | 「软保底激活时，把概率导给这些卡」 | 「我想要这张卡的程度是 2.0」 |

两者只是共享了「weight」这个词，功能层面完全正交。各自独立配置、互不推导——保底分配目标是机制设计，与玩家偏好无关。**撤回此项。**

### ✅ 已收敛：P56 的 `selected_card`——采用策略运行时 NonDrawAction 方案

> **P56 更新后已自行解决。不再需要外部建议。**

P56 已确定方案（§3.6 决议）：`selected_card` 由策略通过 `NonDrawAction("switch_epitomized_target", ...)` 运行时设定，可选范围由池子级 `[[pool]].epitomizable_cards` 声明。三层分工明确：

| 层 | 配置项 | 职责 |
|----|--------|------|
| 池子配置 | `epitomizable_cards` | 哪些卡可被定轨 |
| 保底配置 | `fate_threshold` / `switch_allowed` / `switch_resets_progress` | 定轨规则 |
| 策略运行时 | `NonDrawAction` | 选哪张、何时切 |

此方案与池子级 featured 设计一致——两者都是池子维度声明「这张卡在这个池子里有什么特殊身份」。**P58 之前的 `TargetInstance.extra` 建议（配置时写入、模拟初始化一次读取）与此方案的本质区别是——NonDrawAction 允许策略在模拟中途切换目标。这是 P56 的刻意设计，确认合理。**

### 🟡 矛盾 2：「限定/常驻」判定散落三处，无统一来源

| 位置 | 判定方式 | 可靠性 |
|------|---------|--------|
| 当前 `PoolPitySpec.featured_ids` | 池子构造时从 `card_defs` 推导 | ✅ 结构化 |
| P57 `_collect_ssr_ids` | `card_id.startswith('limited')` | ❌ 命名约定 |
| P56 池子 `epitomizable_cards` | 池子配置显式声明 | ✅ 显式 |

**纠正的方向：** `featured` 不是 CardDef 字段，而是**池子维度的配置**——每个池子声明自己的 `featured_card_ids`。卡层的 `limited` 是推导属性：「这张卡是否至少在某个池子被 featured 过」。P56 的 `epitomizable_cards` 同样遵循这一原则——池子级声明。

P57 应通过 `ConfigStore` 的统一查询接口判断 limited，而非自己发明判定规则。

## 四、对每个计划的修改建议

### 4.1 对 P41 的建议

**无需新增 `featured` 字段。** `featured` 属于池子维度，不由 CardDef 承载。

P41 改造 `target_specs → target_instances` 时，`TargetInstance.pool_ids` 字段已包含每张目标卡的池子归属。P55/P56 需要知道「这张卡在当前池子是否 featured / 是否可定轨」时，通过池子配置查询即可——不需要从 TargetInstance 上读取。

**维持 P41 的原有范围不变。** 对 P55/P56/P57 的唯一影响是类型变更适配（`target_specs: Dict` → `target_instances: List`）。

### 4.2 对 P55 的建议

**`DrawInfo.featured_slots` 从池子配置读取（非 CardDef 字段）**

`featured_slots["ssr"]` 应由当前 `pool_id` 对应的池子配置 `featured_card_ids` 推导，而非从 CardDef 上的某个字段。路径：

```python
# 构建 DrawInfo 时
pool_config = store.get_pool(pool_id)
featured_card_ids = pool_config.featured_card_ids  # ← 池子级配置
featured_slots["ssr"] = tuple(card_to_slot[cid] for cid in featured_card_ids)
```

**不需要为 `selected_card` 做额外处理。** P56 已通过 `NonDrawAction` + `PityState` namespace 自行解决——`TargetedBehavior` 直接从 `ctx.state.get(self._name, "selected_card")` 读取。P55 的 `PityState` namespace 机制是此方案的天然支撑。

### 4.3 对 P56 的建议

**当前方案已合理，无需外部修改建议。**

P56 更新后的设计：`TargetedBehavior` 独立于 `RotatingBehavior`，`selected_card` 由策略通过 `NonDrawAction` 运行时设定，可选范围由 `[[pool]].epitomizable_cards` 池子级声明。这三个决策与池子级 featured 架构一致、与 P55 的 `PityState` namespace 天然兼容。

**仅提醒一点：** `epitomizable_cards` 是池子级配置字段，与 `featured_card_ids` 同为池子维度的「卡牌身份声明」。两者应在 `ConfigStore` 的池子配置中统一管理（同一段 TOML、同一个 `PoolDef` 数据类），避免一个在 `[[pity]]` 一个在 `[[pool]]` 导致配置分散。

### 4.4 对 P58 的建议

**与目标卡体系的交点极窄——只有一个共享产物。**

P58 阶段 A 的 `state.acquired` 是 P41 `instance_index` 推导的简化来源（见 §三 依赖关系图）。除此之外，P58 与目标卡体系无直接交互：
- P58 阶段 B（`MilestoneBehavior`）是纯保底类型——计数器驱动、透传概率、达阈值注入。赠卡时调用 `state.add_card()`（P58 A 产物），不涉及 TargetInstance / GDR / 方案搜索
- milestone 的 `bonus_reward.candidates` 是独立配置的卡 ID 列表——与 P41 的 target_instances 是两套正交数据

**`scope` 语义对齐 P55：** milestone 的 `scope` 退化为排序标记（必须为 `[rarities]` 注册值，默认取池子最高稀有度）。计数器统计所有抽卡，不按稀有度过滤。

**实施建议：** 阶段 A 最先做（顺序 0），阶段 B 在 P55 之后做（顺序 4）——届时 `MilestoneBehavior(CounterBasedBehavior)` 只需覆写两个方法。

### 4.5 对 P57 的建议

**已于 2026-06-17 更新 P57 计划——所有修改已落地：**

- `_collect_ssr_ids(store, scope, limited_only)` —— 用 `store.is_limited(card_id)` 替代 `card_id.startswith('limited')`
- TOML `scope` 字段拆分——`scope = "ssr"`（稀有度名）+ `limited_only = true`（布尔），不再使用 `"limited_ssr" | "all_ssr"` 字符串枚举
- `ConfigStore` 字段——`random_target_scope: str = 'ssr'` + `random_target_limited_only: bool = True`
- CLI——`--random-target-scope`（自由字符串，默认 `ssr`）+ `--random-target-all`（flag 切换常驻）
- GUI——`scope` 稀有度下拉框 + `limited_only` 复选框，不再使用二字串下拉

**`is_limited()` 作为微型任务（~5 行）：** 可在任何阶段独立实施——利用现有 `PoolPitySpec.featured_ids` 遍历池子配置，不依赖 P55。P57 实施时直接调用。详见 P55 §3.13「可提前提取的微型任务」。

## 五、统一架构方案

### 5.1 核心原则

1. **featured 在池子层，limited 在卡层推导**——`[[pools]].featured_card_ids` 是真相源；`limited` = 「是否至少在一个池子被 featured 过」，不存储在 CardDef 上
2. **TargetInstance 是目标卡的数据主干**——P41 之后，不再有 `target_specs: Dict[str, int]` 散落各处
3. **DrawInfo 是保底层的只读视图**——从池子配置构建（`featured_slots` / `scope_cards`），behavior 不修改
4. **池子级「卡牌身份」统一管理**——`featured_card_ids`（P55 rotating 用）和 `epitomizable_cards`（P56 targeted 用）同为池子维度的声明，应在 ConfigStore 的池子配置中统一管理

## 六、实施顺序（2026-06-19 已简化为以下两条）

> 基础设施（P58A + P55 Ph1-4 + 引擎调度 + is_limited/[rarities]）已提取至 [P60](P60%20基础平台——依赖消除与下游并行化.md)。以下两条替代原 7 步串行链。

1. **P60** ——一次交付（~355 行、5 块）
2. **P41 ∥ P55-剩余 ∥ P56 ∥ P58B ∥ P57** ——全部可并行于P60 之上（P57 需额外等 P41 的 TargetInstance 格式）

### 6.1 简化效应总览

```
高杠杆平台（P55 Ph1-4）
  │  简化: P55自身(3个behavior) + P56(2个behavior) + P58B(1个behavior)
  │  合计: ~100行被继承替代 / 6个behavior受益
  │
  ├─ P58A (acquired迁移)
  │    简化: P41(instance_index+acquired来源) + P58B(bonus落脚) + stop + 策略
  │    合计: ~35行 / 4消费者受益
  │
  ├─ is_limited() + [rarities] (微型任务)
  │    简化: P57(消除命名约定) + P55/P58B(scope校验)

  │
  └─ P56 ∥ P58B (并行)
       前提: P55 Ph1-4 平台层交付后
       收益: 缩短关键路径（两者互不依赖）

### 6.2 推荐顺序

| 顺序 | 计划 | 前置条件 | 理由 |
|:---:|------|---------|------|

| **1** | **P58A**（acquired 迁移） | — | ~105行、独立。`state.acquired` 为 P41 提供统一真相源（消灭两本账）、为 P58B 提供 bonus 落脚点、为 stop/策略层解耦统计层。四个消费者受益 |
| **2** | **P55 Phase 1-4**（平台层） | — | ~250行、独立于 P41。**最高杠杆交付——** PityState + DrawInfo + CounterBasedBehavior + BEHAVIOR_REGISTRY 同时简化 P55 自身（3 个 behavior 各 ~80→~30 行）、P56（事件驱动状态存储）、P58B（milestone 60→35 行）。完成后 P56 和 P58B 解耦并行 |
| **3a** | **P41 Phase A+B**（ExpressionWeight + TargetInstance） | P58A（软——不用也能跑，但 `instance_index` 推导更干净） | 波及 ~30 文件、变更核心类型。在 P55 平台层定型后再改可避免 ConfigStore API 二次变更。**与 3b/3c 可并行** |
| **3b** | **P55 Phase 5-13**（behavior 重构 + engine + config） | P55 Ph1-4 | 续建平台层之上的具体 behavior 实现和引擎调度。**与 3a/3c 可并行** |

### 6.3 与旧顺序的差异

| 变更 | 旧顺序 | 新顺序 | 理由 |
|------|:---:|:---:|------|
| **新增微型任务 0** | — | 0 | `is_limited()` + `[rarities]` 合计 ~20行、独立、消除 P57 命名约定——低成本高收益 |

| **P41 与 P55 Ph5-13 并行** | 串行 | 并行 (3a ∥ 3b) | P41 和 P55 互不依赖——前者改目标数据结构，后者改保底引擎。可并行推进 |

| **P57 维持最后** | 最后 | 最后 | 无争议——P57 是所有基础设施的消费者 |

### 6.4 关键互锁条件

| 如果先做 | 后做的计划需要付出的额外代价 |
|---------|--------------------------|
| P58B 先于 P55 Ph1-4 | `MilestoneBehavior` 需手动管理计数器/Flag/active（~60 行）；P55 之后继承 `CounterBasedBehavior` 自动处理（~35 行）。**代价：~25 行样板 + 后续迁移** |

| P41 先于 P55 Ph1-4 | P41 波及 30 文件——若 P55 平台层后续调整 ConfigStore API，P41 需要二次适配。**代价：潜在的 30 文件返工** |
