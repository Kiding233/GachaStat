# P83 性能分析平台——多路径测量·基线回归·现场剖析

> 日期：2026-09-17 | 状态：设计中
> 触发：用户提问「本项目性能分析相关工作有哪些」→ 查证发现三份 profile 脚本全部失效、全仓无性能基线、无任何剖析工具链 → 用户提出重建一条工作流
> 六文件：`subsystems/性能分析/`（2026-09-17 首次建档）
> 前置实证：offscreen Qt 可用、`py-spy --subprocesses` 可采到子进程（2026-09-17 实测，详见 `01-理论.md` §6）

---

## 一、问题

GachaStat 的性能目前只能靠人记得住。五项均已查证到代码级或实跑级证据。

**1. 无性能基线。** 全仓没有任何地方记录「同配置同种子上次跑出来是多少毫秒」，因此「这次改动有没有变慢」无法回答。

**2. 三份测量脚本全部失效且从未入库。**
- `scripts/profile_sim.py:51` 读 `config_store.strategy_name`，该属性已改名 `strategy_key`，实跑抛 `AttributeError`
- `scripts/profile_gui.py:43` 从 `gacha_simulator.gui.batch_simulator` 导入，而该文件是 **0 字节空文件**（2026-06-12 commit `e3b49c3` 清空，`git ls-files` 确认仍被跟踪），实跑抛 `ImportError`
- 三份脚本均被 `.gitignore:28,30`（`benchmark_chart.py` / `profile_*.py`，无目录限定）覆盖，从未入库，因此无 CI、无测试、无引用者，失效后无任何机制报警

**3. 唯一的自动化性能判据只管「失控」不管「变慢」。** `tests/test_p79_stop_condition_matrix.py` 的 8.4 闸门共 4 个用例（实跑 `4 passed`），判据是迭代数上界 1000 与耗时阈值 0.5s，用途是防止 `WaitAction(duration=0)` 空转复现。

**4. 剖析位置错了就测不到东西。** 模拟的真实计算跑在 `multiprocessing.Pool` 子进程里，2026-09-17 实测在主进程挂剖析器时，父进程主线程空等在 `multiprocessing/pool.py:861`。

**5. 无任何剖析工具链。** 全仓 `cProfile` / `pstats` / `py-spy` / `yappi` / `line_profiler` 零命中；`pyproject.toml` 的 dev 依赖只有 `pytest` / `pytest-cov` / `pytest-timeout`。

**为什么不能靠「有 P12 就够了」**：P12 是**优化方案**（Phase 2 Numba / Phase 3 共享内存尚未启动），不是**测量设施**。P12 当年定位到核心瓶颈靠的是分阶段计时，而这个能力当前以失效脚本的形态存在，且零回归保护。

## 二、目标

建立一套按「粒度 × 路径 × 因子」三轴正交组织的性能测量、基线登记与现场剖析平台，使性能成为**可回答的问题**而非记忆。

| # | 目标 | 判据 |
|---|------|------|
| G1 | 回答「这次改动有没有变慢」 | 一条命令产出「配置 X 在路径 P 上对比基线 B 的比值」 |
| G2 | 覆盖用户真实走的四条路径 | `cli` / `gui-qt` / `webui` / `inline` 各有适配器；`gui-qt` 在 `offscreen` 下可独立运行（实测，见 §3.10） |
| G3 | 函数级定位到热点 | `function` 档产出 `(name, ncalls, tottime, cumtime)`，可在 worker 侧采集 |
| G4 | 回答「用户现场为什么卡」 | `py-spy` 可 attach 到运行中的真实进程（含 `--subprocesses`）并产出可读剖面 |
| G5 | 平台自身不再腐烂 | 全部产物入库；有测试；安全协议写入 `README.md` 并作为硬规则 |

**非目标**（明确划出，防止范围蔓延）：
- 跨路径结果等价对照（属测试体系的事）
- 参数扫描 / 通用实验编排（不是性能问题）
- P68 的独立参考实现对照
- `gui/` 与 `webui/` 两套平行编排的收敛（属 P74 换头计划）
- 具体性能优化本身（仍由 P12 Phase 2/3 等承载）
- **图表渲染性能（`scripts/benchmark_chart.py`）：明确划出本平台范围**（2026-09-17 裁决）。理由两条：① 它测的是 Plotly+WebEngine 对比 matplotlib QtAgg 的图表渲染，与模拟性能正交，§一 的五个问题与它无关；② P74 换头将把图表层换成 ECharts，「Plotly 对比 matplotlib」这一比较届时失去对象。故不纳入，并建议随 P74 一并处置该脚本

## 三、方案

### 3.1 三层架构

**① 测量内核**（`benchmarks/perf/`，无 Qt 依赖）：管「测什么、怎么算」。含 `Plan` / 阶段计时 / `cProfile` 采集与聚合 / `py-spy` 调用与解析 / 序列化与比对。它不知道自己在哪条路径上跑。

**② 路径适配器**（每条一个，薄）：实现同一契约 `name` / `is_user_path` / `available()` / `run(plan) → RunResult`。四条：`cli` / `gui-qt` / `webui` / `inline`。

**③ 调用面**（薄壳）：命令入口，最后做。

### 3.2 硬约束（本平台的核心纪律）

**约束 A：适配器不得新写驱动，只能修复或包装已有入口。**

正例：`gui-qt` 适配器 import `main_window` 现有的 `MainWindow` 与 `gacha_panel` 的 `SimulationThread`，用 `offscreen` + `QApplication(sys.argv)` 驱动（**非空 argv，见规则 6**），被测代码一行不改；`inline` 适配器就是修好后的 `profile_sim.py` 驱动逻辑。
反例：为「方便测量」新写脚本去跑模拟。
判别式：**任何适配器如果需要「先写个脚本来跑」，说明它设计错了。**

理由：自己写驱动，测出来的是驱动而不是产品。2026-09-17 已有一起实证事故，详见 §3.4。

**约束 B：测量覆盖 ≠ 代码收敛。** 让 GUI 路径可测不需要重构 `gacha_panel`；收敛 `gui/` 与 `webui/` 的平行编排属 P74。P74 落地时 `gui-qt` 适配器随之删除，内核不动。

**约束 C：路径是一等维度。** 每条 `RunResult` 带路径标识；`inline` 强制 `is_user_path=False`。

**约束 D：每条路径必须能由 agent 独立驱动，不得依赖人工介入（2026-09-17 补）。**

判定方式：该路径的测量能否在**非交互式执行环境**（无窗口站、无交互式桌面会话）中完成。若某条路径必须由人手工运行才能取数，则该路径的测量不成立。

理由：本平台的用途是让「这次改动有没有变慢」成为**可独立回答**的问题。一旦某段数据只能靠人跑，回归就无法自动进行，平台退化为一次性报告；而且这类缺口不会被发现，只会被悄悄绕过。此约束与 §3.4 安全协议同属「平台自身的可靠性」范畴。

### 3.3 三轴模型

**粒度 grain**（逐级叠加，默认 `stage`）：

| 档位 | 产出 | 相对成本 |
|------|------|---------|
| `batch` | 仅总墙钟 | 最低 |
| `stage` | 阶段分解：配置加载 / env 构建 / 进程池启动 / 模拟 / extractor / 分发 | 低（默认） |
| `single` | 追加单次模拟分布 | 中 |
| `function` | 追加 `cProfile` 调用次数与自耗时 | 高（2-5x），N 需下调 |

资源计数（序列化字节数、RSS 峰值）任何档位都采集。

**路径 path**（五条真实入口，见 `01-理论.md` §5.2）：`cli` / `gui-qt` / `webui` / `inline`，加 `run_batch_parallel` 内部单进程与多进程细分（由 `workers` 因子覆盖）。

**因子 factors**：`n` / `workers` / `chunksize` / `strategy_key` / `config` / `seed`。一个 plan 展开为笛卡尔积，每格一条记录。

### 3.4 安全协议（硬规则，来自 2026-09-17 事故）

事故：验证 `py-spy` 时手写探针以 `num_simulations=60000` 无收集器驱动 `run_batch_parallel`，父进程堆积 60000 份 `CompactResult`，用户机器（15.3 GB）内存耗尽崩溃。根因在 `service/batch_simulator.py:415` / `:441` / `:452` 坐实。

| # | 规则 | 违反后果 |
|---|------|---------|
| 1 | 必须传 `on_result` 流式收集器，禁止无收集器裸跑大批量 | 全部结果堆在父进程，必 OOM |
| 2 | 主模块必须有 `if __name__ == '__main__':` 守卫 | Windows spawn 下级联起进程池 |
| 3 | 杀进程必须带 `/T`（`taskkill /PID <pid> /T /F`） | Windows 杀父不杀子，孤儿 worker 残留 |
| 4 | 设 N 上限，且先小规模试跑验证进程模型 | 首次就跑大批量，出错即全量代价 |
| 5 | 启动前检查可用内存，低于阈值直接拒绝 | 在用户正在使用的机器上打满内存 |
| 6 | `gui-qt` 路径必须构造 `QApplication(sys.argv)`（**非空 argv**），且 `QApplication` 之前须 `setAttribute(AA_ShareOpenGLContexts)` | 空 argv 下 QtWebEngine 初始化失败，进程以 `0xC0000409` 终止（2026-09-17 六变体矩阵实测） |
| 7 | `gui-qt` 路径收尾必须显式回收 Chromium 子进程 | `MainWindow` 显示后实测 10 个 `QtWebEngineProcess` 子进程；不回收将残留 |
| 8 | 关闭 `MainWindow` 必须先置 `win._restarting = True` 再 `close()` | 否则弹「确定要退出吗」确认框并阻塞，自动化流程卡死等人点击（`main_window.py:627-641`） |

规则 1、2 特别值得记录：**现有脚本里本来就有这两份防护**（`profile_sim.py:116` 主模块守卫、`:32-33,53` 流式收集器），手写驱动把它们同时丢掉。

### 3.5 回归判据

- **比值不用绝对毫秒**：绝对耗时受频率 / 负载 / 调度影响，跨时间跨机器不可比
- **序列化用字节数不用耗时**：同配置同种子下字节数完全确定、零噪声。**口径为整个三元组的序列化长度**：`len(pickle.dumps((compact, extraction, warnings)))`。
  - **为何不能只量 compact**（2026-09-17 查证）：`extraction` 包内含 `heatmap_ach_bins` / `heatmap_res_bins` 两个长度等于本次抽卡次数的数组，是**唯一随抽数增长的传输分量**，正是 P12 的 Phase 1.5 砍掉 93% 所针对的对象。只量 compact 会正好漏掉它
  - **跨进程传的是对象不是 dict**（2026-09-17 查证，原疑点已证伪）：`CompactCollector.get_result()` 返回 `self._result` 即 `CompactResult` 实例；`run_simulation_compact(...) -> CompactResult` 类型标注一致。`CompactResult.to_dict()` / `from_dict()` **全仓零调用点**（含 `tests/` 与 `scripts/`），不在热路径上
  - 剩余偏差仅来自 pickle 实现与队列分帧，作为回归判据可忽略；当绝对开销读仍会偏
- **`repeats` 默认 3 取中位数**：预估墙钟超 30 秒降为 1 并记录 `repeats_downgraded`；建基线时强制 ≥3。原始各次值保留在 `wall_samples`
- **基线按机器类别分组**（核数区间 + OS 版本）：同组内比比值，跨组只比阶段占比。若只有一台基准机则在基线文件中显式写明适用范围

### 3.6 存储切分

| 目录 | 入库 | 理由 |
|------|------|------|
| `benchmarks/runs/` | 否 | 过程数据，体积与数量不可控 |
| `benchmarks/baselines/` | 是 | 被选择、少量、必须跨时间可追溯 |

`.gitignore` 新增 `benchmarks/runs/`。同时按 P81 既有建议，把 `.gitignore:28,30` 的无目录限定规则收紧为 `scripts/profile_*.py` 形式。

### 3.7 阶段划分

| 阶段 | 内容 | 交付判据 |
|------|------|---------|
| 1 | 内核 + `cli` 适配器 + 基线登记与比对闭环 | 能回答「cli 路径这次比基线慢了多少」（G1） |
| 2 | `inline` 适配器（接管修复后的 `profile_sim.py` 逻辑）+ 修复 `04-问题.md` P1 的失效脚本 | 纯计算基线可复现 |
| 3 | `gui-qt` 适配器（offscreen，`QApplication(sys.argv)`）+ 阶段口径对齐 `profile_gui.py` 分段 | GUI 路径**全程**可进自动化（G2），含面板构造与分发执行 |
| 4 | `webui` 适配器 + `py-spy` 采集层与 speedscope 解析 | 四路径齐备，现场勘查可用（G4） |
| 5 | `function` 档：`cProfile` 在 worker 侧注入与合并（机制见 §3.8） | 函数级判据可进基线（G3） |

阶段 5 单列的原因：它是唯一需要触碰被测量代码（`_wk_init` / `_wk_run_single` 调用形态）的阶段，风险高于其余。

**不拆为多个 P 计划的理由**：内核无适配器则无用，适配器无内核则无从落地，各阶段不是独立可交付物。按阶段逐项 commit、逐项验收。

### 3.8 阶段 5 机制：cProfile 在 worker 侧的注入（2026-09-17 补）

本节补上阶段 5 此前只提名未解释的机制。**它是全平台唯一需要触碰被测量代码的地方**，因此机制本身必须写死，不能留到实施时临场决定。

#### D1 触发载体用 `env` 字段，不用环境变量

先例：`env.return_compact` 由 GUI 抽卡面板与 WebUI 在跑主模拟前置 `False`；`env.n_heatmap_bins` 同理由调用方设置。`SimulationEnv` 已有大量带默认值的字段，注释明确写着「带默认值保证跨进程 pickle 兼容」，照此模式新增即可。

新增四个字段（全部带默认值，不破坏 pickle 兼容）：

```python
profile_enabled: bool = False   # 总开关
profile_dir: str = ''           # worker 侧 profile 落盘目录；空则不落盘
profile_skip: int = 2           # 前 N 次调用不采样（warmup）
profile_count: int = 50         # 采样多少次后关闭
```

否决环境变量的理由：进程全局隐式状态，测试设置后会泄漏影响其它用例；且它不进 `RunResult`，事后无法从记录判断某条数据是否带剖面。这与本库对隐式全局状态的一贯态度相反（P75 的 `_rebind_state` 纪律、P10 把 11 个模块级全局变量合并为 1 个 `_wk_env`，方向都是减少隐式状态）。

#### D2 采样窗口是「围绕单次 `_run_single` 调用」的开闭

**实证依据（本机 Python 3.12.5 源码核验）**：`run_batch_parallel` 用的是 `with MPPool(...) as mp_pool`，而 `multiprocessing.pool.Pool.__exit__` 的实现是 `self.terminate()`。worker 被强杀，**`atexit` 处理器不会执行**。因此「在 `_wk_init` 里 `cProfile.enable()`、进程退出时落盘」这条路走不通。

采用的做法是在 `_wk_run_single` 内对 `_run_single` 的调用做开闭：

```
enable → _run_single(...) → disable → （达到采样上限则 dump_stats）
```

开闭窗口还带来一个必要的附带好处：它在 **Pool 路径与单进程兜底路径上语义一致**。单进程兜底（`mp_failed` 分支）里 `_run_single` 是在父进程内联调用的，若改用进程级 enable，会把父进程的循环、`CompactResult` 装配、`pstats` 写入全部采进剖面，得到一份描述框架而非描述模拟的剖面。

#### D3 结果走文件，不经 `CompactResult` 也不经三元组通道

`_wk_run_single` 有三元组 arity 契约：其 docstring 用 ⚠ 明确警告「四条 return 的 arity 必须一致为 3」，父进程侧有 `len(result) == 3` 守卫。改动 arity 会同时破坏四条早退路径与父进程守卫，并把 `compact` 与 `warnings` 双丢且无告警。

因此 worker 用 `cProfile.Profile.dump_stats(path)` 落盘，父进程在 pool 结束后扫描 `env.profile_dir`，用 `pstats.Stats.add()` 合并。**副产品：`CompactResult` 与 `_RESULT_VERSION` 完全不动。**

文件命名含 pid，避免同机多 worker 撞名。

#### D4 必须跳过 warmup

`_wk_init` 的注释明确说明：不在 initializer 里预导入 `core` / `service`，因为 Windows spawn 下各 worker 同时执行 initializer 会同时加载 scipy 大 DLL 触发页面文件耗尽，故改为在 `_run_single` 首次调用时懒加载。因此第 1 次调用包含 import 开销，从第 1 次开始采样会把 import 算成热点。默认 `profile_skip=2`。

#### D5 有限采样窗口的代价，写清楚

只采前 K 次：

- 得到的是「早期周期」的剖面，不是全程平均。K 之后的抽样不进入剖面。
- 好处是开销被 K/N 摊薄。N 大时若全程采样，整体会慢 2-5 倍。
- 默认 K=50：cProfile 的调用次数是精确计数，50 次模拟对一个逐抽循环足以产生六位数级别的调用样本。
- 需要全程剖面时设 `profile_skip=0, profile_count=N`，但要接受全程插桩开销，且此时 `wall_median` 必然不可比（见 D6）。

#### D6 `function` 档与耗时档强制分两趟

cProfile 有 2-5x 插桩开销，同一次运行里既采剖面又报耗时是不诚实的。规则：

- `grain == 'function'` 时，`RunResult.wall_median` 标注 `not_comparable=True`，**不参与基线比值**（见 §3.5）
- 平台的 `function` 档实现为两趟：先跑一趟 `stage` 档取耗时，再跑一趟带 profiler 取函数统计，合并为一条记录
- `RunResult` 新增字段 `not_comparable: bool = False`

#### D7 失败一律软降级

`profile_dir` 不存在或不可写、`cProfile` 不可用、worker 被提前终止导致文件缺失、`pstats` 解析失败：一律软降级。worker 侧 try/except 后关闭 profiler 继续模拟；父进程侧记入 `RunResult.warnings`，`functions` 置 `None`。

**绝不因剖析失败导致模拟失败。** 这条与 §3.4 安全协议同源：测量工具不得伤及被测对象。

#### D8 内存纳入安全协议

cProfile 累计每次调用的统计，剖面常驻内存随 K 增长。§3.4 规则 5（启动前检查可用内存）须把 `profile_count` 计入估算；`profile_count` 另设硬上限（不超过 500），超过即拒绝运行。

#### D9 单进程兜底路径的处理

`mp_failed` 分支下 `_run_single` 在父进程内联执行，D2 的开闭窗口同样生效，因此剖面可用。但此路径下 `env.profile_dir` 的写入发生在父进程，须在 `RunResult` 中标注该次运行走的是单进程兜底（`BatchResult` 已有 `warnings` 通道，可直接记入），否则剖面会被误读为「多 worker 环境下的热点」。

### 3.9 测试策略（2026-09-17 补）

G5（平台自身不再腐烂）是本平台存在的理由之一，因此测试不是附属品。核心原则：**绝大多数测试不跑真实大批量模拟**，凡需要真实计时的断言一律排除在自动测试之外。

#### T0 测试放哪（需你过目的一处）

`pyproject.toml` 的 `testpaths = ["tests"]`（实测 `pytest --collect-only` 当前收集 1563 项），因此 `benchmarks/tests/` **不会被默认收集**，也就不会被 H9 的 `git push` 前置 `pytest -q` 门控到。

两个选项：

| 方案 | 做法 | 取舍 |
|------|------|------|
| A | 测试放 `benchmarks/tests/`，并把 `testpaths` 扩为 `["tests", "benchmarks/tests"]` | 平台自包含、可整体搬走。代价是改动 `pyproject.toml` 这一共享配置；且在别处跑 `pytest tests/` 时收不到；`pytest --cov=gacha_simulator` 也漏掉这一棵 |
| **B（2026-09-17 改判为推荐）** | 测试放 `tests/benchmarks/` | 零配置改动、自动被默认收集、自动纳入覆盖率统计。代价是平台被测代码与测试分处两棵树 |

**改判理由：** 本库惯例高度统一——所有测试都在 `tests/` 下，且已有「开发侧工具无同名包目录、测试仍放 `tests/`」的直接先例：`tests/harness/test_plan_execute_workflow.py` 测的是 `.claude/skills/plan-execute/` 这个 agent 工具链。初版推 A 的理由（自包含）基于一个假想收益（平台会被整体搬走），却排在了一条真实存在的项目惯例前面；A 的代价（改共享配置、可能收不到、覆盖率漏统计）是实在的。故采 B。

#### T1 内核单测（无外部依赖，秒级）

- `Plan` 因子展开：笛卡尔积、重复因子去重、字段默认值、`Plan.validate()` 的拒绝规则
- `RunResult` 序列化往返：`to_dict` / `from_dict` 等价，覆盖 `None` 字段、浮点、`not_comparable` 标志
- 环境指纹：同机两次采样稳定，字段齐全
- 基线比对判据：**用手工构造的两条 `RunResult` 记录测**，断言比值计算、`repeats_downgraded` 的传播、跨机器类别时降级为只比阶段占比、`not_comparable=True` 的记录被排除

#### T2 安全协议单测（必须测，且不需要跑模拟）

安全协议是硬规则，硬规则没有测试就只是文档。四条可用「构造即断言抛错」的形式覆盖：

| 规则 | 测法 |
|------|------|
| 1 | 构造 `on_result=None` 且 `n` 超上限的 `Plan`，断言拒绝 |
| 4 | `n` 超上限，断言拒绝 |
| 5 | 注入一个返回低可用内存的查询函数，断言拒绝 |
| D8 | `profile_count` 超硬上限，断言拒绝 |

**待定项**：拒绝的形态是构造期抛 `ValueError` 还是运行期返回错误对象。倾向**构造期抛 `ValueError`**：这四条描述的是调用方的编程错误，不是运行时状况，早失败比晚失败好；且实现与测试都更简单（无需构造错误对象、无需断言其形状）。

规则 5 与 D8 的拒绝需要内存查询可注入（默认实现读真实系统内存，测试注入桩），否则测试不可控。该可注入点须在设计里显式留出。

#### T3 适配器契约测试（跑真实模拟，但极小规模）

四条适配器共用一套参数化断言：`name` 互不重复、`is_user_path` 符合约定、返回 `RunResult` 且 `path` 与 `name` 一致、`available()` 与实际可运行性一致。

- 规模参数：`n=10, repeats=1, grain='batch'`，整体秒级
- `inline` 适配器专项断言 `is_user_path is False`
- `gui-qt` 适配器：`pytest.mark.skipif(not _pyqt_available())`，并在用例内断言 `QT_QPA_PLATFORM=offscreen` 与**非空 argv**（规则 6）；用例收尾须走 `_restarting` 路径，不得弹确认框
- `available()` 返回 False 的路径：monkeypatch 强制不可用，断言平台跳过该适配器而非报错

#### T4 阶段 5 注入测试（唯一需要真实并行的一段）

`n=20, workers=2, profile_skip=0, profile_count=4`，断言：

- 至少产出一个 profile 文件，命名含 pid
- 合并后的 `pstats` 含 `_run_single` 调用链上的预期符号
- **`CompactResult` 未被污染**：与不带 profile 的同种子对照组逐字段一致，且 `_RESULT_VERSION` 不变
- **三元组 arity 仍为 3**（对照 `_wk_run_single` docstring 的 ⚠ 契约）
- 关闭 profile 时零副作用：`profile_enabled=False` 不产生任何文件

#### T5 `py-spy` 层只测调用与解析，不测采样质量

`py-spy` 是外部工具，其采样质量不属本平台。测录制的 speedscope JSON fixture 能否被正确解析为 `SamplesMeta` 与热点列表即可，不在测试里真的 attach 进程（attach 需要真实长跑进程，会造成 flaky 与内存风险，违反安全协议规则 4）。

#### T6 明确不测什么

| 不测 | 理由 |
|------|------|
| 绝对耗时数值 | 机器相关必抖，进 CI 必然 flaky |
| 性能阈值门控 | 同上。P79 的 8.4 闸门是既有例外，性质是「防失控」（迭代数上界）而非「防变慢」，判据是确定性的迭代数而非耗时 |
| `py-spy` 采样质量 | 外部工具职责 |
| 真实 GUI 显示路径 | offscreen 已覆盖逻辑路径；真实显示路径由手工验证，不进 CI |

### 3.10 路径可驱动性查证（2026-09-17，由待定项转为结论）

**查证背景：** §3.2 约束 D 要求每条路径可被 agent 独立驱动。`gui-qt` 路径的可驱动性此前未验证，本节给出结论。

**先纠正一个被推翻的前提：本项目没有 CI。** 无 `.github/workflows`、无 GitLab / CircleCI 配置；hooks 定义在 `.claude/settings.local.json`（本机）。唯一自动运行测试的是 H9 的 `git push` 前置 `pytest -q`，**运行在本机**。因此「无显示器」从来不是本项目的约束。

### 结论：`gui-qt` 路径全程可独立测量，含面板构造与分发执行

**根因（2026-09-17 查明）：`QApplication([])` 传空 argv 会导致 QtWebEngine 初始化失败（进程以 `0xC0000409` 终止），`QApplication(sys.argv)` 正常。** `main.py` 用的正是 `sys.argv`，故应用一直正常。

**六变体矩阵（每变体独立子进程 + 25s 超时）：**

| 变体 | 构造方式 | 结果 |
|---|---|---|
| v1_bare | `QApplication([])` | FAIL，rc=`0xC0000409` |
| v2_appname | `QApplication([])` + 设置应用名 | FAIL，同上 |
| **v3_sysargv** | **`QApplication(sys.argv)`** | **OK** |
| v4_import_first | 先 import `QtWebEngineWidgets` | 无效变体（探针脚本自身笔误：`QCoreApplication` 误从 `QtWidgets` 取） |
| v5_custom_profile | 显式 `QWebEngineProfile('probe', None)` | FAIL，`0xC0000409` |
| **v6_mainlike** | `main.py` 的完整初始化顺序 | **OK** |

**决定性验证（`QApplication(sys.argv)`）：**

```
ChartWebView()  构造 0.58s   _loaded=True（2.57s）   Chromium 子进程 1 个
MainWindow()    构造 0.36s   显示后 Chromium 子进程 10 个   RSS 412 MB   九个面板齐备
```

**`offscreen` 与真实平台对照（均配 `sys.argv`）：**

| 平台 | `ChartWebView()` 构造 | `_loaded` | 子进程 |
|---|---|---|---|
| `offscreen` | 0.19s | True（1.52s） | 1 |
| 真实 `windows` | 0.65s | True（1.54s） | 1 |

两者均可用。**适配器采 `offscreen`**：不弹窗、对使用者干扰最小。它会向 stderr 输出 GPU 错误（`Failed to make current since context is marked as lost`），属噪声，不影响功能，报告时须过滤。

### 为何此前八次探针全部失败

它们一律使用 `QApplication([])`。观察到的「挂起」是崩溃后卡在错误报告对话框，**不是环境限制**。这是本计划自身探针的缺陷，既非项目缺陷，也非执行环境限制。

**一条方法论教训（留在文档里）：** 本节初版把该现象归因于「非交互式执行环境」，二次查证改归因于「Chromium 自带沙箱」，**两者均被证伪**；真实原因是探针代码的一处 API 误用。**排查自身工具的失败时，应把「我调用的方式是否正确」列为一等假设，排在环境假设之前。**

### 三条实施要点（已并入 §3.4 安全协议规则 6-8）

1. 必须构造 `QApplication(sys.argv)`（非空 argv），且 `QApplication` 之前须 `setAttribute(Qt.ApplicationAttribute.AA_ShareOpenGLContexts)`
2. `MainWindow.close()` 会弹「确定要退出吗」确认框并阻塞（`main_window.py:627-641`）。**项目自带绕过路径**：先置 `win._restarting = True`（Ps03 的 Ctrl+R 重启即走此路）再 `close()`。适配器须走该路径，**不得依赖人工点击**
3. `MainWindow` 显示后实测 10 个 Chromium 子进程、RSS 412 MB。适配器须显式回收子进程，并按此预算内存（规则 5 的阈值须计入）

**已排除的假设（保留备查）：** 会话隔离（实测 `SessionId = 1`，与 `explorer.exe` 同会话）、工具沙箱、Chromium 沙箱（经授权放行 `--no-sandbox` 实测仍失败，该次失败同样是空 argv 所致）、GPU、单进程模式、profile 目录可写性、输出管道阻塞。**七项全部排除后，真因是本计划自身探针的 API 误用。**

**对设计的影响：** `gui-qt` 适配器覆盖**完整路径**（含面板构造与分发执行），无需任何分段裁剪；P12 实测的 4.13s 面板模块导入与 0.1ms/panel 分发执行均可测。§3.2 约束 D 全程成立。原计划的「分析面板模块冷启动导入」独立计时段降为 `stage` 档子段，不再单列子任务。

## 八、回滚策略

### 8.1 提交边界与耦合对

P83 产物分两类：**纯新增**（`benchmarks/` 全部、四适配器、profilers）单独 revert 只减少覆盖，不使既有判据失效；**修改既有**（`.gitignore`、`pyproject.toml`、`scripts/` 四份脚本、`SimulationEnv`、`_wk_run_single`）须按下列耦合对整组处理。

| 组 | 接口提供者 | 消费者 | 回滚顺序 |
|---|---|---|---|
| A | `1b` 的 `Plan` | `1e` / `1f` / `2d` / `3a` / `4a` | 先 revert 消费者，再 revert 提供者 |
| B | `1c` 的 `RunResult` | `1f` / `1g` / `5c` / `5d` | 同上 |
| C | `1e` 的适配器契约 | `2d` / `3a` / `4a` | 同上 |
| D | `1f` 与 `5d` 的 `not_comparable` 语义 | `1f` / `5d` | 同上（双向） |
| E | `5a` 的 `SimulationEnv` 字段 | `5b` / `5c` | 同上。**`5b` 用 `getattr(env, 'profile_enabled', False)` 读取，故 `5a` 可单独 revert 而不使 `5b` 崩溃**（同 P79 `2b` 的 `getattr(store, 'stop_condition', None)` 处置） |
| F | `5b` 的落盘格式 | `5c` 的合并侧 | 同上 |

### 8.2 唯一触碰产品代码的子任务

`5b` 是全平台唯一改动产品行为的子任务，回滚判据：

- revert 后，`profile_enabled=True` 不再产生任何剖面，`RunResult.functions` 恒为 `None`，且应由 `5f` 的软降级路径记入 `warnings`
- revert 后 `CompactResult` 与 `_RESULT_VERSION` 必然不变（`5b` 本就不动它们）
- **`5b` 不得与 `5f` 分开 revert**：`5b` 引入的失败点依赖 `5f` 的软降级收口，单独 revert `5b` 会留下无降级的注入点

### 8.3 回滚粒度例外

- `benchmarks/` 为纯新增，任何单项均可独立 revert，不构成例外
- `2a` / `2b` / `2c` / `2f` 修的是既有失效脚本，revert 即回到「已知失效」态，不影响产品与测试
- `5a` 单独 revert 安全（`5b` / `5c` 均用 `getattr` 容忍字段缺失）
- **例外一组**：`5b` ↔ `5f`（见 8.2）

### 8.4 基线的回滚

`benchmarks/baselines/` 入库后即为历史参照物，**不得随代码 revert 一并删除**。若某条基线产生于有缺陷的采集代码，应在基线文件内标注作废并在 `05-笔记.md` 记录原因，而非删除文件（同项目「文档移入 `03-归档/`、代码移入 `.recycle_bin/`」的不删除原则）。

## 附二：决策记录（已定稿，实施时不得回退）

1. 路径是一等维度，不是环境细节
2. 测量覆盖 ≠ 代码收敛，适配器只驱动不重构
3. 适配器不得新写驱动
4. `cProfile` 进基线（确定性），`py-spy` 出线索（采样噪声，不进回归）
5. `py-spy` 只进开发依赖，不进发布产物
6. `benchmarks/` 放顶层（先例：`测试体系` 核心文件为 `tests/` 顶层目录）
7. 安全协议 5 条为硬规则
8. 粒度默认 `stage` 而非 `function`（P12 经验：分阶段计时投入产出比最高）
9. 阶段 5 的触发载体用 `env` 字段，不用环境变量（§3.8 D1）
10. 采样窗口是围绕单次 `_run_single` 调用的开闭，不是进程级 enable（§3.8 D2，依据 `Pool.__exit__` 走 `terminate()`）
11. 剖面结果走文件，不经 `CompactResult` 也不改三元组 arity（§3.8 D3）
12. 剖析失败一律软降级，绝不导致模拟失败（§3.8 D7）
13. `function` 档与耗时档强制分两趟，`function` 档耗时标 `not_comparable`（§3.8 D6）
14. 测试放 `tests/benchmarks/`（§3.9 T0，**2026-09-17 由方案 A 改判为方案 B**；先例 `tests/harness/`）
15. 安全协议的拒绝形态为构造期抛 `ValueError`（§3.9 T2）
16. 每条路径必须能由 agent 独立驱动，不得依赖人工介入（§3.2 约束 D）
17. `gui-qt` 适配器用 `offscreen` + `QApplication(sys.argv)` 覆盖**完整** GUI 路径（含面板构造与分发执行）；须显式回收 Chromium 子进程、走 `_restarting` 绕过退出确认框（§3.10、§3.4 规则 6-8）
18. 序列化字节数量整个三元组 `(compact, extraction, warnings)`，不只量 compact（§3.5）
