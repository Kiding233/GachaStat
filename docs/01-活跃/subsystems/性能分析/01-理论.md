# 性能分析 -- 理论

> 创建日期：2026-09-17（首次建档）
> 关联计划：`P83 性能分析平台——多路径测量·基线回归·现场剖析.md`
> 关联模块：`benchmarks/` 目录

本文件承载本子系统的方法论自我约束。与其它子系统不同，性能分析是「测量工具本身」，其正确性不取决于产品设计，而取决于是否守住下面几条约束，因此本文件是最重的一篇。

---

## 1. 核心假设

1. **性能是可回归的**：给定同一配置、同一随机种子、同一机器类别，关键耗时量的**相对结构**是稳定的，因此「与历史基线的比值」是有意义的判据。绝对毫秒不具备跨机器可比性。
2. **测量必须覆盖用户真实走的路径**：测一条没人走的路径，得到的数字不能预测任何人的体验。本项目的四条真实入口（CLI / GUI / WebUI / 直连脚本）在进程模型、线程模型、后处理链上互不相同。
3. **确定性量优于统计量**：能取到确定性指标时优先取确定性指标（迭代数、序列化字节数、调用次数），它们零噪声，必然由代码改动引起；取不到时才退到统计量并用重复测量压噪。
4. **递进下钻优于一步到位**：剖析的分辨率越高成本越高、覆盖面越窄。先粗后细可以筛掉大部分候选，带着明确怀疑再上下一级。
5. **每条路径必须能由 agent 独立驱动**（2026-09-17 补）：判定方式是「该路径的测量能否在非交互式执行环境中完成」。若某段数据只能靠人手工运行取得，则该段测量不成立。理由：平台的用途是让「有没有变慢」成为可独立回答的问题；一旦某段只能靠人跑，回归就无法自动进行，且这类缺口不会被发现，只会被悄悄绕过。

## 2. 安全协议（硬规则）

**共 11 条，分两节**：规则 1-5 是**内核级**（与在哪条路径上跑无关），规则 6-11 是**路径级**（`gui-qt` 与启动测量各自的特有约束）。内核级五条全部来自 2026-09-17 的一次真实事故，不是预防性建议。

**事故经过**：brainstorm 期间为验证 py-spy 可用性，手写探针脚本以 `num_simulations=60000, max_workers=4` 驱动 `run_batch_parallel`，导致目标机器内存耗尽崩溃（该机总内存 15.3 GB）。

**根因（已核实到代码级）**：探针未传 `on_result`，而 `service/batch_simulator.py:415` 是 `results = [] if on_result is None else None`，`:441` / `:496` / `:556` 在无收集器时逐条 `results.append(...)`，`:452` 把整个 list 返回——即父进程同时持有 60000 份 `CompactResult`（含逐抽数组）。

**加重因素**：探针首版漏写 `if __name__ == '__main__':` 守卫，日志中出现两行 `PARENT_PID`，证明 spawn 出的 worker 反过来又去创建自己的进程池，形成级联；Python 最终以 `RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase` 拦下。

### 2.1 内核级（规则 1-5）

| # | 规则 | 违反后果 |
|---|------|---------|
| 1 | 必须传 `on_result` 流式收集器，禁止无收集器裸跑大批量；**无收集器时 `n` 另有独立上限 `n ≤ 1000`** | 全部结果堆在父进程，大批量必 OOM |
| 2 | 主模块必须有 `if __name__ == '__main__':` 守卫 | Windows spawn 下级联起进程池 |
| 3 | 杀进程必须带 `/T`（`taskkill /PID <pid> /T /F`） | Windows 杀父不杀子，孤儿 worker 残留 |
| 4 | 设 N 上限（`collector=True` 时 `n ≤ 1600`），且先小规模试跑验证进程模型起得来（`n ≤ 100` 跑通一次） | 首次就跑大批量，出错即全量代价 |
| 5 | 启动前检查可用内存（`avail ≥ max(2.0 GB, workers × 0.75 GB)`），低于阈值直接拒绝 | 在用户正在使用的机器上打满内存 |

**规则 1 与规则 4 的上限互不包含**（2026-09-21 订正）：若规则 1 沿用规则 4 的 1600，则规则 1 的拒绝集合成为规则 4 的真子集——删掉规则 1，`validate()` 行为分毫不变；而事故量级（60000）恰好落在放行区间内。故规则 1 给出独立阈值 1000，使事故量级不可达。**规则 1 / 4 / 5 的完整口径与理由见 `P83 §3.4`，那里是唯一口径；`benchmarks/README.md` 是面向维护者的副本。**

规则 1 与 2 特别值得记录：**现有脚本早就防住了这两点**，而探针把它们同时丢掉。`scripts/profile_sim.py:116` 有主模块守卫，`:32-33,53` 用了 `SharedResultCollector` + `extract_aggregate` + `on_result=collector.on_result`。绕过已有代码自己写驱动，等于放弃已经付过学费换来的防护。

### 2.2 路径级（规则 6-11）

规则 6-8 来自 2026-09-17 对 QtWebEngine 的实测（六变体矩阵）；规则 9-11 来自 2026-09-18 的启动测量。

| # | 规则 | 违反后果 |
|---|------|---------|
| 6 | `gui-qt` 路径必须构造 **`QApplication(sys.argv)`（非空 argv）**，且 `QApplication` 之前须 `setAttribute(AA_ShareOpenGLContexts)` | 空 argv 下 QtWebEngine 初始化失败，进程以 `0xC0000409` 终止 |
| 7 | `gui-qt` 路径收尾必须**显式回收 Chromium 子进程** | `MainWindow` 显示后实测 10 个 `QtWebEngineProcess` 子进程；不回收将残留 |
| 8 | 关闭 `MainWindow` 必须**先置 `win._restarting = True`** 再 `close()` | 否则弹「确定要退出吗」确认框并阻塞，自动化流程卡死等人点击（`main_window.py:627-641`） |
| 9 | `subject='startup'` 必须在**全新冷进程**内测量，由子进程回传自己的时间线 | 模块 import 缓存是启动成本的主要部分（实测 `MainWindow` import 0.320s）；在已预热的适配器进程内测会趋近 0 |
| 10 | 启动测量前**先跑一次同条件预热并丢弃**，只记录第二次 | 冷热文件缓存相差数倍，而清空 Windows 文件缓存需管理员权限、不可靠复现。**冷启动显式不在覆盖范围内**（见 §10） |
| 11 | RSS 必须**固定采样时刻**（取启动完成时刻的峰值）。**本条只适用于 `subject='startup'`** | 实测空闲期工作集被系统回收，单次运行内 368 MB → 36 MB，不同时刻取值可差十倍。`subject='simulation'` 本期不采集 RSS（记 `None`、按不可比处理），见 §4「资源计数的采集面」 |

**规则 6 的排查教训（方法论，值得单独记住）：** 该现象先后被归因于「非交互式执行环境」与「Chromium 自带沙箱」，**两次都被证伪**；真实原因是**探针自身用了 `QApplication([])` 传空 argv**。**排查自身工具的失败时，应把「我调用的方式是否正确」列为一等假设，排在环境假设之前。** 详见 `P83 §3.10`。

## 3. 驱动复用约束

**适配器不得新写驱动，只能修复或包装已有入口。**

存在两种做法：

- 正例：适配器 import `gui/gacha_panel.py` 里现有的 `SimulationThread`，用 offscreen `QApplication` 驱动它，**不重写该入口**（**2026-09-22 措辞订正**：原文写「被测代码一行不改」，该表述已按 `P83 §3.2`「约束 B 的范围修订」放宽为「**默认路径一行不改**」——需要可观测性的地方一律以 opt-in / 默认关闭的产品侧可选通道补齐，见 §4 资源计数行的收窄与 §11）；`inline` 适配器就是修好后的 `scripts/profile_sim.py` 驱动逻辑
- 反例：为「方便测量」新写一个脚本去跑模拟

**理由**：自己写驱动，测出来的是驱动而不是产品。2026-09-17 的事故是极端例证——手写驱动引入的两个缺陷，直接改变了被测对象的进程模型（级联起池）与内存行为（结果堆积），此时测出的任何数字都不描述产品。

**判别式**：任何一个适配器如果需要「先写个脚本来跑」，说明它设计错了。

**推论**：`scripts/` 下现有三份 profile 脚本是待接管的资产，不是待废弃的旧物。它们编码了踩坑换来的防护（主模块守卫、流式收集），修复它们（`strategy_name` → `strategy_key` 等）就是平台的第一批工作。

## 4. 三轴模型

三个轴正交，任意组合：

**轴一 · 粒度 grain**（纵向分辨率，逐级叠加）

| 档位 | 产出 | 相对成本 |
|------|------|---------|
| `batch` | 仅总墙钟 | 最低，可跑大 N |
| `stage` | 阶段分解：配置加载 / env 构建 / 进程池启动 / 模拟 / extractor / 分发 | 低，默认档 |
| `single` | **本期预留，未实现**（见下） | — |
| `function` | 追加 `cProfile` 的函数级调用次数与自耗时 | 高（2-5x 插桩开销），N 需下调 |

**`single` 档本期未实现（2026-09-21 定死，2026-09-22 同步本表）：** 原表把它写作档位能力，但 §6.0 的 43 项子任务中**没有任何一项承接它**，采集通道表也没有对应采集点，故 `RunResult.single` 恒为 `None`。定死：`SingleStats` 类型与 `RunResult.single` 字段**预留保留**（不删）；`Plan.validate()` 对 `grain='single'` **构造期抛 `ValueError`**（声明一个平台不实现的粒度属调用方编程错误，早失败优于「跑完发现没有分布数据」）；实现该档须先定义「逐次模拟时长」的采集通道（三条执行路径都要有落点，MPPool 路径的采样点在 worker 侧），登记后**再删除**该拒绝规则。**唯一口径见 `P83 §3.3`。**

**资源计数的采集面（2026-09-21 收窄；2026-09-22 同步本表）：原写「在任何档位都采集：几乎免费且确定性」，与「采集主体无归属、`subject='simulation'` 无采样时刻」的实况不符。** 逐项口径如下：

| 读数 | 采集面 | 采集主体与时刻 |
|---|---|---|
| 序列化字节数 | **只有具备回传通道的路径采**（`cli` 经 opt-in `--perf-json`） | 产品侧可选通道（`run_batch_parallel`，受 `collect_perf` 门控，默认关闭）；其余路径记 `None` + `warnings` 标「本路径不可得」 |
| RSS 峰值（`subject='startup'`） | 采（规则 11） | 启动完成时刻的峰值 |
| RSS 峰值（`subject='simulation'`） | **本期不采集**：恒为 `None`，比对时按不可比处理（**不得当 0**） | 无固定可归属采样时刻（worker 由 `Pool.__exit__` 的 `terminate()` 强杀，三条执行路径生命周期边界各异） |

**「免费」这一判断只对 `batch` 档的总墙钟成立；字节数与阶段计时都要靠 opt-in 通道才有数据，且在 `gui-qt` / `webui` 路径上不可得。** 完整理由与取舍见 `P83 §3.3`「资源计数的采集面」。

**轴二 · 路径 path**（在哪跑，见 §5）

**轴三 · 因子 factors**（跑哪些对照）：`n` / `workers` / `chunksize` / `strategy_key` / `config` / `seed`。**`Plan` 自身只承载标量规格**；因子的多值扫描由 `PlanGrid(base, factors).expand()` 承载，产出笛卡尔积并按去重后每格一条记录（**2026-09-22 形态落定**：原写「一个 plan 展开为因子的笛卡尔积」，未区分承载展出的容器与展出结果）。

## 5. 路径是一等维度

### 5.1 为什么不是「环境细节」

本项目历史上性能与行为都出现过路径分叉，有档案可查：

**性能分叉**
- P12：GUI 1000 样本 10-15s 对 CLI 1.6s，差 10 倍。根因是 `DrawSequenceExtractor` 只存在于 GUI 路径且在主进程串行执行，把 18 个 worker 的并行优势完全抵消
- P12 / `04-问题.md`：多面板 CPU 争抢是纯 GUI 现象，CLI 不存在
- P12 / `04-问题.md`：单进程路径全局变量污染，影响 CLI 与单次 GUI 模拟

**行为分叉**
- P54 的触发原因即「CLI 与 GUI 模拟入口分歧严重，CLI 自写 55 行 `run_single_sim()` 独立于统一引擎」（已修）
- P37：旧 `_build_resource_gain()` 对 GUI 创建的规则静默跳过，GUI 建的规则实际不生效而手写配置生效
- P49：往返损坏只发生在 GUI 路径
- P78 ISSUE-109：`_register_resources_from_pools` 的 GUI 侧扫描被判定为**无效通道**，插入的行会被后续 `setRowCount` 整表重建清空

最后一条最能说明问题：**在 GUI 路径上，「看起来做了」和「实际生效」可以是两件事。** 一条从不被独立测量的路径，会长期带着未被发现的偏差存在。

### 5.3 测量覆盖 ≠ 代码收敛

让 GUI 路径可测，**不需要**重构 `gacha_panel`，只需要一个能驱动它真实调用链的薄适配器。收敛 `gui/` 与 `webui/` 两套平行编排是 P74 换头计划自己的事，不在本子系统范围内。

P74 落地时 `gui-qt` 适配器随之删除，内核不动。

### 5.4 `inline` 路径的定位

保留 `inline` 的价值是提供一条不受进程模型干扰的纯计算基线；风险是它极易被误读为「这就是模拟的真实耗时」。

**处置**：`RunResult.is_user_path = False` 强制标注，使它在任何报告中自带「这不是用户路径」的标签。

**实证依据**：`scripts/profile_sim.py:93-111` 测「单次模拟耗时」的办法是在主进程串行跑 20 次 `run_simulation_compact`，这绕开了子进程插桩的难题，但同时换掉了执行环境——没有 spawn、没有 IPC、没有 extractor。那个数字不描述 GUI 里的任何一次模拟。

## 6. 两层剖析分工

| | `cProfile` | `py-spy` |
|---|---|---|
| 机制 | 插桩（每次调用记账） | 外部采样（默认 100/s 读栈） |
| 精度 | 调用次数精确 | 采样，短函数可能漏 |
| 开销 | 2-5x，绝对耗时不可用 | 通常 <5%，接近真实 |
| 覆盖 | **仅被插桩的那个进程** | attach 任意 PID，`--subprocesses` 覆盖子进程 |
| 前提 | 能改代码、能重启 | 都不需要 |
| 可复现 | 高（同种子同 N，次数确定） | 低（采样噪声） |
| 进基线做回归 | 可以 | **不可以**，噪声会被判成信号 |

**分工原则**：进基线的必须是确定性量，故用 `cProfile`；`py-spy` 用于阶段计时与 `cProfile` 都指不出所以然时的现场勘查（主进程串行段、IPC 等待、Qt 事件循环）。

**实测结论（2026-09-17）**：`py-spy 0.4.2` 在本机可用，`--subprocesses` 能采到 `multiprocessing` 子进程并命中 `_wk_run_single` / `build_strategy_context` / `create_strategy`（4 个 worker，8 秒 3193 样本）。同一次实测中，父进程主线程空等在 `multiprocessing/pool.py:861`——**这实证了在主进程挂剖析器测不到有用信息**。

**依赖边界**：`py-spy` 是独立可执行文件（`pip install py-spy`，但不可 `import`），只进开发依赖，**不进发布产物**。

## 7. 粒度经济学

递进顺序为 **批次 → 阶段 → 单次 → 函数 → 进程**。每一级都会筛掉大部分候选。

**为什么默认档是 `stage` 而不是 `function`**：P12 定位到核心瓶颈（GUI 的主进程串行 extractor）用的是分阶段计时，投入产出比极高；而 `function` 档有 2-5x 插桩开销，且在主进程插桩根本覆盖不到 worker。一上来就录火焰图，容易得到一张漂亮但指向错误的图。

**为什么资源计数只对 `batch` 档「免费」**（2026-09-22 订正——原文写「资源计数免费：序列化字节数与迭代数是随模拟自然产生的，不需要额外测量动作，应当无条件采集」，与 §4 收窄后的采集面不符）：**总墙钟**确实是跑一次就自然得到的免费读数；而**序列化字节数与阶段计时不是**——产品侧原本没有它们的采集点，须经 opt-in 通道（`run_batch_parallel` 的 `collect_perf` 门控 + `cli --perf-json`）才能取到，且**在 `gui-qt` / `webui` 路径上不可得**。故本条的正确表述是：**能取到就取，取不到如实记 `None` 并在 `warnings` 标注，不假装免费、也不因取不到而阻断测量**（同 §2.2 规则 11 的 `None` 处置口径）。采集面逐项见 §4。

## 8. 回归判据的理论基础

**用比值不用绝对毫秒**：绝对耗时受 CPU 频率、机器负载、OS 调度影响，跨时间跨机器都不可比。比值（相对历史基线）消掉大部分共模因素。

**用字节数不用耗时**：P12 记录 pickle 传输占总耗时 40-60%，必须有指标盯着。但「pickle 耗时」噪声大且与字节数非线性（对象小而种类多时，memo 记账开销占比上升）；而**同配置同种子下 `CompactResult` 的序列化字节数完全确定，零噪声**，任何变化必然是代码改动引起的。

**口径（2026-09-17 查证后定死）**：量**整个三元组** `len(pickle.dumps((compact, extraction, warnings)))`，不只量 `compact`。

- 为何不能只量 compact：`extraction` 包内含 `heatmap_ach_bins` / `heatmap_res_bins`，两者长度等于本次抽卡次数，是**唯一随抽数增长的传输分量**，也正是 P12 Phase 1.5 砍掉 93% 所针对的对象。只量 compact 会正好漏掉它
- **原疑点已证伪**：跨进程传的是**对象**不是 dict。`CompactCollector.get_result()` 返回 `self._result` 即 `CompactResult` 实例，`run_simulation_compact(...) -> CompactResult` 类型标注一致；而 `CompactResult.to_dict()` / `from_dict()` **全仓零调用点**（含 `tests/` 与 `scripts/`），不在热路径上
- **不可把各分量相加**（2026-09-18 实测）：`compact` 单独序列化 780 KB、`extraction`+`warnings` 1216 KB，之和 1996 KB > 整体 1688 KB（118%）。pickle 的 memo 在**同一次序列化内**共享重复对象引用，分项各自序列化则各记一份。**只能量整体，分项相加虚高 18%**
- 剩余偏差仅来自 pickle 实现与队列分帧，作回归判据可忽略；当绝对开销读仍会偏

**重复测量取中位数**：单次测量在 Windows 上抖动明显（spawn 开销本身有方差）。默认 `repeats=3` 取中位数；预估墙钟超 30 秒时降为 1 并记录 `repeats_downgraded`；**建立基线时强制 ≥3，不允许降级**。原始各次值保留在 `wall_samples`，以便判断结果稳定与否。

**基线按机器类别分组**：基线入库后会跨机器比对，而核数不同则绝对耗时不可比。故基线按「核数区间 + OS 版本」分组，**同组内比比值，跨组只比阶段占比（相对结构）**。若实际只有一台基准机，则在基线文件中显式写明适用范围，而不是假装跨机器可比。

## 10. 启动测量的特殊性（2026-09-18 纳入）

启动速度是**另一个测量对象**，不是模拟路径上的一个阶段。它在三处与模拟测量不同，故有独立约束（对应 P83 §3.4 规则 9-11）。

**一、必须在全新冷进程内测。** 启动成本的主要部分是模块 import，而 import 结果被进程内缓存。实测 `MainWindow` 的 import 为 0.320s；在已预热的适配器进程内测，这个数会趋近 0。故适配器须 spawn 全新子进程，由子进程回传自己的时间线。

**二、冷启动显式不在覆盖范围。** 冷热文件缓存可差数倍，而清空 Windows 文件缓存需管理员权限、不可靠复现。因此采「先跑一次同条件预热并丢弃，只记录第二次」，并在基线记录中标注「热启动」。**这是一条范围上的取舍，不是遗漏**——把不可复现的条件纳入基线，只会制造假回归。

**三、RSS 必须固定采样时刻。** 实测单次运行内 RSS 从 368 MB 掉到 36 MB——Windows 会回收空闲进程的工作集。同一份数据在不同时刻取值可差十倍，故取启动完成时刻的峰值。

**三个时间点而非一个。** 实测（2026-09-18）：**窗口可见 2.3s / 启动工作完成 6.5s / 图表可用 8.2s**。用户感知到的是第一个，第二个才代表启动真的做完，而第三个决定「能不能真用」。三者都记。

**「启动工作完成」必须按整棵进程树统计 CPU。** 实测父进程 6.5s 就 CPU 归零，但 10 个 Chromium 子进程仍在工作，图表要到 8.2s 才就绪。只看父进程会把「父进程闲了」误报成「启动完成」。

**图表可用存在争用。** 单独建一个 `ChartWebView` 的 `_loaded` 约 1.5s；主窗口建 10 个时，**首个**就要 7.90s。这属被测量对象的特性，不是测量误差。

**实测基线（2026-09-18，`python -m gacha_simulator.main`，真实平台）：** 窗口可见 2.3s；启动工作完成（CPU 归零）6.5s；峰值 RSS 368 MB；Chromium 子进程 10 个。分段明细见 P83 §3.11。

**2026-09-22 复核（`3f-1` 落地时，整棵进程树口径，0.5s 采样窗口）：** 0.5s 109% → 1.0-2.6s 3-9% → 3.1-4.1s 42-48% → 4.7s 156%（Chromium 开始起）→ **5.7s 窗口可见** → 6.2-7.3s 615-999%（渲染 + 图表）→ **7.8s 起 0.0%** 并保持（8.8s 有一个 6% 的短促回升）。三点结论：① **「按整棵进程树统计」这条修正成立且必要**——6.5s 附近整棵树正在 615-999% 的满负荷上，只看父进程必然误判；③ 本机比 2026-09-18 那台慢（启动完成 7.8s vs 6.5s），**绝对值不可跨机比，只与同机基线比**。

**同日再测推翻了一条推论（重要）：三个时刻的先后顺序**不**固定。** 加上「图表可用」的采集后实测到 **图表 2.29s 就绪、而整棵进程树到 3.14s 才安静**——顺序与本节上一段相反。这不是测量错误：`ChartWebView` 的 `loadFinished` 只等本地骨架页（含 plotly.js，无网络），而进程树 CPU 归零还要等 Chromium 的后台收尾，两条线互不等待；本机 2026-09-18 那次恰是反过来的。**故八段词汇表的排列是「呈现顺序」而非「时间顺序」**，段值一律按**观测到的先后**相切分（每个时长记在较晚那个时刻的段上），顺序与名义不符时报告里显式写出一条告警。若按名义顺序硬减，颠倒时会算出负值、只能整段丢弃——那会把一个真实存在且可测的时刻变成「永远不可得」。<!-- P83 3f-2 -->

## 11. 价值验证：先证伪，再扩张（2026-09-18 纳入）

**核心原则：在扩张功能覆盖之前，先证明核心能力对一次已知变慢有效。**

本平台的验收有三个层次，混在一起谈会造成「验证过了」的错觉：

| 层 | 问的问题 | 怎么证 | 状态 |
|---|---|---|---|
| 需求层 | 目标能不能达成 | 跑一遍看判据 | 可跑验证 |
| 假设层 | 设计能不能按预期跑起来 | 实测（如 §8/§10 与 P83 §3.8/§3.10/§3.11 的记录） | 已实测多项 |
| **价值层** | **这东西值不值得建** | **故意制造已知变慢，看能不能准确报出来** | **阶段 1 后由 P83 §3.13 的门控回答** |

前两层证不了第三层。一个在所有假设上都成立、但报不出真实变慢的平台，仍然是废的。

**因此设门控而非普通测试**：判据（受控注入的准确度 ≤ ±25%、无关系段落在 `[0.9, 1.1]` 内、真实注入可稳定检出）**预先定死**，FAIL 时**不得继续扩张功能**——瓶颈在测量稳定性而非功能覆盖，返工方向应定死在重复测量与噪声控制上。

**这与本平台的一贯立场一致**：先测准，再铺开。P83 §3.2 约束 A（不许自己写驱动）、§3.4 安全协议、以及「粒度默认 `stage` 而非 `function`」，都是同一条纪律的不同侧面。
