## 业务问题

「跑一次模拟」这件事，现在的完整语义分散在三处：

1. **调用之前**：三条产品入口（GUI / WebUI / CLI）各自构造环境、设置调用态字段
2. **调用之后**：各自消费返回值、各自把结果组装成数据集
3. **调用本身**：`run_batch_parallel`（这一处是统一的）

结果是：同一次模拟，从 GUI 存和从 WebUI 存，得到的数据集不同（`pool_types` 一侧恒空）；新增一个入口要复制一遍胶水；core 内部两个算法模块（撤退搜索、最差影响）反向依赖了 service。

模拟工作区的角色是**给「跑模拟」这件事一个完整的家**：
- 决定跑哪些配置（变换器：从配置派生 sub 配置）
- 组织成可观测、可取消的任务
- 把产物落到工作区，维护它们之间的关系
- 让产物成为一等公民，可被任何消费者按 id 取用

## 设计意图

1. **编排与执行分离**：本层决定「跑哪些、怎么组织、存哪」；模拟服务层负责「怎么跑得快、怎么省内存」。本层调用下层，方向单向
2. **产物是数据集的唯一来源**：所有模拟产物经本层落工作区，带统一元信息，可被分析层按 id 消费
3. **树是视图，不是状态**：配置与数据集的父子关系由指针承载，树由指针解析得出，不另存一份
4. **配置可派生**：基线、最差情况配置、搜索中间配置都是某个配置的派生，派生关系是树上的一条边

## 边界

**属于本层**：配置的派生与编排、任务的进度与取消、模拟产物的落盘与元信息、工作区的组织（配置库、数据集库、关系索引）、树的解析。

**不属于本层**：
- 并行的具体实现（属模拟服务层：`run_batch_parallel`、worker initializer、内存优化）
- 分析（属分析服务层 P86：消费数据集，产出图/表/摘要）
- 渲染（属前端与 `visualization/chart_spec.py`）
- 模拟算法与保底引擎（属 `core/`）

## 与相邻子系统的关系

| 相邻 | 方向 | 说明 |
|---|---|---|
| 模拟服务层 | 本层调用它 | 它是执行器（怎么跑），本层是编排（跑哪些、存哪） |
| 分析服务层（P86） | 它消费本层产物 | 本层产出数据集，P86 按 id 消费；本层不依赖 P86 |
| 配置系统 | 本层承载它 | 配置成为可派生、可持久化的节点（现在只有单份 `config.toml`） |

## 本层的三个系统

本层不是一个系统，而是三个（划分依据是「因什么而变」，详见 `01-理论.md` §三）：

| 系统 | 职责 | 因什么而变 |
|---|---|---|
| 工作区机制（基础设施） | 目录、文件读写、系统注释、索引、锁、版本、迁移 | 存储方式变了 |
| 配置生命周期（领域） | 身份、派生、写时复制、Draft 与 File、冻结规则、引用查询 | 配置的语义变了 |
| 任务编排（领域） | 变换器、运行器、汇合器、任务对象、进度、取消、批次 | 任务类型变了 |

## 理论基础

见 `01-理论.md`。要点：概念层级（配置参数 / 运行参数 / 模拟参数，运行参数不进配置身份）；内容文件化 + 关系注释化，索引为纯缓存；身份用路径而非内容哈希；写时复制「跑过即冻结」与 append-only 不变量；Draft 与 File 两概念；变换器 + 运行器 + 汇合器三段；批次标识使「组」退化为查询；以及第八节的「事实 vs 结构保证」边界登记。
