## 1. 业务问题

GachaStat 是一个概率模拟与分析系统，计算正确性是用户信任的生命线。当前面临三个问题：

1. **核心计算模块缺乏回归安全网**：修改 `strategy.py`、`gdr.py`、`worst_impact.py` 等模块时，无法快速验证"改动没有破坏其他行为"。每次修改依赖人工审查。
2. **覆盖率分布极不均匀**：总体 29%，core/ 层 55%，但简单的工具文件（`bootstrap.py` 93%、`config_store.py` 98%）拉高了均值，真正复杂的计算模块（`worst_impact.py` 22%、`comparison_analyzer.py` 20%）覆盖惨淡。
3. **P0 阻塞项全部落在低覆盖模块**：P19/P26/P28/P31 要改的代码恰好是测试最薄弱的地方——改 bug 时没有测试保护，可能引入新 bug。

## 2. 设计意图

测试体系的核心设计意图：

- **单元测试为主力**：项目特点为纯计算、无 IO、无外部依赖，单元测试是最高效的质量手段
- **集成测试为补充**：service 层编排测试验证模块间协作
- **GUI 不做单元测试**：PyQt6 技术特性（需 QApplication、依赖显示服务、信号/槽异步）决定了 GUI 单元测试 ROI 极低，业界共识为将业务逻辑抽取到 core 层
- **pre-push 快速门禁**：H9 hook 在 push 前运行全量 pytest，当前 4.2s，目标 ≤15s——开发者不会因等待而跳过

**非功能性目标：**
- 测试代码风格与源码一致：简洁 pytest，函数级测试，AAA 模式
- 不引入重量级测试框架（hypothesis、behave 等）
- 几乎不用 mock/patch——构造真实对象喂入断言输出

### 质量门禁

| 门禁 | 触发 | 行为 |
|------|------|------|
| H7 | `git commit` | `ruff check` 格式检查（ms 级） |
| H9 | `git push` | `pytest -q` 全部通过（当前 4.2s） |

### 当前指标

- 测试用例：425（1 skipped）
- 总体覆盖率：29%（16,934 语句，11,994 未覆盖）
- core/ 覆盖率：55%
- 测试耗时：4.2s

## 4. 已知风险

| 风险 | 严重度 | 说明 |
|------|--------|------|
| 核心模块覆盖不足 | 🔴 高 | `worst_impact.py` 22%、`comparison_analyzer.py` 20%、`retreat_search.py` 29% |
| 部分代码可能不可测 | 🟡 中 | 逻辑深度耦合、缺少接口边界——需标记 TODO(skip) 不阻塞 |
| GUI 层无自动化覆盖 | 🟢 低 | 已知限制，通过抽取可测逻辑缓解 |
| 无 CI 环境 | 🟢 低 | 仅本地 pre-push 门禁，依赖开发者手动 `git push` 触发 |
