# 并行效率测量 · 清单与判据（P83 后续增量）

> 建档：2026-09-28
> 关联：`P83 性能分析平台`。**本文件是这一轮增量的判据真值源**——先写判据再实现，
> 与平台既有纪律一致（§3.9 的测试策略、§3.13 的阈值都是先定死再动手）。
> 用户裁定：读数进 `RunResult`（甲）／CPU 时间分到每个 worker（两者都要）／
> 本轮只做 L1+L2，L3 调研后再定／`0.75 GB/worker` 一并实测。

---

## 1. 为什么做这件事（问题）

平台现有的全部读数都是**墙钟量**：总墙钟、逐段计时。它们能回答「慢了多少」，**不能回答
「为什么慢」**——具体到并行场景，缺的是这一问：

> `simulate` 那 12.2 秒里，4 个 worker 是**一直在算**，还是**大部分时间在等**？

这两种情况的优化方向完全相反：前者要动算法/执行引擎（P12 的 Phase 2），后者要动调度、
负载均衡或 IPC。**没有读数就无法判断，而没有判断就谈不上优化决策。**

## 2. 三个层次（框架）

| 层 | 问的问题 | 需要的读数 |
|---|---|---|
| **L1 量** | 起了几个 worker？跑满了吗？ | worker 实际进程数、每 worker 分担的模拟数 |
| **L2 质** | worker 在**算**还是在**等**？ | CPU 时间、**并行效率** |
| **L3 因** | 没跑满的话，卡在哪？ | 等锁／负载不均／序列化／IPC／换页的归因 |

**顺序不可跳**：L3 的归因依赖 L2 先能看出「确实没跑满」。**本轮只做 L1 + L2。**

## 3. 本轮要采的读数（清单）

全部新增到 `RunResult.resources`（`ResourceStats`），**随记录入库、可进基线比值**。

| 读数 | 定义 | 层 | 为何必须有 |
|---|---|---|---|
| `worker_count` | 实际起了几个 worker 进程 | L1 | 最基础。现在 `workers=4` 只是 CLI 默认值，**没有任何读数确认真的起了 4 个**——`_wk_init` 失败会静默落到单进程或 `mp_failed` 兜底 |
| `worker_task_counts` | 每个 worker 各处理了多少次模拟 | L1 | 回答「跑满了吗」。`imap_unordered` 的分配粒度会让「4 个 worker」实际只有一个在加班 |
| `cpu_seconds_total` | 整棵进程树的 CPU 时间（user + system，跨核求和） | L2 | 并行效率的分子 |
| `cpu_seconds_by_worker` | **分到每个 worker** 的 CPU 时间 | L2 | 只看总和看不出「3 个在算、1 个在闲」；分项才是不均的证据 |
| `wall_seconds`（已有） | 墙钟 | L2 | 分母 |
| `parallel_efficiency` | `cpu_seconds_total ÷ (simulate 墙钟 × worker_count)` | L2 | **一个数回答「在算还是在等」** |

**`parallel_efficiency` 的口径定死：**

- 分子取**整棵进程树**（父进程 + 全部 worker）的 CPU 时间，含 user + system。
- 分母的**墙钟取 `simulate` 段**，不是总墙钟——`pool_start` 那 1.0 秒是串行的，
  算进去会系统性压低效率，而那不是并行的锅。
- **> 1 是可能的且正常**：多核机器上 CPU 时间可以超过墙钟。上限是 `worker_count`
  （受核数限制时更低）。**1.0 表示「worker 侧满载」，不是「效率 100%」**——
  父进程侧的序列化/合并也计在分子里，故它可能 > 1 而 worker 并未满载。报告须写清这一点。

## 4. 判据（先定死）

| # | 判据 | 通过条件 |
|---|---|---|
| A | **采到了就标注** | 采不到时记 `None` + 点名成因的 `warnings`，**不得填 0 冒充** |
| B | **`collect_perf=False` 时零采集** | 默认路径上不多一次 `psutil` 调用、不多一次 `cpu_times()`（同 §3.5 对两槽的门控纪律） |
| C | **不改模拟结果** | 采集开关开关两态下，同种子结果逐字段一致（`_RESULT_VERSION` 不变） |
| D | **worker 数可核** | `worker_count` 与 `_wk_init` 实际执行的次数一致（用 worker 侧落一份自报标记来验，同 `6g` 在 T4 用过的形态） |
| E | **分项与总和自洽** | `cpu_seconds_by_worker` 各项之和 ≤ `cpu_seconds_total`（父进程自己那份 CPU 也在总和里） |
| F | **效率读数有鉴别力** | 用 `workers=1` 与 `workers=4` 各跑一次，`worker_count` 必须不同、`parallel_efficiency` 必须能反映差异——**否则它就是又一个无鉴别力的断言**（本项目已在这上面栽过两次） |

**判据 F 是本轮的重点**：`dispatch > 0` 与 `profile_count >= 2` 两次教训都是「断言对
缺陷毫无反应」。故本轮的验收必须包含「**改变并发度，读数必须跟着变**」。

## 5. 规模扫描（本轮测哪些点）

两个正交轴：

| 轴 | 取值 | 想回答 |
|---|---|---|
| `workers` | 1 / 2 / 4 | 效率随并发度怎么变、从哪开始掉 |
| `chunksize` | `None`（自算）/ 1 / 10 | 负载均衡受 chunk 多大影响 |

**范围受规则 5 限制**：要求 `avail ≥ workers × 0.75 GB`，而本机可用内存 3-4 GB。
故本轮**只扫到 `workers=4`**（需 3.0 GB）。

**`workers=8 / 16` 要等第 6 节**——那个 `0.75 GB/worker` 是**没有任何测量依据的初始值**，
若实测证伪（例如实需 0.3 GB/worker），扫描范围随之放宽。

## 6. `0.75 GB/worker` 的实测（前置项）

- **现状**：`plan.MEM_PER_WORKER_GB = 0.75` 是**写死的初始值**，`README.md` 与
  `plan.py` 都只说「规则 5：每个 worker 的增量」，**全仓无测量依据**。
- **要实测的量**：每个 worker 进程在稳态下的峰值 RSS，以及父进程随 `workers` 增长的
  增量（父进程侧还有结果累积）。
- **做法**：在 `workers = 1 / 2 / 4` 三点上采「整棵进程树峰值 RSS」，减去
  `workers=0`（单进程路径）的基线，除以 worker 数即得每 worker 增量。
- **纪律（同 §3.4）**：证伪则**记录原值与理由后修订**，不得静默放宽。
- **它解锁什么**：若实测值显著小于 0.75，`workers=8/16` 的扫描才跑得起来。

## 7. 明确不做的（避免把「测不到」包装成「测了」）

| 不做 | 理由 |

**改产品代码的位置**：`service/batch_simulator.py` 的 MPPool 分支（约 `:634` 起），

| 读数 | 在哪采 | 怎么采 |
|---|---|---|

| `parallel_efficiency` | **不在产品侧算** | 由适配器/报告侧从上面几项算出——**产品侧只采原始量，不做派生**（与 `stage.py` 只解析不采集的分工一致） |

### `worker_task_counts` 的最终口径（上面推演后的结论）

**改父进程侧统计，不改 worker、不换 `imap`**：`imap_unordered` 的返回值里带
`ext_pkt`，而 `WorkerLocalExtractor` 产出的包里有 worker 侧能拿到的身份（`pid`）。
若该包没有可用身份，则**本项降级为「只报 `worker_count`，不报每 worker 的任务数」**，
并在 `warnings` 里写明成因——**宁可少一项，也不引入一个猜的数**。

> 这一条是**实现时才能定死的**（取决于 `WorkerLocalExtractor` 的产出里有没有 pid），
> 故在此写明**两条分支各自的结果**，实现时按实际选一条并回写本节。

## 11. 首轮实测（2026-09-28，`cli` / `n=1000` / `seed=42`）

| `workers` | `simulate` | `worker_count` | `cpu_seconds_total` | 其中父进程 | 每 worker 任务数 | 每 worker CPU | `parallel_efficiency` | 相对 w=1 加速 |
|---|---|---|---|---|---|---|---|---|
| 1 | 35.049 s | `None` | `None` | —— | —— | —— | `None` | 1.00x |
| 2 | 18.816 s | 2 | 38.391 s | 1.156 s | 451 / 501 | 18.52 / 18.72 | **1.020** | 1.86x |
| 4 | 12.949 s | 4 | 52.313 s | 1.656 s | 201 / 201 / 251 / 251 | 12.50–12.80 | **1.010** | **2.71x** |

**判据 F 通过**：并发度变化时 `worker_count`（None→2→4）、效率、任务数、CPU 分项全部跟着变。

### 三条结论

**① worker 侧真的跑满了——瓶颈不在并行度上。**

把父进程那份从分子里剥掉再看：

| `workers` | worker 侧 CPU 之和 | **worker 侧真实并行度**（÷ `simulate` 墙钟） | 父进程占总 CPU |
|---|---|---|---|
| 2 | 37.23 s | **1.979 核** | 3% |
| 4 | 50.66 s | **3.912 核** | 3% |

**w=4 时 3.912 核 / 4 个 worker = 97.8% 的并行度。** 所以「没跑满」不是问题所在——**这条读数把优化方向从「调度/负载均衡」推向了「算法/执行引擎」**，正是做 L1+L2 的目的。

**② 但加速比只有 2.71x，而并行度是 97.8%——差在哪？**

看 `pool_start`：它在 `simulate` 之外，**不受并行度影响**。用首轮数据（`pool_start` 约 1.02 s）：

- `simulate` 占比：`12.949 / (12.949 + 1.02 + 0.18) ≈ 91.5%`
- 总墙钟的理论下限 ≈ `35.049 × 0.085 + 35.049/4 ≈ 2.98 + 8.76 = 11.74 s` → 最大可达 **2.99x**
- 实测 2.71x → **已经拿到理论值的 91%**

> **2026-09-29 履约（上述「降进程启动成本」已实施）：** 病因查明为 **Windows spawn 下
> 每个 worker 都要重新导入主模块**（`cli.py`），而该模块顶层原有 4 条重导入，其中任意一条
> 都触发整个 `gacha_simulator.core` 加载（实测单次 **0.204 s**），由 4 个 worker 各付一遍。
> 把这 4 条下沉到函数体后（`gacha_simulator/cli.py`，commit `be741aa`），顶层只剩
> `_version` / `paths`（合 **0.026 s**，与空解释器持平）。
>
> | `pool_start`（`n=1000` / `w=4` / `seed=42`） | 值 |
> |---|---|
> | 优化前（三次） | **0.824 s**（0.824 / 0.824 / 0.824） |
> | 优化后（三次） | **0.345 s**（0.354 / 0.345 / 0.338） |
>
> 降幅 **0.479 s（58%）**。对照实验佐证病因：轻 `__main__` 的 Pool 构造 0.280 s、
> 重 `__main__`（顶层 `import gacha_simulator.cli`）0.854 s、真实 CLI 0.824 s，三者吻合。
> 残留的 0.345 s 是 worker 在 `_wk_init` 内导入 core 的固有成本（`_wk_init` 不预导入
> core/service 是既有设计，为避开 Windows spawn 下的页面文件耗尽，不可动）。

**故「加 worker 的收益快到头了」**：w=4→8 的边际收益是 `12.95 → 12.95×0.915/2 + 2.98 ≈ 8.9 s`，即再快约 1.45x，而上限 2.99x 已经吃掉大半。**继续加并发度的收益远小于把 `simulate` 本身做快。**

**③ 负载确实不均，但量级不足以解释加速比缺口。**

`n=1000, w=4` 时每 worker 是 201/201/251/251——**不均是 25%，不是两倍**（`n=200, w=2` 那次看到的 51/101 是**小样本效应**：`chunksize = 200/(2×16) = 6`，`imap_unordered` 按 chunk 分发，样本小时尾部偏差被放大）。> **2026-09-29 订正（量纲错误，L3 调研指出）：** 原文在此续写「不均的代价有界（最慢的
> worker 只多 25%）」，**把「不均程度」直接当成了「损失」**。`imap_unordered` 的墙钟由
> **最慢的那个 worker** 决定：最慢者 251 个任务，理想是 250（1000÷4），比值 **1.004**，
> 故理论收益上限是 **0.4%（约 0.05 s）**，不是 25%。25% 是「worker 之间」的差，
> 「相对理想」的差只有 0.4%。**该订正也是 `chunksize` 轴不值得扫的依据之一**（见下方
> 「已知局限」）。

### 用本数据回答「该不该继续加 worker」

**该考虑的是 `pool_start`，而不是 `workers`。** w=1→2 时 `pool_start` 的固定成本已经付过，故 1.86x 接近理想；w=2→4 只有 1.45x，因为 `simulate` 减半的空间被 1 秒的串行成本摊薄。**若把 `supervisor` 的进程启动成本降下来（或复用池），收益会比加 worker 更直接。**

### 已知局限（本轮不做的）

- `workers=1` 走单进程路径、不建池，故 L1/L2 **天然无落点**——`worker_count` 等如实记 `None`，不是缺陷。要它也有读数须给单进程路径单独定义「并行度」的口径（无意义），故**不补**。
- `chunksize` 轴**决定不扫**（清单 §5 曾列为待办，2026-09-29 裁决撤销）。**两侧互换的是
  两个已被证明无收益的项，净收益恒为 0**：调大减少 IPC 次数，而 IPC 空闲本就 ≈ 0
  （父进程仅占 3% CPU，见结论①，故结果队列不积压、worker 不阻塞在管道写）；调小使负载更
  均匀，而上限只有 0.4%（见结论③的订正）。**另有一条会误导人的陷阱**：`n=200, w=2` 时
  看到的 51/101 不均是 chunk 粒度效应，扫 `chunksize` 极可能在那种小样本点上测出「改善」，
  那是把噪声误读成成果。**且那个 `÷16` 的 divisor 是「首次进度回调延迟」的交互约定**
  （`batch_simulator.py:771-774` 注释），不是吞吐旋钮。
- `0.75 GB/worker` 的实测（清单 §6）：**已由 §12.1b（按 pid 分项）与 §12.2b（`workers` 轴）完成**（2026-10-01 订正，原文标「未做」）。每 worker 实测 0.053-0.070 GB 且随 `n` 走，「`workers × 0.75`」这一常数形式被证伪（§12.4 结论 2）。

## 12. `n` 上限的实测校准（2026-09-28，第 6 节的前置项）

清单 §6 原计划测「`0.75 GB/worker`」，实测下来发现**那个问题问错了**——真正的变量不是
`workers`，是 `n`。本节记录推翻的过程与结论。

### 12.1 实测（`cli` / `seed=42` / `workers=4` / 每点单跑一次）

| `n` | `simulate` | **父进程**峰值 | **子进程（worker）**峰值 | 合计 |
|---|---|---|---|---|
| 1,000 | 10.42 s | 41 MB | 479 MB | 520 MB |
| 5,000 | 59.10 s | 41 MB | 1,638 MB | 1,679 MB |
| 20,000 | 278.91 s | 42 MB | **5,430 MB** | 5,471 MB |

**方法**：`suspended_n_limits()`（本次新增的显式逃生口）+ 注入内存查询。**这是测量，
不是常规运行**——探针每点单跑一次、跑完即弃；该逃生口的上下文管理器里写了三条使用
纪律（只在测量脚本用、调用方自行盯内存、**测完必须回写结论**），本节的回写即是履约。

> **2026-09-29 口径修正：上表的「父进程」与「子进程」两列标签都是错的。**
> 原探针用 `_split_rss(os.getpid())` 取 `self`，而 `os.getpid()` 返回的是**探针进程**
> （一个只起采样线程、不跑任何模拟的空壳），探针的 `children()` 才是被测的 cli 进程树。
> 于是：表中「**父进程峰值 41 MB**」测的是探针自己（恒定是必然的，它什么都没干）；
> 表中「**子进程（worker）峰值**」实为 **cli 主进程 + 全部 worker 的总和**。
> 两列的实际含义见下方 12.1b 的修正口径实测。

### 12.1b 修正口径后的实测（2026-09-29，按 pid 逐进程分项）

方法：探针只做采样、不跑模拟；用 `subprocess` 起真实的 `python -m gacha_simulator.cli`，
再按 pid 把「被测 cli 主进程」与「它 fork 出的 worker」分开记录峰值。

| `n` | `w` | **cli 主进程峰值** | workers 合计 | 单 worker | `simulate` |
|---|---|---|---|---|---|
| 2,000 | 4 | **586.6 MB** | 210.6 MB | 53 MB | 22.5 s |
| 4,000 | 4 | **1,121.1 MB** | 279.7 MB | 70 MB | 51.5 s |
| 2,000 | 1 | **527.5 MB** | 无（单进程路径） | —— | 76.3 s |

**主进程随 `n` 近严格线性（1.91x / 2.00x），workers 只有 1.33x。** 这与 §12.2b 初稿的
归因**正相反**：内存大头在**主进程**，不在 worker。`w=1` 与 `w=4` 在同一个 `n=2000` 下
主进程几乎一样（527.5 vs 586.6 MB），说明**主进程那份与并发度无关**。

**单变量对照**（`n=2000` / `w=4`，只在「父进程是否保留 `n` 份结果」上不同，其余全同）：

| 变体 | 峰值 | 保留份数 |
|---|---|---|
| A 现状（`on_result=None`，`return_compact` 取默认 `True`）——**即 CLI 的调用姿势** | **588.1 MB** | 2000 |
| B 加 `on_result` 流式回调 | **227.5 MB** | 0 |
| C `return_compact=False`（**即 GUI/WebUI 的调用姿势**） | **218.0 MB** | 0 |

**归因确证**：CLI 主进程的 `results` 列表攒了 `n` 份完整 `CompactResult`，而 `cli.py`
只用它算 3 个标量（`total_draws` / `ssr_count` / `gdr_percent`，见 `cli.py:369-377`）。
**GUI/WebUI 早已改走 `extraction` 并置 `return_compact=False`，CLI 没跟上。**

线性斜率（由 n=2000 与 n=4000 两点拟合）：**A 为 0.267 MB/模拟**（`n=20000` 外推
约 5.4 GB，与 12.1 表总量吻合），**B/C 为 0.088 MB/模拟**（残项来自
`merge_extraction_packets` 的三处 `n` 份 `append`：`merged_agg` / `merged_transitions` /
`merged_cum`，而同一函数里的热力图却是真累加，见 `core/streaming.py:430-478`）。

### 12.2 两条既有估算的复核（① 的「推翻」不成立，② 成立）

**① 「父进程持有全部 n 份提取包」——本节初稿的「推翻」不成立（2026-09-29 订正）。**

原文写道：「`README.md` 与规则 1/4 的理由都写着『无收集器时父进程持有全部 `n` 份
`CompactResult` 与全部 `n` 份提取包（约 1996 KB/模拟），1000 份约 1.9 GB』。**实测父进程
峰值 41 MB，且 `n` 从 1000 涨到 20000 一点没动。**故规则 1/4 的数值与其理由都建在一个
错误的前提上。」

**这个「推翻」的依据测错了对象**（原探针的 `self` 取的是探针进程自己，见 §12.1 的订正）。
修正口径后（§12.1b）：cli 主进程在 `n=2000` 时 **586.6 MB**、`n=4000` 时 **1121.1 MB**，
**近严格线性**。所以：

> **规则 1/4 的原始理由成立**（父进程确实随 `n` 线性增长），**不应被推翻**。
> 它的真实缺口是另一件事：**没有把 `return_compact` / `on_result` 这两个旋钮算进去**。
> 同一份 `n`，CLI 走默认姿势时攒 `n` 份（0.267 MB/模拟），GUI/WebUI 走
> `return_compact=False` 时不攒（0.088 MB/模拟）。**规则按「攒」定价，对 GUI/WebUI
> 是过估、对 CLI 才恰好。**

至于 README 里那个「1996 KB/模拟」：它按**序列化体积**折算，与**驻留内存**不是一回事
（参 §12.1b 的单变量对照：A 的实测斜率 0.267 MB/模拟 ≈ 273 KB/模拟，远小于 1996 KB）。
**这个「两种口径不能混」的判断仍然成立**，但它是一个独立的口径问题，
**不构成对规则 1/4 理由的推翻**。

**② 「每 worker 一个常数」——形状不对。**

`MEM_PER_WORKER_GB = 0.75` 是「`workers × 常数`」的形式，**漏掉了 `n` 这个变量**：
实测 worker 侧内存随 `n` 显著增长（1000→20000 涨 11.3 倍）。

### 12.2b `workers` 轴补测（2026-09-28）——**内存涨在「执行模拟的进程」里，与是不是 worker 无关**

`n=20000`，只换并发度：

| `workers` | 子进程峰值 | 进程数 | 人均 | `simulate` |
|---|---|---|---|---|
| **1** | **4,617 MB** | 1 | **4,617 MB** | 819.92 s |
| 4 | 5,430 MB | 5 | 1,086 MB | 278.91 s |

**`w=1` 走的是单进程内联路径（不建池），照样涨到 4.6 GB。** 这更正了本节初稿里
「实际涨的是 worker」那句——准确的说法是：

> **涨在「执行模拟的那个进程」里，与它是不是 worker 无关。**

**「与是不是 worker 无关」这个方向判断仍然成立**（`w=1` 不建池也涨），
**但本节初稿对病因的归因是错的**（2026-09-29 订正）：

> **初稿写「每次模拟在进程内留下的东西：那 9 个等长于抽数的数组与累积快照」——
> 经查证不成立。** 那 9 个 `mc_*` 数组是 `WorkerLocalExtractor.process()`
> （`core/streaming.py:265`）的**局部变量，函数返回即释放**，规模是单次模拟的抽数
> （实测约 393）而非 `n`，**不构成随 `n` 增长的驻留项**。真正的 O(n) 项是
> **cli 主进程的 `results` 列表**（§12.1b 已证：斜率 0.267 MB/模拟，它攒 `n` 份完整
> `CompactResult`）。

**本表的「子进程峰值」一列同样是错标签**：它实为 **cli 主进程 + 全部 worker 的总和**，
而其中**主进程占绝对大头**。按 §12.1b 的斜率，`n=20000` 时主进程约 5.4 GB，
与表中 `w=4` 的 5,430 MB 吻合，即**worker 那部分只占零头**。两句旧解释据此修正：

- `w=1`（4,617 MB）≈ 全在主进程（单进程路径不建池，无 worker）；
- `w=4`（5,430 MB）≈ 主进程那份**基本不变** + 4 个 worker 各约 200 MB。

**故「人均 1086 MB 小于 4617 MB」不是「每个 worker 更省」，而是把固定的主进程那份
也摊进了分母**（5430 ÷ 5）。**同一份内存并没有变小，只是被换个方式算。**

**由此定下公式的形状：总量 ≈ `f(n)`，与 `workers` 基本无关。**

| | `n=20000` 总量 |
|---|---|
| `w=1` | 4,617 MB |
| `w=4` | 5,430 MB |

两者同量级（差 18%，来自 `w=4` 时每个 worker 各持一份独立累积）。**故
`MEM_PER_WORKER_GB = 0.75` 那种「`workers × 常数`」的形式从形状上就是错的**——它假设
总量随 `workers` 线性增长，而实测总量基本不随 `workers` 变。**「几十亿」那笔 126 GB 的
账，加多少 worker 都一样。**

### 12.3 曲线的形状（幂律拟合，中间点已交叉验证）

```
子进程内存 ≈ 479 MB × (n / 1000) ^ 0.81
```

用该式预测中间点 `n=5000` 得 1766 MB，**实测 1638 MB，偏差 +7.8%**——模型站得住。

| `n` | 外推 |
|---|---|
| 20,000 | 5.4 GB（**已实测**） |
| 100,000 | **19.5 GB**（超出本机总内存 15.3 GB） |
| 1,000,000 | **126 GB** |
| 1,000,000,000 | 约 7 万 GB |

**幂指数 0.81 < 1 说明它略低于线性，但曲线是发散的**——不存在「涨到头」的 `n`。
**故「几十亿量级」在内存上不可行，与耗时无关。**

### 12.4 结论与待办

**结论三条：**

1. **规则 1/4 的 N 上限：理由成立，缺口是没算上两个旋钮**（2026-09-29 订正；原文写
   「防错了对象」，其依据已在 §12.2① 被证伪）。规则按「父进程持有全部 `n` 份结果」定价，
   而实测父进程**确实随 `n` 近严格线性增长**（§12.1b：0.267 MB/模拟），**故原始理由是对的**。
   缺口在于：**同一份 `n`，CLI 攒而 GUI/WebUI 不攒**（后者走 `return_compact=False`），
   规则按「攒」定价，对 GUI/WebUI 过估约 3 倍、对 CLI 才恰好。
   **上限本身必须保留**——`n=20000` 按 CLI 姿势就是约 5.4 GB，外推到十万是 19.5 GB，一样会 OOM。
   **该改的是「把旋钮算进去」，不是「要不要设限」。**
2. **规则 5 的公式形状不对**：它写成 `max(2.0, workers × 0.75)`，**漏了 `n` 这个主项**
   （§12.1b：主进程那份才是大头，它是 `f(n)` 且与 `workers` 基本无关），而 `workers`
   那一项虽真实存在、**系数却远小于 0.75**（§12.1b 实测每 worker 仅 **0.053–0.070 GB**，
   且它自己也随 `n` 走）。**正确的形状应当同时含 `n` 与 `workers` 两个自变量**
   （再叠一个 base 项），而**三项都还没标定**。**在形状与系数定下来之前不改数值**——
   拿两三个点外推去改一个防 OOM 的阈值，正是本轮反复在防的事。
3. **「转硬盘」治不了这个问题**：数据量随 `n` 线性增长（百万次约 126 GB），落盘一样
   不现实、且 I/O 会变成新瓶颈。**根治方向是「缩减单次模拟的占用」**（用户判断，实测
   支持它）——目标是把增长从「随 n 发散」变成「常数」。

**待办（超出本轮，已登记）：**

- worker 内存随 `workers` 的轴：**已由 §12.2b 完成**（2026-09-28），结论为「总量 ≈ `f(n)`，与 `workers` 基本无关」（2026-10-01 订正，原文标「正在补测」）；
- 曲线在更大 `n` 上是否仍守幂律（**本机测不了**：`n=50000` 按拟合就要约 11.7 GB）；
- **缩减方向的线索（2026-09-29 订正主次。原列「两条」，主次判断反了）**：
  - **① 最大一块：CLI 主进程的 `results` 列表**（**0.267 MB/模拟**，§12.1b 实测）。
    CLI 的调用姿势落后于另两条入口：它攒 `n` 份完整结果，却只用其中 3 个标量
    （`cli.py:369-377`）。改法：走 `on_result` 流式，或改用 `extraction`
    （与 GUI/WebUI 同源）。
    **前置条件**：`return_compact=False` 与 `on_result` 的组合会让父进程把每次模拟都
    误判为失败（`compact is None` 被当作失败，`batch_simulator.py:824-830`），
    故须先把「真失败」的表示与「未回传结果」区分开，再动默认值。
  - **② 次一块：`merge_extraction_packets` 的三处 `n` 份 `append`**（**0.088 MB/模拟**）：
    `merged_agg` / `merged_transitions` / `merged_cum`（`core/streaming.py:430-478`）。
    **同一个函数里的热力图已经是真累加**（`merged_hach[i][b] += 1`），即
    **「可结合归约」在本项目已有现成写法**，只是没铺开到这三处。
  - **③ 原列的「9 个等长于抽数的数组」不作数**：经查证它们是 `process()` 的局部变量、
    函数返回即释放，规模是抽数（约 393）而非 `n`（详见 §12.2b 的订正）。
  - **P12 记的「精简传回 15KB→1KB 砍 93%」砍的是回传体积、不是驻留内存**——
    这两件事要分开量（§12.2① 的订正里给了实测对照：273 KB/模拟 vs 1996 KB/模拟）。
