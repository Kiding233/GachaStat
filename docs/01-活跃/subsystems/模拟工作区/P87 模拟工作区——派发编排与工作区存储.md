# P87 模拟工作区——派发编排与工作区存储

> 日期：2026-09-30 | 状态：设计中，实施未启动
> 触发：用户质疑「统计方法不就应该是一个输入指定的数据集 id 和相关参数、按约定格式输出结果的函数吗」，由此追出三层问题：派发与编排未分离、数据集组装分散、core 反向依赖 service
> 关系：**本计划吸收 P85 的 17 处（见 §3.9），P86 消费本计划产出**（见 §3.1）

## 一、问题

### 1.1 调用点已统一，但「跑一次模拟」的语义没有抽象

全仓 `run_batch_parallel` 有 5 个调用点（CLI 主模拟 + 基线、GUI 主模拟 + 基线、WebUI 主模拟 + 基线、`core/retreat_search.py:207`、`core/worst_impact.py:140`）。函数签名是统一的，实参表也几乎一致（唯一常规差异是 CLI 多传 `collect_perf`）。

但「跑一次模拟」作为一件完整的事有六步，**只有第三步是共享的**：

| 步 | 内容 | 现状 |
|---|---|---|
| 1 | 构造环境（`SimulationEnvBuilder`） | 每处各写 |
| 2 | 设置调用态字段（`return_compact`、`n_heatmap_bins`、`profile_*`） | 每处各写，且已漂移 |
| 3 | 调 `run_batch_parallel` | **共享** |
| 4 | 跑不抽卡基线 | 三条 UI 各写一遍（deepcopy + 置空停止条件 + n=1 + w=1），**异常处理还不同** |
| 5 | 消费返回值（提取结果 or 完整明细） | 每处各写，已分叉 |
| 6 | 组装数据集存库 | 每处各写，**产出已不同** |

第 4 步最能说明问题：同一段逻辑在 `cli.py:371-391`、`gui/gacha_panel.py:106-124`、`webui/api.py:307-319` 各写一遍，而失败处理是「CLI 打印告警」对「另外两条 `except Exception: pass` 静默吞掉」（P85 的 C2）。

### 1.2 数据集组装分散且已分叉

同一次模拟的产物要被组装成 `StoredDataset`，这个动作有两份实现：

- `webui/api.py:388-427` 的 `_dataset_from_bundle`
- `gui/main_window.py` 的 `_on_simulation_finished` 内联段（`:411-500`，`StoredDataset(...)` 在 `:478`）

**产出不同**，最硬的一处：WebUI 的 `pool_types` 是硬编码空字典（`api.py:427`），GUI 传的是从 `store.pools` 真实推导的值（`main_window.py:498`）。`gdr_context` 的序列化方式两边也不同（GUI 走 `to_dict()`，WebUI 放原值）。

后果：同一个数据集，从不同入口存下来内容不同，跨入口的分析结论无法直接对照。

### 1.3 core 反向依赖 service（两处）

- `core/retreat_search.py:203` 与 `:207`：搜索内循环里派发模拟
- `core/worst_impact.py:136` 与 `:140`：`analyze()` 内部派发模拟

两处都用函数内延迟导入（`from gacha_simulator.service.batch_simulator import run_batch_parallel`）绕开循环依赖的报错，但依赖方向是反的（core 是引擎，service 是编排）。

**worst_impact 的三个症状同源**：

1. core 内部派发（上述）
2. `webui/worst_impact_service.py:57-110` 的 `generate_worst_config()` 用 **7 个私有成员**重走 core 管线（`_prepare_pool_info` / `_apply_custom_pool_config` / `_build_success_checker` / `_main_ssr_ids` / `_resource_name` / `_compute_pity_coverage` / `_parsed_cost`）。它之所以重走，是因为 core 的 `analyze()` 把「纯计算」与「派发」焊在一起（`:102-160`），没有「不含派发」的公开入口
3. 无法接受外部数据集（因为它自己生成配置自己跑）

根因同一个：**`analyze()` 把三段焊住**。而它的零件其实已经是分开的：`prepare_simulation_config()`（`:165`，产出配置）与 `analyze_batch_results()`（`:278`，消费数据）都是独立方法。

### 1.4 存储模型两套并存

| | WebUI | GUI |
|---|---|---|
| 形态 | 目录 + 每数据集一文件（`api.py:446` 的 `get_user_data_dir('datasets')`，`:463` 的 `{name}.json`） | 内存 + 手动导出到单文件（`core/result_store.py:378-391` 的 `save_all`） |
| 删除 | `os.remove`（`:471-478`） | 内存删除 |
| 列表 | `os.listdir`（`:480-483`） | 内存字典 |
| 持久化 | 自动 | **不自动**（唯一调用方 `gui/data_manager_panel.py:507/521` 带 path，是用户手动的导出/导入） |

三处路径分散：数据集在 `get_user_data_dir('datasets')`、配置在 `get_config_dir()`、树在 `get_user_data_dir('workspace')/workspace.json`。

`RELEASED=False`，重组无兼容包袱。

### 1.5 基线：当前无随机源，但被当成数据管道

实测（固定配置，三个不同种子 1 / 999999 / 42）：

```
种子=1        final_resources: {'draw_resource': 66420.0, 'exchange_currency': 250.0}
种子=999999   final_resources: {'draw_resource': 66420.0, 'exchange_currency': 250.0}
种子=42       final_resources: {'draw_resource': 66420.0, 'exchange_currency': 250.0}
final_resources 相同 ? True        banner_end_resources 相同 ? True
```

原因在代码层也清楚：`NoDrawStrategy.select_action` 只返回 `WaitAction(duration=next_event_wait(ctx))`，无随机调用；不抽卡则 milestone 不触发，无 `random_cards` 类奖励；当前资源收入的唯一来源是按日程表的确定规则（`core/resource_gain.py`）。

**但这条结论的边界必须写清（2026-09-30 用户指出）**：上面三条只证明了「**当前实现下无随机源**」，不是「基线在结构上必然确定」。它默认了「随时间自然发生的事件不带随机性」这一条；该条现在成立（资源收入全为日程规则），**若将来引入随机送资源的活动、或资源的随机丢失，即告失效**，届时基线会带随机性，「跑 1 次即精确值」不再成立。

**所以设计上不把基线当确定量，而把它当一次普通派发**：它是策略维派生的一个 sub 配置，交给运行器跑，跑几次是运行参数（当前取 1，因为当前无随机源）。将来引入随机资源事件时，把它的次数从 1 改为 N 即可，架构不动。

**消费点共 6 处，全部是展示，无一处参与统计计算**（`_gdr_resource_remaining` 只读 compact 的 `final_resources`，从不读基线）：

| # | 消费点 | 位置 | 用途 |
|---|---|---|---|
| 1 | GDR 分布直方图参考线 | `gui/analysis_panel.py:311-320` / `webui/analysis_service.py:234` | vline |
| 2 | 条件分布图参考线 | `gui/analysis_panel.py:746-755` / `webui/analysis_service.py:600` | vline |
| 3 | 每 banner 分布参考线 | `gui/analysis_panel.py:1129-1142` / `webui/analysis_service.py:869-873` | 每池各自的 vline |
| 4 | 脆弱性山脊图参考线 | `core/vulnerability.py:948-956` / `webui/vuln_service.py:184` | 绿色点线 |
| 5 | 数据管理面板展示 | `gui/data_manager_panel.py:348, 426` | 只读显示 |
| 6 | CLI 打印与 JSON | `cli.py:453-459, 468-469` | 打印 + `no_draw_baseline` |

而它现在以 3 个字段贯穿 `AnalysisWorker.__init__` 与 `update_results()` 的 12 条管道，成本与用途（画线）严重不匹配。

## 二、目标

1. **「跑一次模拟」的完整语义归一处**：三条 UI 入口退化为「组参数、调用、渲染」；新增入口不复制任何胶水。
2. **产物唯一且一致**：所有模拟产物经本层落工作区，带统一元信息；同一配置从任何入口跑，产出逐字段相同。
3. **core 无副作用依赖**：core 不再 import service；两处算法模块的派发外置。
4. **产物是一等公民**：数据集与派生配置进工作区、有 id、可被任何分析消费，包括由任务生成的 sub 配置。
5. **可复现**：同一工作区可无损重开（配置与数据集俱在）；基线与主模拟同构（两者都是一次派发），其设计不依赖「基线必然确定」这一前提。

## 三、方案

### 3.1 分层与边界

```
用户界面（GUI / WebUI / CLI）
      │
      ▼
┌──────────────────────────────────────────┐
│ 模拟工作区（本层，新建 service/workspace/）│
│  编排：变换器（配置 → sub 配置）           │
│        任务（进度、取消）                  │
│        汇合器（产物 → 任务结论）           │
│  归宿：工作区 configs/ datasets/ index    │
└───────────────┬──────────────────────────┘
                │ 调用（单向）
                ▼
┌──────────────────────────────────────────┐
│ 模拟服务层（现有，不改定位）               │
│  SimulationEnvBuilder / run_batch_parallel / GachaService │
└───────────────┬──────────────────────────┘
                ▼
             core（引擎）
```

**三条边界**：

1. **依赖单向**：本层调模拟服务层；模拟服务层不知道本层存在
2. **关注点不同**：模拟服务层管「并行怎么跑、内存怎么省、worker 怎么注入」（`batch_simulator.py` 68KB 的复杂度一件都不上移）；本层管「跑哪些、存哪、怎么组织」
3. **产物形态不同**：模拟服务层返回内存结果包；本层返回工作区里的数据集 id

**与 P86 的关系**：P86（分析服务层）消费本层产物，本层不依赖 P86。P86 §六 的验收标准「同一数据集、同参数，WebUI 与 GUI 产出逐字段一致」以本计划的 §3.5（统一元信息）与 1.2 的组装统一为前提；本计划先行，该条验收可直接用最强的跨侧对照。

**概念层级（本次讨论确立）**：

```
配置参数 = 策略 + 目标卡 + 初始资源 + 池子 + 保底 + Banner + 资源生命周期 + 里程碑 + ...
运行参数 = 种子 + 模拟次数 + 进程数 + 进度回调 + 输出开关 + ...
模拟参数 = 配置参数 + 运行参数
```

**运行参数不进入配置身份**。依据：现状 `compare_fingerprints`（`core/result_store.py:344-373`）虽把 `seed_start`/`seed_end`/`num_simulations` 列入对比维度，但判定逻辑 `ComparabilityDiff.mode_label()`（`:178-196`）判断「是否配置差异」时只用 `['config_hash','target_cards','initial_resources','stop_condition','pool_ids']`，**已排除运行参数**。本计划把现状做干净：指纹拆为 `ConfigIdentity`（进配置身份）与 `RunRecord`（种子范围、次数、耗时，供可复现性与 P83 回归使用，不参与可比性判定）。

### 3.2 编排：变换器 + 运行器 + 汇合器

```
任务 = 变换器 + 运行器 + 汇合器

变换器：配置 → 一组 sub 配置（可以是预定列表、参数化展开、或迭代状态机）
运行器：sub 配置 + 运行参数 → 数据集          （即调用模拟服务层并落工作区）
汇合器：数据集集合 → 任务结果
```

三类任务由此统一：

| 任务 | 变换器 | 运行器调用 | 汇合器产出 |
|---|---|---|---|
| 主模拟（+ 基线） | 策略维变换：派生一个 sub 配置（策略取 `no_draw`） | 2 | 主数据集 + 基线产物（当前样本数为 1） |
| 参数扫描 / 敏感性分析 | 参数维变换：N 个 sub 配置 | N | N 个数据集的汇总 |
| 方案搜索 | **迭代变换**：每轮由前几轮结果决定下一个配置 | 数十次 | 搜索结论 |

**不引入递归的「任务套任务」**。理由：变换器可以是迭代的（依赖已产出数据），已能表达搜索这种看似需要嵌套的形态；递归嵌套会把进度上报、取消、失败传播全部变成递归问题，而实际形态只有「预定列表」与「迭代状态机」两类。出现第三类再升级。

**接口上不区分单点与多点**：调用方说的永远是「跑这批规格，给我数据集」。单点任务退化为一次运行器调用（零额外开销）。

### 3.3 任务对象与注册表（方案 4b）

任务是一个对象，具备 `id` / 状态 / 进度 / `cancel()`，存于共享注册表，GUI 与 WebUI 共用。

现状是两套：WebUI 的 `api.py` 有 `_tasks` 字典（配 `_task_lock`、`_task_seq`）、GUI 有 Qt 线程加信号。将来敏感性分析还要写第三套。

**不做任务落盘**（方案 4c）。触发条件是出现「搜索跑到一半要关机、重开想接着看」的真实需求；当前无证据。

### 3.4 工作区存储

```
<workspace>/
├── configs/
│   ├── root.toml              配置内容 + 系统注释行（可手工编辑；系统只在派生时写注释行）
│   └── root-v1.toml
├── datasets/
│   ├── <name>.json            数据集内容 + 元信息（`StoredDataset` 自带）
│   └── ...
├── index.json                 纯缓存：节点、父子指针、标签、派生方式（可从注释行重扫重建，§3.11 A）
├── lock                       工作区锁（pid + 启动时间，§3.11 G）
└── workspace.json             format_version 与工作区级设置（§3.11 H）
```

**内容文件化，关系索引化**。理由：内容用文件是虚拟容器给不了的能力（可编辑、可寻址、可 diff、CLI 直用），关系用索引是纯文件方式给不了的（构树 O(1) 读一个文件，不必遍历全部数据集，孤儿检测也在此做）。

**多工作区**，机制上换根目录即可。**GUI 本期不暴露工作区选择**，固定指向默认工作区；WebUI 加「打开哪个」的操作。**GUI 与 WebUI 共用同一个默认工作区**（无缝：同一数据集两边可见），跨进程并发一致性押后（默认用户不会同时开两个）。

**迁移**：三处路径收进工作区目录（数据集 `get_user_data_dir('datasets')`、配置 `get_config_dir()`、树 `get_user_data_dir('workspace')/workspace.json`）。`RELEASED=False`，一次性搬运。

**删除 `ResultStore.save_all` / `load_all`**（与 webui 的文件式存储是同一件事的两个实现，保留会在工作区模型之外留下第三个存储实现）。**删除的同时必须补两条路径**，否则 GUI 数据真的不落盘：

- 启动时从默认工作区加载数据集列表
- 模拟完成后写入工作区（不再只进内存）

**不做「部分导出」**。整体打包工作区用操作系统压缩即可，不需要程序功能。若将来出现「只给别人一棵子树」的需求，再按闭包导出设计（需连带索引片段，导入时处理合并与冲突），且必须处理引用完整性。

### 3.5 统一元信息（方案 5a）

派发层为每个数据集**统一写一组固定的小字段**：策略标识、策略参数、目标卡规格、初始资源、种子范围、模拟次数、配置哈希（配置身份）、产生它的配置 id。

依据：现状 `ComparabilityFingerprint`（`core/result_store.py:28-71`）已有 `strategy_key` / `target_cards` / `initial_resources` / `seed_start` / `seed_end` / `num_simulations` / `pool_ids`，**扩展它比另起机制便宜**。

**为什么需要**：最差影响这类分析要判断「这份数据是不是用 `draw_target` 策略按某类配置跑的」，而 `config_hash` 是哈希，只能判等不能反查，所以现在它无法接受外部数据集（见 §1.3 症状三）。有了可读元信息，分析项可以用 `requires_meta` 声明自己要看哪几项（方案 5b，作为本方案的校验层，可后续加）。

**不做完整配置快照**（方案 5c）：该能力已由 §3.10 的配置写时复制以更低代价覆盖。

### 3.6 树作为视图

树**不是状态**，是**由指针解析出的视图**：

| 谁 | 写什么指针 |
|---|---|
| 变换器 | 配置 → 父配置（我由谁派生、怎么派生） |
| 运行器 | 产物 → 配置（我是哪个配置跑出来的） |
| 解析器 | 读两组指针，重建树 |

**顺带收益**：数据集已经有 `fingerprint.config_hash`，它标识了产生它的配置内容，所以「产物 → 配置」这条指针**已经存在**（形式是内容标识，下文把它换成配置 id），只是没被当指针用。需要新增的只有「配置 → 父配置」。

**配置身份 = 工作区内的相对路径**（**修正**：原写「复用 `config_hash`」，经 §3.11 B 的推演否掉——哈希算法演进会让历史身份失效，而 P85 侧即将改动 `compute_config_hash` 的覆盖面）。内容哈希降级为判等用的元信息字段。系统元信息以**注释行**写在配置文件里（见 §3.11 A）。

**三个必须定义的点**：

1. **孤儿处置**：父配置记录被删或改名，子节点指针悬空 → 解析时挂到根并标注「来源缺失」，不丢弃
2. **派生方式要记**：光有「父是谁」不够，还要记「怎么变的」（策略维变换 / 参数维变换 / 迭代生成），否则树只是一堆连线。边上的标签就是变换器的种类
3. **`workspace.json` 的树要删**：它（`webui/api.py:765-782` 的 `save_workspace`/`load_workspace`）是第二份真相。转过去后只保留界面状态（展开的节点、面板布局），树本身不再落盘

**GUI 不改**：GUI 继续读平铺的数据集列表，行为与现在一致。构树只发生在需要树的地方（WebUI 前端）。

### 3.7 基线的定位

**基线是「主配置 + 策略维取 no_draw」的一个派生配置**，不是主流程的附加步骤。它挂在树上自己的节点下：

```
config（主配置，策略=smart）
├── dataset（主模拟产出，N 个样本）
└── 基线（派生配置，策略=no_draw）    ← 派生自上一节点，系统生成，默认折叠
    └── （单值产物）
```

与 WebUI 现有派生机制一致：`onCreateDerived`（`tools/poc_webview/ui_compare/src/App.vue:598-610`）产出的子节点就是 `id: ${cfg.id}-v${seq}`、`parent: cfg.id`、label「变体 N」，带自己的 `configText`。基线正好是一个系统生成的派生变体，不需新机制。

**收益**：用户可以点开基线节点看到它的配置、改它（比如换另一个对照策略）再跑，这是「内联进主数据集」给不了的能力。

**节点的产出类型**：当前基线的样本数为 1，产出是 `final_resources` 加一组 banner 末值，用「**单值产物**」独立类型，不叫数据集，避免分析层把 1 个样本当分布。

**此类型的依据是「样本数为 1」，不是「它是基线」**：若将来引入随机资源事件（见 §1.5），基线样本数改为 N，它的产出即为普通数据集，节点类型随之改变。类型由产出决定，与节点身份无关。

**待落地的连带改动**：`no_draw_resources` 等 3 个字段不再作为数据管道贯穿（现在占 `AnalysisWorker.__init__` 与 `update_results()` 的 12 条管道中的 3 条），改为从工作区元信息读取（P86 §3.4 的 `AnalysisContext` 中间量模型）。

### 3.8 core 两处剥离（**性质已随架构改变，见下**）

> **2026-10-01 澄清（用户提出）**：新架构下，core 里本就没有派发的位置（派发是编排层运行器的职责），所以这**不再是一个「依赖方向错」的架构问题**。但**工作量不消失**：那两个方法不会自己改，仍要有人把它们改成不含派发的形态，且必须在编排层可用之后才能做。
>
> 因此本节的实质是「**把两类既有算法改造成编排系统里的任务类型**」，而不是「剥离依赖」。「剥离」是旧架构（core 自己派发）下的说法；新架构下它属于 §3.3 任务编排的一部分：最差影响是「变换器 + 汇合器」型任务，方案搜索是「迭代变换器」型任务。
>
> 连带影响：这两项同时也是 **P86 的收编前提**（最差影响要能分析外部数据集、要能被 P86 的骨架接入），故本节完成前 P86 的批 4 不含它们（P86 §7 待决项 2 已记）。

**worst_impact：直接拆，不用注入。**

`analyze()`（`core/worst_impact.py:102-160`）拆为三段，零件已是现成的：

```
变换器：现有数据集 → 一张 sub 配置（最差情况配置）    ← core 纯计算
        （复用 prepare_simulation_config，:165）
运行器：（sub 配置 + 运行参数）→ 数据集                ← 本层，即普通派发
汇合器：（数据集 + 阈值）→ 最差影响结果                ← core 纯计算
        （复用 analyze_batch_results，:278）
```

拆开后 §1.3 的三个症状同时消失：core 无派发；WebUI 有了不含派发的公开入口，不必再用 7 个私有成员重走管线；最差影响可分析外部数据集（含用户手工跑或改过的配置）。

**retreat_search：改为状态机 + 外层驱动。**

它与最差影响不同，是**迭代式派发**（每轮依赖上轮结果）。三个部分：

```
变换器（core，迭代）：历史 → 下一个探测点（资源值）
运行器（本层）：（配置 + 资源值）→ 数据集
判定器（core）：数据集 → 成功率        ← 现埋在 _simulate_with_resource（:193-222）后半段
```

变换器在 core 是个状态机，循环驱动在本层。core 里既无派发，二分与 Pareto 的算法逻辑也完整留在 core（不散到本层）。

**迁移注意**：`analyze()` 是现有调用方（WebUI 与 GUI 的最差影响面板）的入口。**先保留 `analyze()` 作为编排外壳**（内部改为依次调用三段，其中派发走本层），等两个前端都切到三段式后再删。否则中途会出现断点。

### 3.10 配置的写时复制（P85 会话移交，用户裁定）

**问题**：数据集要指向产生它的配置（§3.5），而配置身份现在有两个缺口。

**缺口一：配置就地覆盖。** `config_panel.apply_to_store()` 直接写 `self._store`，`get_store()` 返回同一对象；500ms 去抖预览经 `get_config()` 也会调它。`gui/gacha_panel.py` 的 `start_simulation` 只禁用自己那颗按钮，全仓无「运行中」标志。后果：模拟运行期间改配置，落库指纹会指向一份**没有用来跑这次模拟**的配置（P85 实测）。

> 分工：「完成回调读活对象」那 10 个读点由 P85 侧独立修（改为读派出时定格的快照）。本节解决的是**另一件事**：数据集指向的配置稳不稳定。两者都要做，只做一侧问题照旧。

**缺口二：配置身份本身就残缺（P85 已于 2026-10-01 修复，此处记为已解决的历史）。** 移交时 `compute_config_hash` 的覆盖面为 banner/pools、pity、milestone、stop_condition，**未覆盖 `gain_rules` 与 `sim_start_date`**（实测：把 `every_n_days` 的 60 改成 600、删光全部 `gain_rules`、改 `sim_start_date`，hash 均不变）；另有一个恒空的 `schedules_config` 形参（被函数体使用，但生产调用都传 `getattr(store, 'schedules', [])`，而 `ConfigStore` 无该属性）。

**P85 侧的修复（2026-10-01）**：`ff83266` 补入七项遗漏字段并删掉恒空的 `schedules` 形参；`64c4a32` 把策略三个字段合成单一可比性维度（参数改动不再被判「完全相同」）；`74cd41c` 让 `sim_start_date` 落盘；并新增 **`compute_config_hash_for_store(store, ...)`（`core/result_store.py:606`）作为生产代码的唯一入口**，调用点由 2 处收敛为 1 处。

**方案（写时复制）**：**配置一旦用于跑过模拟任务，就不再原地覆盖**；此后编辑一律派生出新配置。

用户表述（2026-09-30 初版）：「保存写更改改为一个用户可感知的状态，UI 状态和文件状态分离；如果被修改的文件有挂着数据集或子配置，就新建配置。」

用户表述（**2026-10-01 修正**）：「不仅是配置文件一旦被数据集引用就不再就地覆盖，**配置一旦开始跑一个模拟任务就不应再原地覆盖，因为未来会有数据集指向它**。」

**这次修正放宽了触发条件，同时简化了判定**：不必反查「是否已被引用」，只需「是否被使用过」一个标记。它在竞态上也更严：模拟跑到一半、结果尚未落库时配置就已冻结，不存在「结果还没落库所以还能改」的窗口。

**它替换掉了 §3.5 的方案 5c**（完整配置快照）。5c 被否的理由是「代价高、出现需要时再加」；写时复制用更低的代价拿到同一个能力（任何时刻都能恢复出当时那份配置），该否决理由不再成立。

**顺带收益**：工作区可整体打包移交。若配置就地覆盖，打包出去的引用可能已失效。

**四个已定问题**：

**① 判定依据 = 「是否被使用过」这一个标记**（2026-10-01 按用户修正调整）。原写的「是否被数据集引用」需要反查引用关系；修正后的条件只需在派发时给配置打一个标记（记进其系统元信息），更简单也更严。仍保留一条：工作区外的文件（程序自带的 `gacha_simulator/config/config.toml` 模板）编辑时复制进工作区，不做就地覆盖。

**② 未保存的 UI 状态不能直接开跑。** 数据集要指向配置，指向需要文件身份；未保存的 UI 状态没有身份。故流程为「改 → 存（新建或被拒）→ 跑」。这正是「保存成为用户可感知动作」的自然结果，代价是多一步。

**③ 数量增长受控。** 条件性派生（只在**被引用**时新建）使增长与「跑过的配置数」成正比，而非「改的次数」；改了但没跑的迭代不产生新文件。界面支持由 §3.6 的树承载（派生关系是树上的边），但需补一项能力：树要能**反向**回答「这份配置被哪些数据集用着」。

**④ 删除语义：允许删 + 警告 + 标记失效。** 删除被引用的配置时给出明确警告（「这份配置被 N 个数据集引用」）；删除后那些数据集的配置引用标为失效并在树上可见（沿用 §3.6 的「来源缺失」标记）。**不级联删除数据集**（数据本身仍在）。

### 3.11 端到端推演与补充设计

以一条完整用户旅程为线索逐段推演，每段问「本架构落地后这里会出什么问题」。另加长任务与并发两条支线，末尾是优雅性审查。

#### A. 启动：索引是真相还是缓存

**推演**：程序打开工作区读索引。用户手工删掉一个数据集文件，或从别处拷进来一个数据集，索引与实际文件即不一致。

**问题**：不一致时谁说了算。索引若是真相，手工操作留下幽灵条目；索引若是缓存，父指针必须能从文件侧重建。

**补充设计（2026-10-01 按用户方案调整）：系统元信息写进配置文件的一段注释，索引降级为纯缓存。**

```toml
# @gachastat: {"label": "崩坏3 主线", "parent": "root.toml", "derivation": "strategy:no_draw"}
# ↑ 系统维护行。不参与 compute_config_hash（hash 算的是解析后的结构，注释天然不在其中）

[resources]
...
```

```
configs/
├── root.toml            配置内容 + 系统注释行
└── root-v1.toml
datasets/
└── smart_01.json        数据 + 元信息（`StoredDataset` 自带：配置 id、指纹、运行记录）
index.json               纯缓存，可完全重建
```

**为什么这比集中式好**：元信息随配置文件走。把一份配置拷给别人、或整体打包工作区，派生关系跟着文件一起走，不会因为漏带索引而丢失。索引由此从「半真相」降为**纯缓存**，删掉可完全重扫恢复。

**要处理的一个张力**：§3.10 说「配置一经跑过即冻结」，那么「已被使用过」这个**会变**的状态放哪？若也写进注释，等于系统在改写用户的文件，与「配置不可变」冲突。

**解法：把这个状态从配置文件里拿出去。** 「配置是否已被使用」可由两件事推出：一是**数据集指向它**（扫数据集或索引），二是**有活动任务正在用它**（查运行中的任务）。两者都不需要改写配置文件。于是注释里只放**不变的部分**（标签、父配置、派生方式），只在派生创建新文件时写一次。

**两个已知的降级场景**（可接受，如实登记）：
- 用户手工删掉注释行 → 该配置在重扫时成为孤儿（内容与数据集俱在，只丢派生关系）
- 用户手工把 `root-v1.toml` 复制为 `root-v2.toml` → v2 带着 v1 的注释，父指针指向 root 而非 v1（有来源线索，但不精确）

**技术前提**：`save_toml`（`core/config_toml.py:116`）现在用 `tomli_w` 序列化，**不写注释**（所以现有 `config.toml` 头部那 32 行注释是手工维护的模板，程序保存后即丢）。承载系统注释需要把它改为「先拼注释行，再接 `tomli_w` 的输出」。

#### B. 配置身份：不能用内容哈希

**推演（2026-10-01 更新：已发生，不再是假设）**：P85 侧已于当日改动 `compute_config_hash`（`ff83266` 补入七项遗漏字段、删掉恒空的 `schedules` 形参；`64c4a32` 策略三字段合成单一维度；`74cd41c` `sim_start_date` 落盘；并新增 `compute_config_hash_for_store` 作为唯一入口）。算法一变，已存数据集里记的 hash 与新算的对不上，且扰动面比原估计更大。

**问题**：**内容哈希作为身份，身份就随算法漂移。** 届时同一份配置重跑被判为「不可比」，历史数据集的配置身份全部失效，且是静默的。

**补充设计（修正 §3.6）**：**身份 = 工作区内的相对路径**（如 `configs/root-v1.toml`），**内容哈希降级为「判等用」的元信息字段**。

- 身份稳定：文件不改名就不变
- 判等仍用哈希：两份不同身份的配置内容是否相同，看哈希
- 哈希算法演进只影响判等精度，不动摇历史身份
- 与写时复制天然契合：派生即新文件，即新身份

#### C. 改配置：三个概念要拆开

**推演**：用户改了几个字段，没保存就点「开始模拟」。

**问题**：§3.10 ② 已定「未保存不能跑」，但没说清内存态怎么管。`ConfigStore` 现在身兼二职：既是运行时用的配置对象（`config_panel.apply_to_store()` 直接写它），又是 UI 编辑的目标。写时复制要求它是「编辑缓冲」，派发要求它是「不可变快照」，两个定位冲突。P85 修的「完成回调读活对象」只是这个冲突的一个症状。

**补充设计**：只需**两个**概念（**2026-10-01 修正**：原写三个，其中的 Snapshot 冗余。用户指出「模拟永远只读本地保存下来的配置文本」即可）。

| 概念 | 职责 | 生命周期 | 落盘 |
|---|---|---|---|
| 编辑缓冲 Draft | 承接 UI 改动 | 面板打开期间（未保存即丢弃） | 否 |
| 配置文件 File | 工作区里的配置文件，**模拟只读它** | 冻结后永久不可变 | 是 |

`ConfigStore` 从「当前工作配置」降级为「编辑缓冲 + 当前配置身份」。

**为什么不需要 Snapshot**：写时复制保证「跑过的配置不再变」，派发直接读文件即可，不必另做内存快照。读文件的时机是任务启动时（随后 pickle 给 worker），「定格」由不可变文件天然提供。

#### D. 派发：原语收快照，不收 ConfigStore

**推演**：模拟运行期间用户改配置。

**问题**：根因是「运行与 UI 共用同一个配置对象」。P85 从完成回调一侧修（改读快照），那是治症状。

**补充设计**：**派发原语签名为 `run(config_id, run_params) -> dataset_id`**（**2026-10-01 修正**：原写 `config_snapshot`，随 §3.11 C 的简化改为配置文件身份）。配置以不可变文件为载体，任务启动时读入并 pickle 给 worker，「定格」由写时复制保证。运行期间 UI 改的是编辑缓冲，与正在跑的配置无交集。P85 修的症状在本层被结构性消除，两侧互为保障。

#### E. 落盘：事务与失败

**推演**：跑了十分钟的模拟，写盘时磁盘满或权限不足。

**补充设计**：

- 单节点写入用「临时文件 + `os.replace`」（原子）
- 一次派发的产物（数据集 + 元信息 + 索引更新）视为**一个事务**：先写全部临时文件，全部成功后统一 replace，最后更新索引
- 数据集命名统一规则落本层（现在 GUI 是 `main_window.py` 里的 `smart_01` 自增命名，WebUI 另有一套），避免同名冲突

#### F. 长任务：产物量与组织（**已定 F2**，2026-10-01）

**推演**：方案搜索跑 50 轮，每轮一个派生配置加一个数据集。

**先纠正一处判断**：50 份配置加 50 个数据集**是正常产物，不是污染**（用户指出）。搜索的本质就是探索配置空间，产物多是其固有形态。真正的问题只有一个：**这批产物在结构上如何被识别为「同一次搜索的产物」**。

**已定方案 F2：派生批次标记。**

- 派生元信息带一个**批次标识**（如 `batch: search-A`），由变换器在派生时写入（与 J1 一致：派生关系是变换器的输出）
- **树的结构不变**：子配置仍挂在它的父配置之下（搜索每轮的配置都派生自同一主配置，故它们是主配置的子节点）
- **「组」是查询而非实体**：同批次即一组，视图按需折叠成组
- 即使不做折叠，「同批次」这个查询本身就有用（把这次搜索的全部产物一起做分析，或一起打包）
- **批次标识同样服务于敏感性分析**：一次敏感性扫描的 N 个配置也是一个批次

**已评估并否决的两个候选**（记录以免后人重走）：

| 候选 | 否决理由 |
|---|---|
| F1 任务节点（子配置挂其下） | 让「产物挂在产生它的配置之下」这条既有规则出现例外；且把「组」实体化，与「树是视图」（§3.6）相悖 |
| F3 配置分类（普通 / 搜索） | 50 个搜索配置仍平铺，只贴了标签；分类维度与派生关系正交，等于多维护一个维度 |

**任务记录**：搜索的结论、进度、产物清单落 `tasks/<task-id>.json`，与配置、数据集并列存放。它是独立实体，**不作为子配置的父**（子配置的归属仍由派生关系决定）；树上如何呈现留给前端设计（见下）。

**产物处置策略**：默认全留（「sub 配置也可以选中做其他分析」是明确要的能力），可配为「只留汇合结果」或「只留最终配置」。

**F2 的连带改动（用户 2026-10-01 补充）**：

- **WebUI 的树显示要改**：支持按批次折叠与展开，否则 50 个子配置平铺在主配置之下
- **任务创建的 UI 要重新设计**：发起搜索的入口、参数、以及任务在树上的呈现位置

这两项落在前端（P74 侧），本计划只负责提供「批次标识」这一数据基础。

**前瞻：敏感性分析**（用户指出，属之后的事，但架构要留口子）。它的需求是「分析任意给定维度」，因而需要**指定遍历范围，甚至直接指定配置生成规则**。这意味着变换器不能是硬编码的几种，要能被调用方指定。留口子的方式是 J1：`derivation` 用开放结构而非枚举，届时加自定义变换器不必改 schema。

#### G. 并发：工作区锁

**推演**：GUI 与 WebUI 共用默认工作区，用户同时开了两个。

**问题**：§8 把并发一致性押后，但两个进程同时写索引会损坏它。

**补充设计（最小锁）**：工作区根放锁文件（含 pid 与启动时间）。打开时若锁存在且进程存活，则以只读方式打开并提示；锁过期（进程已死）则接管。

#### H. 可搬移：版本与相对路径

**推演**：用户把工作区目录压缩发给同事。

**补充设计**：

- 工作区内所有引用一律**相对路径**（绝对路径搬移后失效）
- 工作区根记 `format_version`
- 打开时版本不匹配给明确提示，而非静默错乱

#### I. 迁移

**推演**：现有数据在三个位置（`get_user_data_dir('datasets')`、`get_config_dir()`、`get_user_data_dir('workspace')/workspace.json`），升级后第一次打开。

**补充设计**：阶段 1 附一次性迁移，把三处收进默认工作区。按项目既有纪律「基线固化 + 等价对照」：迁移前固化现有数据的对照快照，迁移后逐字段比对。

#### J. 优雅性审查

以下不改架构，只让形态更一致。

**J1 派生关系是变换器的输出，不是另处维护的元信息。** 变换器返回 `(sub_config, derivation)`，`derivation` 直接进元信息。树上边的标签由此而来，不存在「两处维护」。

`derivation` 用**开放结构**（变换器标识 + 参数摘要），不是「策略维 / 参数维 / 迭代」的枚举。这是为敏感性分析留的口子：它要求「分析任意给定维度，甚至直接指定配置生成规则」（用户 2026-10-01 指出），届时加自定义变换器不需改 schema。

**J2 派生配置由 `(父 id, 变换描述)` 唯一确定，落不落文件可选。** 基线属于「不落文件」那一类（身份可复算、不占工作区）；用户可见的派生（如最差影响生成的配置）落文件。一条规则覆盖两种，不需要为基线开特例。

**J3 工作区是 append-only（除删除）。** 数据集不可变、配置经写时复制后不可变、「改配置」即「派生新配置」。这个不变量带来可审计与可回滚，值得写进设计约束。

**J4「运行」统一为「提交任务」，连单点也不例外。** §3.2 已说「接口上不区分」；实现上也统一后，进度、取消、失败传播、产物归属只有一条路径。

**J5 配置身份用类型而非裸字符串。** `ConfigId` 而非 `str`，避免上层把路径当普通字符串拼接。

## 七、验收标准

- [ ] `core/` 全目录无 `import ...service...`（含函数体内延迟导入），grep 可验
- [ ] 三条入口跑同一配置、同一次数、同一种子，产出的 `StoredDataset` 逐字段相同（含 `pool_types`），固化为自动化测试
- [ ] 工作区可整体重开：配置、数据集、树关系无损继承
- [ ] GUI 启动自动加载默认工作区；模拟完成自动写入（不依赖用户手动导出）
- [ ] `ResultStore.save_all` / `load_all` 已删，仓库中无第三个数据集存储实现
- [ ] 最差影响可分析**非本流程生成**的数据集（含外部改过的配置跑出的）
- [ ] 基线不再作为数据管道字段贯穿；6 个消费点全部改读工作区元信息
- [ ] 任务可报进度、可取消；GUI 与 WebUI 共用同一套任务对象
- [ ] 树由 `index.json` 解析得出；`workspace.json` 不再存树
- [ ] 基线的产出为「单值产物」类型，不被分析层当作样本分布；类型依据为样本数（当前为 1），非节点身份
- [ ] 配置写时复制生效：修改一份被数据集引用的配置会派生新文件，原文件及其数据集引用不受影响
- [ ] 未保存的配置修改无法开跑（流程为「改 → 存 → 跑」，§3.10 ②）

- [ ] 配置身份为工作区内相对路径；工作区整体搬移后所有引用不失效
- [ ] 工作区被另一进程占用时以只读方式打开并给出提示
- [ ] 配置身份不随 `compute_config_hash` 的算法演进失效（历史数据集的配置指向仍成立）
- [ ] 工作区在无删除操作时保持 append-only：既有配置与数据集文件不被改写（§3.11 J3）
- [ ] 配置一经跑过任务即冻结：再编辑必派生新文件（§3.10，修正后的触发条件）
- [ ] 同一次搜索（或敏感性扫描）的全部产物可按批次标识一次取出（§3.11 F）
- [ ] P85 的 17 处各有测试固化（E1、G2 已完成，划出）
- [ ] 「基线当前无随机源」固化为**可失效断言**（同配置不同种子产出相同）。该测试在引入随机资源事件时**应预期失败**，作为前提失效的哨兵；届时基线的运行参数需由 1 改为 N（见 §1.5）
