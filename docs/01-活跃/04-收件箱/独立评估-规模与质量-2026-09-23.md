# 独立评估：项目规模与质量

> 评估日期：2026-09-23 | 代码版本：`2.4.0` | 基线 HEAD：`852d703`
> 触发：用户提问「本项目的规模属于什么水平，项目质量属于什么水平」
> 方法：主 agent 亲自实测 + 三个独立子 agent 分离审查（代码质量 / 测试质量 / 架构一致性）
> 结论：规模属个人项目中的大型；质量分层差异极大，引擎层专业级，外围层未收口

## 〇、方法与局限

**方法声明。** 本评估不采用项目文档（CLAUDE.md、手册、计划文件）的自述作为论据。文档中的机制声明一律视为待验证的假设，实际状态以代码与运行结果为准。凡文档与实际不符处，在第五节单列。

**独立性。** 三个维度由三个不携带本会话上下文的子 agent 独立审查，主 agent 只提供审查范围与检查清单，不引导结论。子 agent 的关键发现在采纳前由主 agent 逐条复核（`test_plan_execute_workflow.py`、`api.py:602`、`worst_impact_service.py` 三项已复核）。

**局限。**

- 未做逐行代码审计，复杂度与重复度基于 AST/token 自动度量
- 覆盖率数据为本次实测，但测量时激活了 GUI 模块导入，语句基数（22,683）高于历史快照（16,934）
- 未评估算法正确性（即统计方法的数学实现是否无误），本评估只覆盖工程维度
- 性能只引用 `benchmarks/runs/1j/` 已有记录，未独立复测

**口径说明（2026-09-23 核对后修订）。** 初稿完成后，由独立子 agent 逐条核对，发现并修正了 10 处数字错误（含一处主 agent 自身的算术错误：webui 覆盖率 0.6% 应为 3.2%）。修正项已在正文更新，此处记录**口径敏感项**，供后续复现时对齐：

**功能性风险实例**（已复核）：

```python
# gui/analysis_panel.py:283-289
try:
    checker = make_gdr_calculator(self._store, target_specs, gdr_key, ssr_ids=ssr_ids)
    values = [checker.compute_gdr(agg) for agg in aggregate_data]
    gdr_dists[gdr_key] = EmpiricalDistribution(values)
except Exception:
    pass
step_done('GDR分布计算完成')
```

该处形式上遵守了「必须用 `make_gdr_calculator`」的规范，但整个调用被 `except Exception: pass` 包住。任何失败都会让该 GDR 项从结果中静默消失，下一行仍报「计算完成」。规范本意是防「权重漏传导致静默退化 1.0」，这里把静默退化换成了静默缺失。

### 3.5 重复代码

## 七、贯穿性观察

四件彼此独立的事实际是同一模式：

1. 代码层：`gui/analysis_panel.py:287` 的 `except Exception: pass` 让 GDR 项静默消失
2. 工具层：`refcheck check` 报「无问题」，实为标记 0 个、无可比对
3. 运维层：7 个 cron agent 停摆 7 周，而 C6 的职责恰是警报静默失败
4. 机制层：`RELEASED` 保险标志零引用，全靠会话内自觉检查

**系统的共同倾向是把「没检查」呈现为「没问题」。** 这不是能力问题，而是一致的实现习惯：防御逻辑写成 `pass`，失败路径不产生可观测信号。

该模式在 core 层不存在（0 处裸 except，覆盖率 80%），集中于 UI 层、工具层与运维层，即「没有被反复检查」的地方。这同时解释了覆盖率的分层：`core/` 80% 与 `webui/` 3.2% 的差距不是技术难度差距，而是是否被反复要求的差距。

## 八、质量定位结论

| 口径 | 判断 |
|---|---|
| 作为抽卡机制建模与统计分析工具 | **优秀**。缺口登记 35 处 + 15 个不确定项，含对自身假设偏差的量化（如 U13 记「官方综合概率 1.9% vs 均匀计算 2.021% 有偏差，可能偏 100」），此类严谨度在这类项目中罕见 |
| 作为可交付产品 | **尚未达标**。无 CI、无发布产物、`RELEASED = False`、第十个 Tab 为空壳 |
| 作为长期可维护工程 | **中上，有明确风险**。`config_panel.py` 7,705 行与 M-1 的假测试是两笔真实负债，且均在增长 |

**分层结论：**

| 层 | 判定 |
|---|---|
| `core/` + `service/` + `strategies/` | 专业级 |
| `gui/` | 有债务但可接受（50% 覆盖率对 Qt 层不算低） |
| `webui/` | P74 在建中间态，不计入当前质量评估 |
| 工具与运维 | 未达标 |

**用于改进的最大杠杆：建立 CI。** 1,919 个测试的运行范围当前等于 AI 会话的活跃时长，没有 CI 意味着这些测试资产在会话之外不产生保护。这正是 cron 停摆 7 周无人察觉的机制性原因。

## 九、webui 的豁免说明

`webui/`（2,970 行，覆盖率 3.2%）是 **P74 UI 换头计划的阶段 1b/2 产物**（`gui/main_webview.py` docstring 自述），计划登记于 `docs/02-待办/P74 UI换头计划——pywebview+Vue3+ElementPlus+ECharts.md`，状态「📋 设计」。其定位是与 PyQt6 旧 UI 平行的在建层，非最终形态。

因此：

- **豁免**：webui 低覆盖率不计入质量评估。整层将被替换，在其上补测试收益有限
- **豁免**：`webui/vuln_service.py` 重写绘图、`webui/process_service.py` 重写格式化文本，属换图表库与换前端的必然工作，代码内有「对齐旧 plot_vulnerability resource_name」这类逐条对齐注释
- **不豁免**：H-1 与 H-2 两条。理由与迁移阶段无关，见第六节各自说明

**P74 计划本身质量良好**：阶段划分（0 已完成的 POC / 1a / 1b / 2 / 3）、影响面表（含 `core/vulnerability.py` 2 处 plotly 这类跨层缺口）、风险表、待决策项、验收标准齐全，且阶段 0 有实证产物（`tools/poc_webview/`）。
