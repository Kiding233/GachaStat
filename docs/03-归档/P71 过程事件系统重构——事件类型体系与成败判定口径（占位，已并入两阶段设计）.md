# P71 过程事件系统重构——事件类型体系与成败判定口径

> 日期：2026-08-05 | 更新：2026-08-05 | 状态：占位（设计待启动）| 优先级：中
> 来源：P58 第 3 轮核查暴露——事件系统只有「抽出来的」三种获得路径，无「累抽得」路径；触发主题是事件系统**整体重构**（类型体系 + 判定条件 + 成败口径），累抽得事件只是新获得路径引入后的一个具体触发点
> 背景：P58 已实施（964 passed），事件分类 draw-only 口径与累抽保底语义矛盾（历史遗留）

## 1. 占位说明

本计划为**占位计划**——登记编号、梳理问题面。主题是**过程事件系统的整体重构**，不是单点补「累抽得事件」。累抽奖励（P58）引入第三种获得路径后，暴露了事件系统在**类型体系、判定条件、成败口径**三个层面的设计问题，需系统性重设计。

## 2. 问题面

### 2.1 现状：事件系统三事件模型（来源：`docs/03-归档/plans/2026-05-15-process-analysis-design.md`）

| 事件 | 语义 | 判定条件 |
|------|------|---------|
| `pity_hit` | 保底出 | 保底机制触发时抽到目标卡 |
| `early_hit` | 提前出 | 保底触发前抽到目标卡 |
| `miss` | 没出 | 抽了卡但没抽到目标卡 |

**现状局限（设计文档已承认 + P58 核查复证）：**
1. 事件分类只覆盖「抽卡获得的」路径——这是事件系统的先天简化
2. 判定条件是**硬编码**的（early = 保底前抽到，pity = 保底触发抽到）——无法表达「累抽得」这类非抽卡获得
3. 成败口径**单一**（目前 draw-only）——无法按用途切换

### 2.2 P58 暴露的矛盾（来源：P58 §3.6b，REVIEW-R1-FIX: ISSUE-007）

P58 里程碑奖励引入「累抽赠送」这一**第三种获得路径**后：

- **GDR / 成功率**：送卡算（里程碑是池子固有属性）——`compute_gdr_from_*` 含 milestone 产出
- **事件分类 / 池子成败**：送卡**不算**（draw-only）——`infer_events` 按 `bonus_events` 减赠卡

**后果：** 同一池可呈现「GDR 成功（含送卡）但事件 miss（不算送卡）」矛盾叙事；当累抽奖励承担**保底职能**（火影每 10 抽送碎片、方舟 300 抽送限定）时，「靠累抽拿到目标卡」被判 `miss`，语义自相矛盾。

### 2.3 事件系统的三个设计维度（本计划的核心设计问题）

**维度 1：事件类型体系（该有哪些事件？）**
- 现状：`pity_hit` / `early_hit` / `miss`（按「是否保底触发」二分）
- 待设计：是否引入 `milestone_hit`（累抽得）作为第四事件？是否还需要按「获得路径」重新组织（抽卡获得 vs 非抽卡获得）？事件是否需要子类型（如 `milestone_hit:gift` 纯赠 vs `milestone_hit:pity_like` 保底语义）？

**维度 2：判定条件（什么算 hit / 什么算 miss？）**
- 现状：硬编码——「保底触发时抽到目标 = pity_hit，保底前抽到 = early_hit，否则 miss」
- 待设计：判定条件是「以目标卡是否获得」为准，还是「以获得路径」为准？`miss` 是否该再细分（抽了没出 vs 没抽（skip/ignore））？`_resolve_skip_ignore` 的 0 抽池判定逻辑是否纳入统一设计？

**维度 3：成败口径（池子成没成功，怎么算？）**
- 现状：draw-only（只认抽出来的），硬编码
- 待设计：成败口径是否可配置？候选口径：
  - draw-only：只认抽出来的
  - 含累抽得：抽出来的 + 累抽赠送（保底类累抽该算）
  - 全获得：所有获得都算
- 口径选择是否按「用途」区分（评估池子价值 vs 判断玩家是否获得）？

### 2.4 与「每池分析语义界定」（P72）的耦合

事件系统的 `infer_events` 消费 `pool_card_counts`（全限定键，已正确），但它依赖的「池子成败」语义与转变分析（`compute_transition_flags_from_gdr`）共享口径——后者另有一个「banner/pool 每池语义」问题（P72）。两个计划在「池子成败判定」上耦合：
- P71 定「累抽得算不算成功」→ 决定 P72 的赠卡处理
- P72 定「每池是组合还是拆分」→ 决定 P71 的 `infer_events` 按哪个粒度判定
