# 三条产品入口的行为差异：独立调查、差异清单与统一方案

调查日期：2026-09-29。调查者：独立子 agent（无前置会话上下文）。
调查方式：只读代码 + 5 个只读探针（真实跑模拟，最小的 n，不修改仓库任何文件）。
证据纪律：每条结论都给出「文件:行号」；真实跑过的结论附原始输出；未经实测的推断明确标注为待确认。

---

## 0. 结论速览（先看这一节就够）

**先回答用户那句「不应该是只是调用核心引擎的入口的问题吗」：用户的直觉是对的，而且实际情况比直觉还好一点，也差一点。**

- 好的一点：三条入口**已经在调用同一个核心函数**（`run_batch_parallel`，定义在 `gacha_simulator/service/batch_simulator.py:651`），而且**实参表逐项几乎完全一样**。把三处的调用并排看，唯一的实参差异是 CLI 多传了一个 `collect_perf`（性能采集开关）。所以「三条入口各写一套模拟逻辑」这种事**不存在**。
- 差的一点：正因为调用本身已经统一，剩下的差异**全部落在「调用之前给环境对象塞的那几个字段」和「拿到返回值之后怎么用」这两段胶水上**，再加上**核心函数内部根据环境对象的字段走不同分支**。这类差异不会在「看调用点」时暴露，只会在「看用户看到的数字」时暴露。
- 因此「统一三条入口」的工程量，主要不在模拟逻辑，而在**把散落在三个文件里的胶水收成一层**。

**本次共列出 22 处差异，独立判断如下：**

| 判断 | 条目 |
|---|---|
| **应当统一，且用户能直接看到变化** | E1（SSR 指标同名不同义）、E2（无目标卡时口径分岔）、F1（配置校验闸门）、C2（基线失败被静默吞掉） |
| **应当统一，属于缺陷级（功能整体失效）** | G2（插件策略在并行下整批失败）、G1（并行路径失败无人计数）、H1（WebUI 从不加载插件） |
| **应当统一，但用户看不到（契约与卫生）** | B1（`return_compact` 三条不一致）、B2（`n_heatmap_bins` 三条不一致 + 字段未声明）、B4（核心函数回写未声明字段）、D1（消费明细还是消费提取结果）、H2（缺省值重复 5 次） |
| **无害的写法漂移（结论就是「其实无害」，建议顺手收敛）** | A3、B5、B6、D2、D3、E3 |
| **本就应该不同（界面形态决定）** | A1、A2（回调形态部分）、B3、F2 |

**最该先解决的三件事（按用户可感知程度排序）：**

1. **插件策略在任何「并行进程数大于 1」的运行里整批静默失败**（§2 G2，已实测）。三条入口都受影响；而且这是 P83 计划里 `1e-3` 那次「放宽命令行取值」的改动**新暴露给用户的选项**，属于「看起来是优化，实际交付了一个必坏的选项」。
2. **CLI 与 GUI 的「SSR 数量」是同一个名字下的两个不同指标**（§2 E1，已实测：同种子同次数同策略下 4.75 对 5.10）。这是最像用户所说「两条路径行为不同」的实例。
3. **配置文件里 Banner 标识重复时，GUI 会弹窗拦住不让跑，CLI 会照跑不误**（§2 F1，已实测：CLI 退出码 0，而该错误会导致保底串池）。

## 1. 背景与术语（本节是后面所有讨论的前提，不需要额外背景）

### 1.1 三条入口分别是什么

| 入口 | 用户怎么启动 | 代码位置 |
|---|---|---|
| 图形界面（旧 UI） | `python -m gacha_simulator.main`，点「开始批量模拟」按钮 | 抽卡面板 `gacha_simulator/gui/gacha_panel.py`，真正干活的是一条 Qt 线程类 `SimulationThread.run()`（`:36` 起） |
| Web 界面（新 UI） | `python -m gacha_simulator.main_webview`，在任务面板新建模拟任务 | `gacha_simulator/webui/api.py` 的 `GachaApi.start_simulation()`（`:258`）派发到后台线程 `_run_simulation_worker()`（`:269` 起）；前端在 `tools/poc_webview/ui_compare/src/App.vue:677` 调它 |
| 命令行 | `python -m gacha_simulator.cli -n 1000 -w 4 -s 42` | `gacha_simulator/cli.py` 的 `main()`（`:151` 起） |

三条入口都通过一个中间层函数 `SimulationEnvBuilder.from_config_store()`（`gacha_simulator/service/batch_simulator.py:972`）把配置对象变成「模拟环境」，再调用核心函数。

### 1.2 关键术语（首次出现即解释）

- **ConfigStore（配置存储）**：把 `config.toml` 解析成内存对象后的容器，装着 Banner 与池子、卡牌、保底规则、目标卡、初始资源等。三条入口拿到的 store 来源不同：CLI 从磁盘文件加载；GUI 用界面里已经改过的那一份内存对象；WebUI 用前端传过来的一段 TOML 文本重新解析（`gacha_simulator/webui/api.py:274`）。
- **SimulationEnv（模拟环境，代码里简称 env）**：一个普通数据类（`gacha_simulator/service/batch_simulator.py:82-155`），装着「这次模拟的静态部分」：池子列表、时间线终点、保底引擎、初始资源、目标卡编号集合、SSR 卡编号集合、停止条件等。它会被整体 pickle（Python 的对象序列化）并发给每个子进程。
- **run_batch_parallel（批量并行模拟，核心函数）**：`gacha_simulator/service/batch_simulator.py:651`。它负责起子进程池、把 N 次模拟分下去、把结果收回来，返回值是 `BatchResult`。
- **worker（工作子进程）**：核心函数起的子进程。Windows 上 Python 用 **spawn** 方式创建子进程，也就是**开一个全新解释器**，只执行主模块的**模块级代码**（写在函数体内的调用不会执行）。
- **CompactResult（完整明细）**：单次模拟的完整记录（逐抽的卡、时间、资源消耗、各卡获得次数等），每次模拟一份。
- **extraction（提取结果 / 提取包）**：子进程在每次模拟结束时顺手算出的轻量统计（总抽数、各卡次数、热力图分箱、池结束快照、转变标记），由 `WorkerLocalExtractor`（`gacha_simulator/core/streaming.py:238`）产出，父进程用 `merge_extraction_packets`（同文件 `:431`）合并成一份。界面上的绝大多数图表都读它。
- **BatchResult（批结果容器）**：`gacha_simulator/service/batch_simulator.py:34`。三个主要槽：`results`（每次模拟的完整明细，当 `return_compact` 为假时为空）、`extraction`（合并后的提取结果）、`warnings`（告警文本列表）。
- **env.return_compact（是否把完整明细交给父进程）**：环境对象上的一个布尔字段，默认真（`:101`）。为真时子进程把每次的完整明细回传；为假时只回传提取结果。它**只影响并行子进程那条路径**（单进程路径不读它）。
- **env.n_heatmap_bins（热力图分箱数）**：环境对象上的一个属性，决定提取结果里热力图直方图的细分数。注意：**它根本没有写在 `SimulationEnv` 的字段表里**（`:82-155` 里没有它），是调用方在构造之后直接赋上去的；核心函数里有 5 处用 `getattr(env, 'n_heatmap_bins', 50)` 读取，即缺省值 50（`:365`、`:706`、`:757`、`:897`、`:947`）。
- **不抽卡基线（no_draw baseline）**：主模拟之后额外跑的一次「只模拟 1 次」的运行，策略固定为 no_draw（全程不抽卡、只等待收资源），用来给出「什么都不做能攒下多少」的对照。三条入口都跑它。
- **保底引擎与全限定键**：保底按「Banner 标识 + 池子标识」拼成的全限定键绑定到具体池子；如果两个 Banner 用了同一个标识，键就撞在一起，会产生保底串池这类静默错误（这一点由 GUI 代码自己的注释点明，见 `gacha_simulator/gui/gacha_panel.py:284-285`）。
- **插件策略**：放在 `gacha_simulator/strategies/` 目录下的 `.py` 文件，通过装饰器把自己注册进全局策略表 `STRATEGY_REGISTRY`。仓库里现成有一个示例 `gacha_simulator/strategies/example_phased.py`，注册键为 `plugin/example_phased`，显示名「两阶段策略」。

## 2. 差异清单（事实 + 判断）

每条格式：**现象**（代码位置）→ **实测或推导** → **判断**。

### A. 传给核心函数的实参差异

#### A1. collect_perf（性能采集开关）：只有 CLI 传

- 事实：CLI 传 `collect_perf=bool(args.perf_json)`（`gacha_simulator/cli.py:349`）；GUI 的调用（`gacha_simulator/gui/gacha_panel.py:82-92`）与 WebUI 的调用（`gacha_simulator/webui/api.py:293-299`）都不传，取默认假。
- **判断：本就应该不同，无害。** 它是 P83 性能测量计划的选用通道，由 CLI 的 `--perf-json` 打开（`gacha_simulator/cli.py:194-195`）。不传时该参数为假，三方行为逐项一致（核心函数内所有采集动作都在 `if collect_perf:` 之下，见 `:688-695` 的注释与各处分支）。GUI 与 WebUI 没有对应的测量开关，也就不该传。

#### A2. progress_callback（进度回调）：三处实现与节流粒度都不同

- 事实：
  - CLI 每完成「总量的十分之一」打印一行（`gacha_simulator/cli.py:330-332`），并可用 `--no-progress` 关掉（`:344`）。
  - GUI 每完成约 N/50 次发一次 Qt 信号（`gacha_simulator/gui/gacha_panel.py:72-80`）。
  - WebUI **没有节流**：每完成一次就推一次 JS（`gacha_simulator/webui/api.py:288-291`），而 `_push_task` 最终走 `self._window.evaluate_js(...)`（`:89-95`），也就是每次模拟一次跨语言调用。
- **判断：回调形态本就应该不同（命令行是文本、GUI 是 Qt 信号、WebUI 是网页桥），但 WebUI 缺节流属于实现质量差异，不是形态要求。** GUI 与 CLI 都做了节流，唯独 WebUI 没做。建议照 GUI 与 CLI 的做法补节流。未实测该项的具体耗时，故只陈述代码事实与方向性判断。

#### A3. strategy_key 与 strategy_params（策略与其参数）的取值写法不同

- 事实：
  - CLI：`--strategy` 优先，否则 `getattr(store, 'strategy_key', 'smart') or 'smart'`（`gacha_simulator/cli.py:262-274`）。
  - GUI：直接 `strategy_key = config_store.strategy_key`，**没有**空值回退（`gacha_simulator/gui/gacha_panel.py:68`）。
  - WebUI：`getattr(store, 'strategy_key', 'smart') or 'smart'`，参数包成 `dict(... or {})`（`gacha_simulator/webui/api.py:285-286`）。
- **判断：无害，三处结果等价。** 理由有两层：环境构造器自己就做了归一化（`gacha_simulator/service/batch_simulator.py:1204`），核心函数对空串也有守卫（`:675-676` 的 `if strategy_key:`，空串时不改环境对象，于是保留构造器填好的值）。所以 GUI 少写一次回退不产生行为差异。但这是「三处各写一遍、读者要同时看三处才能确信等价」的写法，建议收敛到一个辅助函数。

### B. 调用之前对环境对象（env）的字段赋值差异

这是本次调查的核心区。全仓扫描「对 env 属性赋值」得到的清单：

| 赋值 | CLI | GUI | WebUI |
|---|---|---|---|
| `env.n_heatmap_bins` | 不设（内核缺省 50） | 设 `max(20, min(100, int(N**0.5)))`（`gacha_panel.py:62-63`） | 同 GUI（`api.py:281-282`） |
| `env.return_compact` | 不设（默认真） | 设假（`gacha_panel.py:66`） | 设假（`api.py:283`） |
| `env.profile_enabled/dir/skip/count` | 仅在 `--profile-dir` 时设（`cli.py:287-304`） | 不设 | 不设 |
| `env.metrics_dir` | 由核心函数在采集开启时写（`batch_simulator.py:786`） | 不涉及 | 不涉及 |

#### B1. env.return_compact：GUI 与 WebUI 设假，CLI 用默认真

- 事实：`gacha_panel.py:66` 与 `api.py:283` 在跑主模拟前置假，注释写明理由是「不再在主进程冗余累积」。CLI 不设，于是走构造器默认真（`batch_simulator.py:101`）。该字段在子进程侧被读进模块全局 `_wk_return_compact`（`:338`），只决定 worker 返回值三元组第一分量是否为 `None`（`:494-495`）。
- 推导与实测：
  - CLI 之所以「需要」完整明细：它的统计直接遍历 `batch_result`（`cli.py:414-420`），而 `BatchResult` 的迭代器返回的是 `results` 槽。
  - 于是 CLI 的父进程会为每次模拟多留一份完整明细。P83 计划已实测过单价（完整明细约 780 KB/次、提取结果约 1216 KB/次），并把 `return_compact` 登记为跨路径比对的「可比性维度」（`benchmarks/perf/record.py:13,24-26`、`benchmarks/perf/report.py:185`）。
  - **关键陷阱**：如果只是「按用户说的以 GUI 与 WebUI 为准」把 CLI 也设成假，CLI 会**静默产出空结果**。因为并行路径下每次回传的第一分量都是 `None`，而父进程的收集分支是 `elif compact is not None: results.append(compact)`（`:833-834`），于是结果列表恒为空；随后 CLI 用空列表做均值与分位数，输出全是 nan，并在 `np.percentile` 上抛 `IndexError`。我在探针里**实测到了这个失败形态**（见 §2 G2 的原始输出，触发原因不同，但产出形态完全相同）。
- **判断：这是应当统一的漂移，但统一方向不是简单地改一个字。** 真正的问题是核心函数把一个字段用于两件事：一是「父进程要不要每次模拟的完整明细」，二是「父进程靠什么统计这次运行成功了几次」。GUI 与 WebUI 的做法（不要明细、只留提取结果）是更省的形态，值得作为目标形态；但要让 CLI 也走这条形态，必须同时把「成败计数」从「明细是否存在」里解耦，并让 CLI 改从提取结果里取统计量（提取结果里已经含总抽数与各卡次数，见 `gacha_simulator/core/streaming.py:178-199` 的 `extract_aggregate`）。这不是一行改动，属于接口契约调整，风险与验证见 §4。

#### B2. env.n_heatmap_bins：GUI 与 WebUI 按开方公式设，CLI 不设

- 事实：见上表。且该字段**未在 SimulationEnv 的字段表里声明**（`:82-155` 完整字段列表中确实没有），是「往普通数据类上写未声明字段」的写法；项目自己在 `profile_*` 字段注释里点过这个坑（`:103-110`：「SimulationEnv 是普通 dataclass，写未声明字段会静默生效而不报错」）。
- 推导与实测：
  - 对 CLI 当前功能而言**无害**：CLI 只在完整输出模式下输出提取结果的条数摘要（`cli.py:477-490`），从不读热力图直方图。分箱数不同只改变直方图细分数。
  - **但它确实改变了提取结果的内容**，也就是三条入口的提取结果不是同一种东西；同时缺省值 50 在核心函数里**重复写了 5 次**（`:365`、`:706`、`:757`、`:897`、`:947`），任何一处被单独修改就会产生路径间漂移。
- **判断：应当统一，成本极低。** 建议两件事：把 `n_heatmap_bins` 正式声明为 `SimulationEnv` 的字段（带默认值以保持跨进程 pickle 兼容，做法照 P83 的四字段先例）；把「按次数推分箱数」这条规则收成一处（一个辅助函数，或由核心函数从模拟次数推导），三条入口都调它，消灭 5 处重复。

#### B3. env.profile_enabled 等四个剖析字段：只有 CLI 会设

- 事实：`cli.py:287-304`，仅当 `--profile-dir`。注入时机是硬要求（注释 `:281-286` 说明必须在调核心函数之前，因为之后环境对象已经序列化给子进程）。
- **判断：本就应该不同，无害。** GUI 与 WebUI 没有剖析注入通道（P83 决策 39 已登记「函数级档位的产品可达面是 CLI 与 inline」）。

#### B4. env.metrics_dir：由核心函数自己写到调用方的环境对象上

- 事实：`batch_simulator.py:781-786`，采集开启时建临时目录并赋给环境对象。该字段同样未在字段表里声明。
- **判断：属于契约卫生问题，应当统一（不是必须马上改）。** 核心函数修改调用方传入的对象是隐式副作用；目前只有 CLI 触发，所以没有可观测差异。但「未声明字段 + 核心函数回写」这个组合正是项目反复在防的静默失效形态。建议与 B2 一并处理。

#### B5. CLI 在构造环境之前改写配置对象的保底开关（--no-pity）

- 事实：`cli.py:246-247`。GUI 与 WebUI 通过配置界面改保底开关，不在模拟入口改。
- **判断：本就应该不同，无害。** 它只是命令行开关落到配置对象上的写法；顺序上必须在构造环境之前。

#### B6. GUI 往共享配置对象里写运行参数

- 事实：`gacha_panel.py:312-314` 写 `config_store.simulation_count / max_workers / seed`。
- 推导：扫全仓，这三个字段只有配置存储的默认值定义（`gacha_simulator/core/config_store.py:296,332-334`）与配置面板的读写（`gacha_simulator/gui/config_panel.py:6308,6450`，用于界面回填）在用，**模拟引擎不读它们**。
- **判断：当前无害，但是潜在陷阱。** 入口把「本次运行参数」写进共享配置对象，一旦将来有人让环境构造器读这三个字段，就会出现「GUI 生效、CLI 不生效」的隐式差异。建议顺手删掉这个写入，或加注释说明它只服务界面回填。

### C. 调用次数差异

#### C1. 主模拟加不抽卡基线：三条一致，都是 2 次调用

- 事实：三处都是「主模拟 1 次 + 基线 1 次（模拟 1 次、进程数 1）」，且基线实参逐项相同：
  - 都用 `copy.deepcopy(env)` 复制一份环境（`cli.py:369`、`gacha_panel.py:104`、`api.py:308`），再把副本的停止条件置为 `None`（`cli.py:370`、`gacha_panel.py:105`、`api.py:309`）。置空是既有裁决：不让「固定次数」一类用户停止条件把不抽卡基线截断。
  - 都用 `strategy_key='no_draw'`，且都**不传**策略参数。
  - 都用同一个随机种子（第一条主模拟用的那个）。
- CLI 侧的注释明确写了这条基线是**为了与 GUI 和 WebUI 对齐**而加的（`cli.py:357-365`）。
- **判断：一致，无需改动。** 这是「入口已经统一」的正面证据。

#### C2. 基线失败的异常处理不同：CLI 告警，GUI 与 WebUI 静默吞掉

- 事实：CLI 打印一行警告到标准错误（`cli.py:382-385`，注释明说「静默吞掉会让基线缺失与基线为 0 无从区分，正是反复在防的静默失效形态」）；GUI 是 `except Exception: pass`（`gacha_panel.py:121-122`）；WebUI 同样是 `pass`（`api.py:320-321`）。
- **判断：应当统一，方向是 CLI 的做法。** 同一段逻辑，一条入口自己写了「不能静默」的理由，另两条却在静默；这是三处各自为政的直接后果，且属于项目明确要防的静默失效形态。

### D. 拿到返回值之后的消费方式差异

#### D1. CLI 消费完整明细；GUI 与 WebUI 消费提取结果

- 事实：CLI 遍历 `batch_result` 取总抽数与各卡次数（`cli.py:414-420`），并在完整输出模式下读提取结果的计数（`:477-490`）。GUI 只取提取结果（`gacha_panel.py:125-154`），WebUI 同（`api.py:339-383`）。
- 实测：`extract_aggregate`（`gacha_simulator/core/streaming.py:151-199`）产出的聚合字典里**同时含**总抽数与各卡次数，也就是说 CLI 需要的两个量在提取结果里都有。
- **判断：应当统一（与 B1 是同一件事的两面）。** CLI 完全可以用提取结果算统计，从而不必在父进程保留 N 份完整明细，同时省下内存与进程间传输。但如 B1 所述，必须连「成败计数」一起改，否则会静默变成空输出。

#### D2. 基线结果的消费：CLI 只取最终资源，GUI 与 WebUI 另取「各 Banner 结束时的资源」

- 事实：CLI 只取最终资源（`cli.py:381`）；GUI 与 WebUI 还取各 Banner 结束时的资源（`gacha_panel.py:120`、`api.py:319`）。
- **判断：无害但可以补齐。** 差异来自界面需求（面板要按 Banner 展示基线资源）。CLI 的 JSON 里没有这个维度，属于信息缺失而非错误。是否补取决于 CLI 输出契约是否要保持稳定（P54 的验收标准明确要求 JSON 顶层键固定），所以不建议顺手改，先登记。

#### D3. 结果包的形态差异

- 事实：GUI 把热力图分箱边界以 numpy 数组原样放进包（`gacha_panel.py:127-141`），WebUI 转成列表并把 GDR 上下文转为字典（`api.py:345-355`）；WebUI 额外把结果包转成可持久化的数据集并写盘（`_dataset_from_bundle`，`api.py:384-423`），GUI 只把包通过 Qt 信号发给主窗口（`gacha_panel.py:175`）。
- **判断：本就应该不同（展示与持久化形态不同），无害。** 唯一要提醒的是：这类「两个入口各自把同一批数据整理成自己的形状」的代码，是将来再次漂移的高发区，也是 §4 方案乙想收掉的部分。

### E. 计算口径与报告口径差异（用户能直接看到的数字）

#### E1. 同一个名字「SSR 数量」，CLI 与 GUI 指的是两个不同的量（已实测）

- 事实：
  - CLI 的 SSR 计数用的是**目标卡编号**：`ssr = sum(cc.get(tid, 0) for tid in actual_target_ids)`（`cli.py:417-419`），目标编号来自 `_fallback_target_ids(store)`（`cli.py:88-99,407`），正常情况下就是配置文件里列的目标卡。
  - GUI 的「SSR数量」用的是**全部 SSR 卡编号**：`ssr_count = sum(cc.get(sid, 0) for sid in ssr_ids)`（`gacha_panel.py:399`），编号集合来自环境对象的 SSR 集合（`gacha_panel.py:52`），即配置里所有 rarity 为 ssr 的卡，含常驻。
- 实测（探针 probe_metrics.py，用仓库自带配置，20 次模拟、单进程、种子 42、smart 策略）：

```
target_specs = {'limited_ssr_1': 1, ..., 'limited_ssr_6': 1}   （6 张限定）
len(env.ssr_ids) = 12                                          （12 张 SSR，含 6 张常驻）
CLI  “SSR Count” 均值  = 4.75
GUI  “SSR数量”   均值  = 5.10
```

- **判断：应当统一（这是本次调查里最像用户所说「两条路径行为不同」的实例）。** 两个数都算得对，但**名字相同、含义不同**，用户拿两个界面对同一个配置跑同一个种子会得到「不一样」的结论而找不到原因。
  - 统一方向：「SSR 数量」这个名字的通行理解是「抽到多少张 SSR」，也就是 GUI 与 WebUI 的口径，建议以它们为准，CLI 改用全部 SSR 卡编号口径；CLI 原本想表达的「目标卡获得数」它已经另有指标（见 E3），不需要占用这个名字。
  - 注意：这项改动会改变 CLI 的既有输出数字，属于「用户可见但语义修正」的变更，应在计划里显式登记，并在测试里固化新口径。

#### E2. 没有配置目标卡时，两条入口的目标口径分岔

- 事实：CLI 有兜底逻辑，若没有目标卡就取「第一个 Banner 的标识拼上 `_ssr`」当作目标（`cli.py:88-99`）；GUI 与 WebUI 没有这层兜底，目标集合为空，目标达成率按 0 处理（`gacha_panel.py:393,402`）。
- **判断：应当统一或至少显式登记。** 同样「没配目标卡」的配置，CLI 报出一个具体数字，GUI 报 0。这个兜底是历史缺陷修补（注释 `cli.py:89-93` 说明不兜底会让计数恒 0），但两条入口对同一种配置给出不同呈现属于漂移。建议下沉到共享层，并明确「无目标卡」这一配置的语义。

#### E3. 命名漂移：GDR (Target Card %) 与 目标达成率 其实是同一个量

- 事实：CLI 打印 GDR 一行（`cli.py:437-441`），公式是「目标卡获得数除以目标卡总数再乘 100」（`:420`）；GUI 表格的行名是「目标达成率(%)」（`gacha_panel.py:268`），公式同（`:402`）。
- **判断：无害（数值一致），但命名应当对齐。** 同一个量在三处叫了三个名字，会让读者以为存在三种指标。

### F. 入口的闸门与校验差异

#### F1. 重复的 Banner 或池子标识、空成本这类配置错误：GUI 拦、WebUI 半拦、CLI 不拦（已实测）

- 事实：
  - GUI 在开始模拟前调配置面板的校验函数，有错就弹窗并直接返回（`gacha_panel.py:286-293`）；该处的注释写明理由：重复标识会让保底引擎的全限定键撞车，导致保底串池或静默写错。
  - WebUI 有一份逻辑等价的校验 `GachaApi._validate_store()`（`gacha_simulator/webui/api.py:121-152`，注释声明与 GUI 同源），但它**只在保存配置时**被调用（`save_config_text`，`:169-179`）；模拟入口 `start_simulation` 只做「把前端传来的 TOML 文本重新解析后直接跑」（`:274-299`）。
  - CLI 完全没有这道校验。配置加载函数自身只校验保底实例名重复、里程碑名重复、资源生命周期重复等（`gacha_simulator/core/config_toml.py:608,822,1059,1213`），**不含** Banner 或池子标识重复与空成本。
- 实测：
  - 探针：把仓库配置复制到临时目录，把第二个 Banner 的标识改成与第一个相同，然后运行 `python -m gacha_simulator.cli -c <临时文件> -n 2 -w 1 -s 42`。结果：**正常运行，退出码 0**，并打印出结果摘要。
  - 探针：把同一份文本交给 WebUI 的校验函数，**能报出** `['Banner id 重复: pool_c1']`。
- **判断：应当统一。** 这是三条入口里唯一一处「A 入口拒绝的配置，B 入口照跑」的分岔，而且后果是静默的保底串池，属于项目自己认定为必须拦下的错误。建议：把这段校验下沉到 core 层的一个纯函数（WebUI 的注释已经声明希望同源、不得各自复刻），三条入口在构造环境之前各调一次；WebUI 尤其要在**模拟入口**也调，因为前端传给模拟入口的是配置节点的文本，未必经过保存按钮（`tools/poc_webview/ui_compare/src/App.vue:675-677`）。
  - 待确认项：WebUI 的模拟入口是否能真的收到「未保存的脏文本」，取决于前端操作流程；我核对了派遣代码与工作线程解析逻辑，但没有在真实 WebUI 会话里操作验证。

#### F2. GUI 独有的软提醒

- 事实：GUI 在启动前会检查「初始资源为空」「某个池子的分布为空」并写进日志（`gacha_panel.py:301-305`）。CLI 与 WebUI 无此提醒。
- **判断：本就应该不同（界面便利性），无害。** 属于体验层差异，不是引擎行为差异。

### G. 失败可见性（两个缺陷）

#### G1. 并行路径下「失败次数」无人计数，CLI 完全静默

- 事实：并行路径的收集分支（`batch_simulator.py:828-834`）是：若调用方传了流式回调，失败（明细为空）会让失败计数加一；若没传回调，只有「明细非空」才收集，**失败既不入列表也不计数**。单进程路径与兜底路径则会计数并写警告日志（`:736-745`、`:752-753`）。
- 实测：见 G2 的原始输出，告警列表为空，全程没有任何告警。
- **判断：属于缺陷，应当统一修。** 三条入口都不传流式回调（这一点还被 `tests/benchmarks/` 下的适配器契约测试断言着），于是**三条入口在并行路径下都拿不到失败计数**。GUI 与 WebUI 之所以还能提示，是因为它们自己拿「提取结果里的成功条数」与用户请求的次数比较（`gacha_panel.py:362-365`）；CLI 没有这个比较，于是完全静默。
- 建议：把成败计数从「是否有明细」里解耦，在并行路径也累加失败计数，并把「请求次数、成功次数、失败次数」放进批结果容器。

#### G2. 插件策略在「并行进程数大于 1」时整批失败（已实测，两条入口的用户可见面）

- 事实与推导：
  - 三条入口的插件注册都发生在**函数体内**：CLI 在 `main()` 里（`cli.py:164`）、GUI 在 MainWindow 的配置加载方法里（`gacha_simulator/gui/main_window.py:223-224,252-253`）、WebUI 一处都没有（见 H1）。
  - 子进程初始化函数（`batch_simulator.py:333-368`）与单次执行函数（`:371-447`）都不会重新注册插件。
  - Windows 用 spawn 创建子进程，子进程只执行主模块的**模块级**代码，函数体内的插件扫描不会执行。于是子进程的策略表里没有插件键，创建策略时抛「未知策略」的 ValueError（`gacha_simulator/core/strategy.py:360`），异常被 worker 入口吞掉并返回空三元组（`batch_simulator.py:473-476`）。
- 实测（探针，用仓库自带示例插件，2 次模拟、种子 42）：

```
插件加载数: 1   plugin key 是否在注册表: True
workers=1: len(results)=2  n_results=2  warnings=[]
   total_draws = [0, 0]
workers=2: len(results)=0  n_results=None  warnings=[]
```

  子进程标准错误里是两条 `ValueError: Unknown strategy: plugin/example_phased`。

- 用户可见形态实测（真实命令行，4 次模拟、种子 42、策略为插件键）：
  - 单进程：**正常**，退出码 0，输出结果与基线。
  - 两个进程：**整批失败**，输出 `Total Simulations: 0`，四个统计量全是 nan，并在 `np.percentile` 上抛 `IndexError: index -1 is out of bounds for axis 0 with size 0`，退出码 1。默认四个进程同理。
- **判断：这是缺陷，而且与「看似优化」的改动直接相关。** P83 的 `1e-3` 把命令行策略取值从 7 个内置字面量放宽为「策略注册表里全部非内部条目」（`cli.py:176-182`），帮助文案明写「含 no_draw 与已加载的插件键」。于是 CLI **新暴露了一个在默认参数下必然失败的选项**。按项目表述纪律，这属于「改动意图正确，但引入了一条未验证的可达路径」。
- 影响面：CLI 与 GUI（GUI 的策略下拉框同样由注册表生成，`gacha_simulator/gui/config_panel.py:3457-3461,4291-4297`，且 GUI 会加载插件，所以插件显示名会出现在下拉框里）都会「提供选项但跑不通」；WebUI 则相反，见 H1。
- 修法两种（都不复杂）：
  - 甲：在子进程初始化时注册插件，使子进程与父进程的策略表一致。代价是每个子进程多一次插件目录扫描与插件模块导入；收益是插件在并行路径上真正可用。
  - 乙：不修并行路径，而是让 CLI 与 GUI 在起池之前显式拒绝「插件策略加并行进程数大于 1」的组合并给出明确错误，同时在文档里登记该限制。这更快、更保守，但用户拿不到功能。
  - 我倾向甲，理由是项目的「精确建模、不做近似」原则倾向于让机制真正可用；但乙成本更低，且不引入「插件作者代码在子进程里执行」的新语义，取舍应由用户决定。

### H. 相邻发现

#### H1. WebUI 进程从不加载插件（已实测）

- 事实：WebUI 有插件管理相关的接口（列出插件、启用禁用插件），但**没有任何一处调用插件目录扫描函数**（全仓扫描结果：只有 CLI、GUI 的 main_window、GUI 的插件管理面板三处调用）。
- 实测（在 WebUI 进程内）：

```
WebUI list_strategy_options 是否含插件键: False
注册表内是否含插件键: False
list_plugins 返回 8 条，全部为内置策略，其中 plugin_path 字段全为空字符串
```

- **判断：应当统一（属于功能缺失，不是形态差异）。** 与 G2 合起来看：WebUI 完全用不了插件策略，其插件管理页也列不出任何插件；CLI 与 GUI 能用插件策略，但一开并行就整批失败。三条入口对「插件」这件事各有各的坏法。修法最简：WebUI 启动时扫一次插件目录，照 GUI 的做法。

#### H2. n_heatmap_bins 的缺省值在核心函数里重复 5 次

- 事实：`:365`、`:706`、`:757`、`:897`、`:947`。这是一个「同一条规则写了 5 份」的脆弱点，任何一处被单独改动都会造成路径间漂移。
- **判断：属于卫生问题，建议随 B2 一并处理。**

## 4. 统一方案（含选项、权衡、风险、验证）

### 4.0 统一的形态目标

用户的原话是「一切应该以 GUI 与 WebUI 为准」「三条产品入口的行为统一应该怎么做」。我的独立判断分两半：

- **「以 GUI 与 WebUI 为准」在语义指标上成立**：E1 的 SSR 口径、E2 的目标口径、B1 的省资源形态，GUI 与 WebUI 的做法都更符合通行理解、也更省内存。
- **但它不能字面执行**：把它们的字段取值直接搬到 CLI，会踩 B1 描述的空结果陷阱。所以统一的目标不是「三处写成一样」，而是「**把选择和后果定义在一处**」。

推荐的目标形态（一句话）：三条入口只负责「收集用户参数」和「把结果渲染成自己界面的样子」，中间那段（构造环境、设置隐含字段、跑主模拟、跑不抽卡基线、组装统一的运行结果）由一层共享编排代码负责。

### 4.1 方案甲：最小对齐（不改核心函数签名）

适用范围：只修「用户看得到或会致错」的项。改动清单：

1. **E1**：CLI 的 SSR 计数改用全部 SSR 卡口径；旧口径请求的值由既有的目标达成率承担。位置 `gacha_simulator/cli.py:407,414-420`。
2. **E2**：把「没有配置目标卡时怎么办」统一到共享层（例如统一为不兜底、目标数为 0，并在输出里显式提示未配置目标），三处一致。
3. **F1**：把「Banner 或池子标识重复、空成本」校验下沉到 core 层纯函数，三处入口在构造环境前调用；WebUI 的模拟入口也要调，不能只在保存时调。
4. **C2**：GUI 与 WebUI 的基线异常处理改为记录并告警，与 CLI 一致。
5. **G1**：核心函数在并行路径也累加失败计数，并把「请求数、成功数、失败数」放进批结果容器；CLI 显式打印失败数。
6. **G2 加 H1**：插件策略。建议先做「WebUI 启动时加载插件」与「子进程注册插件（甲案）」两条，一起做才能让插件策略在三条入口都真正可用；若决定不做甲案，必须同时让 CLI 与 GUI 在起池前拒绝「插件策略加并行」的组合，并登记缺口。
7. **B2**：把 `n_heatmap_bins` 声明为环境字段，并把「按次数推分箱数」收成一处，消灭 5 处重复缺省值。

- 工程量：约 1 天（不含测试）。
- 收益：用户可见的三处不一致与两个缺陷全部消除；不动核心契约，回归面小。
- 局限：B1、B4、D1 这三条契约与卫生问题仍在，三条入口仍各自维护一段胶水。

### 4.2 方案乙：入口薄壳化（推荐，与甲叠加）

新增一层共享编排（放在模拟服务层，例如一个新模块或核心函数的新函数），输入是：配置来源、模拟次数、进程数、种子、策略键与参数、以及三项运行开关（是否需要完整明细、是否采集性能数据、是否落盘结果）。它内部按固定顺序做：校验、构造环境、设置隐含字段、跑主模拟、跑不抽卡基线、组装统一的运行结果（成功与失败计数、聚合数据、提取结果、基线资源、告警）。

三条入口退化为：CLI 组参数、调它、打印与写 JSON；GUI 组参数、在 Qt 线程里调它、把运行结果整理成面板数据；WebUI 组参数、调它、转成数据集并落盘。

- 收益：C2、D1、D2、D3、B1、B2、B3、B6、A3 这一整类「三处各写一遍」的差异**从结构上消失**；新增第四条入口不再复制胶水。
- 权衡：这一层要处理「三条入口的合理差异」（进度回调、是否需要明细、是否持久化），所以参数表会比现在长；必须把这些差异写成显式参数，否则会退化成「共享代码里写满按入口类型分支」的新胶水。
- 风险：GUI 的编排必须留在 Qt 线程内，因此共享层不能持有任何 Qt 对象；WebUI 的编码与落盘也要留在 WebUI 侧。这两条要在设计时就写死。
- 工程量：约 2 到 3 天（含三入口改接与测试）。

### 4.3 方案丙：核心函数契约显式化（可选，与乙叠加或分步）

把核心函数当前「读环境对象上的隐式字段」的做法改成显式契约：

1. 新增显式参数（例如「是否保留完整明细」），由核心函数在起池前写进环境对象（必须写在起池之前，因为环境对象是随进程池的初始化参数序列化给子进程的，这条纪律在 `cli.py:281-286` 已记录），而不是让每个入口自己去写。
2. 成败计数无条件化（同甲案第 5 条）。
3. `n_heatmap_bins` 与 `metrics_dir` 声明为字段；`metrics_dir` 不再由核心函数回写调用方对象。

- 风险（必须写清楚）：
  - `return_compact` 目前是 P83 跨路径比对的**可比性维度**（`benchmarks/perf/record.py:13,24-26`、`report.py:185,231`），适配器也按路径如实申报（`benchmarks/perf/adapters/cli.py:259-261` 申报真，GUI 与 WebUI 适配器申报假）。若 CLI 改为不保留明细，必须同步改适配器申报值与 P83 的决策记录，否则报告会说谎。
  - 更实际的影响：CLI 的历史基线记录会因该维度取值变化而**判为不可比**（这是机制本身的正确行为），但意味着需要重新建基线；按 P83 的纪律，旧基线文件应标注作废而不是删除。
  - `return_compact` 的默认值**不能直接翻转**：撤退搜索（`gacha_simulator/core/retreat_search.py:207-217`）依赖明细做广义出率判定（它自己构造环境、不设该字段）；最差影响分析（`gacha_simulator/core/worst_impact.py:140-152`）与 `scripts/profile_sim.py:85-92` 通过流式回调拿明细。翻转默认值会让这三处静默失效。
- 验证：见 4.4。

### 4.4 任何方案都必须配的验证（照项目的「基线固化加等价对照」纪律）

1. **金标准对照**：改动前，用固定种子（建议 200 次模拟、4 进程、种子 42，仓库自带配置）跑一次 CLI，把输出 JSON 固化；改动后同命令重跑，逐字段比较。GUI 与 WebUI 侧改为把每次模拟的聚合数据与基线资源固化对照。
2. **三入口等价比对（本次统一真正的验收判据）**：同一份配置、同一模拟次数、进程数、种子、策略下，三条入口产出的「每次模拟聚合数据集合」应逐项相等。注意并行调度的到达顺序不保证一致，所以必须按种子排序后再比，不能按到达顺序比。这条应固化为自动化测试。
3. **失败可见性测试**：注入一个必然失败的策略（最简单的做法是用当前仍不可用的插件键，或直接把单次执行函数换成抛异常的桩），断言批结果里能读到失败计数与告警文本；同时断言 CLI 的退出码非 0（当前实测是「输出 nan 加 IndexError 加退出码 1」，属于偶然而非设计）。
4. **插件策略测试**：示例插件在单进程与双进程下都必须产出全部结果（当前双进程全灭）。
5. **契约测试同步**：`tests/benchmarks/` 下有一批断言「适配器申报值与驱动代码实际驱动方式一致」的用例，凡改动入口代码里对核心函数的调用形状，都必须同步这些断言。
6. **门控与提交纪律**：本次改动会动 `gacha_simulator/cli.py`、`gacha_simulator/gui/gacha_panel.py`、`gacha_simulator/webui/api.py`、`gacha_simulator/service/batch_simulator.py`；这些文件同时也是 P83 的落点，按 P83 既有的分组与回滚边界，`batch_simulator.py` 的接口改动要与 P83 的消费者商定提交顺序，不得单独 revert。

### 4.5 我对方案取舍的建议

- **先做方案甲的第 1、3、5、6 四条**（SSR 指标口径、校验闸门、失败计数、插件）。这四条直接对应「用户看到的数字不一致」与「入口整体失效」，收益最高、风险最低，且不触碰核心函数契约。
- **再做方案乙**，这是用户那句「不应该是只是调用核心引擎的入口的问题吗」的真正答案：把胶水收成一层之后，「三条入口行为统一」成为结构性事实，而不是靠三处对齐维持。
- **方案丙只做第 2、3 两条**（成败计数无条件化、字段显式化），暂不翻转「是否保留完整明细」的默认值、暂不改 CLI 是否保留明细。理由是翻转默认值的爆炸半径覆盖撤退搜索、最差影响分析、三个开发脚本与 P83 的基线体系，而收益（省内存）在 CLI 常用规模（约 1000 次）下并不紧迫，风险却是静默失效。若确要做，按 4.4 的完整验证走一遍，并登记为「改动产品默认行为」。
