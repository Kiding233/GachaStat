# P71 过程事件统计方法重设计——两阶段（重设计门控 + 标签细化落地）

> 日期：2026-08-25 | 状态：设计中 | 优先级：中
> 触发与裁决：响应用户对「单抽级 × 池子级」两层框架的**去强制裁决**——两个维度只是参考维度之一，整个统计方法需从头重新考虑，而非把两层体系视为既定框架。P34/P35 从 `04-问题.md` 的问题段落提取并入本计划，原占位 P71（事件类型体系与成败判定口径）升级为正式设计并扩展为两阶段。

---

## 一、问题

本计划合并 P34 / P35 / P71 三个来源的问题，三个来源均指向「过程事件统计方法需要重新设计」，但在登记时被拆成了三份独立条目。

### 1.1 P34：单抽层稀有卡事件细化

**来源**：`04-问题.md` P34 + `架构设计.md` §1.8 第一层（C11）+ `01-理论.md` §2.3.1~2.3.2

当前 `pity_hit`/`early_hit` 合并了「保底出目标卡」与「保底歪得目标卡」、「提前出目标卡」与「提前歪得目标卡」共 4 种 SVG 单抽层标签；`miss` 合并了 4 种非目标 SSR 事件（歪非目标 up / 歪常驻 × 保底/非保底）。登记时基于「单抽层 8 种」给出了 `pity_hit_on_target` / `pity_hit_off_target` / `early_hit_on_target` / `early_hit_off_target` / `miss_up` / `miss_standard` 等拆分方向。

### 1.2 P35：池子层结果标签细化

**来源**：`04-问题.md` P35 + `架构设计.md` §1.8 第二层（C12）+ `01-理论.md` §2.3.3~2.3.4

当前 `skip`/`ignore` 仅区分「池中是否有目标卡可用」（`pool_target_map`），未区分 SVG 池子层的 12 种终态中的关键维度：计划内/外、免费/非免费、全部/部分、超出需求（浪费资源）。登记时基于「池子层 12 种」给出了 `free_partial` / `free_all` / `unplanned_free_up` / `unplanned_paid_up` / `overdraw` 等拆分方向。

### 1.3 P71：过程事件系统整体重构

**来源**：P58 第 3 轮核查暴露（`P58` §3.6b，REVIEW-R1-FIX: ISSUE-007）+ `01-理论.md` §1.5

事件系统目前是**三事件模型**（`pity_hit` / `early_hit` / `miss`），只覆盖「抽卡获得」路径。P58 里程碑奖励引入「累抽赠送」这一第三种获得路径后，暴露三个设计维度的问题：

1. **事件类型体系**：是否引入 `milestone_hit`（累抽得）作为第四事件？是否按「获得路径」重新组织事件？
2. **判定条件**：判定是以「目标卡是否获得」为准，还是以「获得路径」为准？`miss` 是否该再细分（抽了没出 vs 没抽的 skip/ignore）？
3. **成败口径**：draw-only 硬编码，无法按用途切换。候选口径：draw-only / 含累抽得 / 全获得。

**当前矛盾**：同一池可呈现「GDR 成功（含送卡）但事件 `miss`（不算送卡）」的矛盾叙事；当累抽奖励承担保底职能（每 N 抽送碎片、300 抽送限定）时，「靠累抽拿到目标卡」被判 `miss`，语义自相矛盾。

### 1.4 与 P72 的耦合

事件系统的 `infer_events` 消费 `pool_card_counts`（全限定键，已正确），但它依赖的「池子成败」语义与转变分析（`compute_transition_flags_from_gdr`）共享口径，后者另有一个「banner/pool 每池语义」问题（P72）。两个计划在「池子成败判定」上耦合：P71 定「累抽得算不算成功」→ 决定 P72 的赠卡处理；P72 定「每池是组合还是拆分」→ 决定 P71 的 `infer_events` 按哪个粒度判定。

### 1.5 为何 8 种与 12 种不再是阶段二的既定答案

P34/P35 登记的 **8 种（单抽层）与 12 种（池子层）** 标签，是问题发现时基于「单抽级 × 池子级」两层框架、从理论参考.svg 提取的**参考标签**。经用户裁决，这个两层框架并非强制框架，只是**参考维度之一**；整个统计方法需要从头重新考虑。因此 8 种与 12 种**是否为最终标签，由阶段一重设计决定**，而非直接作为阶段二的既定实现清单。阶段二须在新口径下重新评估这两个标签数是否落地、如何落地。

## 二、目标

### 阶段一：过程事件统计方法重设计（门控）

- 统计方法**从头重新考虑**，不预设「单抽级 × 池子级」两层框架为强制框架
- 评估两个维度（单抽级、池子级）是否引入、如何引入、如何组合——按需进入，不作为既定前提
- 落定三个设计维度：
  - **维度 1：事件类型体系**（该有哪些事件？是否引入累抽得路径？是否需要子类型？）
  - **维度 2：判定条件**（什么算 hit、什么算 miss？判定以「是否获得」还是「获得路径」为准？）
  - **维度 3：成败口径**（draw-only / 含累抽得 / 全获得，是否可配置、是否按用途区分？）
- 与 **P72** 协调「池子成败判定」的粒度与赠卡处理（耦合保留）
- 产出重设计决策，作为阶段二的门控（未通过则阶段二不启动）

### 阶段二：标签细化落地

- 在阶段一重设计后的**新口径**下，重新评估当前 8 种与 12 种标签是否落地、如何落地（而非直接照搬）
- 与 P72 协调落地顺序与影响面
- 与 `00-档案.md` 的「设计愿景」解耦，滚动更新骨架文件，不留强制框架残留

## 三、方案

### 3.1 阶段一：重设计门控（先于一切实施）

1. **重新界定统计方法的目标与适用场景**：明确过程分析要回答的问题、当前 7 种事件的语义缺口、以及两层体系只是众多参考维度之一。
2. **评估两个维度的取舍**：单抽级（每抽事件）与池子级（每池终态）是否都需要、各自回答什么、如何组合。允许结论为「只保留一个维度」「按场景切换」「引入第三个维度」或「维持现状 + 局部细化」。
3. **落定三个设计维度**（见目标）：类型体系、判定条件、成败口径可配置。其中「成败口径可配置」与 P72 的粒度耦合必须在一并落定。
4. **产出重设计决策报告**：作为阶段二门控依据。报告须经独立审查（遵循「编写者不得自审」原则），结论而非过程作为门控。

### 3.2 阶段二：标签细化落地（须在门控通过后）

1. 在阶段一新口径下逐一评估当前 8 种与 12 种标签，确定保留 / 拆分 / 合并 / 不落地，形成最终标签清单。
2. 与 P72 协调「池子成败判定」粒度与赠卡处理，敲定 `infer_events` 的判定粒度与 `core/streaming.py` 的 success 口径。
3. 落地实现与测试扩展（含累抽得 / 纯赠 / 保底类累抽场景），并回归验证与 `00-档案.md` 愿景的**解耦**（愿景仅作参考维度，不作既定目标）。

## 五、风险

- **阶段一可能推翻当前 7 种事件的内核**：波及 `infer_events` / `_resolve_skip_ignore` / 事件枚举 / `PoolEvent`，存在向后兼容风险（`PoolEvent` dataclass 字段变更会影响 GUI 事件类型下拉与着色映射）。
- **成败口径可配置化**：影响 `core/streaming.py` 的 `extract_process` 与 `gui/analysis_panel.py` 成功率 / 转变分析联动，口径切换需对账验证。
- **与 P72 的耦合**：若「池子成败判定」粒度未协调好，可能出现 `infer_events` 按池判定、转变分析按 banner 判定的口径分叉。
- **两层交叉（C10）的多 SSR 汇总规则**：开放设计问题（单抽层多次事件如何汇总为池子层终态），是阶段一设计难点，不宜视为简单实现任务。
- **免费 / 非免费投入维度**依赖上游 `CompactResult` 新增字段或 `ConfigStore.targets` 需求数量，在对应配置场景未就绪时缺乏分析价值。
