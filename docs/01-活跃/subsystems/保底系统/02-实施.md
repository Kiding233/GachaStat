## 二、BEHAVIOR_REGISTRY（10 条目）

对标 `STRATEGY_REGISTRY` 的注册表结构，每条目含 `class` / `display_name` / `default_scope` / `params` / 可选 `ui_params`。

```python
BEHAVIOR_REGISTRY: Dict[str, dict] = {
    "soft_interval": {
        "class": SoftStepBehavior,
        "display_name": "区间软保底",
        "default_scope": "ssr",          # ⚠ 全部 10 条目均为 "ssr"，见下
        "params": {...},
        "ui_params": ["start", "end"],
    },
    ...
}
```

### 完整条目表

| # | btype | display_name | 类 | params |
|---|-------|-------------|-----|--------|
| 1 | `soft_interval` | 区间软保底 | `SoftStepBehavior` | `start`(80) / `end`(90) / `func`(linear) |
| 2 | `soft_additive` | 累加软保底 | `SoftStepBehavior` | `start`(74) / `increment`(6.0) |
| 3 | `soft_step` | 分段软保底 | `SoftStepBehavior` | `deltas`（RLE 分段表） |
| 4 | `hard` | 硬保底 | `HardPityBehavior` | `threshold`(90) |
| 5 | `rotating` | 轮换保底 | `RotatingBehavior` | 无 |
| 6 | `rotating_soft` | 轮换保底（带软保底） | `RotatingSoftBehavior` | `start`(74) / `increment`(6.0) |
| 7 | `rotating_cr` | 轮换保底（递增概率） | `RotatingCRBehavior` | `cr_counter_threshold`(3) / `cr_base_rate`(5.0) |

## 三、PityEngine 详析

### 构造签名（双形态）

```python
PityEngine(
    pool_specs: Dict[str, PoolPitySpec],
    pity_defs,                                # List[PityDef]（新）或 Dict[str, PityDefParsed]（旧）
    behaviors=None,                           # 旧签名关键字
    rarity_rank: Dict[str, int] = None,
    state: 'PityState' = None,                # 新签名关键字
)
```

构造函数按 `isinstance(pity_defs, dict)` 分派新旧两条路径，置 `self._legacy_mode`。新路径为：逐个 `create_behavior(pdef, state)` 构造 behavior 存入 `self.behaviors[pdef.name]`，随后 `_resolve_order()` 排序 + `_validate_behaviors()` 校验。

构造完成后另建 `_activation_graph`：解析 `depends_on` 关系，供激活状态传播使用。

### 三个调度入口

| 方法 | 计数器 | 说明 |
|------|--------|------|
| `get_probabilities(pool_id, state, base)` | **只读** | 策略查询用。`bh.before_draw(ctx, readonly=True)` |
| `before_draw(pool_id, state, base)` | **递增** | 抽卡前调度。`bh.before_draw(ctx)` |
| `after_draw(pool_id, state, reward_id)` | **按条件重置** | 抽卡后结算。`bh.after_draw(ctx)` |

三者共同结构：

```
1. self._rebind_state(state)          # P75：必须先于 spec=None 早退
2. spec = self.pool_specs.get(pool_id); if spec is None: return base.copy()
3. 构造 DrawInfo（含 spec 的五个槽位映射 + rarity_rank）
4. ctx = PityContext(draw=draw_info, current=base.copy(), state=state)
5. for pname, bh in self._behaviors_for_pool(pool_id):
       new_probs = bh.before_draw(ctx, [readonly=True])
       if new_probs is not None: ctx.current = new_probs
6. return ctx.current
```

管道顺序由第 5 步决定，而 `_behaviors_for_pool()` → `get_behaviors_for_pool()` → `for pname in spec.pity_names` 取的是 **TOML 定义顺序**（见 P82）。

### `_rebind_state(state)`

遍历 `self._behavior_list`，逐个调用 `bh._rebind_state(state)`：纯重定向，把各 behavior 的 `Counter`/`Flag` 重建到新 state 上，**不复制旧值**（初始值由 `env.pity_state_init` 快照承载）。

P75 根因：若不重绑，behavior 持有的 `Counter` 指向旧 state，计数器写入错账本、保底快照恒空。

### 查询方法

| 方法 | 返回 |
|------|------|
| `get_spec(pool_id)` | 该池的 `PoolPitySpec` |
| `get_pity_def(name)` | 该 behavior 的原始 `PityDef`（只读视图） |
| `get_behaviors_for_pool(pool_id)` | `[(name, behavior), ...]`：按 `spec.pity_names` 顺序 |
| `get_counter(name)` | 该 behavior 的当前计数器值 |
| `get_trigger_count(name)` | 该 behavior 的触发次数 |
| `is_guaranteed(name)` | 大保底状态（事件驱动型） |
| `is_active(name)` | 该 behavior 当前是否激活（`depends_on` 或 `deactivate_on_early_hit` 可能使其失活） |
| `get_state_summary()` | 全量状态摘要 |

注意 `get_counter()` / `get_trigger_count()` / `is_guaranteed()` / `is_active()` 这四个**不带 `state` 参数**：它们读的是 behavior 内部持有的 `_state`，即**上一次调度时 rebind 的那个**。这是 P75 纪律第 2 条的已知边界（无 state 参数的只读查询不触发 rebind）。

## 四、生命周期与状态

### `CounterBasedBehavior` 的生命周期

子类只需覆写 `_compute_probabilities(ctx, counter)`，计数器管理由基类统一处理：

```python
def before_draw(self, ctx, readonly=False):
    if not self._active.is_set():        # depends_on 未满足 / 已停用
        return ctx.current.copy()
    v = self._counter().value() if readonly else self._counter().incr()
    return self._compute_probabilities(ctx, v)

def after_draw(self, ctx):
    if not self._active.is_set(): return
    if not self._should_reset(ctx): return
    if self._on_reset(ctx): return       # 子类接管（如 deactivate_on_early_hit）
    self._counter().reset()              # 默认重置
```

三个覆写点：

| 钩子 | 默认 | 子类用途 |
|------|------|---------|
| `_compute_probabilities(ctx, counter)` | 抽象 | 唯一的必implement项 |
| `_should_reset(ctx)` | `_reset == "featured"` → `ctx.draw.is_featured`；否则 `ctx.draw.reward_rarity == self._reset` | 定义重置条件 |
| `_on_reset(ctx)` | `return False`（走默认重置） | 返回 True 表示子类已完全处理。软/硬保底用它实现 `deactivate_on_early_hit` |

激活状态由 `_active` Flag 承载：`depends_on` 非 None 时初始不激活，由激活图传播点亮；`deactivate_on_early_hit` 在触发后由 `_on_reset` 清空。

### `PityState`

三层嵌套 namespace 容器，**不是** dataclass：

```python
class PityState:
    data: Dict[str, Dict[str, Any]]        # {behavior_name: {key: value}}

    def get(name, key, default=None)       # 读
    def set(name, key, value)              # 写
    def incr(name, key, delta=1) -> int    # 递增
    def clone() -> PityState               # 深拷贝（逐 namespace dict 复制）
    def to_dict() / from_dict(d)           # 序列化（from_dict 兼容旧 "counters" 格式）
```

每个 behavior 通过自身 `name` 存取任意类型的键：`counter`（计数）、`_active`（激活 Flag）、`_triggers`、`fate_points`、`selected_card`、`guaranteed` 等都在这套结构里，不需要为新增行为改类定义。

### `Counter` / `Flag`

```python
@dataclass
class Counter:
    _state: PityState; _name: str; _key: str = "counter"
    incr(delta=1) / reset() / value() / reached(threshold)

@dataclass
class Flag:
    _state: PityState; _name: str; _key: str
    set() / clear() / is_set()
```

它们是「记住了地址的遥控器」：behavior 只持遥控器对象，`_rebind_state()` 时重建遥控器即可完成 state 切换。

### `LifecycleConfig`

```python
@dataclass(frozen=True)
class LifecycleConfig:
    deactivate_on_early_hit: bool = False     # 提前命中后自我停用
    depends_on: Optional[str] = None          # 依赖另一 behavior 的激活状态
```

frozen 是纵深防御：阻止运行时意外修改。注意 `max_triggers` **不属于本类**（那是里程碑 `MilestoneDef` 的字段）。

### `_build_pity_state_init(pity_defs, counter_init_overrides=None)`

从 `PityDef` 列表构造初始 `PityState`：注入 `counter_init` / `guaranteed_init` / `fate_points_init`。GUI 可经 `counter_init_overrides` 按 name 覆盖计数初值。

## 五、管道载体

### `DrawInfo`（frozen）与 `PityContext`（可变）

```python
@dataclass(frozen=True)
class DrawInfo:                    # 本次抽卡的静态事实，全程只读
    pool_id / pool_instance_id / reward_id / reward_rarity / is_featured
    scope_cards / featured_cards / scope_slots / featured_slots / card_to_slot
    base_probabilities / rarity_rank

@dataclass
class PityContext:                 # 管道中流转的可变载体
    draw: DrawInfo
    current: Dict[str, float]      # 逐跳被覆写
    state: PityState
```

拆成两个类的意义：管道中每个 behavior 都会读 `draw`（事实）并改 `current`（分布），把两者分开后「谁可能被改」在类型层面就明确了。

### `PoolPitySpec`

| 字段 | 说明 |
|------|------|
| `pity_names: List[str]` | 该池适用的保底名列表：**管道顺序**，按 TOML 定义顺序生成 |
| `featured_ids` / `ssr_ids` | 该池的限定卡 / SSR 卡 ID 集合 |
| `resolved_targets` | ⚠️ 旧路径兼容字段，新路径中**始终为空 dict** |
| `scope_cards` / `featured_cards` | 按稀有度分组的卡 ID 元组 |
| `scope_slots` / `featured_slots` | 槽位映射：featured 拆为独立槽位名（如 `ssr_featured`） |
| `card_to_slot: Dict[str, str]` | `card_id → 槽位名`，供 `TargetedBehavior` O(1) 查找 |

### `compute_scope_mappings(pool)`

从池子的 Reward 列表预计算上述五个映射字段，依据 `Reward.extra_info` 的 `rarity` / `featured` 键分组。

槽位机制的意义：把 featured SSR 拆成独立槽位 `ssr_featured` 后，保底的概率提升只作用在该槽位，standard SSR 保持基础概率不变：等价于旧的 `target_distribution` + `resolved_targets`，但改为声明式。

## 六、扩展机制：新增保底类型

1. 在 `core/pity.py` 实现 behavior 类
   - **计数器驱动型**：继承 `CounterBasedBehavior`，覆写 `_compute_probabilities(ctx, counter)`
   - **事件驱动型**：继承 `PityBehavior`，自行管理 `counter` / `Flag`
2. 在 `BEHAVIOR_REGISTRY` 注册条目（`class` / `display_name` / `default_scope` / `params` / `ui_params`）
3. 若是 `_soft` 后缀变体，用 `SoftPityMixin` 复用软保底委托（各子类约 5 行）
4. 在 `create_behavior()` 中传递该类型的专属参数（当前实现按 P55 新格式读 `PityDef` 扁平字段 + P56 参数）

**P75 纪律（新增 behavior 时必须遵守）**：

- 新 behavior 必须实现 `_rebind_state(state)`，或确认走基类空实现；子类特有的 `Counter`/`Flag` 经 `_on_rebind_state(state)` 覆写重绑
- 实现时不得因「当前无覆写者」删除 `_on_rebind_state` 的调用
- 新增的无 `state` 参数的只读查询，须纳入 ISSUE-104 豁免清单或改走引擎级 rebind
