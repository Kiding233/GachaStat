# P86 统计分析层统一——分析服务层抽象

> 日期：2026-09-30 | 状态：设计中（派发剥离等四项边界已由 P87 承接，见 §7）
> 触发：用户质疑「core 里的统计方法层是不是和 gui 的耦合太严重了，webui 还要重写一些方法？统计方法不就应该是一个输入指定的数据集 id 和相关参数，按约定的格式输出结果的函数吗」
> 前置讨论：本计划的问题界定与方案选择经用户逐轮确认（分析项定义的所有权、结果对象形态、设计精化三项、迁移顺序均已有裁决，见 §3.6 与 §7）

## 一、问题

### 1.1 定位：不是 core 与 GUI 耦合，是分析的定义没有所有者

先排除一个误判。**core 层零 Qt 依赖**：grep 全目录 `PyQt|PySide|QtWidgets|QtCore` 只命中三处注释文本（`param_descriptor.py:6`、`result_store.py:218`、`result_store.py:228`），无实际 import。唯一的外部渲染层泄漏是 `core/vulnerability.py:867-869` 与 `:1017-1018` 两处直导 plotly（`plot_vulnerability_ridge`、`plot_vulnerability`），P74 §六 已登记。

真正的形态是：**没有任何一处代码拥有「一次分析是什么」的完整定义。** 用户勾选「GDR分布」、指标选 `target_achievement`、勾上直方图与累积分布，这一句话描述的就是一次分析，但它在代码里找不到对应落点。定义被切成四块：

| 这份分析的什么 | 现住所 |
|---|---|
| 它叫什么、属于哪一类 | `gui/analysis_panel.py:17-46` 的 `ANALYSIS_CATEGORIES` 常量 |
| 它要什么参数 | 一半在 GUI 面板控件里，一半在 `AnalysisWorker.__init__` 的 31 个构造参数里 |
| 它的算法 | `core/` 的 `gdr.py` / `distribution.py` / `per_pool_analysis.py` 等 |
| 它的产出形状 | `ChartWebView.set_charts()` 吃的 dict，或 webui 的 sections 列表 |

要理解「GDR分布」这一个分析，必须同时打开四个文件。

### 1.2 后果：同一批分析两份实现，且已分叉

定义没有所有者，则每个消费者只能自己拼一遍。GUI 拼出 `AnalysisWorker._run_impl`（`gui/analysis_panel.py:201-1450`，约 **1250 行**）；WebUI 出现时无处可问「GDR分布是什么」，只能读 GUI 的代码再拼一遍（`webui/analysis_service.py`，**956 行**，18 个 handler）。这不是 WebUI 走偏，是结构决定的：换任何第三方来也得重写第三遍。

**已发生的分叉（全部经代码取证）：**

| 重复项 | 位置 | 状态 |
|---|---|---|
| 统计编排主体 | `gui/analysis_panel.py:201-1450` vs `webui/analysis_service.py`（18 个方法） | 两份实现，逐一对应 |
| `_spec_to_dict` | `analysis_service.py:37` / `comparison_service.py:203` / `vuln_service.py:25` / `worst_impact_service.py:22` | **4 份**，逻辑同构 |
| `_build_pool_names` | `analysis_service.py:69` / `vuln_service.py:115` | 2 份 |
| `_unique_count` | `gui/analysis_panel.py:2038` / `webui/analysis_service.py:168` | 2 份，**行为已不同** |
| 分析项标识 | gui 用 `cumulative_by_banner`（`analysis_panel.py:43`）vs webui 用 `cumulative_by_pool`（`analysis_service.py:197`） | 已漂移（P72 ISSUE-105 只改了 GUI 侧） |
| 参数默认值 | `analysis_service.py` 对 `gdr` 的读取散在 **7 处**（`:215/267/354/472/563/712/841`），其中 4 处默认值同为 `'target_achievement'`，写法各写一遍 | **散落 7 处** |

`_unique_count` 的分叉是最硬的证据：GUI 版取前 5000 个采样、见到第 3 个不同值即早退（`analysis_panel.py:2038-2046`），WebUI 版是 `len(set(samples))` 全量（`analysis_service.py:168`）。同一个指标名，两种结果。

### 1.3 输入侧已具备条件，缺的是位置与产出契约

WebUI 的接口边界**已经是**用户设想的形态：`webui/api.py:638-682` 的签名是 `run_analysis(dataset_id, method, params)` / `run_vulnerability(dataset_id, params)` / `run_comparison(dataset_ids, params)`，内部 `_get_dataset(dataset_id)` 做内存缓存加磁盘回退。

> **2026-10-09 注**：该处于 2026-10-09 起**降级为历史证据**。用户裁决 webui 后端冻结待重写（见 §3.7），所以它不再是「已实现的形态」，而是「历史实现曾验证过该形态」。结论不变，证据强度下降一档。

两处不足：
1. 它在 `webui/` 而非 `service/`，GUI 侧没有对应入口（GUI 走 `update_results()` 的内存推送，收 **12 条数据管道**，无一条是数据集 id）
2. 产出契约两侧不同：WebUI 已自发长出 sections 列表（`analysis_service.py:57-67` 的三个 helper，全文 32 处调用，形态为 `{'key': 'chart'|'table'|'summary', 'title': ..., ...}`），GUI 用两套分离的容器（`ChartWebView.set_charts()` 吃 `dict[str, ChartSpec]`，摘要另存 `self._summary_data`）

### 1.4 与 P85 的关系

P85「三条产品入口的行为统一」处理**模拟入口（派发侧）**的胶水分散，本计划处理**分析侧**。两者同源（都是「某件事的完整语义没有归属」），共享一个接缝：**数据集形态契约**。P85 §1.1 已给出同构判断（「调用点已统一，胶水没有」）。

数据集组装（同一次模拟在 GUI 与 WebUI 存出不同数据集，最硬一处是 `webui/api.py:427` 的 `pool_types={}` 硬编码为空而 `gui/main_window.py:498` 传真实推导值）**不属于本计划**，已由 **P87 模拟工作区** 阶段 1 承接（见 §7 待决项 3）。

## 二、目标

1. **分析项的定义归一处**：一条登记记录同时承载名字、分类、参数、算法、产出形状。
2. **产出界面无关**：同一数据集、同一参数，GUI / WebUI / CLI 三处产出逐字段一致。
3. **换前端不重写**：结构性判据为「新增一个分析项只写一处；新增一个前端只写渲染器」。三处对齐维持不算达成。
4. **非可视消费者可用**：统计量能从结果对象中无损取出，供 CLI、导出与回归测试使用。

## 三、方案

### 3.1 落点与分层

新建 `gacha_simulator/service/analysis/`，与 `batch_simulator.py` 同级。不放 `core/` 的理由：core 的职责是引擎，本层是编排引擎产出，依赖面也更宽（需 `ConfigStore` 与 `ChartSpec`）。

**算法与编排的界线（本计划的硬约束）：**

| 归属 | 内容 |
|---|---|
| 留在 `core/` | `gdr.py` 的 21 个出率函数、`comparison_analyzer.py` 的检验与支配矩阵、`vulnerability.py` 的 PAVA、`per_pool_analysis.py` 的转移矩阵、`distribution.py` |
| 进 `service/analysis/` | 选哪个指标、对哪些池、阈值取多少、结果如何组织成图与表 |

```
service/analysis/
├── registry.py    # AnalysisSpec + @register_analysis + ANALYSIS_REGISTRY + 导入期校验
├── result.py      # AnalysisResult + 三种 Section
├── context.py     # AnalysisContext（数据集解析 + 中间量按需计算）
├── runner.py      # AnalysisRunner（对外唯一入口）
└── items/         # 分析项实现，按现有 5 个分类分文件
    ├── overall.py      # gdr_dist / gdr_statistics / correlation
    ├── success.py      # success_rate
    ├── risk.py         # risk_var_cvar / risk_worst_case / risk_best_case / conditional_dist
    ├── time.py         # time_series / time_heatmap / draws_vs_gdr / waterfall_3d / waterfall_2d
    └── per_pool.py     # per_pool_draws / per_pool_target_rate / per_pool_pity_rate / cumulative_by_banner / transition_analysis
```

分类与顺序取自现有 `ANALYSIS_CATEGORIES`（`gui/analysis_panel.py:17-46`）的 5 类 18 项，迁移后该常量由注册表派生，不再是手写来源。

### 3.2 分析项注册表

复刻项目已有的同构模式：P69 的 `register_strategy`（`core/strategy.py:45`，装饰器副作用注册 + `StrategyMeta` + 导入期 `_validate_registry()` 五项检查）。

```python
@dataclass(frozen=True)
class AnalysisSpec:
    key: str                              # 'gdr_dist'
    display_name: str                     # 'GDR分布'
    category: str                         # '总体广义出率分析'
    params: List[ParamDescriptor]         # 只装「分析方法本身的参数」（见 3.10）
    reads_from_dataset: Tuple[str, ...]   # 依赖声明：需要数据集的哪些配置参数（见 3.10）
    requires: Tuple[str, ...]             # 依赖的中间量（见 3.6 精化二）
    fn: Callable[[AnalysisContext, dict], List[Section]]
    expandable: bool = False              # 对应现有 _EXPANDABLE_KEYS（analysis_panel.py:49）

@register_analysis('gdr_dist', 'GDR分布', category='总体广义出率分析',
    params=[StringListParam('gdr', '广义出率指标', default=['target_achievement']),
            BoolParam('hist', '直方图', default=True),
            BoolParam('cdf', '累积分布', default=False)],
    requires=('gdr_values',),
    expandable=True)
def gdr_dist(ctx: AnalysisContext, params: dict) -> List[Section]: ...
```

参数类族不新造，复用 `core/param_descriptor.py` 已有的 8 种（`FloatParam` / `IntParam` / `BoolParam` / `StrParam` / `StringListParam` / `PoolIntMapParam` / `ListParam` / `DictParam`），它们零 Qt 依赖且自带 `validate()`。

**附带收益**：GUI 分析参数面板可自动生成。现状 `AnalysisWorker.__init__` 的 31 个参数在面板与 worker 间手工接线；参数改为声明后，`gui/param_renderer.py` 的 `render_param_widgets()` / `collect_params_from_widgets()` 已能从 `ParamDescriptor` 生成控件并回收值。

现状 18 个分析项的参数键共 11 个，面很小，足以枚举：`gdr`、`threshold`、`alpha`、`ci`、`scope`、`unit`、`cond`、`hist`、`cdf`、`eventMode`、`pool_index`。

### 3.3 结果对象

三种 Section 不是新设计，是 WebUI 已自发长出的形态（`analysis_service.py:57-67`），本计划收编它而非另起炉灶，这是方案成本优势所在。

```python
@dataclass
class AnalysisResult:
    ok: bool
    dataset_ids: List[str]                      # 多数据集分析见 3.11
    method: str
    sections: List[Section]
    warnings: List[str]
    error: str | None

ChartSection(key, title, spec: ChartSpec)          # 图（ChartSpec 是声明，不是渲染产物）
TableSection(key, title, headers: List[str], rows)
SummarySection(key, title, items)                  # 统计量，item 带稳定标识（见 3.6 精化三）
```

`sections` 用**有序列表**而非字典：它要表达图、表、摘要在同一分析项内的排列顺序。现状 GUI 用两个平行字典丢失了顺序，靠 `_CHART_DISPLAY_ORDER`（`analysis_panel.py:52`）另外补。`warnings` 沿用 `CompactResult.warnings` 的既有模式（P79 已用）。

### 3.4 运行上下文

`AnalysisContext` 的作用是消除重复计算。现状每个分析项各自重建上下文：WebUI 的 `AnalysisService.__init__`（`analysis_service.py:90`）每次调用都跑 `_compute_all_gdr_dists()` 与 `_build_pool_names()`；GUI 的 GDR 值在 `analysis_panel.py:284`、`:686-689`、`:2072`、`:2346` 各算一遍。

```python
@dataclass
class AnalysisContext:
    dataset_ids: List[str]                      # 多数据集分析见 3.11
    datasets: List[StoredDataset]               # 与 dataset_ids 同序同长
    store: ConfigStore
    pool_names: Dict[str, str]                  # 一次算好
    cost_per_draw: float
    cost_by_resource: Dict[str, float]
    # 中间量按需计算，多个分析项命中同一 key 时复用
    def gdr_values(self, gdr_key: str) -> List[float]: ...
```

中间量做成**有名字的仓库**而非直接暴露数据集字段：分析项声明需要哪些（`requires`），框架按需计算。这个设计带来三件事：不做无用计算、缺数据时提前报错、缓存有天然粒度（某个中间量变了才重算依赖它的分析项）。

### 3.5 入口

```python
class AnalysisRunner:
    def __init__(self, store: ConfigStore, result_store: ResultStore): ...
    def run(self, dataset_ids: List[str], method: str, params: dict) -> AnalysisResult: ...
    def run_many(self, dataset_ids: List[str], tasks: List[Tuple[str, dict]]) -> List[AnalysisResult]: ...
    def defaults(self, dataset_ids: List[str], analysis_key: str) -> dict: ...   # 见 3.10 / 3.11
    def available(self) -> List[AnalysisSpec]: ...   # 供前端拉取分析项清单与参数 schema
```

`run_many` 是关键：GUI 一次勾十来个分析项，现状是一条 1250 行流水线跑完；统一后变成一次调用、**逐项独立**。`available()` 让 WebUI 前端不必手写 18 个分析项的清单与表单。

**错误处理契约（取 GUI 的既有行为）**：现状两侧不同，WebUI 的 `run()`（`analysis_service.py:173`）整体 try/except 失败即整项返回错误；GUI 逐项算、遇问题发警告继续（如 `analysis_panel.py:1344` 的「转变分析需要池结束时间数据，但当前为空，已跳过」）。统一取后者：`run_many` 逐项独立，一项失败不影响其余，每项自带 `ok` / `warnings` / `error`。此条须写进契约，否则迁移后 GUI 会从「部分可用」退化为「一项坏则全盘坏」。

### 3.6 设计精化三项（用户已确认全采纳）

三项都建立在同一骨架上，不改变架构，只是把骨架做扎实。

**精化一：参数类型化。** 每个分析项声明一个参数结构（`ParamDescriptor` 列表），默认值只写一处，同时兼作类型校验与 GUI 控件生成依据。现状 `gdr` 的默认值散在 7 处读取里（§1.2 表末行），改一处漏一处即两前端行为不同。

**精化二：依赖显式声明。** 分析项声明 `requires`（需要的中间量），框架在调用前保证可用，缺则给明确错误，而非运行到中途才发现（`analysis_panel.py:1344` 的跳过警告即此症状）。附带消除「每次调用都算全部 GDR 分布」的浪费。

**精化三：摘要项带稳定标识。** `SummarySection.items` 增加稳定的 metric key，使机器消费者（导出、CLI、回归测试）无需解析中文标签。成本极低。

**一个已评估并否决的方向**（记录以免后人重走）：把分析抽象成「度量 × 分组 × 视图」的笛卡尔积，使新增分析项零代码。表面看 18 项大多符合此结构（GDR 分布 = GDR 指标 × 全样本 × 直方图），但 `correlation`（度量之间）、`risk_var_cvar`（分位数与尾部期望）、`transition_analysis`（状态转移推断）、脆弱性（PAVA 保序回归）均带自定义算法，强行表达会造出表达力不足的 DSL，最终两套机制并存。此为过度设计，否决。

### 3.7 两个前端的接缝

**WebUI 后端：冻结，不改造，做完本计划与 P87 后重写（2026-10-09 用户裁决）。**

原写「WebUI 后端几乎不改，`webui/analysis_service.py` 退化为转发」。用户 2026-10-09 提出「webui 根本不需要适配，直接重写后端更好」，采纳。理由：

1. **「改造为转发」的产物是一次性的。** 把 956 行改成转发，买到的是一个临时桥，而那个桥接着要被重写。同期 P87 又要删 `webui/api.py` 里数据集 / 树 / 任务三组方法（11 个），**改造与删除会打架**。
2. **被取代的部分与需要重写的部分高度重合。** `GachaApi` 的 34 个公开方法里，约 **18 个属编排 / 派发 / 存储**（正是本计划与 P87 的领域），约 **16 个是通用设施**（配置读写、枚举、文件对话框、资源监控），与两份计划正交，新后端**直接搬**即可。所以「重写」不是从零写 34 个，是重写一半、搬一半。

**前端侧的变化**（同日裁决）：`tools/poc_webview/ui_compare/` 那套 UI 设计与交互形态作废，新前端是 `tools/poc_webview/layout_demo/`（`工作区交互形态.md` 的实现）。入口 `gacha_simulator/main_webview.py` **保留**，改指新前端产物。

**由此失效的一句**：原写「前端收的 JSON 形态不变（sections 已是 dict）」。`ui_compare` 不是迁移源，新前端尚未成型，所以 sections 的 JSON 形态**不必迁就旧前端**，可按新设计定；`AnalysisResult` 的 schema 因此有更大自由度，约束只剩「GUI 的 `sections_to_view` 适配层能吃」。

**GUI 侧有一处硬成本，需要一个适配层。** `ChartWebView.set_charts()` 吃 `dict[str, ChartSpec]`（`gui/chart_webview.py:291`），为的是 tab 切换与增量更新（`update_chart(key, spec)` / `remove_chart(key)`），而 sections 是有序列表：

```python
def sections_to_view(sections) -> tuple[dict[str, ChartSpec], dict]:
    charts = {s.key: s.spec for s in sections if isinstance(s, ChartSection)}
    summaries = {s.key: s.items for s in sections if isinstance(s, SummarySection)}
    return charts, summaries
```

约几十行。须保住两点：`_get_ordered_charts()` 的排序（统一后由注册表的 category 与注册顺序派生），以及 P83 启动测量依赖的 `charts_ready()`（`gui/analysis_panel.py:2535`）。

### 3.8 迁移分批

按项目既有的「基线固化 + 等价对照」纪律（CLAUDE.md 无历史包袱原则）：

| 批 | 内容 | 验证 |
|---|---|---|
| 0 | 固定种子跑一个真实数据集，把新旧两条路径的产出（sections / 统计量）存为 golden 快照 | 快照固化 |
| 1 | 建 `service/analysis/` 骨架 + 3 个分析项垂直切片，覆盖三种 Section：`gdr_dist`（纯图）、`gdr_statistics`（摘要）、`per_pool_draws`（表格） | 单元测试 + 骨架是否够用的判据 |
| 2 | **重写后端的第一版（薄桥）**：接 `service/analysis`，只跑通「数据集 id → 分析项 → sections」一条链（不接前端，用脚本或最小桥驱动） | golden 逐字段对照 |
| 3 | **GUI 侧切到新层**，加适配层，`_run_impl` 拆解（风险最高的一批） | golden 对照 + 进度行为不回退 |
| 4 | 其余 15 个分析项逐类迁移 | 每类迁移后重跑 golden |
| 5 | 清理：删 `webui/analysis_service.py` 的重复实现、`_run_impl` 的残留 | 全量回归 |

**顺序裁决**：先 WebUI 后 GUI（用户已确认）。理由是后端那一侧最轻，可最快验证骨架是否够用；代价是 GUI 的问题暴露得晚，由批 3 的 golden 对照兜住。

> **2026-10-09 复核与调整**：裁决成立，但**批 2 的内容变了**（见上表）——从「把 956 行改成转发」改为「重写后端的第一版，薄到只够验证骨架」。改后批 2 的产出**就是新后端的骨架**，不是一次性的东西。

### 3.9 时间演化类图表的重做与完整序列的删除（2026-10-05 补充）

**问题：这一类有五张图，实际只有两个量，其中一个画了三遍，另一个完全没画。**

类别「时间演化」现有五个分析项（`gui/analysis_panel.py:33-38`）：

| 分析项 | 底层量 | 数据源 |
|---|---|---|
| `time_series` GDR时间序列演化 | 个体路径 | `draw_sequences` |
| `time_heatmap` 时间-GDR热力图 | 存量分布 | `heatmap_data`（`ssr_count` 指标时退回 `draw_sequences`） |
| `waterfall_3d` 3D瀑布图 | 存量分布 | `draw_sequences` |
| `waterfall_2d` 2D压缩瀑布图 | 存量分布 | `draw_sequences` |
| `draws_vs_gdr` 抽卡数-目标达成率散点图 | 与时间无关 | `aggregate_data`（不用序列） |

`time_heatmap` / `waterfall_3d` / `waterfall_2d` 是**同一个量的三种渲染**；`time_series` 则试图在一张图里同时表达两个量。

**两个量**（2026-10-05 用真实配置实测，1000 样本）：

- **存量**：某时刻处于各档的样本占比
- **通量**：某时刻有多少样本换档

实测两者的时间重心：存量在各档「主平台」内的相对位置为 0.33–0.43（偏左），通量则贴在平台右端（≈1.00）。面条图（`time_series`）用同一种视觉编码画两者，而不透明的水平线两条即饱和，存量信息在渲染中被压掉，剩下的竖直簇只反映通量。**所以该图的问题不是「信息少」，而是「两个量塞进一个编码、且其中一个饱和」。**

#### 方案：单一数据源 `hist[t][k]`，五张图收敛为四张

`hist[t][k]` = 第 t 抽时**恰好**已达 k 档的样本数（精确档位，非等宽分箱）。

| 分析项 | 量 | 编码 | 相对现状 |
|---|---|---|---|
| `progress_band` 进度分位带 | 存量摘要 | P10/P50/P90 带 + 中位线 | **替换** `time_series` |
| `time_heatmap` 时间-档位热力图 | 存量全貌 | 每抽一列的颜色 | 改数据源（精确档位；去掉 `ssr_count` 对序列的依赖） |
| `arrival_time` 到达时刻分布 | **通量** | 每档一条密度曲线 | **新增** |
| `waterfall_3d` 3D瀑布图 | 存量分布 | 曲面 | 改数据源，外观不变 |
| `waterfall_2d` 2D压缩瀑布图 | 存量分布 | 25 条折线 | **建议删除** |

**删除 `waterfall_2d` 的理由**：它与 `time_heatmap` 是同一量的两种渲染，但时间轴只取 25 个采样点（热力图是每一抽），分辨率更低；且档位数少时（本例 7 档）画出来是「穿过 7 个点的 25 条折线」，形状本身无可读性。3D 瀑布保留，因为曲面能表达分布随时间的流动，这是二维图给不了的。

**热力图改用精确档位的理由**：现状用 50 个等宽 bin 覆盖 [0, 1.05]，而档位只有 `target_count + 1` 个；超出 1.0 的样本被 `min(n_bins-1, ...)` 塞进最后一格（`core/streaming.py:592-602`），该格虚高。

#### 必须标注的边界：通量被模拟终点截断

到达时刻分布的右端**不是真实分布**。实测：第 5 张有 56.1%、第 6 张有 90.7% 的样本到模拟结束仍未达成，其到达时刻被截断。**图必须显式标注「从不达成」的比例**，否则用户会把截断伪影读成真实峰。

同类边界也适用于长尾档位的其它读数（分位带右端、瀑布图末端）。

#### 删除完整序列记录（**本项的一般化见 P89**）

> 2026-10-08：本节删掉的只是**一个**提取器。提取器的注册表化、产出声明、逐项开关由 **P89**（`subsystems/流式分析/`）统一规范。§3.9 的实施应作为 P89 的一次应用，而不是并行的一件独立工作。

`DrawSequenceExtractor`（`core/streaming.py:490-560`）保留前 `max_keep` 个样本的完整逐抽数组，每样本 6 个长度 T 的数组。经核实：

- **6 个键里只有 `draw_card_ids` 有消费点**（`draw_pool_ids` / `draw_times` / `draw_pity` / `draw_resources_consumed` / `draw_resources_gained` 在序列结构内无任何读取方，同名命中均属 `CompactResult` 的字段）
- **4 个消费点全部可由 `hist[t][k]` 替代**：

| 消费点 | 位置 | 替代方式 |
|---|---|---|
| `time_series` | `gui/analysis_panel.py:771-793` | `progress_band` |
| `waterfall_3d` | `gui/analysis_panel.py:922-960` | `hist[t][k]` |
| `waterfall_2d` | `gui/analysis_panel.py:973-1018` | 删除 |
| `time_heatmap` 的 `ssr_count` 分支 | `gui/analysis_panel.py:832-838` | `hist` 增加 SSR 档通道 |
| WebUI 镜像（3 处） | `webui/analysis_service.py:613-635`、`:652-660`、`:726-792` | 同上 |

**代价对照**：`hist[t][k]` 为 `398 × 7` int32 = **10.9 KB**；现存的前 200 条完整序列按紧凑 float32 计 **1.81 MB**，实际更差（Python list of object）。约 **170 倍**。

**新增通道的口径必须与注册表 GDR 一致（2026-10-08 实测后补）**：现在图表侧的达成率是**另一份实现**，与注册表的 `target_achievement` 有一处差别。

| | 算法 | 位置 |
|---|---|---|
| 注册表 GDR | `sum(min(card_counts[cid], qty))`，**按每张卡封顶在 qty** | `core/gdr.py:49-55` 的 `_gdr_target_achievement` |
| 图表侧 | `obtained += 1`（`cid in target_ids` 即计），**不封顶、按出现次数** | `core/streaming.py:571-573`（热力图）、`gui/analysis_panel.py:836-838`（时序图）等 |

**实测结论（1000 样本、目标 6 张卡、种子 42）：两者逐样本完全相同，`max` 均为 1.0000，差异样本数 0。** 即本配置下**不是活缺陷**：`qty` 全为 1 且没有样本把同一张目标卡抽到两次。

**但它是两份实现**，一旦同一张目标卡被重复抽到，两口径就会分叉（GDR 记 1 分、图表记 2 分），且热力图还会把超过 1.0 的值 `min(n_bins-1, ach_bin)` 塞进最后一格静默堆积。

**处置**：不做独立修复（要同时改 6 处、且这些代码正是 §3.9 要替换的，改了等于白做）。改为**约束新的 `hist[t][k]` 通道**：它必须与注册表的 GDR 同口径（按每卡封顶），使重建后的三张图不再继承未封顶的算法。**不这样做的话，实施时会照抄旧代码的算法**，把两份实现原样搬到新通道里。

**顺带修正一处抽样偏差**：序列保留的是**前 `max_keep` 个样本**（`core/streaming.py:521` 的 `if len(self._kept) < self._max_keep`），不是随机抽样；进程池下到达顺序与种子顺序一致，故 `time_series` 的 20 条线取自种子序列前段。改为 `hist[t][k]` 后覆盖全部 N，该偏差消失。

**连带的清理（2026-10-08 补）**：删 `draw_sequences` 时必须**一并删掉 `max_keep` 这条线**，否则会留下一对没有消费者的参数：

- `min(200, max(10, 目标卡数*2+10))`（`service/batch_simulator.py:421/777/983`，每 worker 保留数）
- 硬编码的 `200`（`service/batch_simulator.py:830/1036`，合并端上限）
- `merge_extraction_packets` 里的合并上限判断（`core/streaming.py:454` 的 `len(merged_kept) < max_keep`）

`max_keep` **只被序列使用**（`merge_extraction_packets` 里除它之外没有别的消费者），所以序列一走，这三个点就都成了死参数。

**顺带记一个已消失的缺陷**：这三处口径不一致时，实际保留数是 `min(200, 进程数 × 每 worker 保留数)`。实测同配置同种子只改 `-w`：保留数 22/44/88/176，**且留下的是哪些样本也变**（四组内容摘要各不相同）。删掉序列后该缺陷随之消失，不必单独修。

### 3.10 参数的来源分类与分析记录（2026-10-07 补充）

**背景**：§3.2 的 `params` 当时只写「参数声明」，没有说清**哪些参数属于它**。后续讨论发现，参数按**来源**分三类，判据各自独立，且这个分类决定了它们各自存哪。完整的推导见 `01-理论.md` §五、§六；这里只落接口。

| 类 | 判据 | 例子 | 谁声明 |
|---|---|---|---|
| 配置参数（含作为配置的分析参数） | 产生数据要用它 | 池子、保底、策略、目标卡、权重 | 不属于本层 |
| **分析方法本身的参数** | 改它会影响分析结果 | 阈值、判成功的条件、算哪个指标 | `AnalysisSpec.params` |
| 界面状态与偏好 | 改它不影响分析结果 | 展开折叠、关心哪些指标 | `workspace.json` |

**由此对 §3.2 的两处修正**：

```python
@dataclass(frozen=True)
class AnalysisSpec:
    key: str
    display_name: str
    category: str
    params: List[ParamDescriptor]         # 只装「分析方法本身的参数」
    reads_from_dataset: Tuple[str, ...]   # 依赖声明：需要数据集的哪些配置参数
    requires: Tuple[str, ...]             # 依赖的中间量
    fn: Callable[[AnalysisContext, dict], List[Section]]
    expandable: bool = False
```

`params` **只装「分析方法本身的参数」**。目标卡与权重**不在其中**（它们是配置参数，见下），阈值的声明式默认值在其中。

`reads_from_dataset` **不是参数清单，是依赖声明**。它唯一的用处是：创建分析时知道该从数据集抄哪些值过来，例如 `('target_cards', 'weights')`。抄来之后成为本次分析的输入值，可以覆盖。

**进入 §3.5 入口的一个新方法**：

```python
def defaults(self, dataset_ids: List[str], analysis_key: str) -> dict:
    """取一份完整的参数表：分析项声明的默认值 + 从数据集换算的配置参数。

    多数据集时口径不能自动推导，留空并标必填（见 3.11）。
    """
```

前端流程因此是两个前端完全一致的三步：**取默认 → 表单改 → 提交**。这一步的实质是把参数值从控件里拿出来变成一等数据；现状参数没有一份表，控件本身就是存储（`gui/analysis_panel.py:2193-2215` 逐个控件读值塞进 `AnalysisWorker` 的 31 个构造参数）。

**分析记录**（新建 `analyses/*.json`，属 P87 的工作区目录）：

```json
{
  "anchor": "<一级配置节点的路径，或对比任务的 id>",   // 记录的主键（见下）
  "datasets": ["<数据集 id>", ...],     // 引用，非归属。配置锚点下恒 1 个，对比锚点下 N 个
  "created_at": "...",
  "items": [
    { "key": "gdr_dist", "params": { ... 全量参数值 ... } },
    ...
  ]
}
```

**记录以锚点为主键**（2026-10-08 定）。依据是 UI 文档 §5.1 的锚定模型：分析面板锚定在**一级配置节点**上（§5.3 补：对比任务也可作锚点），锚点子树内的点选不改变面板；§5.2 的「当前数据集」选择器是**单选**。

因此 **分析参数是「每个锚点一套」**：在同一个锚点下切换数据集，分析项与参数不变，只是数据换了。记录由此天然可寻回（打开该锚点即命中），不需要按数据集反查。

**它是工作区里的第二类对象**（可变、就地更新、不被引用、不进树），规则见 P87 §3.11 J3。四条要点：

1. **密存**：全部参数值都写，不写差异。只存差异会让分析项的默认值一改、历史分析静默跟着变
2. **缺键回退**：读取时缺失的键取当前声明。所以分析项新增参数不会作废旧记录
3. **不标来源**：哪些参数来自数据集由 `reads_from_dataset` 现算，不写进记录（记两遍会漂移）
4. **只存配方不存结果**：结果（`List[Section]`）是渲染指令，存它等于把前端实现细节写进磁盘

**必须处理的边界：悬空的可选值**。分析记录密存了**选中集**，而**候选集是打开时现算的**（如 `core/gdr.py:547-576` 的 `get_gdr_expanded_entries`，输入只有注册表与 `resource_defs`）。若某个选项后来消失，旧记录里的值就悬空，**必须报出来，不能静默丢弃**。这与「缺键回退」是同一族规则。

**「控制显示哪些指标」不做成参数**。它不影响结果，做成参数会导致它被密存进每一条分析记录，等于把一份偏好复制 N 份。正确位置是工作区级偏好（`workspace.json` 的 `prefs` 块）。

### 3.11 多数据集分析（2026-10-08 补充）

§3.3 / §3.4 / §3.5 的签名此前全是**单数**（`dataset_id: str`），而现状里已经有复数入口：`webui/api.py:687` 的 `run_comparison(dataset_ids, params)`（接 list，内部 `[self._get_dataset(did) for did in dataset_ids]`）。§1.3 把它当现状描述列了一行，但没有进入设计；§四 又明确 `webui/comparison_service.py` 不在第一批范围。落差由此产生，本计划原未记录。

**用户 2026-10-08 裁决：数据集永远由用户显式指定，或由分析方法按预先设定的规则指定，不自动推导。** 交互形态取 `docs/00-meta/UI设计体系/工作区交互形态.md` §5.2（分析页顶部常驻数据集选择器，候选集按可分析性过滤）与 GUI 现状（`data_manager_panel` 复选框多选 → `comparison_analysis_panel.set_datasets(names)`）。

**改动**：三处签名由单数改复数。

| 位置 | 改为 |
|---|---|
| §3.3 `AnalysisResult` | `dataset_ids: List[str]` |
| §3.4 `AnalysisContext` | `dataset_ids: List[str]` + 按 id 取的接口（不再是 `dataset: StoredDataset` 单个字段） |
| §3.5 `AnalysisRunner` | `run(dataset_ids, ...)` / `run_many(dataset_ids, ...)` / `defaults(dataset_ids, ...)` |

**`defaults()` 的契约随之补一条**：

- **单数据集**：口径（`reads_from_dataset` 声明的那些，如目标卡与权重）能从那份数据集唯一确定，自动填入
- **多数据集**：**不能自动推导**，留空并标为必填，或由分析项声明一条规则

不猜的理由：猜错是静默的。取第一个数据集的、或取交集，都会让另一个数据集的口径被无声忽略，而这类分析（比较）的前提恰恰是两个数据集来自不同配置。

**与 §七 第 4 条「不引入数据集组抽象」不冲突**：那条讲的是「把一组数据集当**一个实体**」，本条讲的是「一次分析**吃多个**数据集」，是两件事。

**连带**：本节的改动同时解开 P88 记录的阻塞（其 §3.9 接缝一：`AnalysisContext` 为单数据集，故该计划在自己的 core 接口上写死了「纯数组进、纯分布对象出」）。P88 侧应标注「已由 P86 承接」。

## 七、边界与待决

本计划**只做分析层**。四项边界已于 2026-09-30 的专题讨论定案，结论落在 **P87 模拟工作区**（`subsystems/模拟工作区/P87 模拟工作区——派发编排与工作区存储.md`）：

1. **派发能力独立成层** → **已由 P87 承接，不再另立计划**。P87 建 `service/workspace/`，内容为编排（变换器 + 运行器 + 汇合器）+ 任务对象 + 工作区存储。涉及的两处 core 内派发（`core/retreat_search.py:207`、`core/worst_impact.py:140`）由 P87 阶段 3 剥离，拆法已定（最差影响直接拆三段并保留 `analyze()` 为过渡外壳；方案搜索改状态机 + 外层驱动）。
2. **最差影响与方案搜索的收编**：拆法见上条。在 P87 阶段 3 完成前，两者仍不可按本层骨架接入，故本计划批 4 不含它们。
3. **数据集组装统一** → **已由 P87 阶段 1 承接**。因此本计划 §六 的验收标准「同一数据集、同参数，WebUI 与 GUI 产出逐字段一致」在执行顺序上要求 **P87 阶段 1 先行**；若 P86 先实施，该条按单侧内部一致验收，待 P87 落地后补一次跨侧对照。
4. **数据集组抽象** → **结论：不引入独立抽象**（注意与 §3.11「一次分析吃多个数据集」是两件事：本条讲把一组数据集当**一个实体**）。同源归属由 P87 的配置树表达（配置 → 派生 sub 配置 → 各自的产物），本次分析的选择由前端勾选表达（`tools/poc_webview/ui_compare/src/App.vue` 的 `checkedDs` 已存在）。原「内核必要、命名与持久化后置」的评估作废。

5. **分析结果持久化** → **结论：只存配方，不存结果**（用户 2026-10-05 裁决）。分析记录进工作区（`analyses/`），分析结果是渲染指令，不落盘。业界对照与推导见 `01-理论.md` §6.1。

**实施顺序**：P87 先于本计划。理由是本层的跨侧一致验收依赖 P87 产出的统一数据集形态。

**收编范围说明**：用户已表态「5 个独立 service 和统计分析面板这两组都应该统一」。本计划按分批落地，**第一批为统计类 18 项**；脆弱性（`webui/vuln_service.py`）经核实**不派发模拟、只消费数据集**，结构上就是普通分析，可在批 4 一并接入。过程分析同理。
