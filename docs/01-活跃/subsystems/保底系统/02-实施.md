## 二、BEHAVIOR_REGISTRY（13 条目）

对标 `STRATEGY_REGISTRY` 的注册表结构。**P64 起每条目为 `class: None` + `preset` 工厂函数**，另有 `display_name` / `default_scope` / `params`（GUI 控件声明面）/ 可选 `ui_params`。

```python
BEHAVIOR_REGISTRY: Dict[str, dict] = {
    "soft_interval": {
        "class": None,
        "preset": _preset_soft_step,
        "display_name": "区间软保底",
        "default_scope": "ssr",
        "params": {...},
        "ui_params": ["start", "end"],
    },
    ...
}
```

`preset(pdef) -> dict` 的**键集恰为** `trackers` / `modifiers` / `lifecycle`（`lifecycle` 必需）+ 可选 `flags` / `counters`。`create_behavior` 对它做两道互补校验：未知键（查多）与缺 `lifecycle`（查漏），均抛 `ConfigError`。

### `_validate_registry()`

模块导入时执行，**每条目一律判 `preset` 可调用**（GATE-3 收口定稿：S4-1 的过渡判据「无 `preset` 键则判 `PityBehavior` 子类」已删除，旧判据的对象已不存在）。导入期**既不调用 preset、也不校验其返回键集**：调用会把 preset 体内的运行期错误提前成 `import` 失败；键集校验在 `create_behavior` 运行期做。

## 三、PityEngine 详析

### 构造签名

```python
PityEngine(
    pool_specs: Dict[str, PoolPitySpec],
    pity_defs,                                # List[PityDef]（P55 扁平化定义列表）
    rarity_rank: Dict[str, int] = None,
    state: 'PityState' = None,
)
```

构造函数流程：

1. 重名校验前置（2026-09-16 修正），重名直接抛 `ValueError`；
2. 逐条 `create_behavior(pdef, state)` 构造并存入 `self.behaviors[pdef.name]`。**构造失败即抛 `ConfigError`**（S4-5）：`create_behavior` 自己抛的 `ConfigError` 原样上抛，其余异常（未知 btype 的 `KeyError`、preset 体内的 `TypeError` 等）一并归为 `ConfigError` 并 `from exc` 保留调用链。旧实现是 `logger.warning` 后跳过该保底，会让「配置里写了保底、运行时该保底不存在且无可见报错」，且使后续两道校验跑在截断后的列表上；
3. `_resolve_order(list(self.behaviors.values()), rarity_rank)` 排序 → `_validate_behaviors(ordered)` 校验 → 存入 `self._behavior_list`；
4. 预计算 `self._pool_order`（**P82-1**）：全局排序在池成员上的子序，供 `get_behaviors_for_pool()` 消费；
5. 建 `_activation_graph`：解析 `depends_on` 关系，供激活状态传播使用。

> **2026-10-13**：原「双形态」签名（`isinstance(pity_defs, dict)` 分派 + `behaviors=None` 形参 + `self._legacy_mode`）已于 P81 A3（2026-09-17）整体删除，现存唯一签名如上。

### 三个调度入口

| 方法 | 计数器 | 说明 |
|------|--------|------|
| `get_probabilities(pool_id, state, base)` | **只读** | 策略查询用。`bh.before_draw(ctx, readonly=True)` |
| `before_draw(pool_id, state, base)` | **递增** | 抽卡前调度。`bh.before_draw(ctx)` |
| `after_draw(pool_id, state, reward_id)` | **按条件重置** | 抽卡后结算。`bh.after_draw(ctx)` |

三者共同结构：

```
1. self._rebind_state(state)          # P75：必须先于 spec=None 早退
2. spec = self.pool_specs.get(pool_id); if spec is None: return base.copy()
3. 构造 DrawInfo（含 spec 的五个槽位映射 + rarity_rank）
4. ctx = PityContext(draw=draw_info, current=base.copy(), state=state)
5. for pname, bh in self._behaviors_for_pool(pool_id):
       new_probs = bh.before_draw(ctx, [readonly=True])
       if new_probs is not None: ctx.current = new_probs
6. return ctx.current
```

**管道顺序由第 5 步决定**：`_behaviors_for_pool()` → `get_behaviors_for_pool()` 取 `self._pool_order`（`_resolve_order` 的排序结果），不再是 TOML 定义顺序（P82-1 接线前是后者）。`PoolPitySpec.pity_names` 保留 TOML 顺序供 `banner.draw_pity_names` 生成输出串。

### `_rebind_state(state)`

遍历 `self._behavior_list`，逐个调用 `bh._rebind_state(state)`。`Pity._rebind_state` 再对三族零件**无条件**调用 `part.rebind(state, name)`（Tracker / Modifier 的 `rebind(state, name)`；Lifecycle 的 `rebind(state, name, namespaces)`，实参面与 `initialize` 严格对称）：纯重定向，**不复制旧值**（初始值由 `env.pity_state_init` 快照承载）。

P75 根因：若不重绑，零件持有的 `Counter` / `Flag` 指向旧 state，计数器写入错账本、保底快照恒空。

### 查询方法

| 方法 | 返回 |
|------|------|
| `get_spec(pool_id)` | 该池的 `PoolPitySpec` |
| `get_pity_def(name)` | 该 behavior 的原始 `PityDef`（只读视图） |
| `get_behaviors_for_pool(pool_id)` | `[(name, behavior), ...]`：按 `self._pool_order` 顺序 |
| `get_counter(name)` | 该 behavior 的当前计数器值 |
| `get_trigger_count(name)` | 该 behavior 的触发次数 |
| `is_guaranteed(name)` | 大保底状态（事件驱动型） |
| `is_active(name)` | 该 behavior 当前是否激活（`depends_on` 或 `deactivate_on_early_hit` 可能使其失活） |
| `get_state_summary()` | 全量状态摘要 |

注意 `get_counter()` / `get_trigger_count()` / `is_guaranteed()` / `is_active()` 这四个**不带 `state` 参数**：它们读的是 behavior 内部持有的 `_state`，即**上一次调度时 rebind 的那个**。这是 P75 纪律第 2 条的已知边界（无 state 参数的只读查询不触发 rebind）。

## 四、生命周期与状态

### `Pity` 骨架的相位（N1 / M4）

`Pity.before_draw(ctx, readonly)` 的三段：

```python
if not self._lifecycle.is_active(self._state, self._name):
    return ctx.current.copy()
for tr in self._trackers:        # N1 首段：计数型先在 before 侧推进
    tr.advance(ctx, self._state, self._name, readonly=readonly)
for tr in self._trackers:        # N1 中段：抽前需读 state 并消费随机源的零件
    tr.prepare(ctx, self._state, self._name, readonly=readonly)
out = ctx.current.copy()
for mod in self._modifiers:      # Modifier 链：返回 None 表示不改动
    nxt = mod.apply(ctx, self._view_for(mod), out, readonly)
    if nxt is not None:
        out = nxt                # 链式应用（非短路）
return out
```

`Pity.after_draw(ctx)` 的次序是**退役先于 `commit`**（ISSUE-018）：`fired = did_fire(ctx)`（即 `any(tr.did_reset(...))`）→ `Lifecycle.should_deactivate(ctx, state, name, fired)` → 退役 → `commit(skip_reset=...)`。`skip_reset` 只在 `deactivate_on_early_hit` 触发的退役上为真（复刻旧 `CounterBasedBehavior.after_draw` 在 `_on_reset()` 返回 True 时提前 return 的语义）。

三族零件各自的覆写点：

| 零件族 | 覆写点 |
|--------|--------|
| `Tracker` | `rebind` / `advance` / `prepare` / `commit` / `did_reset` / `state_keys()`（全部有 no-op 默认实现） |
| `Modifier` | `rebind` / `state_keys()` / `apply(ctx, view, dist, readonly)`（`apply` 在 M1 期为占位实现，各具体类自实现） |
| `Lifecycle` | `initialize(state, name, namespaces)` / `is_active` / `should_deactivate(ctx, state, name, fired)` / `deactivate` / `rebind(state, name, namespaces)` / `state_keys()` |

激活状态由 `_active` Flag 承载（写在 state 的保底命名空间下，**不是**零件对象内）：`depends_on` 非空时初始不激活，由激活图传播点亮；`deactivate_on_early_hit` 或 `max_triggers` 用尽时退役。

### `PityState`

三层嵌套 namespace 容器，**不是** dataclass：

```python
class PityState:
    data: Dict[str, Dict[str, Any]]        # {behavior_name: {key: value}}

    def get(name, key, default=None)       # 读
    def set(name, key, value)              # 写
    def incr(name, key, delta=1) -> int    # 递增
    def clone() -> PityState               # 深拷贝（逐 namespace dict 复制）
    def to_dict() / from_dict(d)           # 序列化
```

每个 behavior 通过自身 `name` 存取任意类型的键：`counter`（计数）、`_active`（激活 Flag）、`triggers`、`fate_points`、`selected_card`、`guaranteed`、`forced_loss` 等都在这套结构里，不需要为新增零件改类定义。

### `Counter` / `Flag`

```python
@dataclass
class Counter:
    _state: PityState; _name: str; _key: str = "counter"
    incr(delta=1) / reset() / value() / reached(threshold)

@dataclass
class Flag:
    _state: PityState; _name: str; _key: str
    set() / clear() / is_set()
```

它们是「记住了地址的遥控器」：零件只持遥控器对象，`rebind()` 时重建遥控器即可完成 state 切换。

### `LifecycleConfig`

```python
@dataclass(frozen=True)
class LifecycleConfig:
    deactivate_on_early_hit: bool = False     # 提前命中后自我停用
    depends_on: Optional[str] = None          # 依赖另一 behavior 的激活状态
```

frozen 是纵深防御：阻止运行时意外修改。`max_triggers` **不进本类**（它是 `PityDef` 的独立字段，由 `build_lifecycle(pdef)` 取用，决定退役维取 `AfterN(n)` 还是 `Never`）。

### `_build_pity_state_init(pity_defs, counter_init_overrides=None)`

从 `PityDef` 列表构造初始 `PityState`：注入 `counter_init` / `guaranteed_init` / `fate_points_init` / `selected_card_init`。GUI 可经 `counter_init_overrides` 按 name 覆盖计数初值。

## 五、管道载体

### `DrawInfo`（frozen）与 `PityContext`（可变）

```python
@dataclass(frozen=True)
class DrawInfo:                    # 本次抽卡的静态事实，全程只读
    pool_id / pool_instance_id / reward_id / reward_rarity / is_featured
    scope_cards / featured_cards / scope_slots / featured_slots / card_to_slot
    base_probabilities / rarity_rank

@dataclass
class PityContext:                 # 管道中流转的可变载体
    draw: DrawInfo
    current: Dict[str, float]      # 逐跳被覆写
    state: PityState
```

拆成两个类的意义：管道中每个 behavior 都会读 `draw`（事实）并改 `current`（分布），把两者分开后「谁可能被改」在类型层面就明确了。

### `StateView` 与命名空间

零件**不直接读 `PityState`**，而是经 `StateView`（`core/pity.py`）读：`Pity` 持一个默认 view（`self._name`）与一组按零件命名空间建的 view（`self._ns_views`），调用零件时经 `self._view_for(part)` 取值。**不得写死 `self._view`**，否则 `X_soft` 的读取全落默认命名空间（`_soft` 族双命名空间）。零件的 `namespace` 属性为 `None` 时用默认 view，为具体命名空间名时用 `StateView(state, ns)`。

### `PoolPitySpec`

| 字段 | 说明 |
|------|------|
| `pity_names: List[str]` | 该池适用的保底名列表：**按 TOML 定义顺序**生成（供 `banner.draw_pity_names` 生成输出串；执行顺序自 P82-1 起由 `PityEngine._pool_order` 决定） |
| `featured_ids` / `ssr_ids` | 该池的限定卡 / SSR 卡 ID 集合 |
| `scope_cards` / `featured_cards` | 按稀有度分组的卡 ID 元组 |
| `scope_slots` / `featured_slots` | 槽位映射：featured 拆为独立槽位名（如 `ssr_featured`） |
| `card_to_slot: Dict[str, str]` | `card_id → 槽位名`，供定轨类零件 O(1) 查找 |

### `compute_scope_mappings(pool)`

从池子的 Reward 列表预计算上述五个映射字段，依据 `Reward.extra_info` 的 `rarity` / `featured` 键分组。

槽位机制的意义：把 featured SSR 拆成独立槽位 `ssr_featured` 后，保底的概率提升只作用在该槽位，standard SSR 保持基础概率不变。旧架构以运行时解析的 `target_distribution`（及其 `resolved_targets` 缓存）表达同一意图；两者均已随 P81（2026-09-17）删除，现由声明式槽位系统承载。

## 六、扩展机制：新增保底类型

**注册层（每次都要做）**

1. 在 `core/pity.py` 写一个 preset 工厂 `_preset_<name>(pdef) -> dict`，键集为 `trackers` / `modifiers` / `lifecycle`（+ 可选 `flags` / `counters`）；
2. 在 `BEHAVIOR_REGISTRY` 加条目：`class: None` + `preset` + `display_name` / `default_scope` / `params`（GUI 控件声明）；
3. 在 `_BTYPE_ORDER` 加该 type 的排序档位（漏加即落默认 99，排到所有已知 type 之后）；
4. 在 `core/config_toml.py` 的 `_PITY_TYPE_KEYS` 加该 type 的专用键集（**漏加即合法键被键契约硬拒、整份配置加载中止**）。

**零件层（按需新增）**

| 扩展 | 位置 | 覆写点 |
|------|------|--------|
| 新 Tracker | `core/pity_tracker.py` | `Tracker` 子类：只覆写真正承担的相位（`advance` / `prepare` / `commit` / `did_reset`），并声明 `state_keys()` 与（可选）`namespace` |
| 新 Lifecycle | `core/pity_tracker.py` | `Lifecycle` 子类：五方法协议 + `state_keys()`；**两个只读属性必须由基类统一代理 `self._cfg`**（ISSUE-406） |
| 新 Modifier | `core/pity_modifier.py` | `Modifier` 子类：M1 期自实现 `apply(ctx, view, dist, readonly)`（返回 `None` 表示不改动分布），S8 起改只写 `compute_delta` |

**P75 纪律（新增零件时必须遵守）**：

- 新零件必须实现 `rebind(state, name)`，或确认走基类空实现。`Pity._rebind_state` 对它**无条件**调用，故方法必须存在、不得省略
- 新零件持有的 `Counter` / `Flag` 必须在 `rebind` 内重建（纯重定向、不复制旧值）
- 新增的无 `state` 参数的只读查询，须纳入 ISSUE-104 豁免清单或改走引擎级 rebind
- 零件**不得把计数写进对象字段**：对象在同一 worker 内跨模拟复用，对象内计数会跨模拟泄漏、破坏「固定种子可复现」（`FiniteActive` 的 `triggers` 因此落在 state 而非对象内）

**声明集与构造期检查**：`Pity.__init__` 汇总三族 `state_keys()` 为 `_declared_keys`，它是 S10-2 两条构造期判据（同一键被两个 Tracker 声明 / Modifier 引用不存在的键）与 S11 状态层 checker 的唯一输入。新增零件若把 `state_keys()` 写错，判据会以 `ConfigError` 报出。
