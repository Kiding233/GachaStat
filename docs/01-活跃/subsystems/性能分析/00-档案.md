## 1. 业务问题

GachaStat 的性能目前只能靠人记得住。

- **全仓无性能基线**：没有任何地方记录「同配置同种子上次跑出来是多少毫秒」，因此「这次改动有没有变慢」这个问题无法回答
- **三份测量脚本全部失效**：`scripts/profile_gui.py`（413 行）、`scripts/profile_sim.py`（117 行）、`scripts/profile_simulation.py`（121 行）均无法运行，且因被 `.gitignore` 覆盖而从未入库，坏掉无人发现
- **唯一的自动化性能判据只管「失控」不管「变慢」**：`tests/test_p79_stop_condition_matrix.py` 的 8.4 闸门共 4 个用例，判据是迭代数上界 1000 与耗时阈值 0.5s，用于防止 `WaitAction(duration=0)` 空转复现，不是性能基准
- **剖析位置错了就测不到东西**：模拟的真实计算跑在 `multiprocessing.Pool` 子进程里（`service/batch_simulator.py` 的 `_wk_init` / `_wk_run_single`），2026-09-17 实测在主进程挂剖析器时，父进程主线程空等在 `multiprocessing/pool.py:861`
- **没有任何剖析工具链**：全仓 `cProfile` / `pstats` / `py-spy` / `yappi` / `line_profiler` 零命中，`pyproject.toml` 的 dev 依赖只有 `pytest` / `pytest-cov` / `pytest-timeout`

## 2. 设计意图

建立一套按「粒度 × 路径 × 因子」三轴正交组织的性能测量与回归平台。

- **粒度分四档递进**（`batch` → `stage` → `single` → `function`），按需下钻。P12 当年定位到瓶颈用的是分阶段计时而非剖析器，这个经验固化为默认档位
- **路径是一等维度**：CLI / GUI(PyQt) / WebUI / 直连脚本四条真实入口各有适配器。理由有实证——P12 记录 GUI 1000 样本 10-15s 对 CLI 1.6s（差 10 倍），根因是 `DrawSequenceExtractor` 只存在于 GUI 路径且在主进程串行；「多面板 CPU 争抢」是纯 GUI 现象；P54 的触发原因本身就是 CLI 与 GUI 入口分歧
- **两层剖析分工**：`cProfile` 出确定性调用次数与占比（进基线、做回归），`py-spy` 出真实进程现场（不进基线、供排查）
- **结果带环境指纹入库**，回归判据用比值而非绝对毫秒；基线按机器类别分组
