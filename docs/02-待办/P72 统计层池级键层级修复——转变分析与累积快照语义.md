## 2. 问题面（已核实，P58 第 3 轮核查 + 消费点盘点）

### 2.1 键空间基准

| 数据源 | 键空间 | 说明 |
|--------|--------|------|
| `pool_end_times` | **banner_id**（`b1`） | P61 后从 pool 级改成 banner 级 |
| `cumulative_snapshots`（streaming） | **banner_id** | 键来自 `pool_end_times` |
| `pool_card_counts` / `pool_draw_counts` / `pool_pity_counts` | **全限定**（`b1.main`） | extract_aggregate 透传 |
| `draw_pool_ids` / `bonus_events[].pool_id` | **全限定** | emit 契约 |

### 2.2 受影响消费点（盘点结果）

**A. 转变分析（transition_analysis）——N1/N2/N3 所在**
- `compute_transition_flags_from_gdr`（per_pool_analysis.py）：`pool_ids_ordered` 来自 `pool_end_times`（banner 键），但 single_pool 分支用它查 `pool_card_counts`（全限定表）→ 恒空（N3）
- single_pool 分支减赠卡改 `agg['card_counts']`，下游 `compute_pool_gdr_single_pool` 读 `pool_card_counts[pool_id]` → 空操作（N1）
- streaming 预计算 `_check_success_draw_only`/`_update_transition` 用**全累计表 cum_cards** 判「池子成败」，赠卡只减当前 banner 的（跨 banner 残留，N2），且「全累计判池成败」本身可能是实现与意图错位

**B. 截止每池的 GDR 分布（cumulative_by_pool）**
- analysis_panel L1094 `pool_ids = sorted(cumulative_snapshots.keys())`——键是 banner_id，实际是「截止每 banner」，与「每池」语义不符

**C. process_analysis_panel 累积模式 GDR**
- L513 `_cumulative_snapshots.get(pool_id)`——pool_id 来自 `pool_events`（全限定）去查 banner 键 snapshots → 错配

**D. 用全限定键、正确（不受影响，验证性）**
- 每池抽卡数/目标卡数/保底数、每池下池出卡率、infer_events 事件分类——直接从全限定表取数，正确

### 2.3 核心设计问题

1. **「池子成败」的判定语义**：转变分析/累积模式想回答的是「池 i 自己这一段目标达没达成」（per-pool 视角），还是「到池 i 为止整体达没达成」（累计视角）？当前实现混用（streaming 用全累计表、回退用 per-pool 表）——需裁决并统一
2. **键层级修复**：`pool_ids_ordered` 应携带全限定池键（从 `cumulative_snapshots`/`pool_card_counts` 派生）而非 banner 键；「截止每池」的累积快照键是否应改全限定
3. **N1 修正**：single_pool 减赠卡改到下游真正读的 `pool_card_counts[pool_id]` 字段
4. **N2 修正**：取决于「池子成败判定语义」裁决——若是 per-pool 视角，用每段增量而非全累计表，天然消除跨 banner 残留
5. **P71 联动**：赠卡算不算池子成败，取决于 P71 的「累抽得事件」口径
