# P85 三条产品入口的行为统一

> 日期：2026-09-30 建档 / 2026-10-01 退化为记录专题 | 状态：**记录专题（不再是待启动的计划）**

> 前置报告：[独立分析-入口行为统一-2026-09-29](../04-收件箱/独立分析-入口行为统一-2026-09-29.md)（独立子 agent 产出，22 处差异清单 + 三套方案，均为实测或代码取证）
> **历史脉络**：本计划是 **P54（CLI/GUI 统一化重构，2026-06-15 归档）的下一层**。P54 解决的是「入口不共用引擎」（CLI 当时自写 55 行 `run_single_sim()` 独立于 `run_batch_parallel()`），已经完成。本计划解决的是它没覆盖的那一层：**共用引擎之后，行为仍然不一致**。

## 一、问题

### 1.1 现状：调用点已统一，胶水没有

三条产品入口（GUI `gui/gacha_panel.py`、WebUI `webui/api.py`、CLI `cli.py`）**确实都在调用同一个核心函数** `run_batch_parallel`（`service/batch_simulator.py`），而且实参表逐项几乎相同（唯一差异是 CLI 多传一个性能采集开关，那是 P83 测量通道，已有裁决）。

但行为仍不一致，因为差异全部落在**两段胶水**上：

1. **调用之前**：各自往 `env`（模拟环境对象）上写不同的字段；
2. **调用之后**：各自用不同方式消费返回值。

这类差异不会在「看调用点」时暴露，只会在「看用户看到的数字」时暴露。

### 1.2 根因：调用态被塞进了配置态

`env`（`SimulationEnv`）承载的是「这个世界长什么样」（池子、保底引擎、初始资源），它会被序列化送给每个 worker，是**共享的配置态**。

而 `return_compact`（worker 要不要把每次模拟的完整明细回传父进程）、`n_heatmap_bins`（热力图分箱数）这类字段，表达的是「**这一次调用我要什么输出**」，是**调用态**。把它们放在 `env` 上，等于让每个入口各自去改一个共享对象：谁忘了改，谁就静默漂移。

CLI 正是在 `return_compact` 这一项上忘了改（GUI 与 WebUI 各自设了假），后果是同一个核心函数、同一份配置，CLI 的进程内存是 GUI 的约 2.7 倍。

### 1.3 差异清单（22 处，按性质分类）

完整清单与逐条实测见前置报告 §2、§3。摘要：

| 性质 | 条目 | 说明 |
|---|---|---|
| **用户可见的不一致** | E1（**已修**）、E2、F1、C2 | 见下 |
| **缺陷级（功能整体失效）** | G2（**已修**）、G1（**已修**）、H1 | 见下 |
| **契约与卫生** | B1、B2、B4、D1、H2 | `return_compact` / `n_heatmap_bins` 三条不一致、字段未声明、核心函数回写调用方对象、缺省值重复 5 次 |
| **无害的写法漂移** | A3、B5、B6、D2、D3、E3 | 结果等价，仅写法不同，建议顺手收敛 |
| **本就应该不同** | A1、A2（回调形态）、B3、F2 | 界面形态或测量通道决定，**不属于要统一的范畴** |

**四条用户可见的不一致**：

- **E1｜同一个名字「SSR 数量」在两个入口指不同的量**（**2026-09-30 已修，commit `319dc34`**）：CLI 用目标卡编号（原 `cli.py:417`），GUI 用全部 SSR 编号含常驻（`gacha_panel.py:399`）。实测同种子同次数：**4.75 对 5.10**。用户裁决以 GUI 口径为准，CLI 改用 `env.ssr_ids`；改后同一批次两条入口同得 **5.315**（逐字段对照：仅 `summary.ssr_counts` 变化，`total_draws` / `gdr_percent` / extraction / 基线全部不变）。
  **附带修掉的**：「SSR Count」与紧随其后的「GDR (Target Card %)」在改前共用同一个分子（目标卡获得数），同一份数被印了两遍、名字却不同；改后两者才真正分离。
- **E2｜没有配置目标卡时口径分岔**（**2026-10-01 已裁决并修复，commit `ef27d25`**）：原描述为「CLI 有兜底（拼 `_ssr`），GUI 与 WebUI 无兜底，报 0」。**2026-10-01 复核更正**：CLI 的兜底合成 `{banner_id}_ssr`，而仓库那份 `config.toml` 的 banner 叫 `pool_cN`、卡叫 `limited_ssr_N`，合成 id **不是任何真实卡**（实测不在 `card_defs` 中、且无任何卡以它为前缀），故 CLI 的命中数**同样是 0**。原描述掩盖了「两边其实都是 0，只是路径不同」，而真实问题是「兜底静默失效且失效时无任何提示」。**用户裁决**：没配目标卡时达成率本就无从计算，应当是 0，CLI 向 GUI / WebUI 看齐。已撤销兜底（`_fallback_target_ids` → `_cli_target_ids`），实测两端同为 0.00%。
- **F1｜配置校验闸门不一致**：GUI 会拦下「Banner/池子标识重复」这类错误（该错误会导致保底串池），WebUI 只在**保存配置时**校验、模拟入口不校验，CLI 完全不校验。实测：重复 Banner 标识的配置在 CLI 上**正常运行、退出码 0**。
- **C2｜不抽卡基线的异常处理不同**：CLI 打印告警，GUI 与 WebUI 是 `except Exception: pass` 静默吞掉。

**三条缺陷级**：

- **G2｜插件策略在并行进程数大于 1 时整批静默失败**（**2026-09-30 已修，commit `38962ab`**）：三条入口的插件注册都在**函数体内**，而 Windows spawn 的子进程只执行主模块的模块级代码，父进程那份注册传不过去。
- **G1｜并行路径的失败次数无人计数**（**2026-09-30 已修，commit `8088873`**）：调用方不传流式回调时，失败既不入结果列表也不计数，三条入口在并行路径下都拿不到失败数。**根因不是漏写 `else`，而是判据选错**：worker 的失败出口返回 `(None, None, ...)`，但 `return_compact=False`（GUI / WebUI 跑主模拟前的默认）时成功也不回传 compact，单看 `compact` 会把每一次成功都记成失败；单看 `ext_pkt` 又会误伤「抽取器自身抛错」的形态。改取「两者同时为空」，并令并行路径与另两条本已正确的路径（进程内 / mp_failed 兜底）同形。worker 的失败原因同时改为经三元组第三分量回传（原先只 `print_exc` 到子进程 stderr，打包后 GUI 无控制台即彻底消失）。
- **H1｜WebUI 进程从不加载插件策略**：`webui/` 全目录无任何 `load_plugin_strategies()` 调用，插件管理页形同虚设。**已登记进 P74**（见该计划 §八）。

### 1.4 另外两条独立缺陷（本次调查中新发现，一并登记）

- **I1｜模拟结果依赖运行日期**（**2026-09-30 用户裁决：这是设计意图，不再作为缺陷处理**，原定性为「破坏可复现性」）：`ConfigStore.sim_start_date` 默认取 `date.today()`（`core/config_store.py:295`），而 `monthly_day` 类收入规则按这个起始日期展开调度表（`core/resource_gain.py:168` 起）。对照实验（只改这一个字段）：起始日期 2026-09-29 / 09-30 / 10-15 → 最终资源 `exchange_currency` 为 **300 / 250 / 300**。**后果**：同一份配置、同一个种子，今天跑与明天跑结果不同；「同种子同结果」这一被当作回归判据的前提在跨天时不成立。**2026-09-30 裁决**：「模拟从今天开始」是预期行为，故不再修。**推论**：本条从待办划出，但跨天不可复现这件事本身没有消失，它转为 P83 基线回归体系的约束（那边须显式固定 `sim_start_date`，`scripts/p79_baseline.py` 已经是这么做的）。
- **I2｜`sim_start_date` 不落盘**（**仍待处理；与 I1 的裁决无关**）：`core/config_toml.py` **完全不读写**该字段，所以 GUI 配置面板里的「模拟起始日期」控件（`config_panel.py:5178`）改了也存不住，每次加载配置都重置为当天。**2026-09-30 实测复核**：设 `2026-03-15` → 保存 → 重载 → 变回当天，落盘文件里根本没有这个键。原注「这两条是同一个字段的两面」在 I1 被裁决后不再成立：**「默认今天」是对的，「改了存不住」不是**，两者不冲突。

## 二、目标

1. **把「选择」定义在一处**：三条入口只负责「收集用户参数」与「把结果渲染成自己界面的样子」，中间那段（校验、构造环境、设置隐含字段、跑主模拟、跑不抽卡基线、组装统一结果）由共享层负责。
2. **用户可见的指标一致**：E1、E2、F1 消除。
3. **新增入口不再复制胶水**：这是「结构性统一」而非「三处对齐维持」的判据。
4. **可复现性成立**：I1、I2 消除（起始日期要么固定进配置、要么显式排除出可复现性声明）。

## 三、方案

**用户已表态：偏好方案乙（入口薄壳化），但具体方案之后再讨论。** 故本节只登记三套方案的轮廓，实施细节待专门讨论。

> **2026-10-01 附注**：**方案乙的内容已由 P87「模拟工作区」的编排层承接并扩展**（变换器 + 运行器 + 汇合器 + 工作区存储，见该计划 §3.2），本节三套方案自此只作沿革记录，不再是本计划的实施方案。

### 方案甲：最小对齐（不改核心函数签名）

只修「用户看得到或会致错」的项：E1 口径、E2 兜底、F1 校验下沉、C2 异常处理、G1 失败计数、H1 插件加载、B2 字段声明。

- 工程量约 1 天（不含测试）
- **局限**：B1、B4、D1 仍在，三条入口仍各自维护一段胶水

### 方案乙：入口薄壳化（用户偏好）

新增一层共享编排，输入是配置来源、模拟次数、进程数、种子、策略，以及三项运行开关；内部按固定顺序做完全部流程；三条入口退化为「组参数、调用、渲染」。

- **收益**：C2、D1、D2、D3、B1、B2、B3、B6、A3 这一整类「三处各写一遍」的差异从结构上消失
- **风险**：GUI 的编排必须留在 Qt 线程内，共享层不得持有任何 Qt 对象
- 工程量约 2 到 3 天

### 方案丙：核心函数契约显式化（只做部分）

把「读 env 上的隐式字段」改成显式参数，成败计数无条件化，`n_heatmap_bins` 与 `metrics_dir` 声明为字段。

- **不建议做的一条**：翻转 `return_compact` 的默认值。独立调查查明三处依赖方（`core/retreat_search.py:207-217` 依赖明细做广义出率判定、`core/worst_impact.py:140-152` 与 `scripts/profile_sim.py:85-92` 通过流式回调拿明细），且它还是 P83 跨路径比对的**可比性维度**（`benchmarks/perf/record.py:13,24-26`），翻转会让这些静默失效。

### 建议顺序

甲的 1、3、5、6 四条（口径、校验闸门、失败计数、插件）→ 乙 → 丙的第 2、3 条。

#### 7.4.1 E3 的查证结果（2026-10-01）【已关闭，留档】

问题：「为什么会有两个入口两个名字，GDR 名称不是统一注册的吗？」

**是统一注册的，但这两个显示串都不来自注册表。** `core/gdr.py` 的 `UNIFIED_GDR_REGISTRY` 有 21 条 `GDRDefinition`，每条带 `display_name`（如 `target_achievement` → `简单目标达成率`）。而：

| 入口 | 字符串 | 出处 | 引用注册表 |
|---|---|---|---|
| CLI | `GDR (Target Card %)` | `cli.py:447` 的 `print` 字面量 | **否** |
| GUI | `目标达成率(%)` | `gacha_panel.py:273` 的列表字面量 | **否** |
| 注册表自己的名字 | `简单目标达成率` | `core/gdr.py` 的 `target_achievement` 条目 | 是 |

**更实质的问题：这个快速统计量本身不对应任何已注册 GDR。** 注册表的 `target_achievement` 算的是 `Σ min(count_i, qty_i) / Σ qty_i`（按份数加权、封顶 100%）；而 CLI 与 GUI 的快统计算的是 `Σ count_i / 目标卡种类数 × 100%`（不封顶，某张卡 `quantity = 3` 时抽满会显示 300%）。两者是不同的量，却共用了一个带有 GDR 术语的名字。

故 E3 的修法不只是「统一名字」：要先定这个快统计量**是**注册表的 `target_achievement`（那就直接调它、用它的名字），**还是**它自己的另一个指标（那就另起一个不借用 GDR 术语的名字）。

#### 7.4.2 GUI 第 2 条的查证结果（2026-10-01）【在办】

问题：「是不是 P87 之后就不成立了？」

**仍然成立。** P87 会消除**部分**结构成因（配置内容文件化到 `configs/*.toml`、数据集组装收进共享函数、任务对象持有配置），但：
