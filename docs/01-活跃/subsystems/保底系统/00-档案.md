## 业务问题

抽卡游戏的核心机制之一：随着玩家连续未抽到高稀有度卡片，系统逐渐提高高稀有度的出率，直到玩家「保底」获得高稀有度卡。保底机制深刻影响玩家的抽卡策略（何时该抽、何时该等）以及模拟结果的统计分布。

需要一个**多池多保底引擎**，能够：

1. 建模软保底（概率从某抽起逐渐递增）与硬保底（达到阈值时 100% 触发）
2. 支持一个池适用多个保底机制（如同时存在 SSR 软保底和限定硬保底）
3. 支持**事件驱动型**保底：大小保底轮换、定轨、捕获明光（P56）
4. 按配置顺序叠加应用多个保底
5. 支持多种重置条件（按稀有度 / 仅 featured / 多种组合）
6. 正确处理保底目标的概率分配：把提升的概率精确投向特定卡片（槽位系统）

## 设计意图

### 类层次

```
PityBehavior (ABC)                     # is_active / _rebind_state
├── CounterBasedBehavior (ABC)         # 计数器驱动型的通用生命周期
│   ├── SoftStepBehavior               # 唯一的 counter 驱动软保底（RLE deltas 驱动）
│   └── HardPityBehavior               # 阈值触发，scope 概率强制 100%
└── （事件驱动型直接继承 PityBehavior）
    ├── RotatingBehavior               # 纯净大小保底（guaranteed 二态翻转）
    │   ├── RotatingCRBehavior         # + 捕获明光（capturing radiance）
    │   │   └── RotatingCRSoftBehavior     （经 SoftPityMixin）
    │   └── RotatingSoftBehavior       （经 SoftPityMixin）
    └── TargetedBehavior               # 定轨（selected_card + fate_points）
        └── TargetedSoftBehavior       （经 SoftPityMixin）
```

`SoftPityMixin` 为「带软保底」的三种后缀类型提供统一的软保底委托，各子类仅需约 5 行增量：它复用 `SoftStepBehavior` 的 deltas 引擎，而非另写一套软保底逻辑。

### 核心抽象

| 类 | 职责 | 关键方法 |
|----|------|---------|
| `PityBehavior (ABC)` | 保底行为基类 | `is_active(counter_value)`；`_rebind_state(state)` |
| `CounterBasedBehavior (ABC)` | 计数器驱动型的通用生命周期：子类只需覆写概率计算 | `before_draw(ctx, readonly=False)` / `after_draw(ctx)` / `_compute_probabilities(ctx, counter)` / `_should_reset(ctx)` / `_on_reset(ctx)` |
| `PityEngine` | 多池多保底引擎：三个调度入口 + 状态重绑定 | `get_probabilities()` / `before_draw()` / `after_draw()`；`get_behaviors_for_pool()`；查询类 `get_counter()` / `is_guaranteed()` / `is_active()` / `get_state_summary()` |
| `PityState` | 单次模拟的保底状态：三层嵌套 namespace | `get(name, key, default)` / `set()` / `incr()` / `clone()` / `to_dict()` / `from_dict()` |
| `PoolPitySpec` | 单个池的保底配置 | `pity_names` + `featured_ids`/`ssr_ids` + 五个槽位映射字段 |
| `DrawInfo`（frozen） | 本次抽卡的**静态事实**：贯穿管道的不可变部分 | `pool_id` / `reward_rarity` / `is_featured` / 五个槽位映射 / `rarity_rank` |
| `PityContext` | 管道中流转的**可变载体** | `draw: DrawInfo` + `current: Dict[str, float]` + `state: PityState` |
| `Counter` / `Flag` | `PityState` 的遥控器：记住地址、封装操作 | `Counter.incr()` / `.reset()` / `.value()` / `.reached()`；`Flag.set()` / `.clear()` / `.is_set()` |
| `LifecycleConfig`（frozen） | 跨 type 共享的生命周期参数 | `deactivate_on_early_hit` / `depends_on` 两个字段 |

`Counter`/`Flag` 的价值在于：behavior 不用每次拼字符串键名去读写状态，且 P75 的 `_rebind_state()` 只需重建这两个遥控器对象即可完成 state 切换。

### 10 种保底类型

**计数器驱动型（4 种）**：`counter` 递增、阈值或分段触发。

| btype | 显示名 | 参数 |
|-------|--------|------|
| `soft_interval` | 区间软保底 | `start`(80) / `end`(90) / `func`(linear) |
| `soft_additive` | 累加软保底 | `start`(74) / `increment`(6.0%) |
| `soft_step` | 分段软保底 | `deltas`（RLE 分段表） |
| `hard` | 硬保底 | `threshold`(90) |

`soft_interval` / `soft_additive` 是 `soft_step` 的语法糖，在 TOML 解析时经 `_expand_soft_to_deltas()` 展开为 deltas，运行时统一由 `SoftStepBehavior` 消费。

**事件驱动型（6 种）**：按「出卡结果」而非计数阈值翻转状态。

| btype | 显示名 | 参数 |
|-------|--------|------|
| `rotating` | 轮换保底 | 无（guaranteed 二态翻转） |
| `rotating_soft` | 轮换保底（带软保底） | 软保底 `start`/`increment` |
| `rotating_cr` | 轮换保底（递增概率） | `cr_counter_threshold`(3) / `cr_base_rate`(5.0%) |
| `rotating_cr_soft` | 轮换保底·递增概率（带软保底） | CR 两参数 + 软保底两参数 |
| `targeted` | 定向保底（定轨） | `fate_threshold`(1) / `switch_allowed` / `switch_resets_progress` |
| `targeted_soft` | 定向保底·定轨（带软保底） | 定轨三参数 + 软保底两参数 |

语义：`rotating` 实现大小保底轮换（小保底沿用基础分布比例，大保底 featured 100%）；`rotating_cr` 在此之上叠加捕获明光；`targeted` 实现定轨：锁定的目标卡（`selected_card`）与命定值累积（`fate_points`），支持中途切换及切换是否清零进度。

### 保底管道机制

一个池可能适用多个保底（如 SSR 软保底提升概率 + 限定硬保底确保特定卡）。这些保底构成一条**管道**：前一个保底调整后的概率分布传入下一个继续调整，最终概率为管道末端输出。

管道载体是 `PityContext`：`current` 字段逐跳被覆写，`draw` 字段全程只读。

**管道顺序的现状**：由 `PoolPitySpec.pity_names` 决定，而它按 TOML 中 `[[pity]]` 的**书写顺序**构造（`service/batch_simulator.py:172-176`）。`_resolve_order()` 会计算一个语义化的顺序（稀有度层级 → type → name），但**该排序结果未接入概率管道**（只写入 `self._behavior_list`，而调度走 `get_behaviors_for_pool()` → `spec.pity_names`）。详见 **P82**。

### P16 修复：查询/修改分离（含 P75 补充）

P16 修复之前，`get_probabilities()` 内部会隐式修改保底计数器，导致所有调用者（包括只做概率查询的策略）都产生副作用。修复后三个入口职责分离：

| 入口 | 计数器 | 用途 |
|------|--------|------|
| `get_probabilities()` | 只读（不递增） | 策略查询「按现在的保底状态，下一抽的概率是多少」 |
| `before_draw()` | 递增 | 实际抽卡前取调整后概率 |
| `after_draw()` | 按 `_should_reset()` 重置 | 抽卡后结算 |

**P75 补充**：以上三者的首行均为 `self._rebind_state(state)`，把 behaviors 的 `Counter`/`Flag` 重绑到本次调用传入的 `PityState` 实例（纯重定向、不复制旧值）。因此 `get_probabilities()` 不再是 P55 归档定义的无副作用纯查询：它仍**不写计数器**，但会改绑 behavior 的内部引用。这个重绑必须先于 `spec is None` 的早退，否则计数器会写入错账本。

## 技术实现

### 调用链

```
GachaService 每步决策:
  1. strategy.select_action(ctx)         # 策略可经 ctx.get_pity_probabilities() 只读查询
  2. pity_engine.before_draw(pool_id, state, base_probs)   # 递增计数器 + 管道调整概率
  3. 按调整后概率执行抽卡（banner.py 完成抽卡 + after_draw 调度）
  4. pity_engine.after_draw(pool_id, state, reward_id)     # 按重置条件结算
```

### 核心数据结构

| 类 | 形态 | 职责 |
|----|------|------|
| `PityBehavior (ABC)` | ABC | 保底行为基类 |
| `CounterBasedBehavior (ABC)` | ABC | 计数器驱动型的统一生命周期 |
| `SoftStepBehavior` / `HardPityBehavior` | 具体类 | counter 驱动的两种实现 |
| `RotatingBehavior` / `RotatingCRBehavior` / `TargetedBehavior` | 具体类 | 事件驱动型的三种基实现 |
| `SoftPityMixin` | mixin | 为三个 `_soft` 后缀类型提供软保底委托 |
| `PityDef` | frozen dataclass | TOML 中一条保底的定义（23 个扁平字段），定义在 `core/config_store.py` |
| `PoolPitySpec` | dataclass | 单个池的保底配置（保底名列表 + featured/ssr ID 集合 + 五个槽位映射） |
| `PityState` | class | 三层嵌套 namespace 容器（`data: Dict[name, Dict[key, Any]]`） |
| `DrawInfo` / `PityContext` | dataclass | 管道载体：前者不可变事实，后者可变流转 |
| `Counter` / `Flag` | dataclass | 状态遥控器 |
| `LifecycleConfig` | frozen dataclass | `deactivate_on_early_hit` / `depends_on` |
| `PityEngine` | class | 多池多保底引擎：组合以上所有组件 |

`PityDefParsed` 仍保留于 `pity.py`，仅作旧格式（`pity.txt` 时代）的兼容路径：新路径不再经过它。

### 实施历史

- **v1.0-v1.5**：单保底、单管道模式
- **v1.6**：引入多保底叠加管道机制
- **v1.8（P16 修复）**：`get_probabilities` 与 `before_draw` 分离，消除隐式副作用
- **P53**：配置源由 `pity.txt` 迁移至 `config.toml`
- **P55**：正交分解重构：`CounterBasedBehavior` 基类、`SoftStepBehavior` 统一软保底（RLE deltas 取代三种 func_type）、`HardPityBehavior` 槽位化、`BEHAVIOR_REGISTRY` 注册表、`_resolve_order()`/`_validate_behaviors()`、`PityDef` 扁平化（23 字段）
- **P56**：事件驱动型保底落地：`RotatingBehavior` / `RotatingCRBehavior` / `TargetedBehavior` 三族 + `SoftPityMixin` 三种软保底变体；`LifecycleConfig` 扩展 `deactivate_on_early_hit` / `depends_on`
- **P60**：`DrawInfo`（frozen）+ `PityContext` + `Counter`/`Flag` 微抽象
- **P75**：`_rebind_state` 纪律，每次调度把 Counter/Flag 重绑到 per-call state，修复保底快照恒空问题
- **当前状态**：10 种保底类型全部可用（4 counter 驱动 + 6 事件驱动）。历史缺陷两处待办：**P82**（管道顺序未接通，`_resolve_order()` 的排序结果未接入概率管道）与 **P64**（状态机引擎重建，📋 设计中）；`_validate_behaviors()` 的冲突校验已生效，但其四条规则里有一条在当前构造路径上不可达，且 `PityDef.scope` 字段被 `create_behavior()` 忽略（详见 `03-审计.md` 与 `tests/core/test_pity_validate_behaviors.py`）。
