## 一、参数的来源分类

本节是全文的核心。前面几轮讨论在「权重属于配置还是分析」上反复打转，根因是**判据选错了**，不是答案难找。

### 1.1 三类参数，判据各自独立

| 类 | 判据 | 例子 |
|---|---|---|
| **配置参数**（含「作为配置的分析参数」） | 产生数据要用它 | 池子、保底、策略、目标卡、权重 |
| **分析方法本身的参数** | 改它会影响分析结果 | 阈值、判成功的条件、算哪个指标 |
| **界面状态与偏好** | 改它不影响分析结果 | 展开折叠、面板布局、关心哪些指标 |

三条判据各自可判定，互不隶属。**它们不是层层包含的关系**，问的是三个不同的问题：

1. 产生数据时用不用它？
2. 改它，跑出来的数变不变？
3. 改了界面上看到的东西变不变，但数不变？

### 1.2 判据为什么必须是「来源」，不能是「用途」

第一轮我用过的判据是「影响结论的进配置，不影响的不进」。它**自相矛盾**：

按它推权重，会得出「权重不影响模拟，所以不是配置参数」。但按同一条推**目标卡也会得出同样的结论**：引擎不知道你要哪张卡，它只按概率发牌，目标卡只影响你怎么看结果。

而目标卡显然必须是配置参数：它进配置身份、是 `ConfigStore` 的一等公民。**所以这个判据不能成立。**

换成「产生数据要用它吗」，「用途」这个词就消失了。目标卡在策略决策与停止判定里被消费，所以是配置参数。权重当前没有策略消费它，**但它仍是配置参数**：因为判据问的是「它有没有可能被产生数据的过程消费」，而不是「当前有没有」。

**为什么权重按当前事实也该算配置参数**：它是 GDR 的输入。而 GDR 是策略的输入（策略吃 GDR，或按 GDR 设计）。所以这条链是

```
目标卡、权重  ->  GDR（两类：一类吃目标卡，一类吃目标卡 + 权重）
                   |
                   v
                策略（吃 GDR，或按 GDR 设计）
```

策略不直接吃目标卡和权重，是**经 GDR 间接吃**。这解释了为什么现状里没有策略声明权重：只是**当前没有哪个内置策略是基于加权 GDR 设计的**，不等于权重不该进配置。

### 1.3 两个维度不能压成一个

「它是什么」（类别）与「它的值从哪来」（来源）是两件事，压在一起就会得出错误结论。

目标卡和权重：

- **类别**：配置参数（因为产生数据可能要用）
- **在分析侧的值的来源**：从数据集指向的那份配置换算

所以「权重是分析方法本身的参数」是错的（类别错），「权重是分析的共享设置」也是错的（不存在这样一个与类别并列的东西）。

**推论**：分析项需要声明的东西有两样，性质不同。

```
AnalysisSpec(
    params = [...],               # 分析方法本身参数，带声明式默认值
    reads_from_dataset = (...),   # 依赖声明：我需要数据集的哪些配置参数
)
```

`reads_from_dataset` **不是参数清单，是依赖声明**。它唯一的用处是：创建分析时知道该从数据集抄哪些值过来。抄来之后它们成为本次分析的输入值，可以改。

### 1.4 候选集与选中集

任何「从一组可选项里选几个」的参数都有两面：

| | 是什么 | 存不存 |
|---|---|---|
| **候选集** | 能有哪些可选项 | **不存**，每次派生 |
| **选中集** | 用户选了哪几个 | 存 |

以 GDR 为例，候选集的构造是纯派生的（`core/gdr.py:547-576` 的 `get_expanded_gdr_entries`，输入只有 `UNIFIED_GDR_REGISTRY` 与 `resource_defs`，没有用户选择参与）。

**由此有一条必须处理的边界**：分析记录密存了**选中集**，而**候选集是打开时现算的**。若某个选项后来从候选集里消失（注册表演进，或某个变体因配置变化不再适用），旧记录里的那个值就**悬空**了。

**必须报出来，不能静默丢弃。** 这与 §2.2 的「缺键回退」是同一族规则：记录里的值权威，但值与当前可选项不符时要显式提示。不这样做，用户会看到少了几项而不知道原因。

### 1.5 「控制显示哪些」不能做成参数

一个自然的想法是把「关心哪些指标」做成参数。**不做**，理由是具体的：

它不影响结果（按 §1.1 的判据属第三类），而做成参数会导致它被**密存进每一条分析记录**，等于把一份偏好复制 N 份，且每条记录都可能不同。

正确的位置是**工作区级的偏好**（见 §4）。

## 二、分析参数为什么必须密存

### 2.1 疏存会静默改变历史结论

存参数有两种做法：

- **密**：全部参数值都写进记录
- **疏**：只写与默认值不同的

疏看起来省，但有一个静默失效：如果只写差异，那么某天分析项的**默认值在代码里改了**（比如置信水平从 0.05 改成 0.01），**所有历史分析会跟着变**，而且是无声的。

密存的话，历史分析保持创建时的值，用户打开还能看见「这条是 0.05」。**看得见就解释得清。**

按本项目一贯反对静默失效的立场（与 P87 的「无条件纳入哈希」同源：宁可冗余，不要静默），只能选密。

### 2.2 密存不足以防声明演进：缺键回退

密存也做不到绝对自包含，因为**分析项的声明会演进**：某个分析项新增了一个参数，老记录里没有这个键。老记录**必须还能跑**，否则一次升级就把所有历史分析作废。

所以规则是两条并列，不是二选一：

```
创建时：全量快照        -> 记录自包含
读取时：缺键回退到声明   -> 声明演进不破坏历史记录
```

分工是：**已存在的键冻结，缺失的键取当前声明。**

### 2.3 不标参数来源

快照里那些来自数据集的参数，**不标记「这个是数据集带来的」**。

理由：来源是**声明**的属性（`reads_from_dataset`），不是**值**的属性。存进记录等于把同一件事记两遍，而两遍会漂移（改了声明忘了改记录）。界面需要时用声明现算。

## 三、分析记录

### 3.1 它存的是配方，不是结果

分析可以持久化的有两样东西，性质完全不同：

| | 存什么 | 大小 | 会不会过期 |
|---|---|---|---|
| **配方** | 吃哪些数据集 + 哪个分析项 + 什么参数 | 几十字节 | 不会 |
| **结果** | 算出来的图表与统计量 | 可能几 MB | 会（数据集变了、算法改了） |

**只存配方**（用户 2026-10-05 裁决）。

业界的分野正是这一条：Jamovi / JASP 存分析状态，打开时重算；SPSS 的 `.spv` 存结果本身。存结果的软件有个共同点：**结果本身就是最终交付物**（用户要拿去贴报告）。而这里的「结果」是 `List[Section]`，那是**渲染指令**，换个前端就渲染不了，存它等于把前端实现细节写进磁盘。

**只存结果不存配方，会留下一堆无法复现的图**：用户下次打开看到一张图，不知道它是哪个数据集、哪个阈值、什么时候跑出来的。

### 3.2 它自包含

创建分析时，把三类参数**全部**取一遍当前值写进记录：

| 类 | 从哪取 |
|---|---|
| 分析方法本身参数 | 分析项声明的默认值 |
| 数据集带来的（目标卡、权重） | 从数据集指向的那份配置换算 |
| 偏好类的 | 工作区级偏好（§4） |

**存快照而不是指向配置的指针**，理由：

- 配置会派生（写时复制），「当前那一份」会变。若每次读配置，一条三天前建的分析记录今天打开会读到**不同**的口径
- 快照之后记录**自包含**，与配置的后续变化解耦
- 配置被删也不影响已有分析（P87 §3.10 ④ 允许删除被引用的配置），只影响「新建分析时去哪抄默认值」，那时报明确错误即可

**代价**：配置改了口径，已有分析不会跟着变。这恰好是想要的行为：**分析是「我当时用什么口径看的」的记录。**

### 3.3 它为什么可变，而配置与数据集不可变

工作区里有两类对象（详见 P87 §3.11 J3）：

| | 规则 | 谁 |
|---|---|---|
| **不可变对象** | append-only，一经产生不再改写 | 配置、数据集、任务记录 |
| **可变对象** | 就地更新 | 分析记录 |

**为什么配置与数据集不可变**：因为它们**会被引用**。数据集指向配置，子配置指向父配置。一旦可改，引用就失去意义，所以要写时复制。

**为什么分析记录可变是安全的**：因为**没有东西引用它**。它是工作区里的叶子，只引用别人。**所有分析平级**（用户 2026-10-07 裁决），不存在「基于上次分析再分析」的引用关系。

**这条性质是「可变」成立的前提，而不是事后接受的例外**：不可变的对象之所以不可变，是因为有人指着它；没有引用的对象可变不引起级联。

**代价**：丢失不可回滚（改了就是改了，没有历史版本）。可接受，因为分析记录**丢了也不致命**（重新勾一遍即可），不像数据集那样不可再生。

**当前不做并发冲突检测**（用户 2026-10-07 裁决）：GUI 与 WebUI 同时开同一工作区这个场景太少见到，不为它增加机制。

### 3.4 与树的关系：引用，不是归属

树表达的是**派生关系**：配置由谁派生、数据集由哪个配置跑出来。它回答「这东西从哪来」。

分析记录回答的是「我拿哪些东西、用什么口径、看了什么」。它的输入是**多个**数据集（比较分析吃两个），输出是一条记录。

**所以它不是树上的父子关系，是引用关系**：一条分析记录引用 N 个数据集。**分析记录不进树。**

允许的反向查询（派生，不另存）：给定数据集，列出「被哪些分析用过」。

## 四、存储位置总表

| 内容 | 存哪 | 可变性 | 写入时机 |
|---|---|---|---|
| 配置参数（含目标卡、权重） | `configs/*.toml` | 冻结后不可变 | 用户保存配置 |
| 数据集 | `datasets/*.json` | 不可变 | 模拟完成 |
| **分析方法本身的参数** | `analyses/*.json` | **可变** | 创建 / 编辑分析 |
| 任务记录 | `tasks/*.json` | 不可变 | 任务启动与结束 |
| 工作区级界面状态与偏好 | `workspace.json` | 可变 | 界面变化时 |
| 会话级界面状态（滚动位置、对话框尺寸） | **不存** | — | — |
| 候选集（可选项清单） | **不存**，每次派生 | — | — |

**界面状态与偏好按作用域分，不按类别分**：

| 作用域 | 例子 | 存哪 |
|---|---|---|
| 工作区级 | 面板布局、树上展开的节点、关心哪些指标、最近打开的工作区 | `workspace.json`，**一份** |
| 分析级 | 这次分析开着哪些标签页、某个图展开没展开 | 若做，随分析记录各存一份 |
| 会话级 | 滚动位置、对话框尺寸 | **不存** |

判据是：**这个状态是「这次分析的」还是「整个工作区的」。**

`workspace.json` 内部再分两块，因为**共享性不同**：

- `ui`：纯个人的呈现（面板布局），别人拿到工作区不需要它
- `prefs`：有语义的默认（关心哪些指标），会随工作区发给同事，对别人有意义

**分析级界面状态先不做**（无证据），与 P87 §八「任务落盘（4c）不做」同一立场。

### 4.1 目标卡与权重在两个地方各有一份，不是冗余

| 那份 | 值来自 | 用途 |
|---|---|---|
| 配置里 | 用户配置 | **产生数据**（策略可能消费） |
| 分析记录里 | 创建分析时从数据集换算抄一份 | **本次分析读取** |

同一个名字、两份值，因为回答的是两个不同问题：「产生这批数据时用的是什么」与「我这次分析要按什么读」。

### 4.2 框架对外只暴露一个入口

```
defaults(dataset_id, analysis_key) -> dict
```

前端流程因此是两个前端完全一致的三步：

1. **取默认**：调 `defaults()` 拿到一份完整参数表
2. **表单改**：用 `AnalysisSpec.params` 的 `ParamDescriptor` 列表自动生成控件，填上第 1 步的值，用户改
3. **提交**：控件收回成一个 dict，调 `run(dataset_id, key, params)`

**这一步的实质是把参数值从控件里拿出来，变成一等数据。** 现状（`gui/analysis_panel.py:2193-2215`）参数**没有一份表**，**控件本身就是存储**，点按钮时从十几个控件逐个读出来塞进 `AnalysisWorker` 的 31 个构造参数。控件降为视图之后：两个前端读同一份声明各生成表单；无界面场景（CLI、回归测试）能直接构造参数表；**参数表就是分析记录里要存的东西**。

## 五、理论边界与失效条件

沿用 P87 理论文档确立的方法论：**「X 必然成立」必须分清是「当前实现的事实」还是「结构性的保证」**。前者会随新需求失效，不能拿来当设计前提。

| 结论 | 性质 | 失效条件 |
|---|---|---|
| 权重不进配置身份是自洽的 | **当前事实** | 出现消费加权 GDR 的策略。用户 2026-10-07 裁决**无条件纳入哈希**，正是为了不让身份随这个事实漂移 |
| 分析记录可变是安全的 | 结构保证 | 前提是**没有东西引用它**。若将来出现「基于上次分析再分析」，本层要重新论证 |
| 密存 + 缺键回退足以复现历史分析 | 结构保证 | 前提是**参数的语义不变**。若某个参数改了含义而不改名，历史记录会静默算错。纪律：**改语义必须换键名**（与 P87 §3.11 H 同一条） |
| 分析记录不进树 | 结构保证 | 前提是分析之间无派生关系（用户已裁决所有分析平级） |

**做法**：把「当前事实」固化为**可失效断言**（测试）。前提被破坏时测试变红，而不是静默出错。
