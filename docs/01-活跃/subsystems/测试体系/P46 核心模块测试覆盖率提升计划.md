# P46 核心模块测试覆盖率提升计划（实施版）

> 日期：2026-06-13 | 状态：实施中
> 触发：用户发起测试覆盖率提高专题计划——现状调查、可行性及经济性报告

## 一、问题

### 1.1 总体覆盖不足

当前总体测试覆盖率 **29%**（16,934 语句，11,994 未覆盖），`core/` 层加权覆盖率 **55%**。425 个测试用例，耗时 4.2 秒。

### 1.2 风险集中在高价值模块

55% 的 core 层平均覆盖率掩盖了严重的内部分化——简单的工具文件（`bootstrap.py` 93%、`config_store.py` 98%）拉高了均值，而真正复杂的计算模块覆盖惨淡：

| 文件 | 覆盖 | 对应 P0 阻塞项 |
|------|------|---------------|
| `comparison_analyzer.py` | 20% | P19 策略比较重构（本周聚焦） |
| `worst_impact.py` | 22% | P31 最差影响缺陷 |
| `retreat_search.py` | 29% | P26 方案搜索改进 |
| `gdr.py` | 43% | P28 每池GDR严谨性 |
| `strategy.py` | 49% | 所有 P0 的依赖基础 |

### 1.3 修改 P0 模块时没有安全网

当前修改 `worst_impact.py`、`retreat_search.py` 等 P0 模块时，无法通过测试套件快速验证"改动没有悄悄破坏其他行为"。每次修改依赖人工审查，效率低且不可靠。

### 1.4 GUI 层难以测试（已评估，不纳入范围）

GUI 层（11 个面板文件，占 41% 代码量）因 PyQt6 技术特性（需 QApplication 实例、依赖显示服务、信号/槽异步）几乎无法做有意义的单元测试。**业界共识：GUI 层不做单元测试，将业务逻辑抽取到可测的 core 层。**

### 2.3 软性标准

- 每个公开函数至少一个 happy path 用例

## 三、方案

### 3.1 总体策略

渐进式覆盖，按"谁依赖谁"排序——先测被依赖的基础模块，再测上层 P0 模块。测试模式对齐现有风格：简洁 pytest，工厂函数，AAA，几乎不用 mock。

### 3.2 文件组织

```
tests/core/
├── test_strategy.py              ← 扩展（46行 → ~400行）
├── test_gdr.py                   ← 扩展（已有51用例 → ~100用例）
├── test_comparison_analyzer.py   ← 新建
├── test_worst_impact.py          ← 扩展（146行 → ~600行）
├── test_retreat_search.py        ← 扩展（181行 → ~500行）
├── test_resource_gain.py         ← 扩展
└── test_streaming.py             ← 新建
```

---

### 3.3 执行约定

**Git 规范：**
- 每个模块完成后单独 commit，格式 `test: {模块名} 覆盖率 {X}%→{Y}% (+N用例)`
- 示例：`test: strategy 覆盖率 49%→73% (+47用例)`
- 禁止将多个模块的测试混在一个 commit

**覆盖率验证：**
- 每完成一个步骤，运行 `pytest tests/core/test_{module}.py --cov=gacha_simulator.core.{module} --cov-report=term -q` 验证增量
- 每完成一个 Phase，运行全量 `pytest --cov=gacha_simulator.core --cov-report=term -q` 确认无回归

**进度追踪：**
- `git log --oneline --grep="test:"` 即为天然进度日志
- 每完成一个模块，在 `05-笔记.md` 追加一条（H4 hook 自动触发 + 手动补充覆盖率数字）

**执行顺序：**
- Phase 内步骤按 S1→S9 顺序执行——后续步骤可能依赖前面构造的 fixture
- Phase 1 必须先完成才能开始 Phase 2（strategy/gdr 是所有 P0 模块的依赖）
- Phase 2 三个模块互不依赖，可并行推进
- Phase 3 两个模块互不依赖，可并行推进

**阻塞处理：**
- 遇不可测代码 → 跳过该子路径，在测试文件中加 `# TODO(skip): {原因}`，在 commit message 中标注
- 遇源文件 bug → 修复 + 单独 commit `fix:` + 回归锚点测试，不混在覆盖率 commit 中
- 遇依赖过深（如 WorstImpactAnalyzer 需完整 ConfigStore）→ 优先测试纯函数方法，外部依赖用最小 mock

**禁止事项：**
- 禁止修改 `core/` 源文件结构——只加测试，不改源码（修 bug 除外）
- 禁止为了覆盖率而重构——"这个函数拆出来更好测"不在此计划内
- 禁止引入新依赖（freezegun、hypothesis 等）——保持测试栈简洁

## 五、风险

| 风险 | 缓解 |
|------|------|
| 代码不可测——逻辑深度耦合、缺少接口 | 跳过不可测路径，标记 `# TODO(skip): 原因`，不阻塞进度 |
| 测试写得过于脆弱——过度 mock 或对实现细节敏感 | 测试只断言公开 API 行为。采用"给定输入→断言输出"的黑盒风格 |
| 覆盖率数字驱动——为了数字而写无价值测试 | 软性标准（公开函数覆盖、边界条件、回归锚点）优先于数字 |
| GUI 抽取逻辑的诱惑——分心去重构 | 严格不改源文件结构。发现可抽取逻辑时记录但不在此计划执行 |
| 时间超预期——某模块复杂性被低估 | 每 Phase +1 周浮动。7 模块中允许 1-2 个不达标，只要 core/ 总体达标 |
| `WorstImpactAnalyzer` 依赖大量外部对象 | 优先测试纯函数（`analyze_batch_results`、`_compute_pity_coverage`），对依赖 `ConfigStore` 的方法用 mock |
| `streaming.py` 多进程路径复杂 | 优先测试单进程路径。多进程部分用 `multiprocessing` 测试技巧或标记为集成测试 |
| scipy 惰性导入在测试环境可能失败 | `comparison_analyzer.py` 的 DD Bootstrap 测试用 `pytest.importorskip('scipy')` |
