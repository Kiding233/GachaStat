# refcheck

把仓库里现存的「文档引用代码」的行号型引用找出来、解析、分类，产出一份存量盘点与一份可复现的抽查稿。
纯读，零写入，零第三方依赖（Python 3.10+；3.11 以下无 `tomllib`，配置不生效但工具仍可跑）。

**它不是漂移检测器。** 漂移需要「记忆」才能存在，而记忆由迁移写入；盘点阶段还没有记忆可比。
它也不判定「锚点指对了没有」，理由见下面「它做不到什么」。

## 用法

```
python tools/refcheck/refcheck.py scan   --root .                  # 人读报告
python tools/refcheck/refcheck.py scan   --root . --format json    # 机器读
python tools/refcheck/refcheck.py sample --root . --n 24 --detail  # 抽查稿
```

## 搬到别的仓库要做什么

1. **复制 `tools/refcheck/` 整个目录。** 工具本体不含任何单个项目的专有知识
   （不认 `03-归档`、不认任何包名），项目知识全部在 `refcheck.toml` 里。
2. **把 `refcheck.toml` 整份重写。** 这一点最容易漏：配置随目录一起被复制走，
   而带错了配置的症状并不明显。工具每次运行都会打印**实际使用的配置文件路径**，
   核对那一行。五项要定：
   - `[scope].include`：去哪里**找**引用（通常只要 `.md` 与 `.py`）
   - `[scope].exclude`：归档、回收站、本工具自身。**归档必须排除**：归档记录的是
     写入当时的事实，它的行号本就应冻结，报出来的失效是对的
   - `[resolve].external`：声明为仓库之外的路径前缀（标准库、`site-packages` 等）
   - `[resolve.alias]`：同名文件消歧。**只在逐条看过引用上下文之后再填。**
     填错的别名会把「可见的歧义」变成「不可见的已解析」，比留空更糟
   - `[checks].deleted_cue`：本仓库里「某符号已删/已作废」的措辞线索。漏填是
     **静默的**：豁免变少、误报变多，而症状看起来像「工具更严了」，不会引起注意
3. 跑 `scan`，看 `file_not_found` 与 `ambiguous` 两档。前者是引用失效，后者是要你裁决。
4. `sample` 出一份抽查稿，交给**独立于工具作者的人**核对（理由见下）。

## 它做不到什么（先读这一段，再决定要不要用）

**「解析成功」不等于「指对了」。** 文件级解析只保证目标文件存在、行号落在文件内，
而文档完全可能把锚点指到同一文件的另一处。实测在标为「解析干净」的引用里，
**约三到四成锚点指向错误位置**（两轮独立审查：32% 与 38%），而加了确定性判据之后，
这些硬错绝大多数仍未被命中。它们的形态是「被引代码在锚点附近整体移动过」「文档引的是
使用处而符号定义在别处」「文档描述的那段分支已被重写」，都要读语义才能判断。

所以两层结论的分工是：

| 层 | 字段 | 含义 | 能不能当结论 |
|---|---|---|---|
| 门控 | `checks` | 高精度判据命中，故 `no_deterministic_issue` 为假 | **不能**当「其余都可信」 |
| 队列 | `queues` | 低精度判据命中，只影响排序 | 是分流器，不是判据 |
| 字段 | `no_deterministic_issue` | 只表示**确定性层面没发现问题** | **不等于锚点指对了** |

字段名刻意不叫 `in_baseline`：那个名字容易被下游读成「可信」或「已核对」。实测基线内锚点硬错率约 **38%**（50 条样本，95% 置信区间 25% 至 52%）。

**因此迁移要按「语义重锚」设计，不能按「机械搬运现状锚点」设计。** 把现状锚点原样
冻进记忆，等于把错误锚点变成永久稳定的记忆：锚在注释或空行上时，那行永不改动，
指纹也永不变，于是那条错引用会一直显示为「未漂移」，比报错更糟。
正确做法是迁移时对每条引用确认正确范围（这一步必须读语义），标记围住**确认过的**范围。

## 两处按语言定死的常量

工具核心不含项目知识，但有两处**按文字系统定死**，换语料前要改：

- `SENT_BREAK`（分句符）收的是 `。！？；;` 与换行，**不含英文句号**（`.` 同时是
  路径分隔符，收进来会把 `pity.py:100` 拆断）。英文语料上分句会退化成整行，
  队列判据的行为随之改变。
- `RIGHT_WINDOW = 12` 是**字符数**，其有效宽度随文字系统变化：中文 12 字符能跨过
  一个完整分句，换成英文同样位置可能要 20 多字符。实测有两条恰好卡在 12 上（改成 11 有两条引用改变行为，改成 13 则无差异，即确实卡在边界）。

这两处没有做成配置项，是因为本项目自己有一条纪律「一个有界的例外清单优于 N 个
开关」。判断是：**换语料时改这两个常量，比让每个仓库都面对两个额外的旋钮更省。**

## 已知覆盖缺口

无文件名的行号引用（`` `L3899` ``、`` `:609` `` 一类，指称对象靠上下文确定）**不识别**，
实测某个约 280 条存量的仓库里有约 65 处、11 个文件。解析规则未定：指称对象有的靠同句
最近提到的文件名、有的靠上文表格列隐含、有的干脆指另一份文档。**规则定错会造出一批
看起来已解析的错引用，比留空更糟**，所以宁可先不实现。

## 踩过的坑（都在这份代码里）

- **`git ls-files` 必须带 `-z`。** 不带时 git 对含非 ASCII 的路径做八进制转义并整体加引号，
  返回的字符串既匹配不上 glob 也打不开文件，症状是这些文件被静默跳过（实测引用数从 341 掉到 18）。
- **扫描集 ≠ 解析集。** 「去哪里找引用」与「哪些文件算合法目标」是两件事。混同的后果是
  引用了非扫描扩展名（如 `pyproject.toml`）的引用被误判成「范围之外」。
- **产出物会污染语料。** 抽查稿本身就在被扫描的目录里，会把自己写进去的引用算成存量，
  于是「为检查而生成的工件」反过来改变了被检查的对象。产出物在**文件头 8 行内**写
  `<!-- refcheck:generated ... -->`，扫描时按它整份剔除。
- **以引用机制为题材的正文也会。** 讨论这个工具的文字里含示例路径，会被当成真引用，
  而整份剔除挡不住（它是正文，不是产出物）。单个示例按行写
  `<!-- refcheck:example -->`，工具跳过那一行。实测某计划文档自身有 15 条这样的示例引用。
  两个标记都要求**完整的 HTML 注释形态**，且是**精确字面量匹配**（不是 HTML 注释感知）：
  只认那几个字的话，一段解释这个标记的正文就会把自己整行（或整份文档）静默移出扫描；
  反过来，写成 `<!--refcheck:example-->`（缺内空格）或大小写不一致会**静默失效**，
  标注者会以为标了其实没标。
- **语料是活的。** 每次编辑都在改变被扫描的存量（实测同一份文档编辑过程中引用计数从 277 走到 280），
  抽查稿因此会在头部记 `HEAD` 与语料规模。任何引用计数都必须与测量时刻一起引用。
- **链接文字与链接目标会重复计数。** `[pity.py:1233](pity.py#L1233)` 会被识别成两条。
  现按「源文件 + 行 + 解析目标 + 写的行号范围」去重，保留链接那一半。
- **别名不能改写限定路径。** 只写 basename 的引用才需要裁决；限定路径自带消歧信息，
  拿它去套别名会把「文件本就在别处」的错引用悄悄改写成另一个文件的正确路径。
- **`--format json` 输出纯 ASCII。** 非 UTF-8 终端下 `ensure_ascii=False` 会抛
  `UnicodeEncodeError`，而失败模式很坏：重定向文件里留下半截 JSON。

## 给 agent 用的提示词要点

如果要把这套方法交给别的 agent 或别的仓库，提示词里有三条不能省：

1. **不要让它把 `no_deterministic_issue` 当成「正确」**。要明确写「这只表示确定性层面没发现问题」，
   否则它会跳过语义核对直接机械写入，把错锚点冻进记忆。
2. **要求它先跑 `scan` 再动手**，并按 `checks` / `queues` 分流：门控命中的先排除，
   队列命中的先处理，其余批量过。
3. **要求独立核对**。盘点结果由工具作者自己抽查就是橡皮图章（本项目 CLAUDE.md 的独立审查原则）；
   抽查要**覆盖全类**，不能取前 N 条（实测取「被标记者列表前 18 条」全部来自同一张表，
   把最大的误报来源整类漏掉，得到 17/18 的假精度，全量核对是 26/48）。
