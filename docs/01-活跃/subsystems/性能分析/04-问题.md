## P0 — 阻塞性缺陷

### 三份测量脚本无规模护栏，修复后即可 OOM 本机

- **来源**：2026-09-22 实施 `2a` 时发现
- **状态**：**已处置**（2026-09-28，提交 `fc2e2db`）——新增平台侧的 `plan.scale_issue()`
  （内部仍走 `Plan.validate()`，**阈值不另立一份**），两份脚本共用并补上 `-n` / `-w`，
  越界即拒绝运行、原样重放平台给的成因。实测 `-w 16` 被拒（「可用 4.70 GB 低于下限
  12.00 GB」），`-w 2` 正常跑。**残留**：三份脚本仍可直接被人工运行，护栏只在它们
  自己调 `scale_issue` 之后生效——本处置把「一跑就真跑」变成「越界就报错」，不是
  「无法运行」。
- **事实**：`scripts/profile_sim.py` 原硬写 `N, workers = 1000, min(16, (os.cpu_count() or 8) - 2)`——**上限 16**，故本机 22 核得 16 个 worker（**2026-09-28 订正**：本段原写「22 核即 20 个 worker、需 15.0 GB」，与代码里的 `min(16, …)` 不符；正确值是 16 个 worker → `16 × 0.75 = 12.0 GB`）。实测可用内存长期在 1.4–5 GB 之间波动。
- **为何是 P0 而不是「已知风险」**：`2a` 修复的是**属性名与关键字**——修好之后这个脚本**从「一跑就崩」变成「一跑就真跑」**，即它此前失效反而构成了一道无意的保护。修复使它可执行，风险随之**由潜伏变为现实**。
- **同型**：`profile_simulation.py` 同构；任何直接调 `run_batch_parallel` 而不经 `Plan.validate()` 的调用点同理（`benchmarks/` 侧无此问题——那是 `Plan` 的构造期拒绝面）。
- **当时不处置的理由（阶段 2 期间，现已不适用）**：§6.0 阶段 2 的边界明写「本阶段只修复与吸收，**不新增任何驱动逻辑**」，护栏属新增逻辑，超出该阶段授权。故当时只登记；收口阶段才按下面的待裁项①处置。
- **处置结果（2026-09-28，采纳当时的待裁项①）**：新增 `plan.scale_issue()`（内部仍走 `Plan.validate()`，**阈值只此一处**），两份脚本共用并补 `-n` / `-w`，越界即中止。「必须显式传参」（②）与「降级为薄包装」（③）未采纳：前者让脚本在内存充足的机器上也必须手填规模，后者改动面大于本问题所需。
- **处置期的两处返工（都是我自己的漏洞，独立审查 2026-09-28 指出）**：① `profile_gui.py` 起初申报 `path='gui-qt'`——规则 5 对 gui-qt 一律按 `workers=1` 计，于是在 16 个 worker 的批量模拟上算出的下限只有 2.5 GB、**照样放行**，与 P0 要防的形态正相反；已改申报 `path='cli'`（吃内存的是那些 worker）。② 两份脚本的安检起初都在**读完配置之后**才执行，`profile_gui.py` 更是晚到 **Phase A 建完 `MainWindow`（含 10 个 ChartWebView 与 Chromium）之后**——安检必须在昂贵动作之前；已把两处的 `_parse_scale()` 提到各自的**第一步**，实测 `-w 16` 现在在任何界面动作之前就被拒。

### 启动冷子进程被 `-X importtime` 的 stderr 堵死（已修，2026-09-22）

- **来源**：实施 `3f-1` 时实测踩到
- **状态**：**已处置**（改为重定向到文件，见 `perf/adapters/gui_qt.py` 的 `_launch_startup_child`）
- **现象**：`subject='startup'` 的测量在硬超时 60s 处失败，报「已取到的时刻：['rss_peak_mb', 'spawn_at', 'stderr']」——即**窗口从未被判定为可见**。而同一命令去掉 `-X importtime` 后，14s 就出现了可见窗口。
- **成因**：子进程的 stderr 接到 `subprocess.PIPE`，整段观测期间无人读。`-X importtime` 给每个被导入的模块打一行，GUI 栈上千个模块的输出量超过管道缓冲区，于是**子进程阻塞在自己的 `write` 上**，永远走不到创建窗口那一步。
- **为何值得登记**：症状（超时）与成因（管道容量）相距极远，而失败信息里没有任何线索指向 stderr。`_drain_stderr` 原本只在观测**之后**读，恰好是最晚的时刻。
- **处置要点**：① stderr 重定向到临时文件（写侧永不阻塞，父进程观测期间一行都不用读）；② 顺带修好可诊断性——`AdapterError` 现在会带上子进程 stderr 的末 8 行，启动失败的第一现场自此在错误信息里可见。
- **同型风险**：任何「子进程 + PIPE + 长输出 + 父进程先干别的」的组合都有这个形状。本库另有两处：`cli.py` 的 `_spawn`（它**当场** `communicate()`，故不中招）与 `_observe_startup` 之外无第三处。

### `-X importtime` 会抬高启动读数，基线须记口径（2026-09-22 登记）

- **来源**：实施 `3f-1` 时实测
- **状态**：**未处置**（口径已写明，未改采集方式）
- **事实**：整条冷子进程都在 `-X importtime` 下跑（第 2 / 4 段的取法要求如此），而 importtime 会给每次导入加一层钩子。实测同机同条件：不带 importtime 时约 11.7s 出窗口，带 importtime 时约 14.9s 完成启动。
- **为何不算缺陷**：§3.11 的采集方式表本就规定第 2 / 4 段走 `-X importtime`；预热与测量两次**同条件**，故基线与回归比值口径一致，可用于「变慢了没有」。**受影响的只是绝对读数的解释**：这个数**不是**「用户感知的启动时间」。
- **待裁项**：若要一个贴近用户感知的绝对值，须另起一次**不带** `-X importtime` 的冷启动（代价是第 2 / 4 段不可得），并把两种口径分成两条 plan，不得混进同一份基线。

### 启动打点的 `QTimer` 因无父对象被 gc 回收，段 8 静默永不出现（已修，2026-09-22）

- **来源**：实施 `3f-2` 时实测踩到
- **状态**：**已处置**（`QTimer(window)`，交给 Qt 持有）
- **现象**：段 8「图表可用」永不出现，父进程等满 20s 宽限后按「该段未采集」收口。**表面上没有任何错误**——回传文件的其余字段都正常，只是缺 `charts_ready`。
- **成因**：定时器与回调之间只有一条「`state` ← `_tick` 的闭包 ← 信号连接 ← `timer` ← `state`」的**环**，没有外部根可达，Python 的 gc 可以整个回收掉它。回收后不再有 tick，`charts_ready()` 也就永远没被问到。
- **为何值得登记**：这是「无报错的功能消失」——诊断成本全在「为什么没发生」上。同型风险是任何「在局部作用域里建 Qt 对象、只靠闭包保活」的写法。
- **旁证**：另一处**不是**缺陷的观察是「所有 `ChartWebView` 一直不就绪」——那是我第一次诊断时用 `processEvents()` + `sleep` 驱动所致；换成真正的 `app.exec()` 后 1.5s 内 10 个全部就绪。**WebEngine 的加载要真事件循环**，这条对将来手工验证该段的人有用。

- **事实**：§3.13 把 `1j` 的参数定死为 `n=1000, workers=4`，实测单次墙钟 **14.2s**；`repeats=3` 的预估 42.7s > §3.5 的 30s 阈值 → 自动降为 1 次 → `register_baseline` 按「建基线须 `repeats >= 3`」拒绝。而 §3.13 要求 `sleep_ctl` 由**先建好的基线**反解，实验因此无从开始。
- **影响面大于 `1j`**：原值把「可建基线的单次墙钟」压到 10s 以下，而平台自己定死的头号配置 `n=1000` 单次就 14.2s——**平台无法为自己的头号配置建任何基线**。
- **处置与残留**：阈值改为 60.0（含义是「一次测量最多花一分钟」，`n` 填错那类分钟到小时的风险照样挡住）。**残留未处置**：比本机慢一倍的机器上 `n=1000` 单次仍可能超 20s，届时依旧建不了基线；通用解是「预算由调用方给」（`Plan` 加字段），属 `1b` 的改动面。已写入 `base.py` 的常量注释。
- **为何值得登记**：这是一处**算术上必然发生**的计划内部冲突（两条数值各自都合理，凑在一起互斥），只有真去跑才暴露。

### 阶段计时取「首次运行」的产出，而三段计时并非零噪声（2026-09-22 登记）

- **来源**：准备 `1j` 判据 2（定向性）时发现
- **状态**：**未处置**（已影响 `1j` 结果的读法，见下）
- **事实**：`_measure` 的注释与 §3.5 都写「阶段分解与资源计数取**首次**运行的产出——它们是确定性量、零噪声，重复测量只为压墙钟噪声」。这句话对 `packet_bytes` 成立（同配置同种子下完全确定），但**对 `pool_start` / `simulate` / `extract` 三段不成立**——它们是墙钟量，噪声不小。实测 `simulate` 单次 12.3s，同配置连跑两次可差数百毫秒。
- **实际后果**：`repeats=3` 只把**总墙钟**压成中位数，三段计时仍是**单次采样**。故 §3.13 判据 2 的 `[0.9, 1.1]` 比值带作用在单次采样的段值上，比它看起来的要严——`pool_start` 实测 1.2s 量级，±10% 就是 ±120ms，而进程池启动本身的抖动可能就超过它。
- **待裁项**：① 阶段计时也取各次重复的中位数（须先把三段存进 `SingleRun` 而非只留首次，属 `1e-1` 的改动面）；② 或判据 2 对三段改用绝对差判据（同它对短段的处理）；③ 或接受现状，但报告须注明「段值是单次采样、`repeats` 只压总墙钟」。**本项不自行选**——它改的是 §3.5 的归一政策或 §3.13 的判据，属计划级改动。

### `cli` 适配器从不传 `--profile-*`，`function` 档静默失效（已修，2026-09-23）

- **来源**：为 `1j` 量砝码重量时撞到（先用 cli 路径取剖面，得到 0 个函数）
- **状态**：**已处置**（`CliAdapter.build_argv` 补传三个开关；并补上 §3.9 T4 要求而缺失的那条断言）
- **事实**：被测 CLI **有** `--profile-dir` / `--profile-skip` / `--profile-count`（`1e-2` 交付，`cli.py:177-183`），`--perf-json` **也**会把 `functions` / `run_id` 回传（AUDIT-BREAK-3 定死的载荷字段），但 `CliAdapter.build_argv` **从不传这三个开关**——链的两端都通，中间没人接线。
- **实际后果**：`cli` 路径上 `plan.profile_enabled=True` 被静默忽略，`RunResult.functions` 恒为 `None`，而**报告里只有一条把读者指向 stderr 的告警**（「被测进程的 stderr 里有具体成因」）——stderr 里什么都没有，因为参数压根没传。这与 §3.13 要防的「报告说谎」同型。
- **为何值得登记**：`cli` 是 §3.8 D1 **指定的 `function` 档主路径**。而 §3.9 T4 原文早就写了这条断言：「断言 `cli` 适配器产出的 `RunResult.functions` 非 `None`……**不测这一条则该链「在两端各自成立、中间断开」时无人发现**」——**这句话精确描述了这个缺陷，而那条断言在 `6g` 里没有落地**。计划预见到了断裂的形状却没配上守卫，这是「硬规则没有测试就只是文档」的第 8 次复发。
- **处置**：① `build_argv` 在 `plan.profile_enabled` 时补传三个开关；② 告警按成因拆成两句（「没传 `--profile-dir`，剖析实际没启动」与 D7 的「剖析故障，成因在 stderr」）——混成一句会把读者指向空处；③ 补上那条缺失的断言（`TestCliFunctionGrainClosure`），实测已能经 `--perf-json` 取回函数统计。

### `1j` 的判据 2 对 0.1-0.5s 量级的段过严（**已处置**，2026-09-28 改为逐段底噪尺子）

- **来源**：`1j` 复跑（改协议 + 加批内底噪尺子之后）
- **状态**：**已处置**（2026-09-28，按 §3.13 的阈值修订条款：判据 2 改为「与该段同批实测的噪声包络比，带子 = `max(0.10, 包络)`」，原 ±10% 降为下限；计划正文已同步，原值与理由记在 §3.13 的修订说明里）
- **处置后的实测**：三轮跑「同条件两次 + 注入一次」，各段包络 `env_build` 18.5% / `pool_start` 10.1% / `extract` 3.4% / `config_load` 2.9%——**固定 ±10% 的形状确实是错的**（差一个量级）。四段全部落在各自带内，目标段效应 1.318，门控 PASS
- **残留（未处置）**：包络由 3 轮估出，基础薄；`extract` 在上一次同类测量里报过 0.868（偏离 13.2%），远超本次同段包络 3.4%，**它的尾比 3 个样本显示的更肥**。提高轮数才能估厚包络
- **事实**：判据 2 的带是**固定** `[0.9, 1.1]`。复跑中 `extract` 报出 **0.868** 越界——而它与注入点**没有因果关系**（注入在模拟热路径 `pool.output`，`extract` 是父进程侧的提取合并），方向还是**向下**（注入臂更快），只能是噪声。`extract` 约 0.2s：比 50ms 的短段门槛大、故吃比值带，但绝对量仍小，**它的逐次相对波动大于 ±10%**。
- **三次阻塞，三次不同成因**：这条判据在 `1j` 上前后挡了三次——① 单次采样的段值（平台的归一取「首次运行」的产出）；② 前后对照把漂移记进去；③ 改成交错之后，剩下的是**该段自身的方差**与**固定带宽**不匹配。
- **为何不得改宽到通过为止**：那是自造假 PASS。**正确做法是把底噪尺子 per-segment 化**——本次只对目标段做了（阶梯里的空档档），其余段仍是写死的 ±10%。逐段批内测一份空档分布，用它定该段的带，带宽就随段长自适应。
- **待裁项**：① 判据 2 改为「每段与同批空档分布比」（需扩展阶梯的落点记录）；② 或按段长分档设阈（<0.1s 绝对差、0.1-1s 相对带放宽并记录原值、>1s 保持 ±10%）；③ 或提高小段的 `repeats` 压方差。三者都要改 §3.13 的判据，属计划级改动。

### `Pool.output` @property 已确认是热区

- **来源**：2026-09-17 py-spy 采样（线索）→ **2026-09-18 cProfile 确定性复核（已确认）**
- **状态**：**已确认**，优化本身属 P12 范畴，不在本平台范围
- **确定性证据**（真实 `_wk_init` / `_wk_run_single` 构造 Pool，N=30，W=2，cProfile 合并后 167 个函数条目）：

| 函数 | 调用次数 | 自耗时占比 |
|---|---:|---:|
| `output` | **498,684** | 9.1% |
| `run_simulation` | 30 | 8.1% |
| `dict.get` | 2,030,911 | 7.0% |
| `is_exchange` | 498,204 | 4.7% |
| `_get_needed_card_exchange` | 16,874 | 4.7% |

- **附带**：`is_exchange`（4.7%）同样调用 `self.output`，两者合计构成一条「每次访问都重算静态事实」的热路径
- **处置**：本平台只负责把它测出来；优化（缓存或预计算）属 P12 范畴
