## ✅ 已完成：缺陷 12：卡级还原段跳过 SR / R 的缩放（高，2026-10-09 实测确认并修复）

- **来源**：独立会话的代码审查（2026-10-09 提出），本文件所在会话**实测复核确认**（走真代码路径，非重写逻辑）
- **严重度**：**高**。它不报错、不崩溃，只让软保底的效果被静默打折；**真实 `config.toml` 的唯一保底 `ssr_soft` 即受影响**（爬升末端实际出率约为意图的一半）
- **位置**（行号为修复前；修复在 `pool.py:241-248` 插入 8 行，其后的锚点已整体下移）：
  - `core/pool.py:234` `infer_rarity_from_spec()`——**修复前只认 SSR**（判 `pity_spec.ssr_ids` / `featured_ids` 两个集合），SR / R 一律 `return None`；修后先按 `scope_cards` 反查
  - `core/banner.py:240-247` 的 `scale_factors` 还原段——非 featured 分支写 `rarity = infer_rarity_from_spec(...)`；`slot = rarity.lower() if rarity else None`
  - `core/pool.py:214` `draw()` 的 `_use_adjusted` 分支按 `random() * self._adjusted_total_weight` 采样（`_apply_probabilities` **不做归一化**，直接以原样和作总权重）
- **机制**（四步）：
  1. `aggregate_probs_by_rarity` 用 `rarity_cache`（来自 `pity_spec.scope_cards`，**含全部稀有度**）得到槽位级分布，`infer_rarity_from_spec` 只是它的兜底分支，故**聚合侧是正确的**
  2. `before_draw` 在槽位级把质量从 SR / R 槽搬到限定卡槽，输出仍配平（Σ = 1）
  3. 还原段算 `scale_factors = {slot: new/old}`，其中 `sr` / `r` 的因子确实 < 1
  4. 但还原段**用 `infer_rarity_from_spec` 反查每张卡的槽位**，SR / R 卡得到 `None` → `if slot and slot in scale_factors` 为假 → **缩放被跳过**，SR / R 保留原概率
- **后果（不是「完全无效」，是「部分施加」）**：喂给 `draw()` 的卡级字典 Σ > 1，采样时全部卡按 `1/Σ` 稀释，故保底效果被**打折**而非消失。稀释幅度取决于 `p(SR+R)`，本池该值 ≈ 0.996，故打折很重
- **实测（真实 `config.toml` 的 `ssr_soft`：`soft_interval`，scope=ssr，`target_featured=true`，start=80 / end=90）**：

| 抽次 | 意图 SSR（槽位级 adjusted 之和） | 实际抽样 SSR（卡级字典 ÷ Σ） | 喂给 `draw()` 的 Σ |
|---|---|---|---|
| 第 80 抽 | 0.094727 | 0.086822 | 1.090727 |
| 第 85 抽 | 0.548362 | **0.3551** | 1.544361 |
| 第 90 抽 | **1.000000**（软保底应给满） | **0.5010** | 1.996000 |

  第 90 抽那行是本缺陷最刺眼的形态：配置意图是 100% SSR，实际只有 50.1%
- **复现**：`.recycle_bin/probe_real_config_soft.py`（真实配置，逐抽打印意图 / 实际 / Σ）与 `.recycle_bin/probe_scale_factors_bug.py`（最小构造 + 蒙特卡洛，20 万次实测与 1/Σ 预测吻合到 1e-3）
- **第二条潜在缺陷（同段，当前配置未触发）**：featured 分支写 `f'{infer_rarity_from_spec(rwd_id, pity_spec) or "ssr"}_featured'`——**非 SSR 的 featured 卡会落到 `'ssr_featured'`**，被按 SSR 限定槽的因子缩放。`compute_scope_mappings` 按卡**自身稀有度**建 `featured_cards` 键，故「SR 的 UP 卡」是合法配置形态；当前 `config.toml` 的 8 张 featured 卡全为 SSR，故不触发。属配置驱动，任何新增 SR/UP 池都会踩
- **测试覆盖缺口（已补）**：全库**原先无测试**覆盖 `aggregate_probs_by_rarity` / `scale_factors` 还原段（实测 `grep` 仅 `banner.py` / `pool.py` / `core/__init__.py` 引用该对符号），故该缺陷此前无验收面。2026-10-09 修复时同批补了 4 条（3 条单测 + 1 条端到端）
- **与 P64 的关系**：P64 §3.9.1 把该段列为「现状路径」（**未标注其有缺陷**），§3.9.3 的 ISSUE-504 决定 S8 时**删除** `infer_rarity_from_spec`（理由是卡级管道下其消费者全部消失）。**S8 会顺带消除本缺陷，但 S8 属 M2**，故本次提前修复
- **⚠ 一条必须记下的弯路（2026-10-09）**：最初提的「**最小修 = 还原段改用 `pity_spec.card_to_slot.get(rwd_id)`**」经实测**是错的**——该改法会打坏最差影响分析。`card_to_slot` 在常规路径确实是被替换槽位名的精确逆映射（真实配置覆盖 19/19），但在 `worst_impact` 路径上它的键是**原始** card id，而该路径的池内 id 是重命名后的 `_wi_featured_{i}`（`_build_pity_engine` 自己一处不一致：`scope_cards` / `card_to_slot` 建自 `self._featured_ids`，而 `featured_ids` / `ssr_ids` 在 `prepare_simulation_config` 传入 `all_featured_ids` 时用的是重命名 id），实测**覆盖 0/2**。按该改法，`_wi_featured_0` 查不到槽位 → 限定卡的缩放被静默跳过 → **最差影响分析丢掉保底调整**（今天反而是对的，走 `ssr_ids` 命中）。`worst_impact` 的这处 id 不对齐是 P64 ISSUE-006 已登记项，归其 S8-5 处置，本次不动

### 缺陷 11：多保底管道无优先级逻辑（中等）

- **来源**：全模块审查 §2.3 + P30 计划
- **严重度**：中等（实现局限，非代码错误）
- **位置**：`core/pity.py` 的 `_resolve_order()` / `_validate_behaviors()`
- **问题**：保底按定义顺序依次调整概率分布。当软保底和硬保底同时触发且目标集不同时，后处理的行为可能覆盖前者的调整。无冲突解决机制。
- **理论立场**：管道顺序语义是设计意图，允许配置者通过排列控制优先级。
- **原推荐方案**：
  1. 在 `pity.py` 模块 docstring 中说明管道顺序语义
  2. 在 `PityEngine.__init__()` 中增加冲突检测：若两个保底适用同一池且目标集部分重叠，发出 `warnings.warn()`
  3. 长期方向：支持显式 `priority` 字段（配置格式变更，需慎重）
- **处置结论**（P55/P56）：两道机制**只有冲突检测真正生效**。
  - **冲突检测：✅ 已生效**。`_validate_behaviors(behaviors)` 把原方案的 `warnings.warn()` 升级为**硬性 `ConfigError`**。四条规则：name 重名 → `ValueError`；同 scope 两个硬保底 / 同 scope 两个事件驱动型 / 同 scope 同 btype 两个软保底 → `ConfigError`。非法配置在 `PityEngine` 构造期即被拒绝，而非运行期告警
  - **顺序确定性：❌ 未接通**。`_resolve_order(behaviors, rarity_rank)` 确实存在、排序键也确为 `(稀有度 rank, btype 顺序, name)`，但其输出**只赋给 `self._behavior_list`**（`pity.py:1178`）。概率管道三个入口（`get_probabilities` / `before_draw` / `after_draw`）走的是 `get_behaviors_for_pool()` → `for pname in spec.pity_names`（`pity.py:1195`，定义于 `:1189`），而 `spec.pity_names` 由 `batch_simulator.py:173-177` 按 **TOML 定义顺序**逐个 append 生成。`_behavior_list` 的消费点只有 `_rebind_state` 重绑定（`pity.py:1247`），与顺序无关。**缺陷原文「顺序由定义顺序决定」在代码上仍然成立**
  - **未实施**：显式 `priority` 字段与「取最高概率」方案均未实施
- **2026-09-15 复核补充**：「互斥校验已强制 → 覆盖场景不可能发生」这一推论**过强**。四条校验只禁「同 scope 两个硬保底」「同 scope 两个事件驱动型」「同 scope 同 btype 两个软保底」三类；同 scope 的**「一软一硬」是合法配置**，而该场景下覆盖确实发生：`SoftStepBehavior._compute_probabilities` 重分配概率后，`HardPityBehavior._compute_probabilities` 触发时以 `result = {k: 0.0 for k in ctx.current}` 重建分布，软保底的调整被整体覆盖。跨稀有度场景由排序键的稀有度优先级保护，同 scope 内的覆盖未被防住
- **2026-09-18 补充（敏感集合修正）**：P64 §3.1.5.4 的反例实测显示，**`target_featured=True` 的 soft 与 hard 共存**时顺序敏感（12 抽对比中第 8–12 抽不同，第 8 抽 `[soft,hard]` 得 `ssr:0.5/ssr_featured:0.5`、`[hard,soft]` 得 `ssr:0.2/ssr_featured:0.8`），故敏感集合应表述为「含 `rotating_cr`，或 `target_featured=True` 的 soft 与 hard 共存」，而非仅后者含 `rotating_cr`
- **当前状态**：⚠️ **部分解决**。P30 已于 2026-09-14 归档；顺序问题整体由 P64 承接，**2026-09-18 已裁决为「接线」**（让排序生效，`priority` 保留为覆盖手段，见 P64 §1.5）
- **派生待办**：`_resolve_order()` 未接通概率管道是一个真实的功能缺口（可能有意留待后续，也可能是遗漏），需单独立项判定——**该项已由 P64 §1.5 的三项待裁决承接**
