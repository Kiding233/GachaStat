## P1 — 高优先级缺陷

### P1-01：条件分布 → 新模拟的逻辑跳跃（缺陷 27）

- **来源**：P31 第 2.1 节
- **严重度**：中等（方向性偏差——高估连续成功池数）
- **现状**：从清空历史的新模拟比真实失败场景更有利（保底归零、兑换完整）
- **偏差估计**：可能高估连续成功池数 1-3 个
- **计划方案**：短期 UI 警告标注 → 中期条件保底计数器初始化 → 长期接续模拟框架
- **状态**：设计中，未实施

### P1-02：虚拟池同质化假设（缺陷 22 / 28）

- **来源**：P31 第 2.2 节
- **严重度**：中等（系统性建模偏差）
- **现状**：99 个虚拟池共享相同成本/概率/持续时间，消除「高成本池连续」失败模式
- **计划方案**：阶段 1 UI 标注 + 敏感度滑块 → 阶段 2 可配置池参数序列 → 阶段 3 历史数据拟合
- **状态**：设计中，未实施

### P1-03：MAX_POOLS=99 硬截断（缺陷 21）

- **来源**：P31 第 2.3 节
- **严重度**：中等（高储蓄玩家 expected_pools 低估）
- **现状**：成功次数分布在 K=99 处截断
- **计划方案**：动态上限 + 截断检测警告
- **状态**：设计中，未实施（P14 时曾搁置，P17 后需重新评估）

## P2 — 低优先级改进

### P2-01：无资源收入假设（缺陷 23）

- **来源**：P31 第 2.4 节
- **严重度**：低等（保守下界，对「最差影响」是合理默认）
- **现状**：`resource_gain=None`，绝对连续成功池数被低估
- **计划方案**：UI 标注说明假设，不改变默认行为
- **状态**：设计中，未实施

### P2-02：自定义资源模式下无验证

- **来源**：代码审查
- **严重度**：低等
- **现状**：用户在「自定义初始资源」输入框输入任意数值，无范围/合理性检查
- **建议**：添加输入验证（如非负数、合理上限）

### P2-03：单线程嵌套模拟性能

- **来源**：代码审查
- **严重度**：低等（UX 问题，非正确性问题）
- **现状**：虚拟池模拟在面板后台线程中 max_workers=1，1000 次 × 99 池可能耗时数分钟
- **建议**：考虑多进程并行（需解决嵌套 Pool 问题）或增量结果更新（每 100 次刷新一次中间图表）

## 已完成的修复

### P17：最差影响保底匹配修复

- **状态**：**已完成**
- **修复内容**：虚拟池 ID 与保底规则的通配符匹配静默失败问题——`fnmatch.fnmatch(pid, pdef.pools)` 现在正确匹配 `*` 模式
- **影响**：修复后保底正确触发，连续成功池数可能显著增加，放大了 P1-03（MAX_POOLS 截断）和 P1-01（逻辑跳跃）的影响

> **⚠ 2026-10-09 订正：「保底正确触发」这一条当时并不成立。** 实测（真实 `config.toml`，虚拟池连抽 200 次）`before_draw` 改动分布的次数为 **0** —— P17 只打通了「哪条保底绑到哪个池」，没打通「卡集合的 id」：`_build_pity_engine` 用 `self._ssr_ids` / `self._featured_ids`（**原始**卡 id）建 `scope_cards` / `featured_cards`，而 `prepare_simulation_config` 已把限定卡改名为 `_wi_featured_{i}`。后果是 `aggregate_probs_by_rarity` 认不出池内那张 UP 卡、把它聚进普通槽 `'ssr'`，软保底的目标槽 `'ssr_featured'` 概率为 0 → 每次早退。故上面那条「影响」评估建立在一个未兑现的前提上。
>
> **同批补完（2026-10-09）**：`_build_pity_engine` 改为按池调 `compute_scope_mappings(pool)` 生成全部卡集合（原 ISSUE-006），并删除卡级稀有度推断里为绕开这张错表而加的两级兜底（表修对后它们永不触发）。
>
> **补完后的数值影响**（`analyze(num_simulations=30, custom_resource=50000)`，两版同参对比）：

| 字段 | 补完前 | 补完后 |
|---|---|---|
| `pool_distribution` | `{0: 0.567, 1: 0.433}` | **`{1: 1.0}`** |
| `expected_pools` | 0.433 | **1.0** |
| `pity_coverage` | 3.472 | 3.472（未变——该字段由**主模拟**在 `prepare_simulation_config` 之前算出，不涉及虚拟池） |

> 即：补完前有 **56.7%** 的模拟判定「清不动下一个池」，补完后全部至少清掉一个。方向上与 P17 当年的预测一致（「连续成功池数可能显著增加」），但幅度此前从未兑现。
>
> **对 P1-01 / P1-03 的连带**：这两项（逻辑跳跃 / MAX_POOLS 截断）的影响评估都以「虚拟池的保底生效」为前提，故须按补完后的输出重估——见 P31。
>
> **口径限定（重要）**：本次补完只覆盖 **in-process `analyze()`** 这条路径。UI 上「生成后续池子配置」走 `webui/worst_impact_service.py` 的另一条构造，那条路径的虚拟池**完全没有保底引擎**（无 `[[pity]]` 段），属另立的 P2-04，不在本次修复范围内。
>
> **`expected_pools = 1.0` 的正确读法**：它是该指标**在此配置下的天花板**，读作「P(清掉首池) = 1」，**不能**读成「分析器现在能算多池连续通关」。原因是抽卡不推进 `real_time`（312 抽全落在 0 号池窗口内，`tests/test_banner.py:777` 的既有注已记录同一点），`_wi_featured_1..98` 恒为 0。多池语义属另一项工作。
>
> **该新值为什么是「对值」而不只是「变了」**：合成池配着软保底（`ssr_soft`，`end=90`），2 万次独立试验实测「312 抽内必得 featured（最大值 90 抽）」，故 `custom_resource=50000`（= 312.5 抽）下清掉首池近乎必然。而修前的 0.4333 与「无保底独立伯努利」的预测 1−0.5355 = 0.4645 在 30 样本的抽样误差内一致——**那正是保底空转的签名**。

## 新登记（2026-10-09，均由 P17 补完那轮的独立审查提出并实测复核）

### P1-04：`success` / `failure` 条件用主配置口径判定合成数据集（中等）

- **位置**：`core/worst_impact.py` 的 `analyze_batch_results`（[:287-288](gacha_simulator/core/worst_impact.py#L287-L288)）
- **问题**：`condition in ('success','failure')` 时它用 `self._build_success_checker(target_specs=self.target_specs, ssr_ids=self._ssr_ids)` 建判定器——两者都来自**主配置**（原始卡 id，如 `limited_ssr_2` / `standard_ssr_1`），而 `aggregate_data` 是**合成配置**的模拟产物，卡 id 是 `_wi_featured_{i}`。id 空间不匹配 → 判定的「是否达成」恒为假
- **实测**（数据集两条记录均含 `_wi_featured_0`，`condition='success'`）：

| `gdr_key` | `distribution` | `expected` |
|---|---|---|
| `ssr_collection` | `{}` | 0 |
| `target_achievement` | `{}` | 0 |
| `target_achievement_obtainable` | `{}` | 0 |

  即该组合下「成功」条件把全部样本滤空。**注意默认组合不显现**：`gdr_key` 默认 `all_targets` 且 `target_specs` 为空时判定恒真，故默认跑一次看不出来
- **严重度**：中等（静默给出「没有一次算成功」，不报错）
- **状态**：新登记，未处置

### P2-04：WebUI 派生配置路径不含保底段（中等）

- **位置**：`webui/worst_impact_service.py` 的 `_build_pool_config_text`（[:113](gacha_simulator/webui/worst_impact_service.py#L113)）
- **问题**：该函数 `store = ConfigStore()` **新建空壳**，只填 `initial_resources` 与由 `sim_config['pools']` 派生的 banner / pool / reward，**不复制源 store 的 `pity` 段、`card_defs`、`rarities` 与资源定义**。于是派生 TOML 加载后 `pities = []`、`card_defs = 0` → `_build_pity_engine` 直接返回 `None` → **该路径的虚拟池没有保底引擎**（比 in-process 路径的「有引擎但不生效」更彻底）
- **实测**：派生 store 的段头为 `['[[banner]','[[banner.pool]','[resources…]','[strategy]']`（无 `[[pity]]`），`env.pity_engine = None`；200 次模拟中拿到 `_wi_featured_0` 的比例 ≈ 0.445，与「无保底独立伯努利」的 0.465 一致
- **与 P17 补完的关系**：2026-10-09 的补完只覆盖 **in-process `analyze()`** 这条路径。UI 上「生成后续池子配置」走的是本函数，症状依旧是「虚拟池不建模保底」
- **状态**：新登记，未处置
