# CLI/GUI 逻辑统一化调查报告

> 日期：2026-06-15 | 触发：用户指令 | 状态：已完成

---

## 一、执行摘要

**结论：统一化高度可行，经济性极佳（净投入约 2-3 人天），且几乎无风险。** CLI 不是"另一套逻辑"——它只是跳过了 GUI 已经封装好的统一模拟引擎 `run_batch_parallel()`，用 55 行内联代码重复了该引擎 80% 的能力。统一化本质上是**删除 CLI 的重复代码，改为调用已有统一接口**。

## 二、现状：两条路径全貌

### 2.1 CLI 路径（`cli.py`，193 行）

```
argparse → load_toml() → ConfigStore
  → SimulationEnvBuilder.from_config_store()  ← 第 92 行：仅用于提取 end_day
  → Pool.map(run_single_sim, args_list)        ← 每个 worker 内部再次调用 from_config_store()
       └→ run_single_sim():
            SimulationEnvBuilder.from_config_store()  ← 重复构建（浪费）
            create_strategy('smart', {})              ← 策略硬编码
            AllPoolsEndCondition(end_day * DAY)
            TargetCardSet 手动构造
            GachaService(...)
            GachaState(resources)
            service.run_simulation_compact(state)
  → 仅取 CompactResult.to_dict()
  → numpy 手算 3 个指标 (total_draws, ssr_counts, gdr_percent)
  → print() + json.dump()
```

### 2.2 GUI 路径（`gacha_panel.py` + `batch_simulator.py`，约 1100 行）

```
ConfigPanel.apply_to_store() → ConfigStore
  → SimulationThread.run():
       SimulationEnvBuilder.from_config_store()  ← 仅一次
       run_batch_parallel(env, target_specs, ...)
         → Pool(initializer=_wk_init, initargs=(env, target_specs))
              └→ _wk_init(): 注入 env + TargetCardSet + WorkerLocalExtractor
         → imap_unordered(_wk_run_single, tasks)
              └→ _run_single(env, target_set, seed, resources)
                   → create_strategy(env.strategy_name)  ← 可配置
                   → GachaService.run_simulation_compact()
              └→ WorkerLocalExtractor.process(compact)   ← 进程内提取
         → merge_extraction_packets()                    ← 主进程合并
         → BatchResult(results, extraction)
  → result_bundle: aggregate_data + draw_sequences + heatmap_data
                   + cumulative_snapshots + transition_flags + gdr_context
  → 分发给 6 个分析面板 + ResultStore 持久化
```

### 2.3 共享部分（两路径完全一致）

| 组件 | CLI | GUI |
|------|:---:|:---:|
| `load_toml()` → `ConfigStore` | ✅ | ✅ |
| `SimulationEnvBuilder.from_config_store()` | ✅ | ✅ |
| `GachaService.run_simulation_compact()` | ✅ | ✅ |
| `CompactResult` 数据结构 | ✅ | ✅ |
| `create_strategy()` | ✅（硬编码 `smart`） | ✅（可配置） |
| `AllPoolsEndCondition` | ✅（硬编码） | ✅（可配置） |

## 三、分歧点逐项分析

### 分歧 A：并行模拟入口（严重性：🔴 高）

| | CLI | GUI |
|---|---|---|
| 入口函数 | 自写 `run_single_sim()` | `run_batch_parallel()` |
| 进程模型 | `Pool.map()` 阻塞式 | `Pool.imap_unordered()` + initializer |
| 环境构建 | **每个 worker 内重建** | 主进程构建一次，initializer 注入 |
| 失败重试 | ❌ 无 | ✅ 3 次降级重试 |
| 单进程兜底 | ❌ 无 | ✅ 自动回退 |
| 进度回调 | ❌ 无 | ✅ batch 信号 |

**根因**：`cli.py` 第 28-55 行的 `run_single_sim()` 是 `batch_simulator.py` 中 `_run_single()` 的**独立复刻**——参数签名不同，但内部逻辑 95% 相同。

**浪费**：CLI 在 N 个 worker 中各自调用 `SimulationEnvBuilder.from_config_store()`（包含池子构造、保底引擎构建、资源调度展开等），N=1000 时重复 1000 次完全相同的计算。

### 分歧 B：流式提取管线（严重性：🔴 高）

| | CLI | GUI |
|---|---|---|
| WorkerLocalExtractor | ❌ 无 | ✅ 每 worker 一份 |
| 提取数据 | 仅 `CompactResult.to_dict()` | aggregate + heatmap + cumulative + transitions |
| merge_extraction_packets | ❌ 无 | ✅ 主进程合并 |
| 内存模型 | O(N×M)（全部 compact 回传） | O(1)（进程内提取后丢弃 compact） |

**根因**：CLI 完全没有接入 `streaming.py` 的提取管线。这导致 CLI 丢失了 GUI 能产出的几乎所有分析数据。

### 分歧 C：结果数据丰富度（严重性：🔴 高）

CLI 产出 vs GUI 产出：

| 数据 | CLI | GUI |
|------|:---:|:---:|
| 每模拟 aggregate dict | ✅ | ✅ |
| draw_sequences（前 200 条） | ❌ | ✅ |
| heatmap_data（热力图分箱） | ❌ | ✅ |
| cumulative_snapshots（池累积快照） | ❌ | ✅ |
| transition_flags（池成败标记） | ❌ | ✅ |
| gdr_context（GDR 上下文） | ❌ | ✅ |
| no_draw 基线 | ❌ | ✅ |
| pool_end_times | ❌ | ✅ |

CLI 当前只计算 3 个标量指标（total_draws / ssr_counts / gdr_percent），无法做：
- GDR 演化曲线 · 热力图 · VaR/CVaR 尾部风险 · Bootstrap 置信区间
- 每池转移分析 · 成败条件概率 · 事件模式统计
- 数据管理/比较/持久化

### 分歧 D：策略与停止条件（严重性：🟡 中）

- **CLI**：策略硬编码 `'smart'`，停止条件硬编码 `AllPoolsEndCondition`
- **GUI**：策略由 `ConfigStore.strategy_name` 控制，停止条件可配置

CLI 用户无法通过命令行切换 `target_hunting`、`pool_quota` 等策略。

### 分歧 E：输出格式（严重性：🟢 低）

- **CLI**：`print()` 到 stdout + JSON 文件（3 指标 × 4 统计量）
- **GUI**：交互式 Plotly 图表 + ResultStore 持久化

这不是"逻辑分歧"而是"呈现层分歧"——底层结果数据结构相同，只是展示方式不同。

### 分歧 F：配置加载（严重性：🟢 低）

两路径均使用 `load_toml()` → `ConfigStore`，此处分歧为零。CLI 额外支持 `--no-pity` 命令行覆盖，GUI 无等效项（但 GUI 可在配置面板中关闭）。

## 四、统一化方案

### 4.1 核心思路

**CLI 改为调用 `run_batch_parallel()`，删除 `run_single_sim()`。**

`batch_simulator.py` 的 `run_batch_parallel()` 已经是一个**完美的统一接口**：
- 接受 `SimulationEnv` + `target_specs` + `initial_resources` + `max_workers` + `seed`
- 支持 `progress_callback`（CLI 可用 tqdm 或简单百分比打印）
- 支持 `strategy_name` / `strategy_params` 覆盖
- 返回 `BatchResult`（`.results` 列表 + `.extraction` 字典）
- 自动处理多进程/单进程/失败回退

### 4.2 改造后的 CLI 调用链

```
argparse → load_toml() → ConfigStore
  → SimulationEnvBuilder.from_config_store()  ← 仅一次
  → run_batch_parallel(env, target_specs, initial_resources,
                        num_simulations, max_workers, seed,
                        strategy_name=store.strategy_name,
                        progress_callback=print_progress)
  → BatchResult:
       .results:      List[CompactResult]   → 兼容现有统计逻辑
       .extraction:   dict                  → 可选增强输出
  → 统计：从 extraction.aggregates 或 results 计算
  → 输出：console + JSON（可扩展为包含 extraction 数据）
```

### 4.3 代码变更量估算

| 变更 | 类型 | 行数 |
|------|------|------|
| 删除 `run_single_sim()` | 删除 | -28 行 |
| 删除第 92 行冗余 `from_config_store()` | 删除 | -1 行 |
| 删除手动 `TargetCardSet` 构造 | 删除 | -10 行 |
| 新增 `run_batch_parallel()` 调用 | 新增 | +30 行 |
| 新增 progress callback | 新增 | +8 行 |
| 扩展 `--strategy` CLI 参数 | 新增 | +8 行 |
| 扩展 JSON 输出（可选 inclusion of extraction） | 修改 | +15 行 |
| 新增 `--output-format` (json/full) 参数 | 新增 | +10 行 |
| **净变更** | | **约 +32 行** |

### 4.4 CLI 新增参数建议

```
--strategy smart|pool_quota|target_hunting|...   # 策略选择（默认 smart）
--output-format simple|full                       # simple=3指标JSON, full=含extraction
--progress / --no-progress                        # 进度条开关
```

### 4.5 兼容性

- `BatchResult` 实现了 `__getitem__`/`__len__`/`__iter__`，可直接替代 `List[CompactResult]`
- `CompactResult.to_dict()` 的输出格式不变
- 现有 JSON 输出格式可保持不变（`--output-format simple` 默认行为）
- 现有 CLI 调用 100% 向后兼容

## 六、根本性分析：为什么会产生分歧

### 6.1 历史原因

`cli.py` 创建于项目早期（约 v0.x），当时 `batch_simulator.py` 尚未成型。`run_single_sim()` 是当时的"唯一"模拟入口。后来 GUI 需求催生了 `run_batch_parallel()` + extraction pipeline，但 CLI 从未被更新。

### 6.2 架构原因

`batch_simulator.py` 虽然名为 "batch simulator"，但它实际是**整个项目的统一模拟引擎**。文件名和模块位置（`service/`）暗示它是"服务层的一个组件"，但实际上它是**唯一应该被使用的并行模拟入口**。CLI 绕过它直接操作底层 API（`GachaService` + `Pool.map`），相当于绕过了抽象层。

### 6.3 设计原则缺失

项目缺少一条明确的架构约束："所有并行模拟必须通过 `run_batch_parallel()` 执行"。如果这条约束写入 CLAUDE.md（类似 GDR 计算必须通过 `make_gdr_calculator()` 的规定），CLI 的独立路径就不会产生。

## 七、建议

### 7.1 立即执行（本次）

1. **重构 CLI 使用 `run_batch_parallel()`**（删除 `run_single_sim`）
2. **新增 `--strategy` 参数**，从 ConfigStore 读取默认策略
3. **新增 `--output-format` 参数**，`full` 模式输出 extraction 数据

### 7.2 架构加固（配套）

在 CLAUDE.md 的架构约束中增加一条：

```markdown
### 并行模拟入口（强制）

所有批量/并行模拟必须通过 `service/batch_simulator.py` 的 `run_batch_parallel()` 执行。
禁止直接使用 `multiprocessing.Pool` + `GachaService` 的组合。CLI/GUI/脚本均通过此统一入口。
```

### 7.3 后续优化（可选）

- CLI 支持 `--output-format html` 输出静态 HTML 报告（复用 Plotly 图表生成逻辑）
- CLI 支持 `--result-store` 将结果存入 ResultStore（与 GUI 共享数据集）
- 将 `run_batch_parallel()` 的 progress_callback 标准化（同时支持 tqdm 和 Qt signal）
