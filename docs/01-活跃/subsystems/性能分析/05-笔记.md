**触发：** 用户提问「本项目性能分析相关工作有哪些」→ 查证发现三份 profile 脚本全部失效、全仓无性能基线、无任何剖析工具链 → 用户提出重建一条工作流 → 头脑风暴 → P83 计划创建。

**查证结论（均有实跑或代码级证据）：**
- 4 份测量脚本存在（`profile_gui` 413 行 / `profile_sim` 117 行 / `profile_simulation` 121 行 / `benchmark_chart` 159 行），**全部在 `.gitignore` 内未入库**
- 三份 profile 脚本实跑失败：`strategy_name` 改名未跟随、`gui/batch_simulator.py` 已成 0 字节空文件
- 全仓 `cProfile` / `pstats` / `py-spy` / `yappi` / `line_profiler` 零命中
- 唯一自动化性能判据是 P79 的 8.4 闸门（4 用例），实跑 `4 passed`，性质是「防失控」不是「防变慢」
- `docs/superpowers/specs/` 为空目录（brainstorming skill 默认路径，与项目约定冲突，未采用）

**关键决策：**
- 三层架构：测量内核（无 Qt 依赖）/ 路径适配器 / 调用面
- 路径是一等维度，非环境细节。理由来自 P12 的实测（GUI 10-15s 对 CLI 1.6s）与四条行为分叉档案（P54/P37/P49/P78-ISSUE-109）
- **测量覆盖 ≠ 代码收敛**：适配器只驱动不重构，P74 落地时 `gui-qt` 适配器随之删除
- 两层剖析分工：`cProfile` 进基线（确定性），`py-spy` 出线索（采样噪声，不进回归）
- 明确划出范围：跨路径等价对照 / 参数扫描 / 通用实验编排 / P68 参考实现对照 / `gui` 与 `webui` 编排收敛

**实测掉的两个前提：**
- offscreen Qt 可用（Qt 6.11.0，`QT_QPA_PLATFORM=offscreen` 下 `QApplication` + `QThread` 正常）→ GUI 路径可进 CI
- `py-spy 0.4.2` 的 `--subprocesses` 可采到 `multiprocessing` 子进程（4 worker，8 秒 3193 样本，命中 `_wk_run_single`）

**事故与教训（重要）：**
验证 py-spy 时手写探针脚本，`num_simulations=60000` 无 `on_result` 收集器，父进程堆积 60000 份 `CompactResult`，导致用户机器（15.3 GB）内存耗尽崩溃。
- 根因在代码级坐实：`service/batch_simulator.py:415` / `:441` / `:452`
- 加重因素：首版探针漏 `__main__` 守卫，spawn 级联起进程池
- **两份防护现有脚本里本来就有**（`profile_sim.py:116` 守卫、`:32-33,53` 流式收集器），手写驱动把两者同时丢掉
- 产物：`01-理论.md` §2 安全协议 5 条、§3 驱动复用约束（适配器不得新写驱动）

## 2026-09-17 | 补 P83 缺口一、缺口二

**触发：** 用户问「系统设计完了吗」→ 自查发现 P83 有两处缺口 → 用户裁定 P83 即最终唯一计划文件（按项目惯例），在此基线上增量补，不另立设计文档。

**用户裁定：**
- 代码目录名保持 `benchmarks/`，不随子系统改名（文档名与代码名不必对应，先例 `测试体系` → `tests/`）
- P83 为最终唯一计划文件，缺口在此文件上补

**补入前的两项实证（都改变了设计）：**
1. `multiprocessing.pool.Pool.__exit__` 实测为 `self.terminate()`（本机 Python 3.12.5 源码核验）→ worker 被强杀、`atexit` 不执行 → 否掉「`_wk_init` 里 enable、退出时落盘」的朴素做法，改为围绕单次 `_run_single` 调用的开闭窗口
2. `pyproject.toml` 的 `testpaths = ["tests"]`（当前收集 1563 项）→ `benchmarks/tests/` 不会被默认收集，也就不会被 H9 门控到

**缺口一（已补，P83 §3.8，D1-D9）：**
- D1 触发载体用 `env` 四字段而非环境变量（先例 `return_compact` / `n_heatmap_bins`）
- D2 采样窗口为围绕单次 `_run_single` 的开闭；附带好处是在 Pool 路径与单进程兜底路径上语义一致
- D3 结果走文件，不动 `CompactResult`、不动 `_RESULT_VERSION`、不改三元组 arity（该 arity 有 ⚠ 明确契约 + 父进程 `len(result) == 3` 守卫）
- D4 必须跳过 warmup（`_wk_init` 注释说明懒加载防页面文件耗尽，首次调用含 import 开销）
- D5 有限采样窗口的代价写清楚（早期周期剖面，非全程平均）
- D6 `function` 档与耗时档分两趟，`RunResult` 新增 `not_comparable`
- D7 失败一律软降级（测量工具不得伤及被测对象）
- D8 `profile_count` 计入安全协议规则 5 的内存估算，另设硬上限 500
- D9 单进程兜底路径的剖面须标注，否则会被误读为多 worker 环境

**缺口二（已补，P83 §3.9，T0-T6）：**
- T0 测试放 `benchmarks/tests/` 并扩 `testpaths`（方案 A），备选 `tests/benchmarks/`（方案 B）
- T1 内核单测 / T2 安全协议四条拒绝规则各有单测 / T3 适配器契约测试（n=10 秒级）/ T4 阶段 5 注入测试（唯一需真实并行）/ T5 `py-spy` 只测调用与解析 / T6 明确不测什么

**同步更新：** P83 §3.7 阶段 5 行、§四 波及范围（补 `testpaths` 行、修正阶段 5 触达对象为 `_wk_run_single`）、§五 风险（补 terminate 致剖面丢失、有限窗口被误读两条）、§六 验收标准（补 5 项）、附二 决策记录（9-15 条）；`02-实施.md` 的 `RunResult` schema 补 `not_comparable`、阶段 5 行指向 §3.8、新增 §8 接口约束与 §9 测试位置。
