## 业务问题

模拟跑完之后，用户要在数据上看几十种分析：出率分布、指标统计、相关性、成功率、风险分析、时间演化、每池分析、脆弱性、最差影响、对比分析、方案搜索。这些分析的**算法**在 `core/` 里（纯函数），但**编排**（选哪个指标、对哪些池、阈值取多少、结果组织成图还是表）此前没有归属。

在没有归属的情况下，每个消费者只能自己拼一遍：GUI 拼了约 1250 行（`analysis_panel.py` 的 `AnalysisWorker._run_impl`），WebUI 又拼了 956 行（`webui/analysis_service.py`）。两遍之间已经出现行为分叉。

分析服务层的角色是**分析的定义者与执行者**：
- 定义「一次分析是什么」：名字、分类、参数、算法、产出形状，收在一条登记记录里
- 执行：给定数据集与意图，产出界面无关的结果对象
- 枚举：对外回答「有哪些分析可用、各要什么参数」，供前端生成界面

## 设计意图

1. **界面无关**：不含任何 Qt 或前端概念；同样的输入，GUI 与 WebUI 拿到逐字段相同的结果
2. **定义归一处**：新增一个分析项只写一处；新增一个前端只写渲染器
3. **自足**：分析项持数据集 id 自取所需，不依赖调用方分发数据
4. **非可视可用**：统计量能从结果对象里无损取出，供 CLI、导出、回归测试使用

## 边界

**属于本层**：分析项的登记与枚举、分析执行、结果组织（图/表/摘要）、统计量的机器可读形态。

**不属于本层**：
- 算法本身（留在 `core/`：`gdr.py`、`comparison_analyzer.py`、`vulnerability.py`、`per_pool_analysis.py` 等）
- 渲染（ChartSpec 是声明，渲染在 `gui/chart_webview.py` 与前端）
- **模拟派发**（跑模拟、组装数据集、存库）。派发是独立能力，本层只消费数据集，不生产数据集
- 配置生成（脆弱性与最差影响的「生成调整配置」部分，产出配置文本交给派发能力执行）

## 本层内部的划分

按「因什么而变」分四块（详见 `01-理论.md` §三）：

| 部分 | 职责 | 因什么而变 |
|---|---|---|
| 分析项注册表 | 分析项的定义与校验 | 加一个分析项 |
| 运行上下文 | 中间量的按需计算与复用 | 加一个中间量 |
| 结果对象 | 产出的形状 | 换前端、加 Section 类型 |
| 分析记录 | 一次分析的持久化 | 加参数类别 |

## 理论基础

见 `01-理论.md`。要点：真正的病灶是「一次分析没有所有者」，分叉是其必然后果；判据是「新增分析项只写一处、新增前端只写渲染器」；声明化（复刻 P69 的 `register_strategy`）使判据从「记得」变成「结构上不可能忘」；算法与编排按「换个前端还要不要」划线；参数按**来源**分三类（配置参数 / 分析方法本身的参数 / 界面状态与偏好），「影响结论与否」的旧判据自相矛盾；候选集派生、选中集才存；分析记录只存配方不存结果、密存 + 缺键回退、可变但不被引用、不进树；以及第八节的「事实 vs 结构保证」边界登记。
