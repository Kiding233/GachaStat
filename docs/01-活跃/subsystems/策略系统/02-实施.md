## 二、策略注册表（8 项）

P69 起注册表条目由 `StrategyMeta` dataclass 承载，策略类通过 `@register_strategy` 装饰器自注册——**类定义即注册**，消除类定义与元数据的分离维护。

```python
@dataclass
class StrategyMeta:
    key: str
    display_name: str
    description: str                       # 由 cls.description() 自动填充
    cls: Optional[type] = None
    params: List[ParamDescriptor] = field(default_factory=list)
    internal: bool = False                 # 内置隐藏——不出现在任何 GUI 列表
    disabled: bool = False                 # 用户手动禁用的插件
    plugin_path: Optional[str] = None
    _invalid_state: Optional[str] = None   # 加载失败的插件占位
```

装饰器副作用两条：写入 `STRATEGY_REGISTRY[key]`；向被装饰类注入 `_strategy_key` 类属性。

### 完整条目列表

| # | key | display_name | 类 | 参数（ParamDescriptor） | internal |
|---|-----|-------------|-----|------------------------|----------|
| 1 | `smart` | 按需追卡 | `SmartStrategy` | 无 | 否 |
| 2 | `pool_quota` | 指定池配额 | `PoolQuotaStrategy` | `PoolIntMapParam('pool_quotas')` | 否 |
| 3 | `pity_reserve` | 保底预留 | `PityReserveStrategy` | `FloatParam('pity_threshold_pct', default=80.0, 0~100)` | 否 |
| 4 | `stop_on_target` | 目标即停 | `StopOnTargetStrategy` | `BoolParam('stop_on_featured', default=True)` + `BoolParam('stop_on_any_target', default=False)` | 否 |
| 5 | `target_hunting` | 指定池追卡 | `TargetHuntingStrategy` | `StringListParam('target_pool_ids')` | 否 |
| 6 | `fixed_count` | 固定次数 | `FixedCountStrategy` | `IntParam('count', default=100, min=1)` | 否 |
| 7 | `no_draw` | 不抽卡基线 | `NoDrawStrategy` | 无 | **是** |
| 8 | `draw_target` | 目标池抽卡 | `DrawTargetStrategy` | `StringListParam('target_card_ids')` + `StrParam('pool_id')` | **是** |

> **参数键名即契约。** 三处易记错的键：`fixed_count` 用 `count`（非 `max_draws`）、`stop_on_target` 用 `stop_on_featured`/`stop_on_any_target`（非 `stop_on_up`）、`pity_reserve` 用 `pity_threshold_pct`（非 `threshold`）。改键名会让旧配置的那一项**静默落回默认值**。

### 注册表自检 `_validate_registry()`

模块导入时自动执行，5 项检查：

| 检查 | 违反后果 |
|------|---------|
| (a) 非 internal、无 `_invalid_state` 的条目 cls 非 None | `TypeError` |
| (b) cls 非 None 的条目其 cls 为 `type`；其中非 internal、无 `_invalid_state` 者还须为 `Strategy` 子类 | `TypeError` |
| (c) cls 非 None 的条目 params 内 `key` 无重复 | `AssertionError` |
| (d) 全局 key 唯一 | `AssertionError` |
| (e) `internal` 与 `disabled` 正交（不同时为 True） | `AssertionError` |

注意适用范围：`cls is None` 且合法的条目（internal 或无 `_invalid_state` 的占位）走 `continue`，跳过 (c)。

抛出异常会阻止模块导入——注册表数据不一致在应用启动阶段立即暴露，不流入运行时。

## 三、StrategyContext 详析

### 构造入口

**唯一构造点**：`core/strategy_context_builder.py` 的 `build_strategy_context(...)`。

P69 阶段 2b 将原先散落在 `GachaService._run_compact()` 中的构造逻辑收敛到这一个模块级函数。实现为函数而非 Builder 类，理由是 `StrategyContext` 只有一处构造点，不需要链式灵活性。

### 字段一览

| 字段 | 类型 | 来源 | 说明 |
|------|------|------|------|
| `state` | `GachaState` | 调用方传入 | 资源、时间、卡牌持有 |
| `current_pools` | `List[Pool]` | 调用方传入 | 当前开放池 |
| `all_pools` | `List[Pool]` | 调用方传入 | 全部池 |
| `future_schedules` | `List[PoolSchedule]` | `schedule_mgr` + `lookahead` | 未来 lookahead 天内的池子开放窗口（**当前无策略使用**） |
| `target_cards` | `TargetCardSet` | 调用方传入 | 目标卡规格 |
| `stop_condition` | `StopCondition` | 调用方传入 | **P79 起为 `CompositeStopCondition([用户条件, 引擎硬边界], mode='any')`**，不是用户配置的条件本身 |
| `_pity_engine` | `Optional[PityEngine]` | 调用方传入 | `repr=False` |
| `_pity_state` | `Optional[PityState]` | 调用方传入 | `repr=False` |
| `pool_draw_counts` | `Dict[str, int]` | 调用方传入 | 每池抽卡次数（键已全限定化） |
| `total_draws` | `int` | 调用方传入 | 总抽卡次数 |
| `acquired` | `Dict[str, int]` | **`@property` 读 `state.acquired`** | P60 起为实时读取，非独立字段 |
| `future_resource_gains` | `Dict[str, float]` | `resource_gain.compute(lookahead*DAY, state)` | P69 阶段 2——未来 lookahead 天资源收入。**当前无策略消费，且恒为 `{}`**（计算受 `lookahead` 门控，而内置策略 `lookahead` 全为 `None`） |
| `inter_pool_pity_links` | `Dict[str, List[str]]` | 从 `pity_engine._behavior_list` 提取 | P69 阶段 2——跨池保底继承关系。**当前无策略消费，且恒为 `{}`**（behavior 无 `pools`/`_pools` 属性，提取分支不命中） |
| `time_discount` | `float = 1.0` | 参数 | P69 阶段 2——时间偏好因子。**当前无策略消费，且恒为 `1.0`**（唯一调用点未传值） |
| `last_draw_pity_triggered` | `bool` | 调用方传入 | 上一抽是否触发保底 |
| `ssr_ids` | `Set[str]` | 调用方传入 | SSR 卡 ID 集合 |
| `_pity_cache` | `Dict[str, Dict[str, float]]` | 惰性计算 | `repr=False` |
| `banners` | `List` | 调用方传入 | P61——活跃 Banner（策略迁移主接口） |
| `all_banners` | `List` | 调用方传入 | P61——全部 Banner |
| `_milestone_engine` | `Optional[MilestoneEngine]` | 调用方传入 | P58——里程碑查询 |
| `resource_expiry` | `List[ResourceExpiryPreview]` | 由 `resource_lifecycle_rules` 计算 | P77——资源到期预览 |

P69 阶段 2 的三字段与 `resource_expiry` 均带默认值，现有策略不经修改即可运行。

### 方法

| 方法 | 说明 |
|------|------|
| `acquired`（property） | 读 `state.acquired`——P60 起不再是独立字段，避免快照与真相源分叉 |
| `get_pity_probabilities(pool_id)` | 惰性计算 + 缓存。P61 起接受全限定键 `{banner_id}.{pool_id}`，经 `banners` 维度拆分定位 `banner.active_pool`；裸键回退 `current_pools` 旧路径。兑换池返回 `{}` |
| `get_milestone_counter(name)` | 相对计数器（**未叠加 offset** 的原始累计值）。P78 注：首节点阶段实际触发点 = `threshold + offset`，按 `threshold - counter` 预测会低估 |
| `is_milestone_active(name)` | 该里程碑是否仍在生效（`at=N` 触发后停用） |
| `get_milestone_defs()` | 全部里程碑定义（含 `threshold` / `bonus_reward`） |

### 派生字段计算

| 字段 | 计算 |
|------|------|
| `future_schedules` | `schedule_mgr.get_future_schedules(real_time, lookahead * DAY)`——需 `schedule_mgr` 与 `lookahead` 同时非空 |
| `future_resource_gains` | `resource_gain.compute(lookahead * DAY, state)`——**复用抽卡/等待结算的同一函数**，而非另写一套未来日程推算（Ps01 R1 修正了原先对 `entry.day`/`gains` 的错误访问） |
| `inter_pool_pity_links` | 遍历 `pity_engine._behavior_list`，`pools` 属性长度 > 1 的保底行为视为共享计数器，为其中每个池子建立到其余池子的链接；提取失败静默回退为空 dict |
| `resource_expiry` | 逐条 `resource_lifecycle_rules` 经 `resolve_expire_time()` 解析到期时刻；`remaining = max(0, ceil((expire_at - real_time) / DAY - 1e-9))`。**ceil 向上取整**——到期当天仍计 1 天，用 `int()` 向下取整会少 1 天，令「剩余 N 天内清仓」阈值提前误判；负值钳 0，与 `GachaService` 三处 `real_time >= expire_at` 的 `>=` 边界语义对齐（ISSUE-036） |

> **实测取值（2026-09-15 复核）**：上表前四行里，`future_schedules` 与 `future_resource_gains` 因 `lookahead` 恒为 `None`、`inter_pool_pity_links` 因 behavior 无 `pools`/`_pools` 属性、`time_discount`（构造参数直接透传）因无调用点传值——**四者在实际模拟中恒为默认常量**（依次为 `[]` / `{}` / `{}` / `1.0`）。`resource_expiry` 是唯一实际产出非空值的派生字段（由 P77 资源生命周期规则驱动）。

## 四、策略决策流程详解

### SmartStrategy（按需追卡）——最复杂

```
1. _get_needed_card_exchange(ctx)：遍历目标卡，找出未满足且存在于某兑换池的卡，
   若该 banner 可用且资源够 → DrawAction(banner_id=<兑换 banner>)
2. 遍历 ctx.banners（活跃 Banner）：
   - 跳过兑换池
   - _pool_needs_target(banner.id)：该 banner 是否含未完成目标卡
   - can_afford_batch(cost, batch_size)：资源检查
   - 命中 → DrawAction(banner_id=banner.id)
3. 无池可抽 → WaitAction(duration=next_event_wait(ctx))
```

缓存：`_pool_to_targets` 按 `id(ctx.target_cards)` 失效重建——目标卡集合身份变化才重建，避免每步重扫目标列表。

### PityReserveStrategy（保底预留）——唯一消费保底概率的策略

```
1. 兑换优先（同上）
2. 遍历 ctx.banners：
   - 跳过兑换池、资源不足、无目标需求的 banner
   - qualified_key = f"{banner.id}.{banner.active_pool_id}"
   - pool_probs = ctx.get_pity_probabilities(qualified_key)
   - pool_probs 非空：累加 ssr_ids 中卡牌的概率，≥ 阈值 → DrawAction
   - pool_probs 为空：直接 DrawAction（读不到保底 spec 时不拦）
3. 无池满足 → WaitAction(duration=next_event_wait(ctx))
```

阈值参数 `pity_threshold_pct` 以百分数书写（默认 80.0），构造时除以 100 转为概率。P61（ISSUE-002）：查询键必须是**全限定键**——传裸 `pool.id` 会查不到全限定 spec，保底阈值静默退化为基础概率。

### PoolQuotaStrategy（指定池配额）

**三段结构**（不是两段——开头有与其他策略同构的兑换优先循环）：

1. **兑换优先**：遍历目标卡 × `ctx.all_banners`，命中 `pool.is_exchange and pool.exchange_card_id == t.card_id` 且 banner 可用、资源够 → `DrawAction(banner_id=<兑换 banner>)`
2. **有目标需求的配额扫描**：遍历 `ctx.banners`，跳过兑换池与资源不足者；配额未超且 `_pool_needs_target(banner.id)` → `DrawAction`
3. **放宽的配额扫描**：不再要求目标需求，仅「未超配额」的任意池 → `DrawAction`

配额与已抽数的读取口径见下。

- 配额键优先全限定 `{banner_id}.{pool_id}`（多 Banner 同名 main 不串池，ISSUE-327），未配置时回退裸 pool id（单 Banner 便利）
- 已抽数读 `banner.pool_draws[banner.active_pool_id]`（**裸池字典键**），不是 `ctx.pool_draw_counts`（其键已全限定化，裸键查询恒 0）

### StopOnTargetStrategy（目标即停）

先判停，后抽卡：

1. `stop_on_featured` 且 `ctx.last_draw_pity_triggered` → 等待
2. `stop_on_any_target` 且任一目标已满足 → 等待
3. 兑换优先 + 按需追卡（同 SmartStrategy 结构）

### 其余策略

| 策略 | 核心决策 |
|------|---------|
| `TargetHuntingStrategy` | 从 `ctx.banners` 筛出 `id in target_pool_ids` 的 banner，第一个资源够的 → `DrawAction`；否则 `WaitAction(duration=3600)` |
| `FixedCountStrategy` | `ctx.total_draws >= count` → 等待；`ctx.banners` 为空 → 等待；否则抽 `ctx.banners[0]` |
| `NoDrawStrategy` | 始终等待——取最近 `available_until` 推进时间，用于计算不抽卡资源基线 |
| `DrawTargetStrategy` | 最差影响分析专用：从 `pool_id` 指定的 banner 抽卡（`pool_id` 为空则取第一个资源够的 banner） |

## 五、扩展机制

### 添加内置策略

1. 在 `strategies/builtin/` 新建 `.py` 文件（或在现有文件内新增类）
2. 用 `@register_strategy(key, display_name, params=[...])` 装饰策略类
3. 在 `core/strategy.py` 的 import 段加一行 `from gacha_simulator.strategies.builtin.<name> import <Class>`——**装饰器仅在被 import 时执行**，漏掉这行策略不会出现在注册表

### 插件策略（不改 core/ 源码）

1. 在插件目录（`paths.get_strategies_dir()`）放 `.py` 文件
2. 注册 key 必须**恰等于** `plugin/<文件名>`（无 `.py` 后缀）：`my_adaptive.py` 里写 `@register_strategy('plugin/my_adaptive', '我的自适应')`。loader 以文件名构造 `plugin_key` 后要求注册表中命中该键——写成 `plugin/` 前缀但名字与文件不符（如 `my_adaptive.py` 注册 `plugin/profile_adaptive`）同样判为加载失败，且报错文案是「必须以 'plugin/' 开头」，容易误导排查方向
3. 启动时 `load_plugin_strategies()` 扫描加载；加载失败的插件注册 `_invalid_state` 占位 meta，GUI 显示错误但不阻止应用启动
4. `reload_plugin_strategy()` / `disable_plugin_strategy()` / `enable_plugin_strategy()` 支持热重载与启停；禁用状态持久化到 TOML `[plugins].disabled`
5. `internal=True` 的策略不可被禁用

### 复合策略（代码级 building block）

不进入 TOML、不进入 GUI，仅供 coding agent 在插件策略中作为子策略组合使用。三者均设 `_strategy_key = None` 哨兵：

| building block | 用途 |
|---------------|------|
| `DrawSegmentStrategy([(start, end, strategy), ...])` | 按累计抽数分段委托，`end=None` 表示到模拟结束 |
| `PriorityChainStrategy([s1, s2, ...])` | 优先级降级链——返回首个非 None 的 Action |
| `ConditionalStrategy(cond, true_s, false_s)` | lambda 条件分支 |

`CompositeStrategy` 保留并委托 `PriorityChainStrategy`，实例化时发 `DeprecationWarning`。

### 参数描述符（`core/param_descriptor.py`）

纯数据类，零 Qt 依赖（CLI 模式 import 此模块不需要 PyQt6）。基类 `ParamDescriptor` 定义 `validate(value) -> Any` 契约，非法值抛 `ValueError`。

| 类 | 校验 |
|----|------|
| `FloatParam(key, display_name, default, min_val, max_val)` | 转 float + 范围 |
| `IntParam(...)` | 转 int（接受 `10.0` 但拒绝 `10.5`）+ 范围 |
| `BoolParam(key, display_name, default)` | bool，或 `'true'` / `'1'` / `'yes'` / `'on'` 等字符串 |
| `StrParam(key, display_name, default)` | 字符串 |
| `StringListParam(...)` | 列表，或逗号/空格分隔的字符串 |
| `PoolIntMapParam(...)` | 池子→整数映射，非法条目抛错（非静默丢弃）；接受 JSON 字符串 |
| `ListParam(..., element_type)` | 通用列表 + 可选元素类型校验 |
| `DictParam(..., value_type)` | 通用字典（键恒为 str）+ 可选值类型校验 |

**控件分派的实际机制**：`gui/param_renderer.py` 自建 `_WIDGET_FACTORY`（一张以 `ParamDescriptor` **类对象**为键的 dict），渲染时用 `_WIDGET_FACTORY.get(type(pdesc))` 取工厂函数——**不消费 `PARAM_TYPE_MAP`**。后者是「类型名 → 类」的映射表，当前仅被测试引用（`tests/core/test_param_descriptor.py`），包内无消费者。

`ListParam` / `DictParam` 只做容器与元素类型校验，元素语义由消费方自身负责——与 `StringListParam` 的分工是：后者是「字符串列表」的便捷形态（支持逗号/空格分隔文本），前者承载元素为任意结构的列表。

### 新增参数的完整链路

`ParamDescriptor` 定义 → `@register_strategy(params=[...])` 声明 → `create_strategy()` 自动合并默认值并经 `pdesc.validate()` 校验 → GUI 由 `param_renderer` 自动生成控件。

**参数键名即契约**：改键名会让旧配置的那一项静默落回默认值。
