## 业务问题

抽卡模拟的核心决策问题：在每个时间步，给定当前状态（资源、已获得卡片、保底计数器、可用池子），应该执行什么行动（抽哪个池、兑换什么卡、还是等待）？

不同的玩家有不同的偏好和约束——有的追求「抽到目标卡就收手」，有的希望「最大化资源效率」，有的采用「固定预算分配」。需要一个**可组合的策略系统**，允许用户选择不同风格的决策规则，并评估它们在各种场景下的效果。

用户的期望使用路径是：**委托 coding agent 编写自定义策略 → 放入 strategies 目录 → 应用自动发现并可用**。框架的职责是为 agent 提供清晰的 API 契约、完整的上下文、和可复用的 building block。

## 设计意图

### 核心抽象

- **Strategy（抽象基类）**：所有策略的统一接口 `select_action(self, ctx: StrategyContext) -> Action`，另有 `lookahead` 类属性（未来信息窗口天数，默认 `None`）与 `description()` 类方法。策略不维护可变运行时状态——所有状态由 `StrategyContext` 传入。
- **StrategyContext（dataclass）**：封装策略所需的全部信息快照。含 `state`、`current_pools`/`all_pools`、`banners`/`all_banners`（P61 起为策略访问池子的主接口）、`future_schedules`、`target_cards`、`stop_condition`、保底引擎/状态、运行时历史（`acquired` 为读 `state.acquired` 的 property、`pool_draw_counts`、`total_draws`、`ssr_ids`）、派生字段（`future_resource_gains`、`inter_pool_pity_links`、`time_discount`、`resource_expiry`）、里程碑查询入口。
- **StrategyMeta + STRATEGY_REGISTRY**：注册表条目由 `StrategyMeta` dataclass 承载（`key`/`display_name`/`description`/`cls`/`params`/`internal`/`disabled`/`plugin_path`/`_invalid_state`），策略类经 `@register_strategy` 装饰器自注册——**类定义即注册**。GUI 策略下拉列表从此注册表自动生成。
- **ParamDescriptor**：策略参数的类型化描述符（`core/param_descriptor.py`，零 Qt 依赖）。注册表 `params` 列表由它构成，工厂据此合并默认值与校验，GUI 据此自动生成控件。
- **Action**：统一行动表示，三个类型——`DrawAction(banner_id)`、`WaitAction(duration)`、`NonDrawAction(action_id, params)`。**无独立的 EXCHANGE 类型**：兑换走 `DrawAction(banner_id=<兑换 banner>)`。

### 8 种注册策略

| key | display_name | 决策逻辑 | 特征 |
|-----|-------------|---------|------|
| `smart` | 按需追卡 | 优先兑换 → 按目标追卡 → 等待 | 综合启发式，含兑换优先、资源检查、目标导向 |
| `pool_quota` | 指定池配额 | 每池指定抽卡上限后切换 | 预算分配型，参数 `PoolIntMapParam('pool_quotas')` |
| `pity_reserve` | 保底预留 | 只在保底概率 ≥ 阈值时抽卡 | 风险规避型，**唯一消费 `get_pity_probabilities()` 的策略**；参数 `FloatParam('pity_threshold_pct', default=80.0)` |
| `stop_on_target` | 目标即停 | 抽到 up/目标卡后停止 | 参数 `BoolParam('stop_on_featured')` + `BoolParam('stop_on_any_target')` |
| `target_hunting` | 指定池追卡 | 只在指定池子抽卡 | 专注型，参数 `StringListParam('target_pool_ids')` |
| `fixed_count` | 固定次数 | 抽满固定次数后进入**推进时间**的等待 | 简单型，参数 `IntParam('count', default=100)` |
| `no_draw` | 不抽卡基线 | 始终等待 | **内部策略**（`internal: True`）——提供不抽卡的资源基线 |
| `draw_target` | 目标池抽卡 | 从指定池抽卡直到获得目标 | **内部策略**（`internal: True`），最差影响分析专用 |

### 工厂与转换函数

| 函数 | 用途 |
|------|------|
| `create_strategy(key, params)` | 数据驱动工厂——查 `StrategyMeta` → `_invalid_state` 守卫 → 合并 `ParamDescriptor.default` → `validate()` → `cls(**resolved)` |
| `strategy_type_to_key(display_name)` | 中文显示名 → 注册表 key（用于 GUI 下拉选择） |
| `strategy_key_to_type(key)` | 注册表 key → 中文显示名（用于展示） |

## 技术实现

### 调用链

```
GachaService.run_simulation()
  → build_strategy_context(...)      # core/strategy_context_builder.py——唯一构造点
  → strategy.select_action(ctx)
    → 策略返回 DrawAction / WaitAction / NonDrawAction
  → GachaService 分发执行 Action → 更新状态 → 下一轮
```

### 核心数据结构

| 类 | 职责 |
|----|------|
| `StrategyContext` | 信息快照 dataclass，封装策略决策所需全部信息。含惰性 `get_pity_probabilities(pool_id)` 与三个里程碑查询方法 |
| `StrategyMeta` | 注册表条目 dataclass——类定义即注册，消除分离维护 |
| `Strategy (ABC)` | 抽象基类，定义 `select_action(ctx) -> Action` 接口 |
| `ParamDescriptor` 类族 | 8 个参数类型（`Float`/`Int`/`Bool`/`Str`/`StringList`/`PoolIntMap`/`List`/`Dict`），各带 `validate()` |
| `Action` | 三个值类型（`DrawAction`/`WaitAction`/`NonDrawAction`），由 `core/action.py` 定义 |
| `TargetCardSet` | 目标卡规格集合，由 `core/target_card.py` 定义 |

### 关键设计决策

1. **策略无状态**：`acquired`、`pool_draw_counts`、`total_draws` 等运行时历史由 `StrategyContext` 传入，策略本身不维护 mutable 状态。保证策略可被多个模拟实例复用。
2. **保底引擎与策略解耦**：保底概率查询通过 `StrategyContext.get_pity_probabilities()` 间接访问，策略不直接持有 `PityEngine` 引用。
3. **未来信息字段齐备但取值恒定、且无消费者**：`future_schedules`（必填字段，无默认值）与 `future_resource_gains`、`inter_pool_pity_links`、`time_discount`（后三者带默认值，P69 阶段 2 补全）均已传入，但**当前 8 个内置策略无一读取**，且**四者在实际模拟中恒为默认常量**——`lookahead` 全为 `None` 导致前两者恒为 `[]`/`{}`，behavior 无 `pools` 属性导致 `inter_pool_pity_links` 恒为 `{}`，无调用点传 `time_discount` 导致其恒为 `1.0`。所有策略仍为一级（或零阶）前瞻，不评估未来池的价值。字段是预留设施，接通数据源前处于空转。
4. **注册表自检在导入期执行**：`_validate_registry()` 于模块导入时校验 5 项（cls 非空/为 Strategy 子类、params 键无重复、全局 key 唯一、internal 与 disabled 正交），违反即抛异常阻止导入——问题在应用启动阶段暴露。
5. **复合策略不入配置**：`DrawSegmentStrategy`/`PriorityChainStrategy`/`ConditionalStrategy` 为代码级 building block（`_strategy_key = None` 哨兵），不进入 TOML 与 GUI，仅供插件策略组合使用。

## 策略枯竭态契约（P79 阶段 1）

策略在「不再有任何想做的事」时必须返回**推进时间**的等待，不得返回
`WaitAction(duration=0)`——后者让 `real_time` 原地不动，时间型停止条件
（`all_pools_end` / `time_limit`）永远够不着，主循环只能烧满 `max_iterations`。
实测同一份工作量的耗时差约 150 倍（`fixed_count` 修复前 1.04s / 修复后 0.007s）。

- 统一入口：`core/strategy.py` 的 `next_event_wait(ctx) -> float`
  （契约：`min(86400, 最近关闭时刻 - real_time)`，86400 为硬上限）
- 调用点一律写 `return WaitAction(duration=next_event_wait(ctx))`：
  helper 返回**时长（float）不是 Action**，直接返回 float 会让 `GachaService`
  的三路 `isinstance` 分发全部落空并抛 `ValueError`
- 受众含插件作者——helper 落在 `core/` 而非 `strategies/builtin/` 私有路径

另有引擎侧的第二道防线：主循环的零进度兜底（连续 3 轮上下文全签名完全相同即
提前收口并写 `CompactResult.warnings`），与迭代预算耗尽告警共用一个通道。
