## 一、问题

### 1.1 兼容性痕迹（原始范围）

代码库存在三类兼容性痕迹，均与「无历史包袱原则」相悖：

1. **死兼容**：旧路径/旧接口无任何生产者，分支不可达（如 `create_behavior` 的 `hasattr(pdef, 'params')` 旧路径、`PityEngine` 旧签名）
2. **假兼容**：声称「向后兼容」实际旧格式会静默失效（如 `is_new_format` 检测只有 `if` 无 `else`，旧格式直接返回 None、保底被禁用）
3. **双路径/双写**：同一信息新旧两处存储（如 `pool_type` 同时写 `PoolEntry.pool_type` 和 `bindings['type']`）

这些痕迹增加理解成本、掩盖真实缺陷、妨碍未来迁移。项目未上线、config.toml 仅示例/测试用（CLAUDE.md「无历史包袱原则」），应一次性干净迁移。

### 1.2 范围扩展（2026-09-12 / 09-14）

原计划只针对「兼容性痕迹」。经两轮扩展后，本专项实际覆盖四类：

| 类 | 内容 | 判据 | 章节 |
|----|------|------|------|
| 一 | **兼容性痕迹** | 为向后兼容而保留，但无生产者或会静默失效 | §三 阶段 A/B |
| 二 | **死代码与孤儿文件** | 全库零引用；或整个文件无 import 且非入口 | §三 阶段 C、§九 |
| 三 | **InfoVector 明细路径** | 整条路径在生产中不可达 | §十 |
| 四 | **非删除类清理项** | 静默异常 / 重复实现 / 陈旧元数据 / 占位实现 | §十一（**仅记录，不排期**） |

第四类不排期是用户 2026-09-12 的裁决：本专项只管「删除/归档」，其余记录备查。

**与 P61/P58 关系**：P61 聚焦「池子结构迁移」（Pool → Banner），P58 聚焦「里程碑引擎」。本计划（P81）聚焦「代码清理专项」（兼容性痕迹 / 死代码 / InfoVector 明细路径），与两者方向一致但独立。P61 已排期的项（如 `Pool.is_rerun`/`original_pool_id` 删除、`get_available_pools` 删除）已随 P61 落地，不在本计划重复排期。

## 二、目标

1. 删除所有无生产者的死兼容分支与死代码
2. 消除假兼容（`is_new_format` 等无 else 检测）
3. 消除双路径/双写（信息只保留新形态）
4. 不触碰活功能：语法糖（`_expand_soft_to_deltas`）、用户可见健壮性回退（旧 TOML 自动迁移）、活跃 API 别名
5. 移除生产中不可达的 InfoVector 明细路径（§十），含其牵连的停止条件 `history` 形参与 GDR 的 O(T) 计算族（后者属设计收缩，见 §10.4 待裁决项）

### 10.1 这条线是什么

CLAUDE.md「核心数据流」记的「两种模式」之一：`List[InfoVector]`（逐抽明细记录），另一模式是 `CompactResult`（紧凑，O(1) 内存，主流）。

`InfoVector`（`core/info_vector.py`，58 行）是一个 `__slots__` 类，一个动作（抽卡或等待）一行，字段为 `action_type`/`card_id`/`pool_id`/`resources_consumed`/`resources_gained`/`real_time_before`/`real_time_after`/`time_elapsed`/`pity_state`/`action_index`/`session_id`/`free_params`/`pity_triggered`。它由 `core/collector.py` 的 `InfoVectorCollector` 累积，经 `GachaService.run_simulation()` 返回。

### 10.3 牵连一：停止条件的 `history` 形参恒空

停止条件接口是 `check(state, history: List[InfoVector], stats)`，6 个条件 + 3 个复合条件都带这个形参。但主循环里**唯一的调用**是：

```python
# service/gacha_service.py:383
if _check(state, [], stats):
```

**`history` 恒为空列表**（其余 `.check(...)` 命中都是复合条件内部的递归透传，传的还是同一个空列表）。后果分两面：

- **功能没坏**：6 个条件都有 `stats` 快路径且优先（`FixedActionCountCondition` 用 `stats.total_actions`、`LastDrawCardCondition` 用 `stats.last_draw_card_id`、`ConsecutivePoolTargetCondition` 用 `stats.card_counts`）。
- **但依赖 history 的回退分支均无行为效果**：`FixedActionCountCondition` 的 `len(history) >= max_actions`、`LastDrawCardCondition` 的 `history[-1].card_id` 永不生效；`TargetAcquiredCondition` 的 `if count <= 0:` 分支**会被进入**（目标卡未持有时 `count == 0`）但 `sum(... for iv in history)` 恒为 0，结果与不回退等价。准确措辞是「进入但无效果」，不是「不可达」。

**这推翻了 §六 的一条既成裁决**：§六 把该回退登记为「功能兜底（`acquired` 为 0 时）」的**保留项**，而该理由在当前调用形态下不成立。§六 该行已标注待重新裁决。

#### 10.8.3 块 3 的收拢方向（本批唯一的语义决策）

`_is_compact` 同时兼任「汇总账本是否存在」的开关：非紧凑路径把 `total_consumed` / `total_gained` 置 `None`（无账本），紧凑路径置 `{}`（有账本）；`_settle_resource_expiry` 内以 `if total_consumed is not None:` 容忍前者（注释见 `gacha_service.py:232`）。

**收拢规则：一律取紧凑侧。** 实际待处理的形态有 **四类**（2026-09-17 复核补全；早前只给了前两类中的一部分，且第 3 类的动作写错）：

| # | 位置 | 原形态 | 动作 |
|---|------|--------|------|
| 1 | L366 | `sorted(...) if _is_compact else []` | 取 `sorted(...)`。**另一侧是 `[]` 而非 `None`**，早前规则字面是「`{} if … else None` → `{}`」，落不到它 |
| 2 | L367-370 | `set()` / `{}` `if _is_compact else None` | 取左侧 |
| 3 | L507-518 | `if _is_compact:` **带 `else:` 子句**（L517-518 `combined_gained = rg.copy() if rg else _EMPTY_DICT`） | **删 `else` 分支、保留 `if` 体**。早前写「去条件」是错的：照字面去条件会留下孤立的 `else`，语法错误 |
| 4 | L555/568/591/607 | 无 `else` 的 `if _is_compact:` | 去条件，体提升（de-indent）。**注意 L662 `return collector.get_result()` 去条件后成为不可达死返回**（L660 已 `return result`），须一并删；ruff 默认规则**不报**不可达代码，不会自动提示 |

**误删方向的风险评估**：若错误地收拢到 `None` 侧，**最早的失败点是自身代码**——主循环第一次抽卡的 L509 `total_consumed[k] = total_consumed.get(k, 0) + v` 立刻 `AttributeError`（`None.get`）；即便绕过 L509，收尾 L621 `merged = dict(total_gained)` 对 `None` 抛的是 **`TypeError`** 而非 `AttributeError`。**故这是响亮失败而非静默改变。**

### 12.1 触发与根因

收尾时删掉 `distribution.py` 的 13 个零调用方法，其中 **9 个在该轮之前就已零调用却从未被发现**。查根因：§九 那次扩展扫描的口径是**模块级定义**（192 个 `.py` / 1262 个模块级 def），**类方法整层不在扫描范围内**。这不是「漏查几条」，而是「整层没扫过」，与 §9.9 所记的四条盲区同类。

### 12.2 本次扫描

范围：`gacha_simulator/**/*.py` 的 190 个文件、**1939 个类方法**（不含 dunder）。判据：零属性访问（`.name`，含非调用式访问）、零裸名引用、零字符串常量引用、零 `getattr/setattr/hasattr` 字面名引用。

### 12.3 三类假阳性必须先于结论排除（本节最重要的产出）

| # | 假阳性类 | 机制 | 处理 |
|---|---------|------|------|
| 1 | **pytest 按名收集** | `TestX.test_*` 由 pytest 按名字约定收集，天然零显式引用。整轮扫描 931 个「零引用」中，绝大多数是此类 | 排除 `tests/` 后重算；测试方法不参与 |
| 2 | **框架钩子** | Qt 事件处理器（`paintEvent`/`mousePressEvent` 等）由 Qt 按名调用；**pywebview `js_api` 桥类**（`webui/api.py` 的 `GachaApi`）由**仓库外的 Vue3 前端**按名字调用，而本仓库**不含前端资产**（`gacha_simulator/webui/` 下只有 `.py`） | Qt 钩子名列白名单；**`GachaApi` 全类豁免**，其 25 个方法不得视为死代码（静态不可判定） |
| 3 | **构造式派发** | `PlotlyRenderer` 用 `getattr(self, f"_build_{spec.chart_type}")`（`plotly_charts.py:164-165`），f-string 目标静态不可见 | `PlotlyRenderer._build_*` 全族（11 个）豁免 |

**扫描器的固有限制**：只能捕获**字面量** `getattr` 目标；f-string、拼接、路由表、跨语言调用一律漏判。故本节的任何「零引用」结论都必须先过上述三类筛。

### 12.4 结果：确定死（全库含 `tests/` 也零引用，且不属上述三类）

### 12.5 结果：仅测试在用（性质不同，须单独裁决）

生产零调用、但测试在直接调用，属「测试是被测对象本身」：

- `PlotlyRenderer.to_html`（`tests/visualization/test_plotly_charts.py:213/220/228`）
- `generator/schedule_generator.py` 与 `generator/target_generator.py` 的 6 个 `generate()`（`tests/generator/*`）
- 同类还有 `EmpiricalDistribution._count_distinct` / `_empirical_quantile`（`tests/core/test_distribution.py`）

这一类的判定标准与死代码不同：删它们等于删测试的下测对象，须先决定「该 API 是否还要保留能力」。

### 12.6 处置建议：不并入 P81

理由三条：

1. **性质不同**：这批与「历史包袱／兼容痕迹」无关，是按名查询 API 的自然冗余，删掉不减少任何历史负担；
2. **其中若干是有意的公开接口**：`GachaState.total_holding`、`ConfigStore.is_select_voucher` 都写在 `CLAUDE.md` 的契约里，`StrategyContext.get_milestone_*` 面向策略与插件，`TargetCardSet.get_quantity_needed` 面向调用方；
3. **删除它们需要先定义「公开 API 存废标准」**，而 P81 的宗旨是清兼容痕迹与死代码，不含 API 面收缩。这与 §0.4-2 那类「活类上的零调用方法算不算死代码」是同一个口径问题。

**建议**：本节先作为**扫描结果与盲区记录**留存；是否立独立计划（含 API 面存废标准）由用户决定。若决定清理，§12.4 的 15 个是最低争议的起点（全部零测试引用）。

**本节的直接收益（不必等裁决）**：把「§九 的扫描口径不覆盖类方法」这一事实记入计划，避免日后重复排查；并给出三类假阳性的筛法，供后续任何「类方法零引用」类检索直接套用。
