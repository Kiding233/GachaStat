# 性能分析 -- 理论

> 创建日期：2026-09-17（首次建档）
> 关联计划：`P83 性能分析平台——多路径测量·基线回归·现场剖析.md`
> 关联模块：`benchmarks/` 目录

本文件承载本子系统的方法论自我约束。与其它子系统不同，性能分析是「测量工具本身」，其正确性不取决于产品设计，而取决于是否守住下面几条约束，因此本文件是最重的一篇。

---

## 1. 核心假设

1. **性能是可回归的**：给定同一配置、同一随机种子、同一机器类别，关键耗时量的**相对结构**是稳定的，因此「与历史基线的比值」是有意义的判据。绝对毫秒不具备跨机器可比性。
2. **测量必须覆盖用户真实走的路径**：测一条没人走的路径，得到的数字不能预测任何人的体验。本项目的四条真实入口（CLI / GUI / WebUI / 直连脚本）在进程模型、线程模型、后处理链上互不相同。
3. **确定性量优于统计量**：能取到确定性指标时优先取确定性指标（迭代数、序列化字节数、调用次数），它们零噪声，必然由代码改动引起；取不到时才退到统计量并用重复测量压噪。
4. **递进下钻优于一步到位**：剖析的分辨率越高成本越高、覆盖面越窄。先粗后细可以筛掉大部分候选，带着明确怀疑再上下一级。

## 2. 安全协议（硬规则）

以下五条全部来自 2026-09-17 的一次真实事故，不是预防性建议。

**事故经过**：brainstorm 期间为验证 py-spy 可用性，手写探针脚本以 `num_simulations=60000, max_workers=4` 驱动 `run_batch_parallel`，导致目标机器内存耗尽崩溃（该机总内存 15.3 GB）。

**根因（已核实到代码级）**：探针未传 `on_result`，而 `service/batch_simulator.py:415` 是 `results = [] if on_result is None else None`，`:441` / `:496` / `:556` 在无收集器时逐条 `results.append(...)`，`:452` 把整个 list 返回——即父进程同时持有 60000 份 `CompactResult`（含逐抽数组）。

**加重因素**：探针首版漏写 `if __name__ == '__main__':` 守卫，日志中出现两行 `PARENT_PID`，证明 spawn 出的 worker 反过来又去创建自己的进程池，形成级联；Python 最终以 `RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase` 拦下。

**五条硬规则**：

| # | 规则 | 违反后果 |
|---|------|---------|
| 1 | 必须传 `on_result` 流式收集器，禁止无收集器裸跑大批量 | 全部结果堆在父进程，大批量必 OOM |
| 2 | 主模块必须有 `if __name__ == '__main__':` 守卫 | Windows spawn 下级联起进程池 |
| 3 | 杀进程必须带 `/T`（`taskkill /PID <pid> /T /F`） | Windows 杀父不杀子，孤儿 worker 残留 |
| 4 | 设 N 上限，且先小规模试跑验证进程模型起得来 | 首次就跑大批量，出错即全量代价 |
| 5 | 启动前检查可用内存，低于阈值直接拒绝 | 在用户正在使用的机器上打满内存 |

规则 1 与 2 特别值得记录：**现有脚本早就防住了这两点**，而探针把它们同时丢掉。`scripts/profile_sim.py:116` 有主模块守卫，`:32-33,53` 用了 `SharedResultCollector` + `extract_aggregate` + `on_result=collector.on_result`。绕过已有代码自己写驱动，等于放弃已经付过学费换来的防护。

## 3. 驱动复用约束

**适配器不得新写驱动，只能修复或包装已有入口。**

存在两种做法：

- 正例：适配器 import `gui/gacha_panel.py` 里现有的 `SimulationThread`，用 offscreen `QApplication` 驱动它，被测代码一行不改；`inline` 适配器就是修好后的 `scripts/profile_sim.py` 驱动逻辑
- 反例：为「方便测量」新写一个脚本去跑模拟

**理由**：自己写驱动，测出来的是驱动而不是产品。2026-09-17 的事故是极端例证——手写驱动引入的两个缺陷，直接改变了被测对象的进程模型（级联起池）与内存行为（结果堆积），此时测出的任何数字都不描述产品。

**判别式**：任何一个适配器如果需要「先写个脚本来跑」，说明它设计错了。

**推论**：`scripts/` 下现有三份 profile 脚本是待接管的资产，不是待废弃的旧物。它们编码了踩坑换来的防护（主模块守卫、流式收集），修复它们（`strategy_name` → `strategy_key` 等）就是平台的第一批工作。

## 4. 三轴模型

三个轴正交，任意组合：

**轴一 · 粒度 grain**（纵向分辨率，逐级叠加）

| 档位 | 产出 | 相对成本 |
|------|------|---------|
| `batch` | 仅总墙钟 | 最低，可跑大 N |
| `stage` | 阶段分解：配置加载 / env 构建 / 进程池启动 / 模拟 / extractor / 分发 | 低，默认档 |
| `single` | 追加「单次模拟」分布（min/median/max） | 中，需额外串行采样 |
| `function` | 追加 `cProfile` 的函数级调用次数与自耗时 | 高（2-5x 插桩开销），N 需下调 |

资源计数（序列化字节数、RSS 峰值）在任何档位都采集：几乎免费且确定性。

**轴二 · 路径 path**（在哪跑，见 §5）

**轴三 · 因子 factors**（跑哪些对照）：`n` / `workers` / `chunksize` / `strategy_key` / `config` / `seed`。一个 plan 展开为因子的笛卡尔积，每格一条记录。

## 5. 路径是一等维度

### 5.1 为什么不是「环境细节」

本项目历史上性能与行为都出现过路径分叉，有档案可查：

**性能分叉**
- P12：GUI 1000 样本 10-15s 对 CLI 1.6s，差 10 倍。根因是 `DrawSequenceExtractor` 只存在于 GUI 路径且在主进程串行执行，把 18 个 worker 的并行优势完全抵消
- P12 / `04-问题.md`：多面板 CPU 争抢是纯 GUI 现象，CLI 不存在
- P12 / `04-问题.md`：单进程路径全局变量污染，影响 CLI 与单次 GUI 模拟

**行为分叉**
- P54 的触发原因即「CLI 与 GUI 模拟入口分歧严重，CLI 自写 55 行 `run_single_sim()` 独立于统一引擎」（已修）
- P37：旧 `_build_resource_gain()` 对 GUI 创建的规则静默跳过，GUI 建的规则实际不生效而手写配置生效
- P49：往返损坏只发生在 GUI 路径
- P78 ISSUE-109：`_register_resources_from_pools` 的 GUI 侧扫描被判定为**无效通道**，插入的行会被后续 `setRowCount` 整表重建清空

最后一条最能说明问题：**在 GUI 路径上，「看起来做了」和「实际生效」可以是两件事。** 一条从不被独立测量的路径，会长期带着未被发现的偏差存在。

### 5.2 五条真实入口

| 路径 | 入口 | 备注 |
|------|------|------|
| `cli` | `cli.py:150` → `run_batch_parallel` | 无 extractor |
| `gui-qt` | `gui/gacha_panel.py:82` → `run_batch_parallel`，另有 `:106` 一条 no_draw 基线 | 主进程串行 extractor + 面板分发 |
| `webui` | `webui/api.py:293` → `run_batch_parallel`，另有 `:310` 一条 no_draw 基线 | 走 `_build_result_bundle` 自有的结果装配链 |
| `inline` | 直接构造 `GachaService` + `run_simulation_compact` | **不是任何用户路径** |
| （细分） | `run_batch_parallel` 内部单进程（`max_workers <= 1`）/ 多进程双路径 | 由 `workers` 因子覆盖，不单列适配器 |

### 5.3 测量覆盖 ≠ 代码收敛

让 GUI 路径可测，**不需要**重构 `gacha_panel`，只需要一个能驱动它真实调用链的薄适配器。收敛 `gui/` 与 `webui/` 两套平行编排是 P74 换头计划自己的事，不在本子系统范围内。

P74 落地时 `gui-qt` 适配器随之删除，内核不动。

### 5.4 `inline` 路径的定位

保留 `inline` 的价值是提供一条不受进程模型干扰的纯计算基线；风险是它极易被误读为「这就是模拟的真实耗时」。

**处置**：`RunResult.is_user_path = False` 强制标注，使它在任何报告中自带「这不是用户路径」的标签。

**实证依据**：`scripts/profile_sim.py:93-111` 测「单次模拟耗时」的办法是在主进程串行跑 20 次 `run_simulation_compact`，这绕开了子进程插桩的难题，但同时换掉了执行环境——没有 spawn、没有 IPC、没有 extractor。那个数字不描述 GUI 里的任何一次模拟。

## 6. 两层剖析分工

| | `cProfile` | `py-spy` |
|---|---|---|
| 机制 | 插桩（每次调用记账） | 外部采样（默认 100/s 读栈） |
| 精度 | 调用次数精确 | 采样，短函数可能漏 |
| 开销 | 2-5x，绝对耗时不可用 | 通常 <5%，接近真实 |
| 覆盖 | **仅被插桩的那个进程** | attach 任意 PID，`--subprocesses` 覆盖子进程 |
| 前提 | 能改代码、能重启 | 都不需要 |
| 可复现 | 高（同种子同 N，次数确定） | 低（采样噪声） |
| 进基线做回归 | 可以 | **不可以**，噪声会被判成信号 |

**分工原则**：进基线的必须是确定性量，故用 `cProfile`；`py-spy` 用于阶段计时与 `cProfile` 都指不出所以然时的现场勘查（主进程串行段、IPC 等待、Qt 事件循环）。

**实测结论（2026-09-17）**：`py-spy 0.4.2` 在本机可用，`--subprocesses` 能采到 `multiprocessing` 子进程并命中 `_wk_run_single` / `build_strategy_context` / `create_strategy`（4 个 worker，8 秒 3193 样本）。同一次实测中，父进程主线程空等在 `multiprocessing/pool.py:861`——**这实证了在主进程挂剖析器测不到有用信息**。

**依赖边界**：`py-spy` 是独立可执行文件（`pip install py-spy`，但不可 `import`），只进开发依赖，**不进发布产物**。

## 7. 粒度经济学

递进顺序为 **批次 → 阶段 → 单次 → 函数 → 进程**。每一级都会筛掉大部分候选。

**为什么默认档是 `stage` 而不是 `function`**：P12 定位到核心瓶颈（GUI 的主进程串行 extractor）用的是分阶段计时，投入产出比极高；而 `function` 档有 2-5x 插桩开销，且在主进程插桩根本覆盖不到 worker。一上来就录火焰图，容易得到一张漂亮但指向错误的图。

**为什么资源计数免费**：序列化字节数与迭代数是随模拟自然产生的，不需要额外测量动作，应当无条件采集。

## 8. 回归判据的理论基础

**用比值不用绝对毫秒**：绝对耗时受 CPU 频率、机器负载、OS 调度影响，跨时间跨机器都不可比。比值（相对历史基线）消掉大部分共模因素。

**用字节数不用耗时**：P12 记录 pickle 传输占总耗时 40-60%，必须有指标盯着。但「pickle 耗时」噪声大且与字节数非线性（对象小而种类多时，memo 记账开销占比上升）；而**同配置同种子下 `CompactResult` 的序列化字节数完全确定，零噪声**，任何变化必然是代码改动引起的。

**已知近似**：字节数只是代理指标，不等于真实传输开销（Pool 实际是分批发、有 IPC 缓冲与分片）。另外 `CompactResult` 提供 `to_dict()` / `from_dict()`，暗示跨进程传的是 dict 而非直接 pickle 对象——因此「用 `len(pickle.dumps(result))` 估算」是否符合真实传输路径**需在实施时核对，当前是假设不是结论**。作为回归判据够用，当绝对开销读会偏。

**重复测量取中位数**：单次测量在 Windows 上抖动明显（spawn 开销本身有方差）。默认 `repeats=3` 取中位数；预估墙钟超 30 秒时降为 1 并记录 `repeats_downgraded`；**建立基线时强制 ≥3，不允许降级**。原始各次值保留在 `wall_samples`，以便判断结果稳定与否。

**基线按机器类别分组**：基线入库后会跨机器比对，而核数不同则绝对耗时不可比。故基线按「核数区间 + OS 版本」分组，**同组内比比值，跨组只比阶段占比（相对结构）**。若实际只有一台基准机，则在基线文件中显式写明适用范围，而不是假装跨机器可比。

## 9. 已知局限

1. **采样归因对极短函数有噪声**。2026-09-17 的 8 秒采样中 `pool.py:160` 的 `output` 属性占 12.5% 自耗时，但这是采样值，需 `cProfile` 的确定性调用次数坐实。**该结论当前定位是「待复核的线索」，不是「发现」。**
2. **`gui-qt` 适配器的面板分发段尚未验证可整体驱动**。`SimulationThread.__init__(self, config_store, simulation_count, max_workers, seed, parent)` 只需 `ConfigStore` 即可构造，但结果回来后各分析面板的 `update_results` 分发链是否依赖 `MainWindow` 装配，尚未查证。实施时先把覆盖面定到 `SimulationThread` 结束，面板分发单列后续增量。
3. **`benchmark_chart.py` 的归属待定**。它测的是图表渲染（Plotly+WebEngine 对 matplotlib QtAgg），与模拟性能正交，且依赖 PyQt6 展示层。是否纳入本平台待实施时判断。
4. **不覆盖 GPU 路径**。继承 P12 结论：抽卡模拟是强序列依赖的决策树，GPU 的 SIMD 模式无法利用，经评估大概率是负优化（见 `subsystems/模拟服务层/01-理论.md` §6）。
5. **本子系统是工具，不改善产品性能本身**。它只提供「测得准」的能力；具体优化仍由 P12 的 Phase 2/3 等计划承载。
