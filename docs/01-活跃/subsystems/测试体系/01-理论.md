# 测试体系 -- 理论

> 创建日期：2026-06-13（首次建档）
> 关联计划：`P46 核心模块测试覆盖率提升计划.md`

---

## 1. 核心假设

1. **纯计算可隔离测试**：core/ 层模块无外部 IO、无数据库、无网络。给定固定输入 → 断言确定性输出。这是所有测试策略的基础假设。
2. **覆盖率与缺陷发现率正相关**：在 30%-70% 区间，每提升 10% 覆盖率能发现约 1-3 个隐藏 bug（业界实证研究）。超出 70% 后边际收益递减。
3. **GUI 层不应单元测试**：PyQt6 的信号/槽异步机制、QApplication 依赖、显示服务要求使得 GUI 单元测试脆弱、缓慢、维护成本极高。业界标准方案是 Model-View 分离——将可测逻辑抽取到纯 Python 模块。
4. **测试速度是门禁有效性的前提**：超过 30 秒的 pre-push 测试套件会诱使开发者 `--no-verify` 跳过。15 秒内是心理学上的"可接受等待"。

## 2. 覆盖率经济学

测试覆盖率的边际成本曲线：

| 区间 | 边际成本 | 单百分点成本 | 说明 |
|------|---------|-------------|------|
| 0% → 30% | 极低 | ~1 用例 | 少量集成测试覆盖大量 happy path |
| 30% → 50% | 低 | ~3 用例 | 每模块独立单测，主要测正常路径 |
| 50% → 70% | 中等 | ~6 用例 | 需覆盖分支、边界、异常路径 |
| 70% → 85% | 高 | ~15 用例 | 需 mock 复杂依赖、覆盖罕见边缘 |
| 85% → 95% | 极高 | ~40 用例 | 覆盖率工具盲区，每个百分点极贵 |

P46 计划聚焦 **55%→70%** 区间——投入产出比最优的区域。

## 3. 风险分层原则

不是所有代码同等重要。测试资源按风险分配：

| 风险等级 | 层级 | 代码占比 | 目标覆盖率 | 策略 |
|---------|------|---------|-----------|------|
| 🔴 高 | core/ 计算引擎 | ~52% | 70%+ | 全覆盖：每个公开函数 + 边界 + 回归锚点 |
| 🟡 中 | service/ 编排层 | ~5% | 60-70% | 重点覆盖：编排逻辑 + 模块间协作 |
| 🟢 低 | visualization/ | ~2% | 维持现状 | 不主动追加 |
| ⚪ 豁免 | gui/ 面板 | ~41% | 不设目标 | PyQt6 不可测，通过抽取逻辑缓解 |

## 4. 测试金字塔适配

```
        /\
       /E2E\        ← 手动验证 GUI（开发者自查）
      /------\
     / 集成测试 \    ← service 层编排测试（少量）
    /----------\
   /  单元测试    \   ← core 层纯计算测试（绝对主力）
  /--------------\
```

与标准金字塔不同的是，本项目的单元测试占比远超典型 Web 应用——因为无 IO、无 DB、无外部依赖。

## 6. 已知局限性

- 覆盖率数字不衡量测试**质量**——只衡量代码被执行过。一个没有断言的测试也能贡献覆盖率。
- 不覆盖 GUI 意味着 ~41% 代码永远不在自动化测试中——需依赖开发者手动验证和用户反馈。
- 已废弃文件（`.recycle_bin/`）不在统计中，但它们中的逻辑可能已迁移到当前文件。
