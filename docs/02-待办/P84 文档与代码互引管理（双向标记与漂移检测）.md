# P84 文档与代码互引管理：双向标记与漂移检测

> 日期：2026-09-18 | 状态：设计中
> 触发：用户提出「文档按行号引用代码，代码一改，后面所有行号引用全部失效；按内容引用的文档在代码修改后也不会更新；反过来改文档，对应代码又对不上了」，希望有工具自动维护引用并在语义对齐变化时报告
> 关联：P66（plan-execute workflow）、P42（plan-review 阶段独立运行）同属 harness 层
> 定位：本项目（GachaStat）自身的文档治理工具，不属于产品功能，不进入 GUI，不影响模拟/分析链路

---

## 一、问题

### 1.1 三个失效方向

项目文档对代码的引用大致三种，每种各有失效方式：

| 引用形式 | 例子 | 失效方式 |
|---|---|---|
| 行号引用 | `analysis_panel.py:506-760` | 上方插入几行，该引用及其后全部行号引用集体失效 |  <!-- refcheck:example -->
| 内容引用（贴代码） | 文档里的代码块 | 代码改了，贴的那份不更新 |
| 功能对应引用 | 「P75 四条纪律」这类设计描述 | 代码改了实现，文档的设计断言可能不再成立 |

反向也成立：文档被改写后，代码侧没有任何信号。

### 1.2 现状（实测，非估计）

| 范围 | 引用总数 | 有效 | 失效 | 其中文件已不存在 | 其中行号超界 |
|---|---|---|---|---|---|
| `docs/03-归档` | 1376 | 1230 | 146 | 84 | 62 |
| `docs/01-活跃` | 207 | 190 | 17 | 7 | 10 |
| `docs/02-待办` | 16 | 15 | 1 | 0 | 1 |
| 其他（05-参考资料、架构设计） | 10 | 10 | 0 | 0 | 0 |
| **合计** | **1609** | **1445** | **164** | **91** | **73** |

扫描口径：`docs/` 下全部 markdown，匹配 `xxx.py:NNN[-NNN]` 形式的文本引用，共 320 篇。

两点结论：

1. **活跃文档失效率约 8%（17/207），绝对量小**，说明任何增量门控在日常提交上的摩擦都很低。
2. **债集中在归档，而归档里的失效是对的**。归档记录的是写入当时的事实，它的行号本就应冻结。任何检测都必须排除归档。

**口径补充（2026-09-18）**：上表是全 `docs/` 的口径，1609 条里 1376 条在 `docs/03-归档`（85.5%）。而阶段二的迁移范围明确「归档不动」，所以**真正要迁移的是 233 条**（01-活跃 207 + 02-待办 16 + 其他 10），不是 1609。§二 目标 6 引用的数字按此读。

上表还是**纯文档扫描**（`docs/**/*.md` 里的 `xxx.py:NNN` 文本形态，含归档）。阶段一扫描器（`tools/refcheck/`）口径更宽：含代码文件、markdown 链接形态、`#LNN` 锚点，且排除归档。同一时刻实测去重引用 **269 条**（给本文档自己的 14 条示例加了行内标记后的数；加标记前是 283 条）。与 233 条的差主要来自代码侧引用与链接形态。

**一条使用上的注意**：语料是活的，本计划每次编辑都在改变被扫描的存量（实测本轮编辑过程中该数字从 277 走到 280）。所以**计划正文里的引用计数天然会过期**，任何以它为判据的结论都必须写明测量时刻；工具每次运行自己打印计数，不要引用计划里的旧数字。

### 1.3 一个必须写在最前面的事实（检测上限）

上述扫描只能判断「文件在不在、行号越没越界」。**1445 条所谓「有效」里，有多少指向了错误的代码（行号对得上但语义已变），确定性工具看不出来。** 这正是本计划要解决的核心，也是所有确定性工具的天花板，只能靠 LLM 语义核对补上。

**这个上限被两轮独立审查量化了（2026-09-18）**：对阶段一扫描器标为「解析干净」的引用独立抽样核对，**约三到四成锚点指向错误位置**（第一轮 10/31 = 32%，第二轮 19/50 = 38%，置信区间 25% 至 52%）；而加了两层确定性判据之后，这些硬错**绝大多数**仍未被命中（第一轮实测十条里只命中三条）。判据各自的精度与召回详见 §九。**结论有两面，别只读一面**：「锚点是否正确」这个问题在确定性层面上**不可判**，判据能做的只是分流；但「判据的召回已到顶」是错的（第三轮审查给出反例并证实：9 条漏报里有 6 条可由确定性修掉，修完确实找回）。两句话都要，缺任一句都会导向错误结论：只读前半句会停止改进判据，只读后半句会以为判据能替代语义复核。

### 1.4 外部工具调查结论（详见 §五）

没有现成工具覆盖「三类引用 × 三层检查」。最接近的两个：`drift`（机制最正，无 Windows 二进制）与 `menard`（Python，判定偏松）。二者共同缺口是**只做代码侧检测，不做文档侧**，而文档侧正是本项目最初提出的问题。

## 二、目标

1. **双向检测**：引用两端任意一端内容变化，即产出「需复核」事项，而不是产出「错误」。
2. **确定性部分与语义部分分离**：工具只做可机械判定的部分（指纹比对、状态派生），语义核对交给 agent。
3. **不可蒙混**：核对结论只对核对当时的状态成立，之后任一端再变自动重新打开。
4. **不绑定语言与场景**：工具核心不含格式知识，格式知识全在可插拔的 resolver 里。
5. **可长期维护**：不依赖外部服务、不依赖 git 历史、无中心注册表、零第三方依赖也能退化为可用。
6. **迁移可行**：存量引用必须有迁移路径，不得靠人工一条条手工建绑定。**（2026-09-18 更正）** 此处原写「1609 条」且写「机械迁移路径」两处都不准：1609 含归档而迁移范围排除归档，真正要迁的是 233 条（§1.2）；而「机械」这个限定词经第二轮审查证伪（现状锚点里混着约三成错的，机械照搬会把错锚点冻成记忆），正确说法是**「可批量推进的迁移路径」**：工具负责分流与排序，定位那一步由语义复核完成，不需要人类逐条建绑定。详见 §九。

## 三、方案（当前收敛结果）

### 3.1 核心不变量

> **系统里没有「自己的过去」，只有「对方的过去」。**

引用标记存被引侧的指纹，被引标记存引用侧的指纹，两端都不存自己。

这解决了三件事：

- **无自指**。文件里不出现「包住这段哈希的那段文字」的哈希，剥离规则因此不必与自身纠缠。
- **不冲突**。两个字段记录的是**不同的事实**，互为镜像；只有同一事实的两份声明才冲突。
- **就地显现**。检测必须能在「你所在的那一端」暴露：改代码的人当场被通知，读文档的人当场看见。

**设计纪律**（2026-09-18 新增）：**引擎只规定判定所需的机制**（谁存谁的指纹、怎么配对、怎么派生状态），**不规定工件是什么格式、谁扮演什么角色、范围怎么划**。凡是出现「必须」「只能」「一定」的措辞，先问它是不是判定必需；不是，就是实现偏好冒充模型约束。

本计划曾被七次按此纪律更正，留档以便识别同类错误：

| # | 曾经的约束 | 为什么它不必要 |
|---|---|---|
| 1 | 双向是特权，单向是常态 | sidecar 之后四类工件都有可写位置，期望应当统一 |
| 2 | 片段标记属被引侧 | 引用侧的 `h={1:…, 2:…}` 本就是片段映射 |
| 3 | 片段不得嵌套，必须顺序排列 | 起止按 id 配对即可，嵌套与交叉都不需要栈 |
| 4 | 引用侧是内容单元、被引侧是工件 | 引擎不要求关于工件种类的任何东西（§3.2.2） |
| 5 | 多段时需要另设一个「头部」 | 头部就是段 1，另设概念属多余（§3.2.3） |
| 6 | 声明与段标记是同一个对象 | 两者数量与职责都不同；合并后既自相矛盾，又覆盖不了没有段标记的场合（§3.2.3） |
| 7 | 把标签挪到机器区之外的散文里 | 那样工具就得认识宿主语言的注释语法才能找到它，语言无关性丢失（§3.2.1） |

**结构上的一条观察**（2026-09-18 补充）：一条关系是**两个有向边合起来的无向边**。引用标记记着被引侧的样子，被引标记记着引用侧的样子，两头各自记对方，合起来就是对同一条无向边的双向记账。这解释了此前两个结果：为什么两份记忆不会冲突（各记不同的事实），以及为什么检测天然双向。

**方向由声明给出，不由引擎强加。** 引擎的机制完全对称，`tgt_drift` 与 `src_drift` 只是同一次比较在两个端点上的两个名字。方向真正买到的东西只有两样：

1. **补救方向**：哪一端是「描述」、哪一端是「被描述」。漂移时默认改描述方，而不是因为文档写了什么就去改代码。
2. **核对时的立足点**：说明这条关系主张的是什么，让核对者不必从零猜。

因此方向是**作者声明**的：两端各由声明里的**标签**自报（§3.2.4 词表），并且**可校验**。同一条关系的两端必须报互补标签，都报同一种即 `role_conflict`。这是「假定互补」升级为「检查互补」的收益：两端对这条关系的理解不一致，本身就是一个值得报出来的错误类别。

### 3.2 标记形态

#### 3.2.1 两类记号

（2026-09-18 第七轮更正：**id 属于范围，不属于关系**。原先把 id 挂在「引用标记 / 被引标记」上，后果是同一个范围被多处引用时要重复圈三遍。现拆成两类记号。）

| 记号 | 定义什么 | 标识 | 携带 |
|---|---|---|---|
| **范围标记** | 一段内容（可多段） | 该范围的 id | id + 段标签 |
| **声明标记** | 两个范围之间的关系 | **对方范围的 id（+段标签）** | 标签 + 记忆（对方指纹）+ 视图 |

<!-- refcheck:example:start -->
```
范围（id 属于它；可多段；可被多条关系共用）
  <|e:A#*|> … <|/e:A#*|>                     单段：标签可省，用 * 占位
  <|e:A#get_probs|> … <|/e:A#get_probs|>     多段：每段一个唯一标签

声明（可多个；**必须落在自己的范围之内**，故只需写对方）
  <|引用对象：B#get_probs;h=ast-v1:1a2b|(pity.py:1258;ok)>
  <|引用者：A#*;h=sec-v1:4c7e|(02-实施.md:289;ok)>
  <|规格：C#*;h=sec-v1:9d3f;v=e77fa66|(03-审计.md:41;ok)>
                                  └─ `v` 是可选字段（核对时的基线提交），见 §3.2.6
```
<!-- refcheck:example:end -->

**标签写在机器区最前，用 `：` 分隔**（第九轮）。它替代了早期的 `as=` 字段，并且**必须留在机器区内**：一旦挪到散文里，工具就得认识宿主语言的注释语法才能找到它，语言无关性随之丢失（这正是留档表第 7 条）。

**段用稳定标签，不用位置序**（第九轮）。`h={get_probs:91ac, before_draw:44de}` 的键就是对方的段标签，因此中间插入一段不会让其余键错位（位置序会整体错位，报一批假漂移）。单段可省标签或写 `#*`，由它保证「总有一个合法标签」。

**「引用 / 被引」不是两类记号，而是声明里的标签取值**（§3.2.4）。作者在哪一侧写 `引用对象`、哪一侧写 `引用者`，方向就定在那边。

由此得到两条先前做不到的性质：

- **一个范围内可以有多个声明**：一段话在不同位置分别引不同的地方，各自带自己的记忆与视图。
- **一个范围可以被多条关系共用**：同一段被多处引用时，它只标记一次，因为范围的 id 独立于关系。

关系不需要第三个 id：它由「本范围的段标签 + 对方范围的段标签」确定。

（2026-09-18 更正：字段名原为 `doc_hash`，那是把「引用侧一定是文档」当成了模型的一部分。两侧统一为 `h`。）

#### 3.2.2 引擎要求什么，不要求什么

**要求只有三条**：

1. 一条关系有两个端点，一端标为引用方、一端标为被引方（断言是有方向的）
2. 两端都是 uid 标识的范围
3. 引用标记存被引侧的指纹，被引标记存引用侧的指纹

**其余一律不要求**。特别地：

| 不要假定 | 实际情况 |
|---|---|
| 引用侧是散文、被引侧是代码 | 两端可以是任何格式的任意范围。「文档引用代码」只是最常见的一组搭配 |
| 角色由工件类型决定 | 角色由断言的方向决定，与工件是什么无关 |
| 引用侧是「内容单元」、被引侧是「工件」 | 两端都只是范围。代码注释引用设计文档时，代码那一端就是引用方 |

（2026-09-18 更正：早期草稿末尾曾提出「引用侧是内容单元、被引侧是工件」是一条隐含不对称，并建议写进 §3.1。**该提议已撤回**：引擎不需要它，写进去等于凭空加一条约束。）

#### 3.2.3 必需性：范围必需，声明是关系的载体

（2026-09-18 第七轮更正：上一轮把「声明必需 / 段标记可选」并列比较，是拿两类不可比的东西比。正确的是下面这样。）

| 对象 | 必需性 | 数量 | 从哪来 |
|---|---|---|---|
| **范围** | **必需**（没有范围就无从比对） | 每侧 1 个（可多段） | 范围标记；**仅当宿主格式自带地址时可省** |
| **声明** | 一条关系两侧各一份（没有声明就没有记忆，也就没有可检查的关系） | 一个范围内可有多个 | 标记，或 sidecar |

**F1（样例一实测，阻断级）：范围的 id 必须来自某处。** 标记能带；宿主格式自带地址也行（JSON 指针 `/menu/title`、TOML 键、Markdown 标题 slug）；**但「由宿主结构推出、本身却没有地址」不行**。后果：**对 Python 代码，范围标记是必需的**，早期设想的「宿主定界（整个符号）」实际不可用，因为那样的范围拿不到可被对方命名的 id。JSON / TOML / YAML 不受影响，指针本身就是地址。

三种场合：

| 场合 | 范围从哪来 | 声明在哪 | 备注 |
|---|---|---|---|
| 就地界定的散文或代码 | 范围标记 | 就地 | **默认场合** |
| JSON / TOML / YAML 目标 | resolver（指针寻址） | sidecar | 指针即地址，合法 |
| 内容会被重写的文件（如 C1 每日重写的 `技术栈.md`） | sidecar 记录地址 | sidecar | **更贵的模式，见 G2** |

**为什么记忆与视图只挂声明这一处**：视图显示的是这条关系的状态，不是某一段的状态，所以只能有一处；记忆同理。若每段都带，同一事实就有 N 份副本，副本之间会互相矛盾，于是又需要调和规则（这正是本设计在别处一致在消除的失效模式：两份独立声明才冲突）。规则是：**身份信息可以分散（段号各段自带），记忆与视图单份。**

（上一轮我把这条表述为「记忆挂段 1」，那是把两类对象合并之后打的补丁。拆开之后更直白：声明本来就只有一份，段标记本来就不带记忆。）

**两侧段数不必相等。** 段数是**端点的属性，不是关系的属性**，所以 1:1、1:N、N:1、N:M 都允许，机制都能处理：记忆是「对方各段指纹的映射」，键为对方的段号。段数不等不产生额外规则。

**但段数不等会暴露一个建模问题**（工具判定不了，属建模纪律）：「多段」的语义应当是**同一个东西的不连续部分**，不是「多个东西」。若某一侧的多段其实是若干独立对象，那应当是若干条关系，而不是一条关系的多段。引擎只看到 uid 与段号，无法分辨，所以这条只能靠核对发现，不能靠引擎阻止。

**起止按 id 配对，不按嵌套**，因此嵌套与交叉都可处理：

<!-- refcheck:example:start -->
```
嵌套（合法）  <|e:x#a|> … <|e:y#b|> … <|/e:y#b|> … <|/e:x#a|>
交叉（合法）  <|e:x#a|> … <|e:y#b|> … <|/e:x#a|> … <|/e:y#b|>
同段属两关系（合法）  两对范围标记圈住同一范围
```
<!-- refcheck:example:end -->

（2026-09-18 更正：早期草案写「片段不得嵌套，必须顺序排列」，那是把解析方式限制成了栈。按 id 配对后两者都不需要栈，该限制取消。）

替代「禁止嵌套」的错误态：

| 错误 | 判据 |
|---|---|
| `dup_segment` | 同一范围内同一段标签出现两次 |
| `unmatched_start` / `unmatched_end` | 范围标记无对应闭标记，或闭标记出现在开标记之前 |
| `orphan_segment` | 范围标记没有对应的声明（只有范围没有记忆，什么也检查不了，属错误而非退化） |
| `dup_decl` | 同一个范围内出现两条指向同一对方段的声明 |
| `role_conflict` | 两端标签不构成词表里已知的一对 |
| `decl_lost` | 承载声明的段被删，其余段变为无人看守（G4） |

**散文范围一律用显式起止**，因为标题给出的范围通常比想引用的那段话粗，靠宿主结构会圈进多余文字。

#### 3.2.4 关系身份、声明位置与标签

**关系身份 = 两端（范围 id + 段标签）构成的四元组**，不需要第三个 id。

- 声明放在自己的范围之内时，**本方那两元由包含关系确定**，因此标记里只写对方两元。
- 同 `(本方段, 对方段)` 只能有一条关系。这不是限制：**记忆的内容只取决于「对方的段」**，与本方有几个断言无关，所以同一对里合并多条不丢信息。若确实需要两条，说明本方应当拆段。

**声明位置是软约束**（第九轮放宽）：**最好写在语义对应处，但不硬性要求**。位置影响的是读者的注意力，不是真值，只要模型实际会看全即可。代价必须一并标出：

| | 写在范围内 | 写在范围外 |
|---|---|---|
| 本方那两端 | 由包含关系确定，**不必写** | **必须写全两端** |
| 悬空态 | 不可能出现（声明必须在自己的范围之内） | 不可能出现 |
| 视图位置 | 必然落在所描述的文字里 | 可能离得很远，**「就地显现」降级为尽力而为** |

（第三条是本轮唯一的实质损失。）

（sidecar 里条目并列，没有包含关系可依赖，因此那里一律显式写全两端。）

**标签描述对方**（第八、九轮）：标签是名词，天然是在给对方命名，所以读标记的人不必先学一条规则，看字面就懂；也没有「此处」这类指示词带来的指代歧义。

| 关系种类 | A 端标签 | B 端标签 |
|---|---|---|
| 引用（**默认**） | `引用对象` | `引用者` |
| 描述 | `描述对象` | `描述者` |
| 实现 | `规格` | `实现` |
| 测试 | `被测物` | `测试` |
| 依据 | `出处` | `依据` |

三条要求：**名词性**、**必须是词表原样字面**（不能同义改写）、**成对登记**（引擎只校验两端构成词表中已知的一对；不同种类不必字面互逆，语义明确即可）。

校验：两端填同一种、填了不成对的组合、或填了词表外的值，都判 `role_conflict`。

**词表带来两样东西，都属语义层**：

1. **核对时的立足点**：核对者读到「这一端是『实现』，另一端是『被实现』」，比读到泛泛的「引用 / 被引用」更知道该核对什么。
2. **补救方向的默认值**：不同种类的默认补救侧不同。「实现」漂移时通常改实现方而不是改需求方；「依据」漂移时通常改引用方的表述。可按种类声明默认补救侧，未声明则回落到「改引用方」。

**引擎仍然不解释它**：词表只影响命名与默认补救侧，不影响判定（判定永远是「对方指纹是否还对得上」）。这条要守住，否则词表会渗进判定逻辑，从一个语义约定变成一套硬编码规则。

**不放自由文本的理由**：自由文本无法校验两端是否构成互逆对，也无法发现它自己腐烂。若确实需要一句话摘要，它应作为**核对那一刻的证据**存在，而证据按 2026-09-19 的裁决记在**提交信息**里（不再是标记里的字段），因为它记录的是「一次核对」，与散文是两回事。

#### 3.2.5 两条实现约束

**算指纹时必须剥离全部标记**（不只是本段自己的）。这带来一条必要性质：**范围之间互不扰动**，在 X 的范围内插入 Y 的标记，不改变 X 的指纹。Python 走 AST 归一化天然排除注释；退化为原始内容哈希的格式必须先剥标记文本。

**被引标记不存引用方的路径。** 谁引用了我，靠扫描引用标记得到，路径在渲染时现算。存路径等于把定位符当身份，正是 §3.3 要消除的东西。

#### 3.2.6 字段最小集

机器区与渲染区严格分离：**工具从不解析渲染区**，渲染区手改会被下次渲染覆盖，因此它不是第二真相源。

| 字段 | 位置 | 说明 |
|---|---|---|
| `id` | 范围 | 身份，全库唯一，建议随机值或 ULID，生成后永不变 |
| 段标签 | 范围 | 多段时每段唯一；单段可省或写 `*` |
| 标签（关系种类） | 声明 | 取自登记词表，写在机器区最前，用 `：` 分隔 |
| `h` | 声明 | **对方**上次核对时的指纹；多段时为「对方段标签 → 指纹」的映射。**判定的载体** |
| `v` | 声明 | **核对时的基线提交**（当时的 HEAD，即承载这次核对的提交的父提交）。**便利字段**，非载体；非 git 环境省略 |
| 渲染区 | 声明 | 最短定位形式与状态；纯输出，工具从不解析。**不带年龄**（状态是派生的，不会腐烂） |

**`v` 的边界（2026-09-19 补）**：它记的是「核对时的 HEAD」，所以 `git diff <v>..HEAD` 只在**顺序提交**这个常见情形下算得出「自上次核对以来的差异」。三种情形算不出来：

| 情形 | 后果 |
|---|---|
| rebase / squash / amend 改写历史 | 提交被重建、父提交变了；旧提交可能不再在历史里、最终被 gc 掉，`git diff <v>` **失败** |
| detached HEAD | `v` 仍是有效提交，但不在任何分支上 |
| 工作区脏时 rebind | `v` 记的 HEAD 快照与实际核对的内容不完全对应。那份内容已由 `h` 记死，**不影响判定**，只影响 diff 起点的精度 |

这三条是 `v` 作为**便利字段**的边界，不是缺陷：算不出 diff 只是少一条线索，判定完全由 `h` 承担。写在这里，是为了避免将来有人以为 `v` 永远算得出 diff。

**`ev` 为什么要有（2026-09-19 补理由，原先给的理由不成立）**：我原来说它是「核对须写证据」以挡橡皮图章——**这条站不住**：一句套话「核对：实现与规格一致」复制粘贴零成本，挡不住任何东西。它真正的价值在别处：

> **它是唯一能承载「判断」的地方。** 确定性层面判不出锚点是否指对（实测约四成错）。当人或模型把一个**非显然**的对应确认下来时，这个判断的**理由**没有别处可存——`h` 记的是内容，`v` 记的是时点，都不记「为什么这条对应是对的」。而下一个遇到这条关系的人（修漂移的人、审计迁移的人）正需要它。

它同时也是**独立抽查能落地的前提**：E1 或审查者可以抽几条 `ev` 问「这个说法现在还站得住吗」；没有它就只能比对指纹，而指纹恰恰是单独不可信的那一项。

**代价与风险**也要写清：套话会让它变成噪声，并给出虚假的覆盖感。所以它的定位与 `v` 一样是**便利字段**——「声明里没有它」在格式上合法；只是本工具实现的 `rebind` 每次都要求写一条（`--note`），因为硬情形恰恰是最容易被省略的那种。routine 情形写短词即可，硬情形才写判断。

**机器区是 `;` 分隔的键值字段列表**（2026-09-19 写明）：`标签：对方uid#段[;k=v…]`。
`h` / `v` 只是当前用到的键，加字段**不改语法**。字段顺序有规范（`h` → `v`
→ `ev`），写回时按规范序重排，`git diff` 于是只显示值变化。认不出的键要报出来
（键名写错会静默失效）。

### 3.3 uid 定位，路径只是渲染产物

**身份即定位**：解析靠扫描 uid，不靠路径。路径与行号在渲染时现算。

由此消掉的机制（相比早期草案）：

| 早期机制 | 现状 | 原因 |
|---|---|---|
| 恢复线索（引文加前后文） | 不需要 | 无模糊恢复需求 |
| `moved` 状态 | 不需要 | 位置变了不影响 uid 命中 |
| 符号名解析 | 变成可选 | 片段由标记界定，不由 AST 界定 |
| 迁移时 AST 反推符号 | 变成可选 | 只需圈定片段边界 |

**三个前提**（缺一则塌）：

1. **扫描范围 = git 受控文件集**。实测受控 776 文件 / 17.8 MB，而目录遍历一次是 50414 文件 / 460 MB / 5581 ms。必须走 `git ls-files` 或等价索引，不能 `os.walk`。规则需写明「标记只对受控文件加当前工作区未跟踪文件生效」。
2. **uid 免分配**。用随机值或 ULID 而非计数器，否则需要中心发号表，第三方文件借尸还魂。
3. **uid 重复是错误态**。复制粘贴导致同一 uid 出现两处，解析出多候选，工具必须拒绝自动绑定并报错。

**阶段一实测补正（2026-09-18）**：上面前提 1 说的「扫描范围 = git 受控文件集」过窄，实测暴露两处必须分开的东西：

| 概念 | 含义 | 由什么决定 |
|---|---|---|
| **扫描集** | 去哪里**找**引用 | include glob（例如只扫 `.md` 与 `.py`） |
| **解析集** | 哪些文件算**合法目标** | 全部受控文件减去显式排除 |

混为一谈的后果很具体：引用了 `pyproject.toml` 的引用被误判成「范围之外」。此外解析还要多一档：**被 `.gitignore` 排除但磁盘存在的文件**。本仓库实测有 16 条引用指向 `scripts/profile_*.py`，被 `.gitignore:30` 排除；若把它们算作「文件不存在」，给出的处置建议就是错的（正确处置是纳管、声明为外部、或停止引用）。

因此解析阶梯是：

```
ok（在解析集内）→ out_of_scope（受控但被排除，如已归档）
→ untracked（被忽略但磁盘存在）→ external（本就在仓库外，如标准库）
→ file_not_found（真失效）
```

**另一个噪声源**：零字节文件会造成假歧义。本仓库 `gui/batch_simulator.py` 是 0 行，与 937 行的 `service/batch_simulator.py` 同名，于是 12 条引用全部变成歧义。歧义报告必须列出各候选的行数、并标出「被引行号范围能否容下」，这是人做裁决时最有用的一条判据。

**实测效果**：未经分档时看着有 16 条「文件不存在」加 11 条「行号超界」；分档之后 `file_not_found` 归零，真正失效的只有 **8 条行号超界**（且集中在 P22、P41、P26 三篇）。也就是说，**「引用大面积失效」这个印象，多半是分类不足造成的假象。**

### 3.4 双向标记与三态（双向是默认）

（2026-09-18 更正：本节原先写「双向是特权不是默认」，那是 sidecar 方案定型之前的立场。把 sidecar 视作工件的一部分之后，每一类工件都有了可写位置，**双向因此是默认而非特权**。）

三态保留，语义变为「一个正常态」加「两类异常」：

| 状态 | 含义 | 处置 |
|---|---|---|
| 双向 | 两端标记齐全 | **唯一的正常态** |
| 单向 | 该有却缺（host 未声明，或 sidecar 被清理、被生成过程覆盖） | 报缺口，可自动补 |
| 悬空 | 引用侧标记指向的 uid 完全扫不到 | 阻断（新增）/ 报告（存量） |

**双向成为默认的直接后果是 `dh` 兜底路径消失**：既然每端都有地方写，就不需要「引用标记存自己那段散文哈希」这条自指退路，系统里最后一处自哈希来源被清除。

### 3.5 四类工件

| 目标端 | 能否写 | 会变 | 会被重新生成 | 被引标记的家 | 检测方向 |
|---|---|---|---|---|---|
| 手写代码、文档 | 能 | 会 | 否 | 就地 | 双向 |
| 生成文件、codegen 产物 | 能 | 会 | **是** | sidecar（放在生成范围之外） | 双向 |
| 数据与配置（JSON 等无注释格式） | 不能 | 会 | 否 | sidecar | 双向 |
| vendor、发布产物、外部规范 | 不能 | **不会** | 否 | sidecar | 双向，但语义退化为「版本记录」 |

要点：

- **四行都能做到双向**，差别只在被引标记的家。不存在「天然只能单向」的工件类别。
- 第二行需要配置声明哪些路径属于生成产物（同 menard 的 `auto_generated` 的成因），且 sidecar 必须落在生成范围之外，否则下次生成被覆盖，表现为退化为「单向」。
- 第四行内容永不变，哈希恒匹配，检查无意义，剩余价值仅为记录核对时所用版本，其语义应叫「版本记录」。
- 任何一行的 sidecar 若被 gitignore 或清理，都会退化为「单向」，此时失去孤儿检测与互相恢复，**但检测仍然工作**（引用侧还在）。

### 3.6 sidecar（本期新增）

按工件同名同目录放置，把它视作**工件的一部分**，于是四类工件都能有被引侧：

```
locales/zh.json     目标（不可写）
locales/zh.refs     被引标记与关系头（TOML）
```

| 决策 | 取值 | 理由 |
|---|---|---|
| 命名 | 与工件同名，同目录 | 工件改名时 sidecar 同名跟随，键是路径也断不了 |
| 格式 | TOML，非标记语法 | 机器专用，无需剥离，无自指风险 |
| 发现 | 确定性，看 `X.refs` 在不在 | 无需扫描即可反查 |
| 提交 | 提交 | 小、可 diff、孤儿检测依赖它 |
| 生成产物 | sidecar 放在生成范围之外 | 否则下次生成被覆盖 |

**降级**：sidecar 若被 gitignore，跨 clone 即不存在，该类工件失去孤儿检测与互相恢复，**但检测仍然工作**（引用侧还在）。这个降级是安全的，因为 sidecar 承载的从来不是检测能力。

**「sidecar 算作工件的一部分」有一个前提**：它的位置必须落在**工件的生命周期之外**。生成产物会重写目录、submodule 更新会重置、`git clean` 会清掉未跟踪文件，任何一种都会连带清掉旁边的 sidecar。因此规则不是「就放在旁边」，而是：

> **每类工件的 resolver 必须声明两件事：被引标记的家在哪、该位置如何免于被工件的生成或更新过程覆盖。**

这条声明同时是「四类工件都能双向」的依据，也是「单向」成为异常态（而非正常态）的依据。

### 3.7 片段模型（分散 uid 块）

一个 uid 块的片段可分散在多处（甚至跨文件），引用该 uid 解析出多个路径与行号范围。

**分段是单元形态，与角色无关**（§3.2）：引用侧同样可以分段（一段文字对应多处代码），被引侧同样可以单段（一个函数被一段文字引用）。早期草案把片段标记写成被引侧专属，是分类错误，已更正。

这顺手解掉了实测发现的问题：活跃文档 237 条 `.py` 引用中有 **39 条落在模块级**（不属于任何函数）。片段由标记界定之后，这类引用只需圈定连续范围，不必回答「这段属于哪个符号」。

三个必须遵守的细节：

1. **记忆按片段存**（`h={1:…, 2:…}`），不能存单一聚合哈希，否则无法定位是哪一片变了。
2. **引用侧记片段键集合**，对账时比对集合，缺少即报 `fragment_missing`（否则删掉一段片段标记会静默缩小关系）。
3. **文档哈希归属随片段数变化**：单片段放被引侧最优（消灭自指）；多片段若也放被引侧则有 N 份冗余，需权衡（见 §六 待定项）。

### 3.8 状态机（全部派生，不存储）

| 状态 | 判据 | 处置 |
|---|---|---|
| `ok` | 两侧指纹与片段集合均匹配 | 无 |
| `tgt_drift`（被引侧变了） | 引用标记的 `h` 与被引侧当前指纹不符 | 进复核队列 |
| `src_drift`（引用侧变了） | 被引标记的 `h` 与引用标记所辖范围当前指纹不符 | 进复核队列 |
| `fragment_missing` | 片段集合少项 | 进复核队列 |
| `broken` | uid 扫不到（含 sidecar 缺失） | 新增的阻断，存量的报告 |
| `ambiguous` | 同一 uid 出现在多处 | 拒绝自动绑定，报错 |
| `unregistered` | 文档有标记但未被任何对账覆盖 | 报告 |

**状态按侧渲染**：`tgt_drift` 与 `fragment_missing` 出现在**引用侧**视图（由引用侧持有的 `h` 判定）；`src_drift` 出现在**被引侧**视图（由被引侧持有的 `h` 判定）；`broken` / `ambiguous` / `unregistered` 是关系级问题，两侧都报。这样每个方向的漂移都落在「行动者所在的那一端」（§3.2.1）。

**归档路径一律排除在检测之外。**

### 3.9 触发点与写入纪律

**对账函数是核心原语**：从磁盘现状出发，扫标记、算指纹、派生状态。幂等、无状态、谁都能调。钩子只是闹钟。

| 触发 | 范围 | 写盘 | 目的 |
|---|---|---|---|
| `SessionStart` | 全量 | 刷新渲染区 | 会话内读到的都是新的 |
| `PostToolUse(Edit\|Write\|Bash)` | 增量（先 stat 找脏） | 刷新受影响区域 | 改代码当场知道 |
| `PostToolUse(Read)` | 单篇 | **不写**，仅注入实时状态 | 读文档时看见 |
| `Stop` | 增量 | 刷新 | 兜住经 Bash 等不透明路径的改动 |
| `pre-commit` | 全量 | 刷新 | 提交态不说谎；新增 `broken` 阻断 |

**为什么不需要拦截文件系统**：对账从现状出发，不依赖注册表，因此任何写入者（agent、脚本、`git checkout`、IDE 自动保存）都改不掉真相，最多晚一点知道。同时 FUSE 类方案另有硬伤：读侧在原理上不可为（`read()` 不能阻塞于跨文件重算并改写自身），Windows 上亦无 FUSE（需 WinFsp 或 Dokan 这类第三方内核驱动）。

**写入纪律只有一行**：

> **只有 `rebind` 写记忆；对账只写渲染区。**

查不出来的东西才值得存：路径、行号、当前哈希都可重算，写进文件只会换来无限 diff churn；「引用时它长什么样」不可重算，必须存。

#### 3.9.1 提交点闭包门控与传染（2026-09-18 新增）

提交是本设计里**唯一不需要驻留进程的正确性锚点**。规则不是逐文件检查，而是**关系闭包**：

> 以暂存文件为起点，沿关系扩张连通闭包。闭包内**所有关系**必须处于非漂移状态（或已登记暂缓），否则拒绝提交。

**判据必须落在「关系」上，不能落在「文件内的标记」上。** 这是本条最容易写错的地方：**漂移显示在对面那一端**。改引用侧 A，漂移出现在被引侧 C 的视图里（`src_drift`），而 C 的标记不在 A 里。所以「检查暂存文件自己的标记」会漏掉它刚造成的那一半；必须按关系扩张闭包。

**两种传播必须分开看**，混为一谈会得出错误的结论：

| 传播 | 载体 | 轮数 | 谁决定停止 |
|---|---|---|---|
| **视图传播**（机械） | 渲染写入视图文本 | **有界**：至多两次提交尝试 | 结构决定 |
| **内容传播**（语义） | 修复时的散文或代码编辑 | **不限，可成环** | 作者判断 |

**视图传播有界**，因为视图不是状态的输入（§3.10 的剥离规则使然）：渲染 B 只改 B 的视图区，而 A 的记忆是 B 的**范围**，范围一个字没动，A 的状态因此不变。所以一轮渲染之后所有视图即新鲜。落成提交行为就是：**第一次尝试渲染并把被刷新的文件标脏，第二次尝试判定**，不会再需要第三轮。

**内容传播无界，而且这是正常的、必须支持的**：修复一处可能要求改对面，改对面又使本端失配，如此往复，成环（A↔C 互引）也可以。它终止于作者判断「不再需要改」，而不是终止于某个结构不变量。**改成连环是合理的，不该被设计阻止。**

**钩子必须写盘，正是为了驱动第二种传播。** 渲染把对面文件在磁盘上标脏，于是它进入 `git status`，于是它被逼进提交集合；若钩子只做判定不写盘，那么「对面需要一起提交」这件事就只存在于工具的知识里，agent 少走一步就漏了，闭包也就不再诚实。**「逼 agent 多提交一次」不是副作用，它就是机制本身。**

**注意钩子读的必须是索引内容，不是工作区内容**，否则会出现「检查通过、但提交进去的是未检查的那一版」。渲染写的是工作区，因此钩子渲染后要**中止**并列出被刷新的文件，要求 agent 自己重新暂存，而不是悄悄 `git add`。

**代价与边界**：

- 闭包扩张的规模与**漂移量**成正比、与图规模无关：没有漂移的提交零扩张。实测关系图是「以代码文件为中心、扇入不超过 8」的星形，即使扩张也有限。
- **门控用 git 原生钩子，纯本地，不涉及远端**（2026-09-18 裁决）。`.githooks/pre-commit` 进版本库，靠一次 `git config core.hooksPath .githooks` 启用。它拦的是 `git commit` 本身（非零退出即中止），因此**对人类与任何 agent 一视同仁**，不依赖 Claude Code 运行时。

  | 机制 | 覆盖谁 | 唯一绕过方式 |
  |---|---|---|
  | `.githooks/pre-commit`（本计划采用） | 任何在本仓库提交的人或 agent | `--no-verify` |
  | Claude Code 钩子（H3/H5/H7/H9，已有） | 仅经 Claude Code 发起的提交 | 不装钩子 |

  两者是同一实现的两个薄适配器：核心在 `tools/refcheck/`，`.githooks/pre-commit` 与 `.claude/hooks/*` 都只是调用它。**不引入 CI、不碰远端、不改仓库设置**：本计划要的是「本地提交不会把漂移带进去」，不是「不可绕过的强制」。后者要服务端或平台分支保护，属另一个层面的决定，与本计划无关。

- **真正的风险不是绕过，是安装静默失效。** `.git/hooks` 与 `.git/config` 都不进版本库，所以「钩子没装」没有任何症状。两条应对：`check` 检测 `core.hooksPath` 是否指向 `.githooks/` 并告警；`SessionStart` 钩子可幂等补上这次设置（首次执行时打印一行说明），把安装成本降到零。后者会让一个钩子去改 git 配置，是否采用留待实现时定。
- **`--no-verify` 可绕，而这是可接受的。** 项目自身的 `HARNESS_BYPASS` 机制就是「显式认可的绕过通道，且 C4 三十分钟后自动删除」，即已经接受「门控可绕，但绕过要留痕、会过期」。P84 的暂缓记录正是同一个角色。所以不必为了追求不可绕过而加远端门：**把误报压下去比把门焊死更划算**。判据很直白：门控准，绕过是罕见例外；门控吵，绕过是必然，那时门控本身才是问题。
- **必须有显式且有记录的暂缓**（带日期、带理由、持续报告）。否则人们会走 `--no-verify`，门控沦为装饰。暂缓不是「认为关系没问题」（漂移状态照旧），只是「本次提交不为它阻塞」。
- **渲染不得静默改写已暂存内容**：钩子渲染后若有文件被刷新，应中止提交并提示复核重新暂存，而不是悄悄 `git add`。

### 3.10 渲染区规则

- **两侧都渲染各自视图**（§3.2 分工表）：引用侧显示被引侧状态，被引侧显示引用侧状态。写入次数与**状态跳变次数**成正比、与编辑次数无关（视图显示的是状态而非哈希，是阶跃函数），所以「改文档会写进源码」的 churn 是有界的，一次核对周期内每侧至多两次
- 视图挂在**声明**上（每关系每侧一份声明，故视图也只此一份），因此交叉与嵌套时不争位置
- **视图只放最短定位形式**（F5）：`pity.py:1258` 或符号名即可，完整限定路径由工具在需要时展开。样例一实测：完整路径会让该行膨胀到 85 字符，其中约 51 字符是视图，而其中大半是可以推出来的信息  <!-- refcheck:example -->
- 机器区与视图**可分两行**，仍在同一区域内（本节约束的是区域，不是行）
- **视图应标出该端是就地还是 sidecar**（H2）：让核对者知道这一端有没有就地兜底
- HTML 注释包裹（结构惰性，插到任何位置都不破坏 markdown）
- **危险位置（markdown 的代码块内、表格内）报错拒绝写入**，不硬写。此判据只看**标记自身**所处的位置：落在别的单元范围内是正常的（正是交叉与嵌套），落在代码围栏内才是错误
- 剥离顺序固定：**先剥标记与渲染区 → 再切段 → 再归一化 → 再哈希**。顺序反了会自锁
- 只替换内容真正变化的区域，逐字节比对，相同则整文件不写
- 渲染区里放**判定结论**，不放当前哈希（当前哈希每次代码改动都变，会制造 churn 且信息量为零）
- **不带年龄**（2026-09-19 定）：状态是**派生**的（`ok` = 记下的指纹与当前内容相符，此刻算出来的事实），不是一条会过期的存储声明，所以没有「腐烂」这回事；视图新鲜度由**重渲染比对**判定，与年龄无关。附带的时间信息只在机器区的 `v`（基线提交）里，那是**核对记录**不是视图字段

四条验收：连续渲染两次第二次零 diff；无标记文件渲染后不变；危险位置必须报错；**交叉与嵌套片段解析正确，且两侧视图互不干扰**。

### 3.11 五个轴与可逆字段（已定，见用户裁决）

| 轴 | 定值 | 落盘 | 可逆性 |
|---|---|---|---|
| 存储位置 | 标记为权威（第三方表降级为即用即生成的派生缓存） | 是 | `sources` 字段 |
| 标识符 | id（身份）+ 路径行号（渲染产物）+ 指纹（记忆）三件套 | 是 | 本身即设计 |
| 权威源 | 标记与指纹为权威 | 否 | 改判定逻辑 |
| 检测时机 | 写入侧阻断 `broken` + 定期消费队列 | 否 | 改配置 |
| 归一化 | 结构级，指纹带算法标签（`ast-v1:` / `sec-v1:` / `json-v1:`） | 是（在指纹里） | 算法标签前缀 |

原则：**能算出来的不写进文件；写进持久数据的轴花一两个字段买可逆；纯代码的轴当场定死。**

`sig` 带算法标签是本设计相对 `drift` 的一处明确改进：drift 存裸十六进制，一旦改进归一化算法会导致全库同时报 stale。

### 3.12 地址优先级（sidecar 不许存行号当记忆）

| 目标格式 | 地址用什么 |
|---|---|
| JSON | JSON 指针 `/menu/title` |
| TOML | 点号键 `a.b.c` |
| YAML | 键路径 |
| CSV | 列名加行主键 |
| 数据库 | 主键 |
| Markdown | 标题 slug |
| 无结构文本、二进制 | 位置 + 引文双选择器（W3C 注解模型） |

**行号可以回到系统里，但只能作为渲染提示或命中加速，永远不能作为「上次核对时它长什么样」。** 记忆必须是内容或格式自带的地址。

### 3.13 发现机制与扫描范围（两次扫描 + 派生缓存）

uid 定位意味着解析靠扫描（§3.3），而全仓内容扫描不能每次都做。分两步，两步都不依赖中心注册表：

| 步 | 动作 | 成本 |
|---|---|---|
| 一 | 在**声明的 glob 范围**内找标记（`git grep` 等价物） | 需读候选文件内容，但只做文本匹配 |
| 二 | 只解析命中的文件：切片段、算指纹、派生状态 | 解析与哈希才是真正的开销 |

**第一步的成本用派生缓存压掉**：缓存 `(路径, mtime, size) → 标记位置`。对账时先 `stat` 全部受控文件（实测 776 个，毫秒级），只对 mtime 或 size 变化的文件重跑文本匹配。缓存**默认失效、可随时删除**，删掉后下次对账全量重建，**正确性不依赖它**。

**范围由 glob 声明**（如 `docs/**`、`gacha_simulator/**`），与 menard 的 `doc_paths`、drift 的 `scan.include` 同构。

**glob 限定会带来一类假 broken，必须有出口**：标记若落在声明范围之外，被引侧扫不到，会被误报为悬空。处置是**在判定 `broken` 之前先做一次慢路径全仓查找作为诊断**，仅当慢路径也找不到才判 broken。慢路径只在出现 broken 候选时触发，日常成本不受影响。

**为什么不采用「控制区登记制」的强形式**（标记只允许出现在登记过的文件里）：登记本身需要一个中心文件，等于把已否掉的第三方表换个名字请回来。glob 声明是范围限定，不是逐文件登记，两者成本差一个量级。**如果将来发现标记被大量写错位置，再考虑加一层「范围外标记即报错」的收紧，但那时报错依据仍应是扫描结果，不是登记表。**

### 3.14 命令面：钩子内跑的与模型手动跑的

**钩子独占地负责「正确性」**，因为那是唯一必须在「变更固化」那一刻发生的事。一个 `pre-commit` 就够：

1. 从**索引**内容对账（读；不是工作区）
2. 从暂存文件沿关系扩张闭包
3. **渲染**闭包内视图过期的文件（写工作区）
4. 若有文件被改写 → **中止**，列出被刷新的文件，要求 agent 复核后重新暂存（不得悄悄 `git add`）
5. 否则判定：闭包内关系若有漂移且未登记暂缓 → 中止并列出工单
6. 否则放行

第 3、4 步合起来的效果是：**渲染这一轮最多额外花掉一次提交尝试**（详见 §3.9.1 的两种传播）。

**钩子的失败输出是给模型的工单，不是给机器的错误码。** 这是「一个钩子够用」的关键：它必须说清关系 id、两端位置、状态、上次核对（`v`，证据记在提交信息里）、以及下一步动作（跑 `rebind` / 改文档 / 登记暂缓）。读这封工单的通常就是刚才尝试提交的那个模型，所以它同时是整个设计里最准时的注入点。

**模型需要手动跑的只有「读」与「核对写回」两类**，因为这两类它自己做不了：

| 命令 | 为什么模型做不了 | 何时用 |
|---|---|---|
| `check [--changed <path>] [--format json]` | 需要全库扫描与指纹计算 | 钩子、随时 |
| `status <file>` / `status <rel> --explain` | 同上；后者还要列出两端解析结果与「记忆指纹 vs 当前指纹」的具体差异 | 读文档或改代码之前；诊断单条关系 |
| `refs <target>` | 需要反查全库 | 改代码之前，先知道影响面 |
| `rebind --rel <uid> --note <证据>` | 需要把新指纹**同时写回两侧**并保证格式正确 | 漂移之后。**这是唯一改判定的写操作**，故必须带证据、且环上拦住 |
| `render [--changed <path>]` | 与钩子同一条渲染路径，但手动触发 | 不想提交时也想让磁盘上的视图新鲜 |
| `doctor` | 需要自检扫描范围、glob 配置、钩子是否装上、缓存状态 | 排障，尤其针对安装静默失效 |

**明确不需要的命令：`bind` / `unbind`。** 建与拆关系就是**编辑文本**：标记是纯文本，模型直接写即可，做命令反而把「模型本来就能做的事」包了一层，还多一套要维护的接口。写错了由 §3.2.3 的错误态（`orphan_segment` / `decl_lost`）兜住。

**阶段性**：阶段一只需要 `check`（其雏形就是迁移就绪报告）；阶段三加 `rebind` / `status` / `refs` / `render`；`doctor` 在阶段四随钩子一起上；`migrate` 属阶段二。

### 3.17 给模型的说明书（2026-09-19 补，当前最薄的一环）

工具已经能跑，但**模型不知道怎么用它**——这是现在最缺的一块，而它不是「写一篇文档」能解决的：字段集与状态集会随实现变，手写的说明必然与代码脱节。本项目自己那条纪律（「参数键名即契约」）在这里的推论是：

> **说明书必须由工具生成，不能手写。** 工具持有字段表、状态表与命令表，就由它输出（如 `refcheck.py manual`），注入与 `--help` 都取同一份。手写的那份只会成为下一个腐烂的文档。

要覆盖四块，缺任一块都会出错：

| 块 | 内容 | 为什么不能省 |
|---|---|---|
| **能力清单** | `scan` / `sample` / `check` / `diag` / `render` / `rebind`（+ 后续 `uids` / `doctor`），每个标出**读还是写** | 读写的区分是唯一能防事故的东西：随口跑一次 `render` 就会把工作区改脏 |
| **字段表** | `id` / 段标签 / 标签 / `h` / `v` / 渲染区，每个标明**谁写**、**能否手改** | 标记是纯文本、模型直接写，所以必须说清哪一格不许手改：**渲染区**（会被下次渲染覆盖）与 **`h`**（手改等于绕过证据做了一次 `rebind`） |
| **规范流程** | ①新建引用 ②改内容 ③修漂移 ④核对（含 §3.16 的环上前提：先把环上各端表述一起定稿再逐条 `rebind`） | 「怎么写一条新关系」现在只散在 §3.2 各处，模型读不出操作顺序 |
| **状态 → 动作** | 每个状态对应「下一步做什么」 | §3.14 早就要求工单给出「下一步动作」，而当时 `check` / `diag` 只打状态、不打动作（同日补上，见本表下方 2026-09-19 那条） |

**一处实现缺口**（写这一节时发现）：**新建的关系没有 `h`**，而当前实现把「`h` 缺失」报成 `fragment_missing`（那是多段时缺某一项的错）。新建关系的正确状态是**「尚未核对」**，应当是一个独立状态、且不阻断——它不是错，是还没开始。这条要修。

**`ev` 删除，证据移到提交信息（2026-09-19 定，用户裁决）**

我上一版提的是「按状态门控 `ev` 的显示」，**那是个补丁，而且补不到地方**：门控只能做在**工具的输出**里，而 `ev` 是**写在文档里**的。模型直接读文件、或 grep 一下，照样看到那份没有任何标注的旧证据，与漂移并列。数据层的问题不能用显示层修。

更根本的是：**`ev` 是同一份有效性的第二个表示**。它成立的条件恰好就是 `h` 匹配，也就是漂移信号本身。按 §3.1，同一事实的两份表示会互相分歧——而这里它连分歧都发现不了，只会静静地过期。所以它**对当下什么也没多加，却能被读成安心**。

**证据归位到它本来所属的地方：提交信息。** 核对的证据是**一次事件**的记录，而事件的家是提交，不是被核对的内容：git 给出时间、作者、可追溯，且它不会躺在文档里冒充现状。

| 项 | 处置 |
|---|---|
| 字段 `ev` | **删除**（`FIELD_ORDER` 回到 `h` → `v`） |
| `rebind --note` | 保留，但用途改为**生成建议的提交信息**（并打印出来），不再写进标记 |
| 由谁保证落进提交 | **钩子**：暂存的 diff 里若含 `h` 变化，提交信息必须带上那条证据（这条可机械校验） |

留下的 `v`（基线提交）不受影响：它是**时点**而非判断，且事实只有一个（`h` 匹配与否），不存在两份表示。

**说明书放在哪（2026-09-19 定稿，同日实现）**：**做成 skill，skill 只做触发器；agent 文件只放一行「必须调用该 skill」。**

- 触发概率最高的是每次会话都加载的文件（`CLAUDE.md`），指针放那里，且写成强制（「必须调用 `refcheck` skill」）而不是可选提示。
- 但**不粘正文**：正文每次会话都进上下文有体积代价，且它会随实现变，粘进去的副本就是下一个腐烂的文档（正是本节开头的论点）。
- 正文的获取路径因此只有一条：调用 skill → skill 说「先跑 `manual`」→ 现场打印。**不给 skill 正文副本**，于是不存在「skill 正文与工具不一致」这类新失效模式，也不需要保鲜机制（原本要保鲜，是因为担心工具会变；而工具只在开发期随设计变，开发结束后它冻结）。
- 三条硬规则（渲染区不许手改 / `h` 不许手改 / 写标记前后跑什么）**不放进 agent 文件**，改由 `manual --brief` 输出。它们是「不跑命令也必须知道」的部分，而 agent 文件已强制调用 skill，所以拿到它们的路径是确定的。少一处副本就少一处漂移点。
- 这与之前那轮「交付形态」的结论一致：**强制靠 git 原生钩子（不分 agent、不会漂移），引导靠 agent 文件（触发概率高）**，而内容只有一份、由工具生成。

**实现（2026-09-19，`20e17ef`）**：`tools/refcheck/manual.py`（三张表 + 流程散文 + 自检）、`refcheck.py manual [--brief]`、`.claude/skills/refcheck/SKILL.md`（纯触发器）、`CLAUDE.md` 一行指针。自检第一次运行即抓出 `BLOCKING` 里的死条目 `drift`（它是**边**的内部状态 ok/drift，不是会抛出的问题状态，会抛的是 `tgt_drift` / `src_drift`）。

**那处不彻底已收敛（2026-09-19，同日）**：正文只有一份了，见本表下方最后一条。代码里的 `Issue` 只带实例事实，意思与动作一律查表拼上。

**（原提法留档）`ev` 的显示按状态门控**：用户问「如果没有 `ev`，模型会不会更可能自己核一遍」——这个风险是真的：在一份**漂移**的工单里同时显示「上次核对 3 个月前，证据：实现与规格一致」，模型可能读成「有人核过了，大概只是小改动」而跳过复核。而按本设计，**漂移一出现，上次核对就已失效**（这正是指纹的机制）。所以：

- 状态 `ok` 时才显示 `ev`——那时结论仍然成立，`ev` 说的是「为什么这条对应是对的」，有用。
- 漂移时要么不显示、要么**显式标注为已失效**（「上次核对的记录（该结论已因漂移作废）」）。工单的职责是让模型**动手**，不是让模型**安心**。

### 3.15 可见性注入（正确性之外）

钩子只在提交时说话，所以会话中途读到的视图可能是旧的。这不是正确性问题（提交时会被拦），是体验问题，由三个可选触发点补：`SessionStart` 全量刷新、`PostToolUse(Read)` 注入实时状态、`PostToolUse(Edit|Write|Bash)` 反查通知。三者都可缺，缺了只是提示变少，检测照旧。

### 3.16 关系图诊断（辅助一次改对）

**为什么要它**：没有拓扑信息时，模型只能按钩子的工单逐条处理，走到第二、三轮才发现「这是一条链」甚至「这是一个环」，于是前面做的 `rebind` 被后面的改动推翻，白费一轮。有了拓扑，它可以先规划再动手。**图由程序生成，不是交给模型去建。**

**互引在本项目里很可能是常态，而不是例外。** 文档引代码、代码注释引文档，这正是现行做法。实例：`gacha_simulator/core/pity.py` 第 1238 行的注释写着「P55 文档 line 1785-1789 预见的 A/B 分裂」，即代码侧引用文档；而文档侧同样引用该函数。两者互引即是一对。（顺带一提：那条注释引用的也是**行号**，同样会漂移，是 P84 §一 那三类失效的又一个实例。）

**但一对互引不算「环」，判环只看长度 ≥3。** 早期实现把无向图里**每一条边**都报成环（`A -> B -> A`），于是上面这一对永远在环上，`rebind` 对它一律拒绝，逼人天天加 `--allow-cycle`，守卫变成橡皮图章。理由是：一对互引就是**一条**关系，不存在「先把环上各端定稿再逐条处理」的需要，而长度 ≥3 的环才有（A→B→C→A，改任一端都会牵动另外两端）。已在 `cycles()` 里修（DFS 跳过「来时的那条边」，无向图的标准做法）。

**输出什么**：

| 内容 | 为什么 |
|---|---|
| 卷入的范围（节点）与关系（边） | 让人看见分量有多大、有没有超出预期 |
| 每条边的状态，以及**哪一端变了** | 区分「源头」与「后果」 |
| **拓扑标注**：链 / 星 / 树，或**成环**（列出环上的关系） | 决定处置策略 |
| 该范围**自 HEAD 以来的实际文本差异**（`git diff`，默认折叠，`--diff` 展开） | 指纹只能说「变了」，差异才能让模型判断「这个变化是否影响对面的断言」 |

差异那一项要标注口径：**它不等于「自上次核对以来的差异」**（核对自己不必伴随提交），所以它是最佳可得的近似，不是精确口径。写明这一点，免得模型误以为那就是全部变化。

**由拓扑决定的两条处置规则**：

- **无环**（链、星、树）：从**变了的源头**向外逐层推进，每层一次 `rebind` 或一次编辑即可。
- **成环（长度 ≥3）**：**先把环上各端的表述一起定稿，再逐条 `rebind`**。逐条处理无论怎么排序都会互相推翻：改 A 会让 C 失配，改 C 又会让 A 失配。（**一对互引不属此类**，它是长度 2，见上。）

**形态**：`check --graph [--changed <path>] [--format text|json]`，与钩子中止时的工单共用同一份输出（命令名待定）。

### 3.18 钩子的视图刷新写到哪里（未决，2026-09-21 记）

**这一节是留给回来继续时的入口，不是结论。** 钩子的主体是机械的：审 index → 对账 → 渲染到不动点 → 有阻断就中止并出工单 → 校验「暂存 diff 含 `h` 变化时提交信息必须带证据」。未决的只有一处。

**背景（三份内容）**：git 里同一个文件有三份内容，工作区（磁盘上你编辑的那份）、index（`git add` 放进去的那份）、HEAD。`git commit` 提交的是 **index**，不是工作区。所以钩子审 index，这一条已定（§3.14 也写着「从索引而非工作区对账」）。而渲染按裁决是**无条件全局**，于是钩子每次跑都必然发现一批过期视图、必须把它们写出去。写进哪一份内容，就是这处分叉。

| 选项 | 做法 | 代价 |
|---|---|---|
| 甲 写工作区 | 用现成的 `render.apply` 写盘，然后中止，要求重新 `git add` | `git add <文件>` 是**整份暂存**，会把这个文件里没打算提交的改动一起卷进这次提交，`git add -p` 的局部暂存也被冲掉；而且提交能否过关取决于人在正确时刻做对一步 |
| 乙 写 index | `git hash-object -w --stdin` 造 blob，`git update-index --cacheinfo 100644,<sha>,<路径>` 换进 index，工作区不动 | 提交后工作区那份仍显示旧视图，`git status` 多出一处改动（实测 `MM`）；补救是「该文件本来没有未暂存改动时顺带也写工作区」（实测补上后回到 `M `，即正常的已暂存待提交） |

**我倾向乙**：甲把「提交进去的树里视图与内容一致」的达成条件挂在人的后续动作上，而它出错的方式恰好是本项目已经吃过一次亏的那类（漏 stage 的改动静默漂移；动他人暂存）。乙让钩子自己对这件事负责。**但阶段四的清单里已经写着甲**（「渲染后若有文件被刷新，中止提交并提示复核重新暂存（不得静默改写已暂存内容）」），那条写于「按闭包收窄渲染」的时期，当时要刷的视图少、重新暂存是顺手的事；改成「每次提交全量」之后它的成本变了。**这一条我不擅自改，等裁决。**

**两条路都躲不掉的前置**：钩子今天审不了 index，因为 `marks.derive()` 从磁盘读文件。得先把 index 物化成临时目录：`git checkout-index -a --prefix=<临时目录>/`。实测拿到的是 index 那份内容（工作区是 `A-worktree-newer` 时，快照里是 `A-staged`）。注意它**默认不覆盖已存在的文件**，所以要么每次用空目录，要么加 `-f`。上面三条 git 命令都在仓库外的空仓库实测过，不是照文档推的。

**另一项前置**：§六 待定项 4（全量刷新的性能上界）原先挂「实现时再测」，随渲染改为每次提交全量而变成钩子的前置。本仓库现规模线性扫描无压力，但上界要实测，否则它是提交延迟的隐藏成本。

**状态（2026-09-21）**：`rebind` 与显示层已完成（`65bd8a7`）；阶段三两条验收当日补齐。**未做**：钩子本体、`doctor`、阶段二迁移。复核用的仓库外样例与驱动脚本在 `$TEMP/p84_fx/`（`fx` 至 `fx6`，`drive8.py` 是端到端骨架、`drive9.py` 是渲染三条）；TEMP 被清理就会丢，重建时按「每个状态造一份」写即可。

## 五、外部造物调查（prior art，供后续复用）

### 5.1 三层能力分别有工具，无一个全覆盖

| 能力 | 工具 | 状态 |
|---|---|---|
| 行号引用校验与自动修 | `docs-coderef`（npm） | MIT，0 star，AST 仅 TS/JS |
| 内容引用（构建期生成） | Sphinx `literalinclude`、`pymdownx.snippets`、`embedme` | 成熟；embedme 238 star 但停更于 2024-10 |
| 绑定 + 漂移门控 | `drift`、`menard`、`docalign`、`maat`、Swimm（商业） | 见下 |

### 5.2 drift（fiberplane，Zig，MIT，146 star，v0.10.1 / 2026-06-22）

内容寻址的指纹锁：`drift.lock` 存 `doc + target + sig`；`sig` 是 tree-sitter AST 归一化遍历（只取节点类型、结构、token 文本，不含空白与位置）后 XxHash3 的结果。判定完全不依赖 git 历史（DECISIONS #4：SHA 在 rebase 后可能不可达，内容指纹永远可重算）。支持文件级、符号级 `#Symbol`、文档标题级锚点。附带 markdown 死链检查、`origin` 跨仓跳过、`--changed` 增量、版本化 JSON schema `drift.check.v1`。**relink gate**：目标已变时 `drift link` 默认拒绝，需 `--doc-is-still-accurate` 才放行。**无 Windows 二进制**（release 矩阵只有 macOS/Linux 四个目标），构建需 Zig 0.16（pre-1.0，破坏性变更频繁），非 vendor 源码约 33.6 万字节。

**不可直接 fork 的理由**：工具链风险 + 无 Windows + 去语言化等于重写（符号能力全建在 tree-sitter 与每语言 `.scm` 查询上）。

### 5.3 menard（Python，Apache-2.0，0 star，0.4.0 / 2026-04）

git diff 时序判定：解析文档标题得章节行范围，先看 `git diff --cached`，再回退 git 历史，判断章节行范围内在代码最后一次变更之后有没有被编辑过。`.menard/links.toml` 声明绑定；`transitive_depth` 走 import 图；`donttouch` 保护章节与字面量；`auto_generated` 跳过工具生成文档；`exclude_docs` 排除 ADR/计划这类「记录历史决策」的文档；`bootstrap` 自动建议绑定；`reviewed.json` 记 `{code_file, doc_target, reviewed_at, code_commit_at_review, reviewed_by}`，代码再变则已核对失效。CI 仅 ubuntu。

**判定偏松**：章节行范围内一次空白编辑即可清除 stale。

### 5.4 Doorstop（Python，LGPLv3，CI 覆盖三平台，2014 起）

最接近本设计的先例，且已跑十几年：每个条目（YAML）有 `reviewed:` 字段存**自身内容**指纹；每条链接存「父条目 UID + 建链时父条目指纹」；父条目指纹变即报 suspect link；必须显式 `doorstop clear` 才清除。这证明「双端指纹 + 显式核对 + 改动自动重开」这套设计可跨平台、可长期存活，且完全不依赖编程语言。

**不可直接用的理由**：粒度是整条目文件而非文档段落；自带整套需求管理生态（document tree、HTML/Excel 发布、GUI）；绑定仍手工建，无存量反推能力。

### 5.5 其他可复用机制

- **W3C Web Annotation Data Model**：`TextPositionSelector`（起止位置，便宜精确）与 `TextQuoteSelector`（`exact` + `prefix` + `suffix`，且 `exact` 须 normalization）**并存**。这是「引用如何熬过编辑」的成熟工程答案，且语言无关。本计划 §3.12 采用其思路。
- **XLink / HyTime（ISO/IEC 10744）**：把链接按存放位置分为 inline / inbound / third-party 三类。本设计的「引用侧标记 / 被引侧标记 / sidecar」正对应这套三分法。
- **Python `doctest`**：执行并校验内联输出，官方定位含「检查 docstring 是否最新」。
- **`inline-snapshot`**：把期望值直接写进源码并可一键更新。
- **`nbstripout`**：反向教训，notebook 内联结果腐烂后的标准补救是干脆删掉。
- **失败模式教训**：内联派生数据（notebook 输出、org-babel `#+RESULTS:`）的失败全部来自「没人负责重算」，因此在 §3.9 把重算做成事件驱动加提交时强制。

## 九、实施顺序与验收标准

**一条排序上的事实**（2026-09-18 补）：**漂移报告需要「记忆」才能存在，而记忆由迁移写入。** 所以在迁移之前，工具只能产出「迁移就绪报告」（每条引用能解析成什么、指纹是多少、哪些解析不了），不可能产出漂移报告。原文把阶段一定义为「双哈希比对」是错的（比对两边里有一边还不存在），已更正；原先挂在阶段一的验收准则（幂等、危险位置）也属渲染阶段，一并后移。

### 阶段一：解析与指纹内核 + 迁移就绪报告（纯读，零写入）

产出一个能读懂**现状**（旧格式引用）的工具，既为迁移产出入参，也在真实数据上验证全链路里最难的两块。

- [x] **引用解析**：识别现存的三种形态（`file.py:NNN`、`file.py:NNN-MMM`、markdown 链接里的 `path.py#LNN`），处理有无目录前缀、有无行号
- [x] **消歧与解析**：basename 到唯一文件的解析；解析不了的要分类报因（文件不存在 / 行号超界 / basename 歧义）。实际落成五档阶梯：`ok` / `out_of_scope` / `untracked` / `external` / `file_not_found`（外加 `ambiguous` / `unparsable` / `line_out_of_range`），每档对应一种不同的处置

- [x] **指纹器**：代码侧 `ast` 归一化哈希（`ast-v1:` 标签），文档侧散文归一化哈希（`sec-v1:` 标签）；模块级锚点用 `line-v1:` 行指纹
- [x] **报告**：JSON 与人读两种；另有 `sample` 产出可复现的分层抽查稿
- [x] 扫描范围走 `git ls-files -z`（**必须带 `-z`**：不带时 git 会八进制转义含非 ASCII 的路径，症状是这些文件被静默跳过，实测引用数从 341 掉到 18）

- [x] **确定性**：同一输入连跑两次，报告逐字节相同（两轮编辑后各复验一次）

- [ ] 门控层判据的召回：实测十条锚点硬错里只有三条被命中，其余七条形态上不可判（详见 §1.3 与 §九）

| 项 | 结果 |

**结论：不支持「解析层已可信，可以进入迁移阶段」。**

支持的是**文件级**：目标文件全对，别名裁决经内容核实成立。不支持的是占九成的 `ok` + `module_level`（307 条）——它们现在的「可信」只等于**「行号仍落在文件内」**。抽到的 12 条已解析项里硬错 2 条，粗估该类比里混着 17% 到 33% 的错锚点（n 小，区间宽）。

**因此迁移前必须加一道目标侧校验**，它不需要重做解析（2026-09-18 已实现，见下节）：

- 文档若点名了符号，**该符号必须覆盖目标行的位置**（这是那条硬错 `gdr.py:427` 的直接判据）；  <!-- refcheck:example -->
- **模块级单行锚点**不得落在注释或空行上；
- 未过校验者**不进迁移基线**，先人工重锚。

**这两条后来被拆成两层，理由见本节末尾**：第一条的精度只有约七成（文档既引定义处也引使用处），当门控会挡掉大量正确引用，故降为「复核队列」；门控层只留高精度判据。

**原列的第一条（「目标行不得是注释、字符串或 docstring」）经实施后实测被否。** 本项目注释承载论证，被文档有意引用是常态，单看这一条时 17 条命中里只有 3 条是真错。真正的危险只有「模块级」这一种：符号内部的锚点指纹是整个符号，代码动了指纹就动；而模块级的指纹就是被锚的那一行本身，锚在永不改动的行上等于没有记忆。收窄到「模块级 + 单行 + 非字符串」后，本仓库 414 个文件里只剩 4 条命中（2 条注释 + 2 条空行），逐条核对全为真错位。此外范围锚点一律不报（范围首行是注释无妨），已落在字符串（docstring）内的行也不报。

**不做这道校验的后果已经看到**：那条错引用落在注释行上，而注释永不变动，于是它在后续漂移检测里会表现为**永久稳定**（「假稳定」）。按当前指纹固化基线，等于把错误锚点冻进记忆。工具其实已经持有可用信号（源侧的 `py_signal_lines` 算出了注释/字符串行集，`symbol_at` 也拿到了符号名），只是没用于**校验目标行**。

#### 由审查结论引出的设计更正（重要）

修完判据后重测，门控 8 条（7 真 1 误）、复核队列 23 条（16 真 4 误 2 条属「讨论引用机制的正文」）。但**真正的结论不是判据精度提到了多少，而是判据这条路走不通**：

> 审查在基线里找到 10 条锚点硬错，**没有任何确定性判据能认出来，最终只补抓到 3 条**。剩下 7 条的形态是「被引代码在锚点附近整体移动过」「文档引的是使用处而符号定义在别处」「文档描述的那段分支已被重写」，这些都要读语义才能判断。§1.3 早就写过这个上限（确定性工具只能判断文件在不在、行号越没越界），本轮把它量化了：**约三成**。

**据此更正两处设计：**

1. **`in_baseline` 的语义降级。** 它此前写的是「可进迁移基线」，容易被读成「可信」。现更正为：**只表示「确定性层面没发现问题」，不表示锚点指对了**。工具输出里也照此措辞。
2. **阶段二不再是「机械迁移 + 冻结当时的锚点」，而是「语义重锚 + 写下记忆」。** 这是更根本的一处：原写法假定迁移是纯机械的，把现状锚点原样冻进记忆。既然现状锚点里混着约三成错的，冻结等于**把错误锚点冻成永久稳定的记忆**，正是本计划自己最担心的「假稳定」。改为：迁移时对每条引用确认正确的范围（这一步必须读语义），标记围住的是**确认过的**范围。

### 阶段三前置：`rebind`（已落地）

`tools/refcheck/rebind.py` + `rebind` 子命令。**名字不叫 `verify`**：那个名字读起来像纯读的检查，而它恰恰是**唯一改变判定结果的写操作**，名字与后果反着。叫 `rebind` 是因为它**不改关系的存在，只把记忆重新绑到现状**——与 §3.14 否掉的 `bind`/`unbind`（建与拆关系）是两回事。

三条约束，各有出处：**必须带证据**（`--note`，§八「语义核对被橡皮图章」→「核对须写证据」）；**环上拦住**（§3.16「成环时必须先把环上各端表述一起定稿再逐条处理」）；**顺序无关**（写 `h` 不改变任何指纹，故两侧一起写不自锁）。

样例三验过：漂移后写回两侧即消解；两侧都落 `v=`；幂等（第二次 0 处写入）；证据必填、含 `;` 被拒；视图原样保留（随后由 `render` 刷新）；环上不带 `--allow-cycle` 被拒（报出环 `D1 -> S1 -> D1`），带则放行。

**测试当场抓到一个哑掉的守卫**：环上应当拦住，第一版却没拒绝。原因是我拿 **uid** 去**文件级**的环里找，永远找不到。判「这条关系在不在环上」必须用 **uid 图**——一个文件里可以有几十个范围，文件级的环会把不相干的关系也算进去。已改为 uid 图，`diag` 仍用文件图（它回答的是「改这个文件牵动哪些文件」）。

### 机器区是「`;` 分隔的键值字段列表」（写明，非改格式）

`rebind` 要写核对时间与证据，这两样必须落在**机器区**：渲染区是纯输出、会被下次渲染覆盖，放那里等于丢；而 §3.14 明确要求钩子工单能读到「上次核对时间与证据」。加字段**是否算改格式**，取决于机器区的读法：

| 读法 | 加 `;v=…` 算不算改语法 |
|---|---|
| 机器区是**键值字段列表** | **不算**。只多一个字段，分隔符、边界、两段结构一个字符没变 |
| 机器区是固定 `;h=` 槽 | 算，要重新冻结 |

**采用第一种**，理由是分号的存在本身就说明它是字段列表（否则那个 `;` 只是给 `h` 配的装饰），§3.2.6 的字段表也把机器区当作承载多个字段的地方。**这是把格式已经蕴含的东西写明，不是改格式。**

配套三条规则：
- **字段顺序固定**（`h` → `v` → `ev`，见 `FIELD_ORDER`）：`rebind` 按规范序重排而非追加，`git diff` 于是只显示值变化。
- **值里不许出现 `;` `|` `<` `>`**：前两个是分隔符，后两个破坏标记边界。提交哈希天然合法（只有十六进制与字母）；**校验并拒绝**含这些字符的值，不静默截断——截断等于数据被悄悄改掉。
- **认不出的字段要报**（`unknown_field`）：依据本项目「参数键名即契约」那条纪律，键名写错会让那一项静默失效，必须喊出来。

**年龄仍然不进视图。** B 的含义就是：视图保持 `(最短定位;状态)` 不变，时间只作为**核对记录**留在机器区。理由是状态是派生的、不会腐烂，视图里的年龄没有用途；而证据是一句**在某个时刻作出的断言**，它需要时间戳才可解释。

### 阶段二/三前置：`render`（已落地，第一个会写盘的命令）

`tools/refcheck/render.py` + `render` 子命令，`--dry-run` 就是设计里说的**时效性诊断**（只报哪些文件的视图会变，不落盘）。渲染**无条件全局**，不接种子集。

仓库外样例三（2 文件 / 3 关系）验过六条：写对；**不自锁**（渲染后 `check` 仍全绿，印证 §3.10 的剥离顺序使写视图不改变任何指纹）；**幂等**（第二次待写 0 处）；漂移后视图转 `tgt_drift`；**改回原样自动恢复 `ok`**（因为是「记忆 vs 现状」的比较，不是「有没有被改过」，所以误改后撤销不留工单）；危险位置拒绝写入。

**定位符用行号，不用符号名（2026-09-19 两次更正）。** 我一度改成「符号优先」（能用符号名就用 `pity.py::compute_pity`），理由是行号会随上方代码移动而变、引起视图重写。**这个理由把优先级搞反了**：

- **让行号自动更新本来就是这套设计的初衷之一**（最初的问题就是「代码一改，按行号引用的地方全部失效」）。把行号从视图里去掉，等于删掉一个设计特性去换一个不是问题的东西。
- **行号变化不改变指纹、不改变漂移状态**，所以它引起的视图重写**不是正确性事件**，只是把显示刷新一次。实测：在文件头插入 3 行 → **2 处视图重写、0 条阻断**，原样提交即可。

**由此顺带更正 §3.10 的一个说法。** 那里写「写入次数与**状态跳变次数**成正比、与编辑次数无关（视图显示的是状态而非哈希，是阶跃函数）」。这句对**状态**字段成立，对**定位符**字段不成立：定位符会随行号移动而变。准确措辞是**写入次数与「状态跳变次数 + 定位符移动次数」成正比**，而两者都不与编辑次数成正比。这个更正不改变设计的任何机制，只是把一句过强的断言收准。

**「行号自动更新」这个承诺的实现点**：不在记忆（记忆是内容指纹，与行号无关），而在**视图的定位符**——它每次渲染重新算，永远是当前行号。这才是「按行号引用不再失效」的实现方式。

`--dry-run` 与 `render` 共用同一条路径，所以「时效性诊断」不是一个独立能力，是渲染的只读模式。

### 阶段二前置：`check`（对账函数，已落地）

设计里把对账函数叫**核心原语**（§3.14）：从磁盘现状出发，扫标记、算指纹、派生状态。幂等、无状态、谁都能调，**钩子只是闹钟**。它是阶段二唯一的验收仪器（「迁移后 `check` 全绿」），所以先于迁移做。

实现落在 `tools/refcheck/marks.py` + `refcheck.py check` 子命令，纯读。已验证：`ok` / `tgt_drift` / `src_drift` / `broken` / `orphan_segment` / `unmatched_start` / `unmatched_end` / `dup_segment` / `dup_decl` / `role_conflict` / `unparsable_mark` 各自的触发；改被引侧内容后引用侧报漂移、改回原样后恢复 `ok`；两侧段数不等（2 段对 1 段）能配；代码侧范围走 `ast-v1`、文档侧走 `sec-v1`。

**样例一（仓库外，2 文件 12 范围 8 声明）查出我实现的四个 bug**，四个都是「设计到代码」的转换错误，纸面读不出来：

| # | bug | 后果 |
|---|---|---|
| 1 | 范围切片按**行的首尾**，不按标记自身的偏移 | 同一行并排两段时，两段被切成同一段、**指纹相同**，于是「这两段内容不一样」永远检不出来 |
| 2 | `orphan_segment` 只找「范围**之内**的声明」 | 被对端声明指着的范围被误报孤立。正确判据是「之内没有声明**且**全库没有声明指向它」 |
| 3 | 漂移状态名按**被引文件的扩展名**猜（一个两分支相同的残留表达式） | `src_drift` 永不出现。正确来源是**这份声明自己站在哪一端**，而站哪一端由标签自报（`引用对象/描述对象/规格/被测物/出处` 是引用侧，另一列是被引侧） |
| 4 | 打错的标记**不可见** | 闭标记多写一个 `>`（`<\|/e:S1#*>\|>`）表现为「这里没有标记」，症状只有范围变 `unmatched_start`，真正的原因看不见。现加近失标记检测 |

**样例另暴露四个计划里没写清楚的问题，两个必须在迁移前定**：

1. **两端都写的形态没有语法。** H1 定了「声明不在自己的范围之内时必写全两端」，但 §3.2 的样例只示范了「只写对方」那一种，没写「两端都写」长什么样。解析器现在把这种情形报成 `orphan_decl`。**迁移前必须定**：Python 里范围是函数、声明作为注释落在函数体内（合法），但表格行、代码围栏里的声明可能不得不放在范围之外。
2. **代码围栏内的标记会被当真标记读进来。** 实测本仓库 14 个标记全部落在 P84 自己的语法示例代码块里，`check` 报出 7 条阻断问题、全是假的。§3.10 说「标记落在代码围栏内是错误」，所以方向一致，但需要：扫描时先判围栏、把围栏内的标记单独报成一类，以及给语法示例一个不被扫的写法（与 `refcheck:example` 同类）。
3. **标签词表的五对是互斥的。** 样例里文档侧写 `引用对象`、代码侧写 `实现`，被正确地报成 `role_conflict`。含义是：一条关系只能从五对里挑**一对**用到底；「用默认那对还是用语义那对」是逐关系的决定，迁移时需要一条一致的规则，否则会批量产生 `role_conflict`。
4. **代码侧的范围应该圈什么，计划没明说。** 样例里我自然地把范围圈在了注释行上，而真实引用指的是**代码**。按 F1（Python 必须有范围标记）推断，范围应圈符号本身、标记以注释形式贴在符号外；这条要写成迁移规则，否则每条引用都要临场判断。

**围栏感知已实现，`check` 现在能跑真实仓库**：本仓库对账结果是「0 个标记 / 0 个范围 / 0 条关系，无问题」——仓库里确实还没有真关系。围栏内的标记单独报成一类（`mark_in_fence`，阻断），因为 §3.10 把围栏内定为危险位置（那是**示例**，不是真标记）。据此给本计划自己那两段语法示例代码块加了**区域形式**的示例标记：

```
<!-- refcheck:example:start -->
（代码块）
<!-- refcheck:example:end -->
```

区域形式是必需的：展示标记语法的代码块里，逐行插单行标记会把示例本身弄脏，而它恰恰是最需要排除的一类。单行形式 `<!-- refcheck:example -->` 保留给散句里的示例。加上区域标记后，本计划自身贡献的引用从 15 条降到 **0 条**，仓库的去重引用总数从 279 降到 268。

**围栏那条规矩的精确措辞（2026-09-19 更正）**：错误判据是**「标记自身落在围栏内」**，不是「范围覆盖围栏」。后者是**正常用法**，也正是引用一段代码块的做法：标记贴在围栏外面，范围圈住整段围栏内容，视图落在围栏外的散文里正常渲染。

<!-- refcheck:example:start -->
````

<|e:X#*|>                      ← 标记在围栏外
```python
def compute_pity(...): ...
```
<|/e:X#*|>                     ← 标记在围栏外
<|引用对象：Y#*;h=…|(…)>
````

**为什么围栏内是错误，理由要说准**：不是「视图会变成代码里的字面文本」——围栏里的标记本来就是字面文本，多一段视图只是更多字面文本。真正的理由是**内容保真**：围栏里要么是被引用的代码、要么是要被引用的代码片段，读者与工具会照抄；往里写任何**会变**的东西（视图随状态重写），这段引用就不再是它声称的那段内容。设计原文的措辞其实已经收得很准（§3.10「此判据只看标记自身所处的位置」），是行文里一度被说宽了。

**一处仍未做的判定**：四空格缩进的代码块（非围栏）不算围栏，因为那里面通常正是**要被引用**的代码片段，标记落在其中是否为错误，本期不定。

### 阶段二/四前置：本轮定下的五条（2026-09-19）

**1. 「两端都写」这个形态取消了，声明位置回到硬约束。** 原先 H1 把声明位置放宽为软约束，代价是「必写全两端」并新增 `dangling_decl`。**该放宽没有必要**：标记贴在外层、**声明放在开标记之后**即可，声明因此既在自己的范围之内、又落在围栏或表格这类不便的位置之外。

<!-- refcheck:example:start -->
````

<|e:X#*|>
<|引用对象：Y#*;h=…|(…)>
```python
def compute_pity(...): ...
```
<|/e:X#*|>
````
<!-- refcheck:example:end -->

而且指纹会**剥离全部标记**，所以声明这段文字不改变 X 的指纹。Python 同理：整身是 docstring 的函数，把声明写成注释放在 docstring 之后即可，注释不进 AST，指纹稳定。**唯一例外是 sidecar，而它不是标记语法**（§3.6 明写「格式：TOML，非标记语法」），键值形态里两端都得写出来是自然形态。

连带结论：短形态（只写对方）够用；**取消** `dangling_decl`；`orphan_decl` 恢复为真错误（声明不在任何范围之内）；§3.2.6 字段表不多项。

**2. 渲染：无条件的全局，任何场合都不按闭包收窄。**（2026-09-19 更正：我一度写成「能力全局、钩子写入按闭包收窄」，那是错的。）渲染的输出（最短定位符 + 状态）是**全局事实**，不依赖从哪个文件出发，所以「哪些视图该变」本身就是全局的、结果与种子集无关、可用「连续两次零 diff」验收。更关键的是**只有无条件全局才能保证没有任何视图在报「ok」而实际已漂移**：按闭包收窄时，闭包外的过期视图会一直显示 ok，读那份文档的人被误导，而那份漂移恰恰是「需要被注意到的」。所以：每次提交把**全库**视图刷到最新、只写字节真变了的，**要求重新暂存的范围限闭包内、其余列为建议**（写入足迹与提交要求是两件事，前者由「状态是否真的变了」决定，后者由第 3 条决定）。

**这条把 §六 待定项 4（渲染区全量刷新的性能上界）从「实现时再测」提前为前置**：原先只有 SessionStart 全量，现在是**每次提交全量**。本仓库现规模（414 文件 / 约 270 条引用）线性扫描无压力，但上界要实测，否则它变成提交延迟的隐藏成本。

**3. 判定要求 = 闭包内；闭包外刷新只列为「建议一并提交」。** 机制的本质是保证**提交进去的那一份**是对的，以及**提交之后**未被改动的东西仍然是对的（零改动自洽）。

「提交之后」这个限定词是关键，不能省：**很久不提交、不重渲，已经提交且未被改动的引用也可能真的漂移了**（别的文件被改了，记忆就与现状不符）。所以不变量只在**提交那一刻**成立——那一刻整个工作区刚刚通过检验。两次提交之间漂移自由累积，这是正常的；它会在下一次提交时被重新检验，而不是被静默放过。

**4. `status` 并入 `diag`；`rebind` 必须独立。** `status --explain` 与 `diag` 是同一次派生、更窄范围、更多细节，故并成 `diag --rel <uid> --explain`。但 **`rebind` 不是 `render` 的局部版**：

| | 写什么 | 性质 |
|---|---|---|
| `render` | **渲染区**（状态显示） | 幂等、可随时跑、跑错无害（下次渲染覆盖） |
| `rebind` | **机器区的 `h`**（记忆） | 整套里**唯一改变判定结果**的写操作；跑错就把错误范围冻进记忆，而错锚点的指纹自洽、**此后永远检不出来** |

故 `rebind` 独立、必须带证据（`--note`），且按项目规矩不得由编写者自查。

**5. uid：走「全库清单 + 判定覆盖归档」，不发号命令。** uid 必须全库唯一，但扫描集**不覆盖归档**，所以归档里的 uid 会被漏看，撞号要等到文档被恢复时才暴露。做法：产出一个**含归档与 `.recycle_bin`** 的全库 uid 清单（只扫 uid、不解析内容，成本很低），并让撞号判定也覆盖归档。agent 自己挑，工具负责抓。不新增发号命令，理由与 §3.14「建关系就是编辑文本」一致。**已定（2026-09-19）**：与归档中的 uid 相撞**算阻断**。理由：换一个随机 id 是零成本，而漏掉的代价是几年后恢复某份文档时突然冒出 `ambiguous`。

**6. 四空格缩进代码块：本期不判定。** 实测本仓库 0 处。它与围栏的语义不同（围栏多用于示例或引用的代码，缩进块多用于**要被引用**的代码片段），标记落在其中是否为错误没有依据，故暂按「不判定」处理；将来若真出现，按围栏同样处理。

### 阶段二/四前置：`diag`（关系图诊断，已落地）

设计里 §3.16 的关系图诊断与 §3.9.1 的闭包门控，本轮合并成**一个**命令：一次计算、三种视图。原打算拆成「hook + 传染核查」两个，是错的：**图本身不可行动**——「这些文件连在一起」不说明任何该做的事，可行动的是「提交时会被报什么」，而两者本来就是同一次计算的产物。

```
python tools/refcheck/refcheck.py diag [--changed <paths>]
```

输出三块：**闭包**（节点与边，每条边带状态）、**环**、**模拟提交判定**（闭包内会被报的项）。纯读。`hook` 将来就是它加上两步钩子独有的东西（从**索引**而非工作区对账、有文件被改写就中止）。

样例上的实测（两文件）：

```
docs/spec.md#D1  --引用对象(ok)-->  src/pity.py#S1
src/pity.py#S1   --引用者(ok)-->    docs/spec.md#D1
起点 src/pity.py -> 闭包 [docs/spec.md, src/pity.py]
   环：[docs/spec.md -> src/pity.py -> docs/spec.md]
```

**环在这个最小样例上当场出现**，印证设计里那条预判（「环在本项目很可能是常态而非例外」）。这条输出就是诊断的价值：让改的人在动手前知道自己在环里，而不是改完一圈才发现。

**一条措辞上的精确化**：能计算的是**闭包**（关系图上连通的节点集合），不能计算的是**传染**（「改了 A 就必须改 B」是语义判断，设计里叫内容传播，无界、可成环、终止于作者判断）。工具能给的是闭包加状态，也就是把「你可能要改的东西」摆全。

**一处设计漏洞（已定，2026-09-19）**：视图要带年龄，但机器区没有任何「上次核对时间」，而工具不解析渲染区，所以年龄没有可读来源。**定案（用户选 B）**：视图**不带年龄**（状态是派生的、不会腐烂，年龄在视图里没有用途），改为在机器区加 `v`（核对时的基线提交）与 `ev`（证据）两个**可选**字段，作为核对记录。见 §3.2.6。

### 阶段二：存量迁移（语义重锚 + 写下记忆）

**范围更正（2026-09-18，由第二轮审查引出）**：原写「机械迁移，迁移时写入当时的指纹」，假定迁移是纯机械的、把现状锚点原样冻进记忆。**这个假定是错的**：实测现状锚点里混着约三成错的，冻结等于把错误锚点冻成永久稳定的记忆。故本阶段定义为「对每条引用确认正确范围、标记围住确认过的范围」，其中定位那一步必须读语义，不是机械替换。

- [ ] 逐条确认锚点（模型执行，工具的分流器给优先级：门控命中的先排除，队列命中的先处理，其余批量过）
- [ ] 标记围住**确认过的**范围，写入当时的指纹
- [ ] 先 01-活跃，再 02-待办；归档不动
- [ ] 无文件名的行号引用（`` `L3899` ``、`` `:609` ``，实测约 65 处 / 11 个文件）先定解析规则再纳入，或显式排除并登记

验收：

- [ ] 迁移后 `check` 全绿
