# 模拟工作区 -- 理论

> 创建日期：2026-10-01（首次建档）
> 来源：2026-09-30 至 10-01 的设计讨论（用户逐轮裁决）。计划文件见 `P87 模拟工作区——派发编排与工作区存储.md`；本文只讲**为什么**，不讲怎么做。

---

## 一、这一层为什么存在

「跑一次模拟」作为一件完整的事，有六步：构造环境、设置调用态字段、调核心函数、跑不抽卡基线、消费返回值、组装数据集。其中**只有第三步是共享的**（所有入口都调 `run_batch_parallel`），其余五步每一处调用方各写一遍。

后果有三层：

1. **同一次模拟的产物不一致**：WebUI 存出的数据集 `pool_types` 恒空，GUI 存的是真实推导值
2. **新增入口要复制胶水**：不是「改一处」，而是「再写一遍」
3. **core 反向依赖 service**：两个算法模块（撤退搜索、最差影响）在自己的循环里派发模拟，靠函数内延迟导入压住循环依赖的症状

第三层最能说明问题：**派发没有自己的家，所以谁需要谁就自己调。** 本层的存在就是给它一个家。

## 二、概念层级

这一节的结论决定后面所有设计，故先立。

### 2.1 三个概念

```
配置参数 = 策略 + 目标卡 + 初始资源 + 池子 + 保底 + Banner + 资源生命周期 + 里程碑 + ...
运行参数 = 种子 + 模拟次数 + 进程数 + 进度回调 + 输出开关 + ...
模拟参数 = 配置参数 + 运行参数
```

「配置参数」是 `ConfigStore` 承载的全部内容；「运行参数」是每次跑的临时参数。两者不是并列的两类字段，而是**层级关系**：运行参数附着在配置参数之上，加在一次具体的运行上。

### 2.2 运行参数不进配置身份

**判据**：改种子只是同一配置换一组样本，改次数只是换样本量，都不产生新的配置语义。所以「两份数据是否可比」只应看配置参数。

现状是半自治的：`compare_fingerprints` 把 `seed_start` / `seed_end` / `num_simulations` 列入对比维度，但判定逻辑 `ComparabilityDiff.mode_label()` 判断「是否配置差异」时已把它们排除。本层把这个现状做干净：**指纹拆为 `ConfigIdentity`（进配置身份）与 `RunRecord`（种子范围、次数、耗时，供可复现性与回归使用，不参与可比性判定）**。

### 2.3 推论

- 配置身份与运行记录是两件事，不应挤在一个结构里
- 「同种子同结果」是**可复现性**问题，不是**可比性**问题
- 数据集必须同时记住两者，但只有前者决定它能不能与别人比

## 三、本层内部的三个系统

本层不是一个系统，而是三个。划分依据是「变化的原因」：什么变了会导致哪一块要改。

| 系统 | 职责 | 因什么而变 | 对外接口 |
|---|---|---|---|
| **工作区机制**（基础设施） | 目录结构、文件读写、系统注释、索引、锁、版本、迁移 | 存储方式变了（换数据库、加文件类型） | 读/写配置与数据集；查关系；加锁 |
| **配置生命周期**（领域） | 身份（相对路径）、派生、写时复制、Draft 与 File、冻结规则、引用查询 | 配置的语义变了（加模板、加继承） | 从草稿创建配置、派生、查「谁引用它」 |
| **任务编排**（领域） | 变换器、运行器、汇合器、任务对象、进度、取消、批次 | 任务类型变了（加敏感性分析） | 提交任务、查进度、取消、按批次取产物 |

### 3.1 为什么这三者可以分开

**工作区机制与配置生命周期的分界**：「文件在哪、怎么读」是机制，「什么时候该派生新配置、谁引用它」是语义。机制可以整体替换（文件系统换成数据库），而语义不变。

**任务编排与前两者的分界**：编排管的是「跑什么、跑到哪了」，产物落在哪、怎么组织是工作区的事。两者通过「运行器」这一个接口相接：编排交出「配置身份 + 运行参数」，拿回「数据集 id」。

### 3.2 不属于这三个系统的部分

以下不属于本层，只是被本计划触发：

- **既有算法模块的接入**（最差影响、方案搜索改造为任务类型）：它们是「把既有代码接进编排系统」，属任务编排的一次应用，不是新系统
- **基线节点**：是配置生命周期（派生）与任务编排（策略维变换）的联合应用，本身不构成系统
- **`core/` 的重构**：引擎层的事，本层只是触发者

## 四、工作区机制的原理

### 4.1 内容文件化，关系注释化

工作区里的「东西」分两类，它们的存储方式不同：

- **内容**（配置文本、数据集）用**文件**：可编辑、可寻址、可 diff、CLI 能直接吃、可被操作系统工具处理。这是虚拟容器给不了的能力
- **关系**（这份配置派生自谁、这个数据集用了哪份配置）用**注释行**写在内容文件里

关系放注释的理由，是让**元信息随内容走**：把一份配置拷给别人、整体打包工作区，派生关系跟着文件一起走，不会因为漏带索引而丢失。等价地，这也让另一个方案（每配置一个伴生的 `.meta.json`）显得多余：它只是把文件数翻倍，换不到注释拿不到的东西。

关系用注释而不是写进配置结构，是因为它**不参与配置身份**：`compute_config_hash` 算的是解析后的结构，注释天然不在其中。系统字段混进 TOML 的表结构里，会让「配置内容」与「系统记账」纠缠。

### 4.2 索引是纯缓存

索引（`index.json`）是从注释与文件扫出来的**派生结果**，不是真相。删掉它，重扫即可恢复。这是「元信息随内容走」的直接推论。

但要如实区分可恢复的程度：

| 内容 | 丢失后能否重扫恢复 | 依据 |
|---|---|---|
| 配置列表、数据集列表 | 能 | 扫目录 |
| 数据集 → 配置 的归属 | 能 | 数据集元信息自带配置身份 |
| 配置的父子关系与派生方式 | 能 | 配置文件的注释行 |
| 「配置是否被使用过」 | 能 | 由「数据集引用」或「活动任务」推出 |

**代价与降级场景**（如实登记，不假装完美）：
- 用户手工删掉注释行 → 该配置在重扫时成为孤儿（内容与数据集俱在，只丢派生关系）
- 用户手工把 `root-v1.toml` 复制为 `root-v2.toml` → v2 带着 v1 的注释，父指针指向不精确

两者都可接受：丢的是关系的形状，不是内容。

### 4.3 可搬移性

工作区是一个**自包含、可整体搬移**的单位。据此有两条硬约束：

- 工作区内所有引用一律**相对路径**（绝对路径搬移后失效）
- 工作区根记 **`format_version`**（未来格式演进时给出明确提示，而非静默错乱）

## 五、配置生命周期的原理

### 5.1 身份用路径，不用内容哈希

**内容哈希作为身份有一个致命缺陷：它随算法漂移。** `compute_config_hash` 的覆盖面是演进的（2026-10-01 一天之内就先后补入七项字段、删掉恒空形参、把策略三字段合成单一维度）。算法一改，历史数据集里记的哈希与新算的对不上，同一份配置重跑会被判为「不可比」，且是**静默**的。

因此：

- **身份 = 工作区内的相对路径**（文件不改名就不变）
- **内容哈希降级为「判等用」的元信息字段**（两份不同身份的配置内容是否相同，看它）

这个设计还有一个自然性质：**派生即新文件，即新身份**，与写时复制天然契合。

### 5.2 写时复制：跑过即冻结

**触发条件**：配置一旦用于跑过模拟任务，就不再原地覆盖；此后编辑一律派生新配置。

为什么不取「被数据集引用」而取「跑过」：一是判定更简单（一个标记 vs 反查引用），二是**更严**。「被引用」有个窗口：模拟跑到一半、结果尚未落库时，配置在技术上还「未被引用」，仍可被改。而事实上它已经与某次运行绑定，未来必然有数据集指向它。

**由此得到一条贯穿全层的不变量：工作区是 append-only（除删除操作）。** 数据集不可变、配置冻结后不可变、「改配置」即「派生新配置」。它带来可审计与可回滚，也简化了并发与缓存的一切推理。

### 5.3 Draft 与 File：只需要两个概念

配置在系统里有两种存在形态：

| 概念 | 职责 | 生命周期 | 落盘 |
|---|---|---|---|
| **Draft**（编辑缓冲） | 承接界面改动 | 面板打开期间，未保存即丢弃 | 否 |
| **File**（配置文件） | 工作区里的配置文件，**模拟只读它** | 冻结后永久不可变 | 是 |

**为什么不需要第三个「内存快照」概念**：写时复制保证「跑过的配置不再变」，所以派发直接读文件即可，「定格」由不可变文件天然提供，不必另做一份内存副本。

**推论**：未保存的编辑态不能直接开跑（它没有文件身份，而数据集要指向配置）。流程是「改 → 存 → 跑」，保存因此成为一个用户可感知的动作。

### 5.4 冻结后的删除语义

删除一个已被数据集引用的配置：**允许删，但给出警告并标记失效**（「这份配置被 N 个数据集引用」），那些数据集的配置指向随后显示为失效。**不级联删除数据集**，数据本身仍在。

理由：数据集的价值在于它的数据，配置指向只是来源记录。为了来源的完整性而阻止用户清理，代价大于收益。

## 六、任务编排的原理

### 6.1 变换器 + 运行器 + 汇合器

一项任务由三个部件构成：

```
变换器（Tx）：配置 → 一组 sub 配置
运行器（Run）：sub 配置 + 运行参数 → 数据集        （即调用模拟服务层并落工作区）
汇合器（Agg）：数据集集合 → 任务结论
```

三类任务由此统一：

| 任务 | 变换器 | 运行次数 | 汇合器产出 |
|---|---|---|---|
| 主模拟（+ 基线） | 策略维变换：派生一个 sub 配置（策略取 `no_draw`） | 2 | 主数据集 + 基线产物 |
| 参数扫描 / 敏感性分析 | 参数维变换：N 个 sub 配置 | N | N 个数据集的汇总 |
| 方案搜索 | **迭代变换**：每轮由前几轮结果决定下一个配置 | 数十次 | 搜索结论 |

**这个划分的要点在于变换器是「配置到配置」的纯逻辑**：它不认识模拟、不产生副作用，只是决定「下一步该跑什么」。正因如此，它可以是预定的列表、参数化展开、或依赖历史的状态机，而不需要为每种情形换一种任务类型。

**变换器的输出含派生描述**（`(sub_config, derivation)`），树上「这条边是怎么来的」直接取自它，不需要在别处再维护一份。

### 6.2 为什么不做递归嵌套

「任务套任务」看起来很诱人（搜索像是在任务里跑任务），但不必要：

- **变换器可以是迭代的**（依赖已产出数据），这已能表达搜索这种形态
- 递归会把进度上报、取消、失败传播**全部变成递归问题**，而实际形态只有「预定列表」与「迭代状态机」两类

出现第三类形态再升级不迟。

### 6.3 批次标识：组是查询，不是实体

一次搜索（或一次敏感性扫描）产生的一批配置与数据集，需要在结构上被认出是「同一批」。做法是派生的元信息里带一个**批次标识**，同批次即一组。**不引入容器节点**，子配置仍挂在它的父配置之下。

理由：容器节点（「任务节点」）会让「产物挂在产生它的配置之下」这条既有规则出现例外；而「组」实体化也与「树是视图」相悖。批次标识把「组」退化为一个查询，视图按需折叠成组即可。

即使不做折叠，这个查询本身也有用：把一批产物一起做分析、或一起打包。

### 6.4 派发原语收配置身份，不收内存对象

运行器的签名是 `run(config_id, run_params) -> dataset_id`。配置以不可变文件为载体，任务启动时读入并传给 worker。

之所以不需要传「配置快照对象」：写时复制已保证那份文件不会变，「定格」由文件本身提供（§5.3）。

**这条也结构性消除了「运行期间改配置污染结果」**：运行期间界面改的是 Draft，与正在运行的任务读的文件无交集。

### 6.5 基线是变换器的一次平凡应用

基线（不抽卡的资源水平）**不是主流程之后的附加步骤，而是策略维上的另一个规格点**：同一配置、策略取 `no_draw`。

这个视角解释了两件事：

- 为什么现在的基线实现别扭：它没有被安排进「变换器」的位置，只能被硬塞成附加步骤，于是三条入口各写一遍
- 为什么它能自然拿到「树上的位置」：它是主配置派生的一个 sub 配置，与用户手工派生的变体同构

**一处必须写清的边界**：基线当前与种子无关（实测三种子产出一致），因为当前**无随机源**：策略全程只等待，不抽卡则不触发里程碑，资源收入全为日程规则。**这是当前实现的事实，不是结构性的保证**。若将来引入随机送资源的活动或资源丢失，基线会带随机性，届时它必须跑多次并产出分布，样本数由 1 改为 N。设计上因此不把基线当「确定量」，而把它当**一次普通派发**，跑几次是运行参数。

## 七、与其他子系统的关系

### 7.1 与模拟服务层（下层执行）

| | 模拟服务层 | 本层 |
|---|---|---|
| 管什么 | 并行怎么跑、内存怎么省、worker 怎么注入 | 跑哪些、怎么组织、存哪 |
| 产物 | 内存里的结果包 | 工作区里的数据集 |
| 依赖 | 不知道本层存在 | 调用它 |

本层**不搬**模拟服务层的复杂度（并行细节、流式提取、worker 注入），只调它。

### 7.2 与分析服务层 P86（上层消费）

本层产出数据集，P86 按 id 消费；本层不依赖 P86。P86 的跨侧一致验收（同一数据集、同参数、两个界面产出逐字段一致）依赖本层产出的统一数据集形态，故**本层先行**。

### 7.3 与引擎 `core/`

`core/` 是纯算法层，无副作用。本层依赖它，它不依赖本层。既有算法模块（最差影响、方案搜索）里若夹着派发，那是历史遗留，随本层落地一并改造（见 §3.2）。

## 八、理论边界与失效条件

本节记录设计过程中确立的一条方法论：**「X 必然成立」必须分清是「当前实现的事实」还是「结构性的保证」**。前者会随新需求失效，不能拿来当设计前提。

已知的边界，逐条登记：

| 结论 | 性质 | 失效条件 |
|---|---|---|
| 基线无随机源，跑 1 次即精确值（§6.5） | **当前事实** | 引入随机资源事件（随机送资源、资源随机丢失）。设计上已按「一次普通派发」处理，届时把运行参数由 1 改为 N 即可 |
| 内容哈希可判等两份配置是否相同 | 当前事实 | `compute_config_hash` 的覆盖面演进（**已发生过**，2026-10-01）。故哈希只作判等，不作身份（§5.1） |
| 索引可完全重扫恢复 | 结构保证 | 前提是配置文件的注释行完好；手工删注释会降级为孤儿（§4.2） |
| 工作区 append-only | 结构保证 | 删除操作（有意为之）；外部工具直接改写文件（工作区外的模板编辑时须复制进来） |

**做法**：把「当前事实」固化为**可失效断言**（测试）。前提被破坏时测试变红，而不是静默出错。例如基线的确定性由一条测试守，谁引入随机资源事件，它就报出。
