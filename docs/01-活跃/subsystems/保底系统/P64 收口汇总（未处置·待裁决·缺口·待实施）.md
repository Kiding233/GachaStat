### 1.1 缺陷 13：`_validate_behaviors` 的互斥校验是引擎级、概率管道是池级

**状态：✅ 已修复（2026-10-15，用户裁定「必须修复」后同日落地）。**

**修复结论**：规则 2/3/4 的适用域由「全部 behaviors」**下沉为「按池分组后的组内判据」**（规则 1 重名保持全局）。落点：`core/pity.py` 的 `_validate_behaviors(behaviors, pool_specs=None)` + 新增 `_pool_scoped_groups()` / `_check_scope_overlap()`；调用点改为 `_validate_behaviors(ordered, self.pool_specs)`。**组的成员取自 `PoolPitySpec.pity_names`**（运行时那份绑定事实，与 `batch_simulator` 的 `fnmatch` 口径同源）；**部分重叠仍互斥**（`('*',)` 与任何具体池都相交，故仍拒）；`pool_specs` 缺省或为空时回退单一全局组（既有语义）。测试：`tests/core/test_pity_validate_behaviors.py::TestPoolScopedMutexRules` 8 条（**改动前 3 条必红**）；手册 §1.4 的原神旗舰示例形状**自此可加载**。变异实测：退化为全局单组 → 3 条放行用例必红；删掉规则 2 判据 → 6 条拒收用例必红。完整记录见 `04-问题.md` 缺陷 13 节。

以下为修复前的原始记录（保留以便回溯）：

- **现象**：两条同 scope 的保底，只要 `pools` 不相交（各自绑定不同的池），仍会被**引擎构造期**拒收。
- **最小复现（本次实跑，原文照录）**：

```python
from gacha_simulator.core.pity import PityEngine, PityState, PoolPitySpec
from gacha_simulator.core.config_store import PityDef

defs = [PityDef(name='hard_a', btype='hard', scope='ssr', threshold=90, pools=('pool_a',)),
        PityDef(name='hard_b', btype='hard', scope='ssr', threshold=90, pools=('pool_b',))]
PityEngine({'pool_a': PoolPitySpec(pity_names=['hard_a']),
            'pool_b': PoolPitySpec(pity_names=['hard_b'])},
           defs, state=PityState(), rarity_rank={'ssr': 0})
```

  实测输出：`RAISED: ConfigError : 同 scope 'ssr' 存在两个硬保底：'hard_a' 与 'hard_b'（每个稀有度最多一个硬保底）`。

- **根因**：`_validate_behaviors`（`gacha_simulator/core/pity.py:1812`）在 `PityEngine.__init__` 的调用点 `:2131` 对**全部** behaviors 执行；而概率管道是**池级**的：`self._pool_order` 在 `:2148-2157` 按 `PoolPitySpec.pity_names` 预计算，`get_behaviors_for_pool()`（`:2168`）按池过滤。池间保底从不共同执行，故互斥判据的适用域应是「**同一池内**」。受影响的是**规则 2 / 3 / 4**（`:1842-1849` 两 hard / `:1850-1855` 两事件驱动型 / `:1856-1863` 同 scope 同 btype 两 soft）；**规则 1**（重名，`:1832-1839`）应保持全局（`name` 是 `engine.behaviors` 与 state 命名空间的键）。
- **归属**：**非 P64 引入**（该判据早于 P64，47 块不含此项）。
- **影响面**：默认配置只有 1 条保底（`gacha_simulator/config/config.toml:1100-1106` 的 `ssr_soft`），**默认配置不可达**。真实游戏里「角色池一个硬保底、武器池一个硬保底」是常态，而**手册 §1.4 的原神旗舰示例正是这个形状**（`char_hard` 与 `weapon_hard` 的 `pools` 不相交；`char_soft` 与 `weapon_soft` 同为 `soft_additive` 且 pools 不相交，触发规则 4），故该示例按现状**无法加载**。
- **补充实测（本次）**：TOML 解析层（`gacha_simulator/core/config_toml.py`）**没有**对应的互斥校验，故 `_validate_behaviors` 是**唯一防线**，缺陷无第二道冗余可绕。
- **建议修法**：把规则 2/3/4 的判据从「全局 behaviors」**下沉为「按池分组后的组内判据」**（规则 1 保持全局）。须为「组」的定义（按 `pools` 交集分组）与「部分重叠」的处置（重叠池内的两条仍应互斥）一并定稿。
- **代价**：中等。`_validate_behaviors` 是唯一调用点、影响面可枚举；成本主要在「组」的语义定稿与配套用例。

### 1.2 `worst_impact` 的两条同根因缺陷

#### 1.2a 多张 SSR 塌缩成一张

**状态：未处置。**

- **现象**：参照池「有 SSR 卡但无 featured 卡」时，全部 SSR 被判为 featured；随后重命名把它们压成**同一个** id，池内出现**重复 reward id**、Σ 静默变小，最差影响分析的数值随之失真。
- **证据**：回退分支 `gacha_simulator/core/worst_impact.py:412-417`（`if not self._featured_ids and self._ssr_ids:` 内 `self._featured_ids = set(self._ssr_ids)`）；**同形副本**在 `_apply_custom_pool_config` 的 `:469-474`。重命名在 `:177`（`featured_id = f'_wi_featured_{i}'`）+ `:181-188`（**所有** `r.id in self._featured_ids` 的 reward 都被赋**同一个** `featured_id`）。
- **最小复现**：把参照池 SSR 卡的 `featured` 全置 false，7 张 SSR 全部塌缩为 `_wi_featured_0`，池内出现 7 个同名 reward id。
- **归属**：非 P64 引入（S8-5 审查发现并登记，2026-10-14）。
- **影响面**：随包 `config.toml` **不可达**（`_prepare_pool_info` 取 `pool_entries[-1]`，该池 `limited_ssr_2` 的 `featured=true`，故 `_featured_ids` 非空、回退分支不触发）；**GUI / WebUI 自定义分布路径可达**（`gui/worst_impact_panel.py` 的「载入上次池子配置」把最后一个 enabled 池的分布逐字段照抄、含 `featured`；`webui/worst_impact_service.py` 接受调用方任意 `distribution`）。只要用户最后一个池没有 featured 标记的 SSR，缺陷即触发。
- **建议修法**：回退分支只在「参照池确实没有 featured 概念」时生效，或对重命名做逐卡去重（每张卡一个独立 id）。

### 2.4 `reset="never"` 的语义（两个互斥候选）

**✅ 已裁决并落地（2026-10-15，用户裁定）**：取**候选 B**（「保底触发时归零」），
落地为新增取值 **`reset = "on_effective"`**（非本段原拟的 `"on_trigger"`，GUI 显示名

type 配它抛 `ConfigError`。**候选 A 未被删除**：`reset = "never"` 语义与字面一致、

**「连带」已复核**：`InvariantChecker._check_counters_monotonic` 的边界 3

**测试**：`tests/core/test_pity_reset_on_effective.py`（两形态 + 负例 + round-trip +
S11 不误报 + 变异实测）。

以下为裁决前的原始记录（保留以便回溯）：

- **背景**：`reset = "never"` 是 G16 幻塔「出金不重置 80 抽保底」的配置入口，含义是「保底计数器**不因出金而归零**」。
- **现状 vs 预期（本次独立实跑复现）**：构造 `hard` / `scope='ssr'` / `threshold=80` / `reset='never'` 单保底加含 `scope_cards` 与 `featured_cards` 的池规格，连跑 90 抽，逐抽记「scope 组总概率是否等于 1」。实测输出：`forced draws: [80, 81, 82, 83, 84, 85, 86, 87, 88, 89, 90]`、`counter final: 90`。即行为是「第 80 抽起**每一抽**都被强制为 scope 100%」、counter 单调增至 90 从不归零，也就是「第 N 抽起每抽都强制」。而手册写的是「等价于每 N 抽一个额外的『白送』保底金」，那要求 counter 在**保底触发时归零**。`reset` 的取值集合（空串 / `featured` / 稀有度名 / `never`，白名单见 `config_toml.legal_reset_values`）**没有**「触发时归零」这一项。
- **为什么今天无人钉住它**：G16-2 已**撤掉**两条 `counter == THRESHOLD` 断言（`f9c271e`），因为两个候选下的期望值分别是 80 与 0，钉住其一会让另一候选的裁决必红。
- **选项与推荐**：**候选 A**「计数器永不归零、第 N 抽起永久保底」（现实现）；**候选 B**「保底触发时归零、非保底出金不归零（即每 N 抽白送金）」。**推荐候选 B**：候选 A 下「保底」只发生一次、之后每一抽都恒 100%，与任何真实机制都不符；而手册与幻塔机制的双信源口径都指向周期性白送。采纳 B 须新增一个 `reset` 取值（如 `"on_trigger"`）并改 `CounterTracker`。
- **连带**：采纳 B 会**触及 `InvariantChecker` 的一条已登记边界**（S11 审查的 (C) ③：「将来出现『重置到非零』的语义会误报它为破坏」，`gacha_simulator/core/invariants.py` 的计数器判据），须同批处置。
- **代价与可否回退**：中等（新增取值 + 白名单 + GUI 下拉 + 用例 + 手册 + checker 边界）；可回退。
- **登记处**：手册 §21 G16 行（`:2401`）+ §5.4 幻塔缺口表（`:780`）+ §5.3（`:718`）；计划 §六 G16 段（L2733）；`模块状态矩阵.md` P64 行；报告 §六 第 2 条。
