# P68 终极验证体系——分层独立参考实现与统计对比

> 日期：2026-07-20 | 状态：设计中
> 触发：上线前必做一次性测试方案——为每个游戏编写独立于 GachaStat 的参考实现，产出对比，一致才算通过

## 一、问题

GachaStat 是一个通用抽卡模拟引擎，配置手册覆盖 19 款游戏。当前测试覆盖率 29.2%，集中在单元测试——没有端到端的「引擎产出 vs 游戏真实机制」对比。

**核心风险：引擎对某款游戏的机制理解本身就有偏差，但单元测试无法发现——因为测试和实现在同一套假设下。** 配置手册中登记了 17 个功能缺口（G1-G20），其中 G16（出金不重置）/ G17（捕获明光）/ G20（bonus 语义）等涉及引擎对游戏机制的根本性理解。

P46 覆盖率提升计划解决的是「代码有没有 bug」，本计划解决的是「建模对不对」——两个正交问题。

## 二、目标

上线前，对 19 款游戏中的 18 款（异环搁置）执行分层验证，确保 GachaStat 引擎产出与独立参考实现 / 专项断言 / 快照一致。不一致则阻塞上线。

| 指标 | 目标 |
|------|------|
| S 层 5 款游戏 | 独立参考实现 + 五项统计指标全部通过 |
| A 层 9 款游戏 | 每项差异化机制专项测试通过 |
| B 层 5 款游戏 | 固定种子快照无回归 |
| 总代码量 | ~2,800 行（测试代码，不计入覆盖率统计） |
| 全量运行耗时 | ≤ 3 分钟（n_sims=100,000 × 5 款 + 专项 + 快照） |

### 3.3 S 层——独立参考实现规范

**设计原则：**

| 约束 | 理由 |
|------|------|
| **硬编码游戏常量**——不从 TOML 读取 | TOML 解析本身可能含 bug |
| **命令式循环**——不抽象 Behavior / Strategy | 抽象层就是 bug 来源——参考实现越「笨」越可信 |
| **单文件、单游戏**——200-400 行/款 | 一人一小时内可完整审计 |
| **双重运行模式**——`python x.py` 独立 CLI + `import x` 可被其他脚本调用 | 可脱离 GachaStat 仓库分发给玩家审计 |
| **输出 JSON**——与 GachaStat CLI `--output` 同 schema | `compare.py` 读两个 JSON 做统计对比 |

**运行方式：**

```bash
# 独立运行参考实现
python genshin_impact.py --n 100000 --seed 42 --output ref.json

# 独立运行 GachaStat
python -m gacha_simulator.cli -n 100000 -s 42 -c genshin.toml --output gs.json

# 独立对比（compare.py 零依赖 GachaStat 引擎，只读 JSON）
python compare.py ref.json gs.json
```

CI / 上线前置脚本中 shell 串这三步。不需要 pytest。

**S 层各游戏覆盖的机制矩阵：**

| 游戏 | rotating | targeted | soft | hard | 特殊机制 |
|------|:---:|:---:|:---:|:---:|------|
| 原神 | 50/50 | 武器定轨 | additive(74) | 90/80 | 捕获明光(LossStreak) + 副产物闭环 |
| 星铁 | 50/50+75/25 | — | additive(74/66) | 90/80 | 300自选 |
| 绝区零 | 50/50 | 邦布(threshold=0)+音擎(不清零) | additive(74) | 90/80 | 福利保底 |
| 鸣潮 | 50/50 | 常驻武器(threshold=0) | additive(65) | 80 | 限定武器不歪 |
| 终末地 | 50/50 | — | additive(65,+5%) | 80+120+240 | 三重计数器+武器配额+G20 bonus |

### 3.4 对比指标体系（替代 KS 检验）

| # | 指标 | 方法 | 回答的问题 | 失败阈值 |
|:---:|------|------|-----------|---------|
| 1 | **均值差** | Bootstrap CI（10,000 resamples, BCa） | 「期望抽数差了几抽？」 | CI 不含 0 且 \|Δ\| > 0.5 抽 |
| 2 | **关键分位差** | Bootstrap CI for P50/P75/P90/P95/P99 | 「非酋体验差多少？」 | 任一关键分位 \|Δ\| > 1.0 抽 |
| 3 | **保底触发率** | 精确二项检验 (Exact Binomial Test) | 「硬保底触发概率一致吗？」 | p < 0.01 且 \|Δp\| > 0.1% |
| 4 | **软保底区间** | 分箱 χ²（逐抽分箱） | 「概率爬升斜率对吗？」 | p < 0.01 → 存疑 |
| 5 | **整体分布形状** | Anderson-Darling 双样本 | 「分布形状有实质差异吗？」 | p < 0.001 → 存疑（辅助参考） |

**为何不用 KS 检验：** KS 对中位数敏感、对尾部迟钝（gacha 关键差异恰好在尾部）；N=100,000 时 trivial 差异也能 p<0.001；只判「不同」不判「哪里不同」。

**判定矩阵：** 指标 1-3 任一项失败 → ❌ 阻塞；指标 4-5 存疑 → ⚠️ 人工审查。

不需要完整模拟，只对差异化机制做**确定性断言**。每个专项对标手册 §二十一 中的一项缺口：

### 3.6 B 层——固定种子快照

B 层游戏机制可用已有基建覆盖。固定种子 + 固定配置 → 记录关键指标 checksum，防回归。

### 3.7 建模边界——资源闭环的切割线

gacha 模拟涉及两个闭环：

```
抽卡 → 获得卡牌 → 重复卡牌 → bonus资源 → 兑换池 → 更多抽卡资源 → 继续抽卡
```

参考实现需要在闭环中划一条线——哪些建模、哪些不建模：

| 层面 | 参考实现是否建模 | 理由 |
|------|:---:|------|
| 逐抽概率 + 保底 | ✅ 建模 | 核心验证目标 |
| 抽卡产出 bonus 资源（星辉/星尘/金票/武器配额等） | ✅ 建模——记录在 `bonus_events` 明细中 | 重复卡牌→bonus 是机制的一部分，受保底类型和 acquired 状态影响，且不同游戏规则不同 |
| 兑换池消费（星辉换纠缠之缘等） | ❌ 不建模 | 兑换是策略层决策，不影响引擎概率建模的正确性。兑换池本身的正确性由 GachaStat 单元测试覆盖 |
| 月卡/每日/活动资源注入 | ❌ 不建模 | 外部资源注入，与抽卡机制正交 |

**bonus 产出的验证方式：** bonus 是确定性规则映射（「重复 5★ → 10 星辉」），不是概率问题。不做统计检验，做**精确断言**——归入 A 层专项测试（对标 G20）：

```python
# A 层专项——非 S 层统计指标
def test_g20_bonus_rules():
    for draw in history:
        if draw.rarity == "SSR" and draw.is_duplicate:
            assert draw.bonus == {"starglitter": 10}
```

## 五、风险

| 风险 | 概率 | 缓解 |
|------|:---:|------|
| 参考实现本身有 bug——两边同错 | 中 | 硬编码常量 + 命令式循环——审计难度远低于引擎代码。5 款 S 层互相独立，不可能 5 款同时同向偏差 |
| Bootstrap CI 在大样本下 trivial significance | 中 | 判定以效应量（Δ 抽数 / Δp）为主，CI 仅提供区间估计。阈值设为 0.5 抽 / 1.0 抽——具有实际意义 |
| 游戏版本更新后参考实现过时 | 低 | 参考实现标注版本号（如「5.0+」），与手册对齐。版本更新 → 同步更新参考实现 |
| 引擎缺口未完成前无法跑通 S 层验证 | 高 | S 层参考实现的编写与引擎开发同步推进——写参考实现的过程反向暴露缺口。参考实现可独立运行（不依赖 GachaStat），先验证自身正确性 |
| 五项指标体系过度敏感 / 过度迟钝 | 中 | 阈值可在首批游戏验证中校准。计划中阈值为初始值，实施阶段可根据实际效果调整 |
