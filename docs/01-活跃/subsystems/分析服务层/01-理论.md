## 一、这一层为什么存在

### 1.1 先排除一个误判：这不是耦合问题

会话的起点是「core 里的统计方法层和 GUI 耦合太严重」。核实后不成立：**core 层零 Qt 依赖**（全目录 grep `PyQt|PySide|QtWidgets|QtCore` 只命中三处注释文本，无实际 import）。唯一的外部渲染层泄漏是 `core/vulnerability.py` 两处直导 plotly，已另案登记。

### 1.2 真正的病灶：一次分析没有所有者

用户勾「GDR分布」、指标选 `target_achievement`、勾上直方图与累积分布。**这一句话描述的就是一次分析，但它在代码里找不到对应落点。**

定义被切成四块：

| 这次分析的什么 | 现住所 |
|---|---|
| 它叫什么、属于哪一类 | `gui/analysis_panel.py` 的 `ANALYSIS_CATEGORIES` 常量 |
| 它要什么参数 | 一半在 GUI 面板控件里，一半在 `AnalysisWorker.__init__` 的 31 个构造参数里 |
| 它的算法 | `core/` 的 `gdr.py` / `distribution.py` / `per_pool_analysis.py` 等 |
| 它的产出形状 | `ChartWebView.set_charts()` 吃的 dict，或 WebUI 的 sections 列表 |

要理解「GDR分布」这一个分析，必须同时打开四个文件。

### 1.3 分叉是必然结果，不是偶然

**定义没有所有者，每个消费者就只能自己拼一遍。**

GUI 拼出 `AnalysisWorker._run_impl`（约 1250 行）；WebUI 出现时无处可问「GDR分布是什么」，只能读 GUI 的代码再拼一遍（`webui/analysis_service.py`，956 行，18 个 handler）。

**这不是 WebUI 走偏，是结构决定的**：换任何第三方来也得重写第三遍。

已发生的分叉是这条推论的证据（全部经代码取证）：`_spec_to_dict` 4 份、`_build_pool_names` 2 份、`_unique_count` 2 份**行为已不同**、分析项标识 `cumulative_by_banner` 与 `cumulative_by_pool` 已漂移、`gdr` 默认值散在 7 处。

### 1.4 本层的判据

**结构性判据：新增一个分析项只写一处；新增一个前端只写渲染器。**

「三处对齐维持」不算达成，因为对齐靠人记得，而上面那些分叉正是「记得」失效的结果。

## 二、概念层级

```
分析项（AnalysisSpec）   一次分析的完整定义：名字、分类、参数、算法、产出形状
   │
   ├── 分析参数          分析项自己的参数（§五）
   ├── 分析记录          一次分析的持久化形态（§六）
   └── 结果对象          一次分析的产出（AnalysisResult）

上层：用户界面（GUI / WebUI / CLI）
下层：模拟工作区（产出数据集） -> 模拟服务层 -> core
```

**与 P87 的分界**：P87 管「跑一次模拟」，本层管「读一批数据」。两者共享一个接缝（**数据集形态契约**），所以 P86 的跨侧一致验收依赖 P87 先落地。

## 三、本层内部的划分

划分依据与 P87 相同：**因什么而变**。

| 部分 | 职责 | 因什么而变 | 对外接口 |
|---|---|---|---|
| **分析项注册表** | 分析项的定义与校验 | 加一个分析项 | 枚举分析项与参数 schema |
| **运行上下文** | 中间量的按需计算与复用 | 加一个中间量 | 按名取中间量 |
| **结果对象** | 产出的形状 | 换前端、加 Section 类型 | 交出 sections |
| **分析记录** | 一次分析的持久化 | 加参数类别 | 读写一条记录 |

**四者可以分开的理由**：注册表管「有什么」，上下文管「算什么」，结果对象管「长什么样」，记录管「存什么」。它们通过一个入口（`run(dataset_id, key, params)`）相接，彼此不知道对方的内部结构。

**不属于本层的部分**（只是被本计划触发）：

- `core/` 的算法（`gdr.py` / `comparison_analyzer.py` / `vulnerability.py` 等）：本层只调，不改
- 派发与工作区存储：属 P87
- 五个独立 service（脆弱性 / 过程分析 / 最差影响 / 比较 / 方案搜索）的收编：分批接入，不是新系统

## 四、分析项的原理

### 4.1 为什么必须声明化

**同构于项目已有的成功模式**：P69 的 `register_strategy`（装饰器副作用注册 + `Meta` dataclass + 导入期 `_validate_registry()`）。P86 复刻它做 `@register_analysis`，不是新发明。

声明化的收益不只是「少写字」，而是**判据从「记得」变成「结构上不可能忘」**：

| 现状 | 声明化后 |
|---|---|
| 参数默认值散在 7 处读取里 | 只写一处 |
| 参数定义一半在控件、一半在构造参数 | 只写一处，控件自动生成 |
| 依赖的中间量靠运行到中途才发现缺失 | 声明 `requires`，调用前保证可用 |
| 摘要项的中文标签要被机器消费者解析 | `SummarySection.items` 带稳定 metric key |

**一个已否决的方向**（记录以免后人重走）：把分析抽象成「度量 × 分组 × 视图」的笛卡尔积。18 项里大多符合这个结构，但 `correlation`（度量之间）、`risk_var_cvar`（分位数与尾部期望）、`transition_analysis`（状态转移推断）、脆弱性（PAVA 保序回归）均带自定义算法，强行表达会造出表达力不足的 DSL，最终两套机制并存。**这是过度设计。**

### 4.2 算法与编排的界线

| 归属 | 判据 | 内容 |
|---|---|---|
| 留在 `core/` | **换个前端还要不要？要，是算法** | `gdr.py` 的 21 个出率函数、`comparison_analyzer.py` 的检验、`vulnerability.py` 的 PAVA、`per_pool_analysis.py` 的转移矩阵 |
| 进本层 | **不要，是编排** | 选哪个指标、对哪些池、阈值取多少、结果如何组织成图与表 |

这条线保证 core 保持「纯算法、无副作用」的定位，也让算法可被 CLI、回归测试、未来的其它前端直接调用。

### 4.3 为什么结果对象是有序列表

`sections` 用**有序列表**而非字典，因为它要表达图、表、摘要在同一分析项内的**排列顺序**。现状 GUI 用两个平行字典，丢了顺序，只能靠 `_CHART_DISPLAY_ORDER` 常量另外补回来。

**收编已有形态而非另起炉灶**：WebUI 已自发长出 sections 列表（三个 `_sec_*` helper，全文 32 处调用）。这是方案的成本优势所在。

**产出契约取 GUI 的既有行为而非 WebUI 的**：现状两侧错误处理不同（WebUI 整体 try/except，一项失败则全项返回错误；GUI 逐项算、遇问题发警告继续）。统一取后者，因为前者会让 GUI 从「部分可用」退化为「一项坏则全盘坏」。

## 五、参数的来源分类

会话的后半段在「权重属于配置还是分析」上反复打转。根因是**判据选错了**，不是答案难找。

### 5.1 三类参数，判据各自独立

| 类 | 判据 | 例子 |
|---|---|---|
| **配置参数**（含「作为配置的分析参数」） | 产生数据要用它 | 池子、保底、策略、目标卡、权重 |
| **分析方法本身的参数** | 改它会影响分析结果 | 阈值、判成功的条件、算哪个指标 |
| **界面状态与偏好** | 改它不影响分析结果 | 展开折叠、面板布局、关心哪些指标 |

三条判据各自可判定，互不隶属。**它们不是层层包含的关系**，问的是三个不同的问题：产生数据时用不用它？改它跑出来的数变不变？改了界面变但数不变？

### 5.2 判据为什么必须是「来源」，不能是「用途」

最初的判据是「影响结论的进配置，不影响的不进」。它**自相矛盾**：

按它推权重，得出「权重不影响模拟，所以不是配置参数」。但按同一条推**目标卡会得出同样的结论**：引擎不知道你要哪张卡，它只按概率发牌，目标卡只影响你怎么看结果。而目标卡显然必须是配置参数。

换成「产生数据要用它吗」，「用途」这个词就消失了。权重当前没有策略消费它，**但它仍是配置参数**：判据问的是「它有没有可能被产生数据的过程消费」，而不是「当前有没有」。

**为什么权重按当前事实也该算配置参数**：它是 GDR 的输入，而 GDR 是策略的输入。

```
目标卡、权重  ->  GDR（两类：一类吃目标卡，一类吃目标卡 + 权重）
                   |
                   v
                策略（吃 GDR，或按 GDR 设计）
```

策略不直接吃目标卡和权重，是**经 GDR 间接吃**。这解释了为什么现状里没有策略声明权重：只是**当前没有哪个内置策略是基于加权 GDR 设计的**，不等于权重不该进配置。

### 5.3 两个维度不能压成一个

「它是什么」（类别）与「它的值从哪来」（来源）是两件事，压在一起就会得出错误结论。

目标卡和权重：**类别**是配置参数；**在分析侧的值的来源**是从数据集指向的那份配置换算。所以「权重是分析方法本身的参数」是错的（类别错），「权重是分析的共享设置」也是错的（不存在这样一个与类别并列的东西）。

**推论**：分析项要声明两样，性质不同。

```
AnalysisSpec(
    params = [...],               # 分析方法本身参数，带声明式默认值
    reads_from_dataset = (...),   # 依赖声明：我需要数据集的哪些配置参数
)
```

`reads_from_dataset` **不是参数清单，是依赖声明**：创建分析时知道该从数据集抄哪些值过来。抄来之后成为本次分析的输入值，可以改。

### 5.4 候选集与选中集

任何「从一组可选项里选几个」的参数都有两面：

| | 是什么 | 存不存 |
|---|---|---|
| **候选集** | 能有哪些可选项 | **不存**，每次派生 |
| **选中集** | 用户选了哪几个 | 存 |

以 GDR 为例，候选集的构造是纯派生的（`core/gdr.py:547-576` 的 `get_expanded_gdr_entries`，输入只有 `UNIFIED_GDR_REGISTRY` 与 `resource_defs`）。

**由此有一条必须处理的边界**：分析记录密存了**选中集**，而**候选集是打开时现算的**。若某个选项后来从候选集里消失（注册表演进，或某个变体因配置变化不再适用），旧记录里的那个值就**悬空**了。**必须报出来，不能静默丢弃**，否则用户会看到少了几项而不知道原因。

### 5.5 「控制显示哪些」不做成参数

一个自然的想法是把「关心哪些指标」做成参数。**不做**，理由是具体的：它不影响结果，做成参数会导致它被**密存进每一条分析记录**，等于把一份偏好复制 N 份，且每条记录都可能不同。正确的位置是**工作区级偏好**（§6.6）。

## 六、分析记录

### 6.1 它存的是配方，不是结果

| | 存什么 | 大小 | 会不会过期 |
|---|---|---|---|
| **配方** | 吃哪些数据集 + 哪个分析项 + 什么参数 | 几十字节 | 不会 |
| **结果** | 算出来的图表与统计量 | 可能几 MB | 会（数据集变了、算法改了） |

**只存配方**（用户 2026-10-05 裁决）。

业界的分野正是这一条：Jamovi / JASP 存分析状态，打开时重算；SPSS 的 `.spv` 存结果本身。存结果的软件有共同点：**结果本身就是最终交付物**（用户要拿去贴报告）。而这里的「结果」是 `List[Section]`，那是**渲染指令**，换个前端就渲染不了，存它等于把前端实现细节写进磁盘。

**只存结果不存配方，会留下一堆无法复现的图**：用户下次打开看到一张图，不知道它是哪个数据集、哪个阈值、什么时候跑出来的。所以配方的优先级高于结果。

### 6.2 它自包含

创建分析时把三类参数**全部**取一遍当前值写进记录：分析方法本身参数取声明的默认值，数据集带来的（目标卡、权重）从数据集指向的那份配置换算，偏好类的取工作区级偏好。

**存快照而不是指向配置的指针**，理由：

- 配置会派生（写时复制），「当前那一份」会变。若每次读配置，一条三天前建的分析记录今天打开会读到**不同**的口径
- 快照之后记录**自包含**，与配置的后续变化解耦
- 配置被删也不影响已有分析（P87 §3.10 ④ 允许删除被引用的配置），只影响「新建分析时去哪抄默认值」，那时报明确错误即可

**代价**：配置改了口径，已有分析不会跟着变。这恰好是想要的行为：**分析是「我当时用什么口径看的」的记录。**

### 6.3 为什么密存，以及密存的不足

**密存**（全部参数值都写，不写差异）。疏存有一个静默失效：若只写差异，某天分析项的**默认值在代码里改了**，**所有历史分析会跟着变**，且无声。密存则保持创建时的值，用户打开还能看见「这条是 0.05」。**看得见就解释得清。**

按本项目一贯反对静默失效的立场（与 P87 的「无条件纳入哈希」同源：宁可冗余，不要静默），只能选密。

**但密存也做不到绝对自包含**，因为分析项的声明会演进：新增一个参数，老记录里没有这个键。老记录**必须还能跑**，否则一次升级就把所有历史分析作废。所以是两条规则并列：

```
创建时：全量快照        -> 记录自包含
读取时：缺键回退到声明   -> 声明演进不破坏历史记录
```

分工是：**已存在的键冻结，缺失的键取当前声明。**

**不标参数来源**：哪些参数来自数据集由 `reads_from_dataset` 现算，不写进记录。来源是**声明**的属性，不是**值**的属性；记两遍会漂移。

### 6.4 它为什么可变，而配置与数据集不可变

工作区里有两类对象（规则详见 P87 §3.11 J3）：

| | 规则 | 成员 |
|---|---|---|
| **不可变对象** | append-only，一经产生不再改写 | 配置、数据集、任务记录 |
| **可变对象** | 就地更新 | 分析记录 |

**不可变是因为有人指着它**：数据集指向配置，子配置指向父配置。一旦可改，引用就失去意义，所以要写时复制。

**分析记录可变是安全的，因为没有被引用的对象可变不引起级联**。它是工作区里的叶子，只引用别人。**所有分析平级**（用户 2026-10-07 裁决），不存在「基于上次分析再分析」的引用关系。

**这条性质是「可变」成立的前提，不是事后接受的例外。** 代价是丢失不可回滚，可接受：分析记录丢了不致命（重新勾一遍即可），不像数据集那样不可再生。

### 6.5 与树的关系：引用，不是归属

树表达**派生关系**：配置由谁派生、数据集由哪个配置跑出来，回答「这东西从哪来」。

分析记录回答的是「我拿哪些东西、用什么口径、看了什么」，它的输入是**多个**数据集（比较分析吃两个）。**所以它不是树上的父子关系，是引用关系。分析记录不进树。**

允许的反向查询（按数据集列出被哪些分析用过）是**派生**的，不另存。

### 6.6 存储位置总表

| 内容 | 存哪 | 可变性 | 写入时机 |
|---|---|---|---|
| 配置参数（含目标卡、权重） | `configs/*.toml` | 冻结后不可变 | 用户保存配置 |
| 数据集 | `datasets/*.json` | 不可变 | 模拟完成 |
| **分析方法本身的参数** | `analyses/*.json` | **可变** | 创建 / 编辑分析 |
| 任务记录 | `tasks/*.json` | 不可变 | 任务启动与结束 |
| 工作区级界面状态与偏好 | `workspace.json` | 可变 | 界面变化时 |
| 会话级界面状态（滚动位置、对话框尺寸） | **不存** | — | — |
| 候选集（可选项清单） | **不存**，每次派生 | — | — |

**界面状态与偏好按作用域分，不按类别分**：

| 作用域 | 例子 | 存哪 |
|---|---|---|
| 工作区级 | 面板布局、树上展开的节点、关心哪些指标、最近打开的工作区 | `workspace.json`，**一份** |
| 分析级 | 这次分析开着哪些标签页、某个图展开没展开 | 若做，随分析记录各存一份 |
| 会话级 | 滚动位置、对话框尺寸 | **不存** |

判据是：**这个状态是「这次分析的」还是「整个工作区的」。** `workspace.json` 内部再分 `ui`（纯个人呈现）与 `prefs`（有语义的默认）两块，因为**共享性不同**：工作区发给同事时后者有意义、前者没有。**分析级界面状态先不做**（无证据），与 P87 §八「任务落盘不做」同一立场。

**目标卡与权重在两个地方各有一份，不是冗余**：

| 那份 | 值来自 | 用途 |
|---|---|---|
| 配置里 | 用户配置 | **产生数据**（策略可能消费） |
| 分析记录里 | 创建分析时从数据集换算抄一份 | **本次分析读取** |

同一个名字、两份值，因为回答的是两个不同问题：「产生这批数据时用的是什么」与「我这次分析要按什么读」。

### 6.7 框架对外只暴露一个入口

```
defaults(dataset_id, analysis_key) -> dict
```

前端流程因此是两个前端完全一致的三步：**取默认 → 表单改 → 提交**。

1. **取默认**：调 `defaults()` 拿到一份完整参数表
2. **表单改**：用 `AnalysisSpec.params` 的 `ParamDescriptor` 列表自动生成控件，填上第 1 步的值，用户改
3. **提交**：控件收回成一个 dict，调 `run(dataset_id, key, params)`

**这一步的实质是把参数值从控件里拿出来，变成一等数据。** 现状参数**没有一份表**，**控件本身就是存储**，点按钮时从十几个控件逐个读出来塞进 `AnalysisWorker` 的 31 个构造参数。控件降为视图之后：两个前端读同一份声明各生成表单；无界面场景（CLI、回归测试）能直接构造参数表；**参数表就是分析记录里要存的东西**。

## 七、与其他子系统的关系

### 7.1 与模拟工作区（下层，产出输入）

| | 模拟工作区 | 本层 |
|---|---|---|
| 管什么 | 跑一次模拟、存哪、怎么组织 | 读一批数据、怎么算、怎么展示 |
| 产物 | 工作区里的数据集 | 分析结果（不落盘） |
| 依赖 | 不知道本层存在 | 消费它的产出 |

共享一个接缝：**数据集形态契约**。P86 的跨侧一致验收（同一数据集、同参数，两个界面产出逐字段一致）依赖 P87 产出的统一数据集形态，故 **P87 先行**。

### 7.2 与 `core/`

| | core | 本层 |
|---|---|---|
| 内容 | 算法 | 编排 |
| 判据 | 换个前端还要不要？要 | 不要 |

本层依赖 core，core 不依赖本层。core 保持零 Qt 依赖与无副作用。

### 7.3 与用户界面

本层不 import 任何具体前端。两个前端通过同一个入口相接，各自只写渲染器。**GUI 需要一层适配**：它现有的 `ChartWebView.set_charts()` 吃的是 dict（为 tab 增量更新而设计），而 sections 是有序列表，需要一个几十行的转换，并保住 `_get_ordered_charts()` 的排序与 P83 启动测量依赖的 `charts_ready()`。

## 八、理论边界与失效条件

沿用 P87 理论文档确立的方法论：**「X 必然成立」必须分清是「当前实现的事实」还是「结构性的保证」**。前者会随新需求失效，不能拿来当设计前提。

| 结论 | 性质 | 失效条件 |
|---|---|---|
| 权重不进配置身份是自洽的 | **当前事实** | 出现消费加权 GDR 的策略。用户 2026-10-07 裁决**无条件纳入哈希**，正是为了不让身份随这个事实漂移 |
| 分析记录可变是安全的 | 结构保证 | 前提是**没有东西引用它**。若将来出现「基于上次分析再分析」，须重新论证（§6.4） |
| 密存 + 缺键回退足以复现历史分析 | 结构保证 | 前提是**参数的语义不变**。若某个参数改了含义而不改名，历史记录会静默算错。纪律：**改语义必须换键名**（与 P87 §3.11 H 同一条） |
| 分析记录不进树 | 结构保证 | 前提是分析之间无派生关系（所有分析平级，用户已裁决） |
| 候选集可每次派生 | 结构保证 | 前提是注册表与 `resource_defs` 是候选集的全部输入。若引入需要持久化的用户自定义分析项，须重新论证 |
| 「换个前端还要不要」能划清算法与编排 | **当前事实** | 出现仅某个前端需要的「算法」（如为某渲染器特化的聚合）。届时它应作为该前端的实现细节，不得回流 core |

**做法**：把「当前事实」固化为**可失效断言**（测试）。前提被破坏时测试变红，而不是静默出错。
