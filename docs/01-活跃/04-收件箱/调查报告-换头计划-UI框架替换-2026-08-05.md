# 换头计划调查报告：UI 框架替换的可行性、经济性与风险

> 日期：2026-08-05
> 性质：架构决策前置调查（对应「换头计划」需求）
> 目标：评估全面替换 PyQt6 + Plotly（WebEngine）为更现代 UI 方案的可行性、迁移成本与风险，给出推荐方案

---

## 0. 执行摘要

**推荐方案：pywebview（系统 WebView2）+ 现代前端（Vue 3 / React + ECharts）+ Vite 构建，Python 计算引擎完整保留。**

该方案是唯一同时满足全部硬性约束的路线：

| 需求 | 满足方式 |
|------|---------|
| 全面替换 PyQt6 + 当前画图库 | 保留 `core`/`service`/CLI（零 Qt 耦合），仅重建 `gui/` 层为 Web 前端 |
| 交互式图表（hover/缩放/框选） | 浏览器环境，ECharts / Plotly.js 全能力 |
| 现代化 UI | Web 组件库（Element Plus / Naive UI / Ant Design Vue 等）属当前天花板 |
| 热重载 | 开发期 Vite HMR 完整可用 |
| 不附带浏览器内核（空间小） | Windows 系统自带 WebView2 运行时（Win 10 1803+ / Win 11 预装），打包产物不捆绑 Chromium |

核心优势：**Python 仍是主进程**，现有 `multiprocessing.Pool` 并行模拟代码零改动，这是相对 Tauri（Rust sidecar）的决定性优势。

**主要成本**：`gui/` 层约 17,492 行需重建为前端，其中 `config_panel.py`（5895 行复杂表单）是最大难点。估计单人工作量 6~12 周（含测试与打磨）。

## 1. 调查范围与需求约束

### 1.1 目标

全面替换当前 PyQt6 + PyQt6-WebEngine（Chromium）+ Plotly 的 UI 实现，换取更优雅、更灵活、视觉效果更好的界面，同时满足：

1. **交互式图表**：hover / 缩放 / 框选数据导出 / 富 tooltip / 联动
2. **现代化 UI 体验**
3. **热重载**（用户表述为「最好有」，软性要求）
4. **打包后不附带浏览器内核**（空间小，硬性约束）
5. **保留 Python 计算引擎**（numpy / scipy / binsreg / PySDTest）

### 1.2 约束的本质

「不附带浏览器内核」是本次调查的**分水岭约束**。它排除了：
- Electron / CEF / PyQt6-WebEngine（捆绑 Chromium，约 120MB，占当前打包体积 50-65%）

但它**不排除**使用操作系统自带的 WebView2（Windows 系统组件，Win 10 1803+ 通过 Edge 分发、Win 11 预装）。这构成「Web UI + 系统 WebView + Python 后端」混合路线的可行前提。

## 2. 现状盘点（基于代码事实，已核验）

### 2.1 架构分层与 Qt 耦合度

```
core/       计算引擎：池子/状态/策略/保底/GDR/分析算法     ≈12K 行，numpy only
service/    业务层：GachaService + batch_simulator         零 Qt 依赖
gui/        PyQt6 面板 + Worker 线程                        17,492 行，唯一 Qt 耦合层
visualization/  ChartSpec IR + PlotlyRenderer + 字体配置
cli.py      独立命令行入口                                  零 Qt / plotly / matplotlib 依赖
```

**关键结论（已 grep 核验）：**
- `core/` 与 `service/` **零 PyQt6 依赖**。`param_descriptor.py` 声明零 Qt，`result_store.py` 用消息队列模式规避 QWidget 线程亲和性崩溃。
- `cli.py` 完全无 Qt / plotly / matplotlib 引用，是独立路径。
- **计算引擎可 100% 保留**，换头只需重建 `gui/` 层。

### 2.2 图表架构：已有良好的解耦抽象

本项目图表层已采用**中间表示（IR）模式**（[图表引擎 01-理论.md](../subsystems/图表引擎/01-理论.md)）：

```
面板分析数据 → ChartSpec（纯数据 IR，零绑图库依赖）→ PlotlyRenderer（唯一转换点）→ ChartWebView
```

- `chart_spec.py`：10 种类型化图表数据（直方图/CDF/山脊/箱线/散点/条形/热力图/3D瀑布/子图网格/表格）+ 注解 + 便捷构造函数，**纯数据、可序列化为 JSON**。
- `plotly_charts.py`：`PlotlyRenderer` 是后端唯一 `import plotly` 的转换点。
- `ChartWebView`：WebView 已承载图表**与表格**（`TableData` 替代 QTableWidget），说明 Web 渲染在本项目已被验证为主流路径。

**对换头计划的重大利好**：`ChartSpec` IR 是纯 JSON 可序列化的数据契约。迁移到 Web 前端后，后端只需把 `ChartSpec` 序列化推给前端，由前端 ECharts / Plotly.js 渲染。**后端图表构建逻辑大量复用，PlotlyRenderer 可整体被前端 renderer 替代。**

**需要修正的偏差**（打破「唯一转换点」假设）：`core/vulnerability.py` 有 2 处直接 `import plotly.graph_objects` + `make_subplots`（绕过 IR），迁移时需一并处理。

### 2.3 打包现状与体积痛点

- 打包工具：PyInstaller（onedir），`.spec` 已深度优化（过滤 Qt 无用 DLL、plotly widgetbundle/datasets）
- 体积痛点已由项目文档明确记录（[应用打包 01-理论.md](../subsystems/应用打包/01-理论.md) §3.3）：
  - **Chromium 内核约 120MB，占打包产物 50-65%**，PyInstaller 无法缩减
  - 文档给出了三个选项（matplotlib 后端 / WebChannel + 系统浏览器 / CLI-only），当时均未采纳
- `spec` 已排除 matplotlib、tkinter、pandas、statsmodels 等

**体积优化的真实下限**：移除 Chromium 后，**scipy 成为新的体积主导项**（scipy 安装约 200-300MB，PyInstaller 按需打包后仍占大头）。任何方案的总包体量下限受 scipy 制约，换头能省的是「浏览器/引擎」部分（约 100-150MB）。

### 2.4 测试锚点

| 层 | 测试数 |
|----|-------|
| 总测试 | 938 |
| GUI 测试（tests/gui/） | 84 |
| 可视化测试（tests/visualization/） | 55 |
| 其余（core/service/CLI 等） | ~800 |

**core/service 的 ~800 个测试不受换头影响**，构成行为等价性的回归基线。GUI 层 139 个测试需适配到新前端（或改写为前端测试）。

### 2.5 其他现状

- 热重载：当前**无 UI 热重载**（仅策略插件系统有热重载能力）
- 异步：GUI 用 QThread + Worker（21 处引用），多面板各有自己的 Worker
- matplotlib：仅 `font_config.py` 配置中文字体，**无任何渲染调用**（历史遗留，spec 排除正确）
- Python 3.12.5，Windows 11（自带 WebView2）

## 3. 候选方案评估

> 说明：本部分基于模型知识（训练截止 2026-01）评估，**无法在线核实最新版本**（本次调查网络访问受限）。关键原理性结论（WebView2 系统共享、ImGui 即时模式、Tauri sidecar 机制）置信度高；具体字节数、版本号标注【估计】。

### 3.1 方案总览

| 方案 | 体积量级（打包后） | 热重载 | 交互图表 | 现代 UI | Python 集成成本 | 维护活跃度 | 是否满足全部硬约束 |
|------|------|--------|---------|--------|---------------|-----------|------------------|
| **A. pywebview + Web 前端** | 最小（~150-200MB，scipy 主导）【估计】 | 高（Vite HMR） | 高（Plotly.js/ECharts 全能力） | 高 | 中（JS 桥 + pythonnet） | 中（单维护者 v5.x）【估计】 | ✅ |
| **B. Dear PyGui** | 中（~250-300MB，wheel 就 ~100MB）【估计】 | 部分（Runner 整 app 重启） | 中（缩放/平移/hover，框选弱） | 中低 | 低（纯 Python） | 1.x 活跃，2.0 Rust 重写中【估计】 | ⚠️ 热重载弱、UI 现代感不足、体积优势不成立 |
| **C. Flet（Flutter）** | 大（Flutter 引擎 ~100-200MB）【估计】 | 部分（run --watch 重启） | 低中（内置图表基础，达不到 Plotly 级） | 中高（Material） | 低中（新范式，数据走协议） | 年轻、API churn 大【估计】 | ⚠️ 体积未解决、图表交互弱 |
| **D. Tauri v2（Rust）** | exe 极小 + Python sidecar（~170-220MB）【确定/估计】 | 高（前端 HMR） | 高 | 高 | **高**（Rust 工具链 + sidecar + IPC） | v2 新（2024-10）、快节奏【估计】 | ✅ 但 Python 集成成本过高 |
| **E. 部分替换（PyQt6 + pyqtgraph）** | 中（~200-280MB，省 WebEngine ~120MB）【估计】 | 低（无原生 HMR） | 中低（pyqtgraph 最佳，框选/富 tooltip 需手写） | 中低 | 低（最小改动） | 高 | ❌ 不满足「全面替换」+ 交互降级 |

### 3.2 分方案要点

**方案 A：pywebview（推荐路线）**
- 架构【确定】：调用系统 WebView。Windows 后端为 WebView2（Chromium 内核，由微软以系统运行时提供，不随应用打包）。Win 11 预装。
- 体积【估计】：pywebview + pythonnet 很小（几 MB）；前端构建产物 1-5MB。总包 ~150-200MB，其中 scipy 占主导。相对现状省掉 Chromium + PyQt6 两坨（约 120-150MB）。
- 热重载【确定】：开发期 Vite dev server（localhost:5173），pywebview 加载该 URL，前端 HMR 完整可用；生产加载构建产物。
- 迁移平滑度【估计】：现有图表是 Plotly.py 生成，可走 `fig.to_json()` 直接喂浏览器端 Plotly.js；或更优，**直接序列化 ChartSpec IR 给前端 ECharts 渲染**，后端图表代码零改动。
- **关键优势【确定】：Python 仍是主进程，现有 `multiprocessing.Pool` 并行模拟代码零改动**。
- 维护【估计】：pywebview v5.x，单维护者项目，活跃度中等。

**方案 B：Dear PyGui**
- 基于 Dear ImGui 的 C++ 内核 + Python 绑定，GPU 即时模式，与 Qt/Web 的「控件树 + 事件循环」模型完全不同【确定】。
- 硬伤：wheel 本身约 100MB【估计】，体积优势基本不成立；热重载是整 app 重启（状态丢失）；implot 交互（框选/富 tooltip/联动）明显低于 Plotly；UI 现代感需大量自定义。
- **三选二都勉强，综合不推荐**。

**方案 C：Flet**
- Python 通过 WebSocket/JSON-RPC 驱动嵌入的 Flutter 桌面客户端渲染【确定】。
- 硬伤：Flutter 引擎体积未解决（换了个等量级引擎）；图表交互弱（`flet-plotly` 支持弱）；大数据走协议传输有损耗（对批量模拟结果推送不利）；API 不稳定。
- **不推荐**。

**方案 D：Tauri v2**
- Windows 用系统 WebView2，不捆绑 Chromium【确定】；exe 仅几 MB【估计】。
- 硬伤：Python 计算引擎需作为 sidecar 进程另行打包（PyInstaller onedir），引入 Rust 工具链 + 进程生命周期管理 + IPC 设计，对一个纯 Python 项目是显著过载【估计】。
- **能力上限最高，但性价比低。建议作为 pywebview 路线的长期升级备选**，若日后产品化程度加深再评估迁往。

**方案 E：部分替换（PyQt6 保留 + pyqtgraph 等）**
- 去掉 QtWebEngine 省约 120MB【估计】，保留 PyQt6 基础控件库。成本最低、风险最小。
- 代价：交互图表降级（框选/富 tooltip 需手写）、无原生 HMR、现代观感靠 QSS 自建、QtCharts 在 PyQt6 下授权为 GPL/商业【待核实】。
- **不满足「全面替换」需求，作为退路方案记录**。

### 3.3 其他否定项

- **Toga**：BeeWare 项目进展缓慢，Windows 后端基于 WinForms，观感陈旧，无交互图表生态【估计】
- **wxPython**：满足「保留 Python 引擎」但其余要求大多不满足，图表只能走 matplotlib wxagg（交互弱）【估计】
- **Kivy/KivyMD**：图表交互弱，KivyMD 维护停滞【估计】
- **PySimpleGUI**：2023 年改商业 license 且作者搁置，不推荐【估计】
- **NiceGUI**（补充参考）：Python 全栈 Web UI，`ui.run(native=True)` 底层即用 pywebview 包成桌面窗，自带 `ui.plotly`/`ui.echart` 与自动重载。**能以最低改动量快速验证「Web UI + 系统 WebView」路线可行性**，但多套一层框架、大数据性能与长期维护是代价【估计】。

## 5. 风险分析

### 5.1 风险矩阵

| 风险 | 等级 | 说明与缓解 |
|------|------|-----------|
| **config_panel 复杂表单迁移** | 🔴 高 | 5895 行，含动态行、批量创建、嵌套对话框（PoolDistribution/RandomCardPool）、级联校验。缓解：最后迁移、保留 Qt 版本可并行运行直至覆盖 |
| **技术栈变双语言** | 🟡 中 | Python + TS/JS 双栈。缓解：前端只做 UI 表现层，业务逻辑全在 Python 侧，前端无业务复杂度 |
| **WebView2 系统依赖** | 🟢 低-中 | 旧版 Win10 / 企业锁定机可能缺失。缓解：Win 10 1803+ 基本覆盖；可选 Evergreen bootloader 引导安装（不捆绑内核）。**当前环境（Win 11）已 POC 实测可用** |
| **pythonnet 依赖脆弱性** | 🟢 低 | pywebview Windows 后端依赖 .NET 互操作。**POC 实测：pythonnet 3.1.0 正常加载，无异常** |
| **JS-Python 桥大数据传输** | 🟡 中 | 模拟结果 MB 级跨桥 JSON 有损耗。缓解：大数据改走本地 HTTP server（pywebview 支持静态/动态路由） |
| **pywebview 单维护者风险** | 🟡 中 | 社区不大。缓解：核心依赖面窄（只作窗口容器），主要能力在前端与 Python，替换容器成本低 |
| **杀软误报** | 🟡 低-中 | Python 打包误报问题依旧存在，但 DLL 数量大幅减少可能降低触发面。缓解：文件夹分发 + 可选代码签名（EV 证书年费约 $300-500） |
| **scipy 体积制约** | 🟡 中 | 任何方案总包下限受 scipy 制约，换头只能省 Chromium 部分。缓解：若体积是硬约束，评估裁剪 scipy 子模块或换实现（超出本调查范围） |
| **QtCharts 授权（方案 E）** | 🟢 低 | 仅部分替换方案涉及，GPL/商业授权需确认【待核实】。推荐路线不涉及 |

### 5.2 与现有架构的兼容性检查

- **multiprocessing.Pool**：pywebview 方案中 Python 是主进程，`run_batch_parallel()` 零改动【确定】。Tauri 方案需处理冻结 exe 内 spawn + `freeze_support()` + 避免 onefile（已知坑）。
- **配置读写**（`config_toml.py` / TOML）：纯 Python，不受影响。
- **插件系统**（策略插件热重载）：Python 侧逻辑，前端只需暴露触发入口。
- **ResultStore / 数据管理**：纯 Python，前端通过桥调用。
- **文件对话框**：pywebview 有 `create_file_dialog` API，可替换 QFileDialog。

## 6. 推荐方案与路线图

### 6.1 推荐结论

**首选：方案 A（pywebview + Vue 3/React + ECharts + Vite），保留 Python 引擎。**

理由排序：
1. 唯一同时满足「交互图表 + 现代 UI + 热重载 + 无捆绑内核 + 保留 Python 引擎」五要求的方案
2. 图表层迁移平滑度最高（现有 `ChartSpec` IR 可直接作为前后端数据契约；或 Plotly 走 `fig.to_json()` 兜底）
3. Python 并行模拟零改动（相对 Tauri 的决定性优势）
4. 现有 WebView 已承载图表与表格，Web 渲染路径在本项目已被验证

**图表库子决策（已定）：ECharts。** 2026-08-05 垂直切片实测（4 种分布双库对比），用户判定 ECharts 视觉与交互显著优于 Plotly.js，且体积更小（约 1MB vs 4.6MB）。`ChartSpec` IR 保持「数据与渲染分离」，后端零改动，前端实现 ChartSpec → ECharts 映射即可（见 8.2）。

**升级备选：Tauri v2**。若日后产品化加深、需要跨平台与更强架构，可在 pywebview 前端不变的前提下迁往 Tauri（前端代码复用率近 100%），只换窗口壳 + 引入 Python sidecar。

**退路方案：方案 E（PyQt6 + pyqtgraph）**。若接受交互降级与无热重载，可快速落地省掉 Chromium。

### 8.2 垂直切片：ChartSpec 跨端 + 图表库对比

在最小示例基础上验证真实迁移路径（`tools/poc_webview/` 的 `comparison.html` + `spec_renderers.js` + `spec_to_json.py` + `build_charts.py`）。

**核心验证主张**：「ChartSpec 作为前后端数据契约」是否成立（不经过 PlotlyRenderer，直接序列化给前端渲染）。

| 验证点 | 结果 | 说明 |
|--------|------|------|
| ChartSpec 序列化 | ✅ | 自实现 spec_to_json（dataclass → 纯 JSON，numpy → list），4 张图 336KB 一次跨桥传输 |
| 双库独立渲染 | ✅ | 同一份 ChartSpec，Plotly.js 与 ECharts 各自实现 renderer 均成功渲染 |
| 4 种分布对比 | ✅ | 柱状图 / 概率质量分布 / 累积分布 / 山脊线图，两库逐一对比 |
| 中量数据跨桥 | ✅ | 336KB JSON 经 JS-Python 桥无感（大数据 HTTP 通道仍未测） |
| 前端分箱 | ✅ | ECharts 无自动分箱，前端实现 binCounts 补齐（Plotly 有 nbinsx 自动分箱） |

**图表库对比结论（用户实测判定）：ECharts 显著优于 Plotly.js。**
- 视觉：更现代、平滑、专业
- 交互：两者均可补足缩放/保存（Plotly 默认模式栏；ECharts 需显式配置 toolbox + dataZoom，已实测可用）
- 体积：echarts.min.js 约 1MB，远小于 plotly.min.js 4.6MB

**图表库决策：定为 ECharts。** 后端 `ChartSpec` IR 保持不变（纯数据契约），前端实现 ChartSpec → ECharts 映射即可，后端零改动。

**过程中修复的一个实现 bug**：ECharts 直方图均值线最初误用 `markLine.yAxis`（画成频次水平线），改为 `xAxis`（抽数量纲垂直线）并改用 value 型 x 轴后与 Plotly 一致。

**未覆盖的验证项**：Vite HMR（需 node 工具链，属阶段 1 工程化）、大数据 HTTP 通道、config_panel 复杂表单交互。

### 8.4 组件库对比：Vue 3 生态四库实测

用 Vite + Vue 3 搭建四库并排对比 demo（`tools/poc_webview/ui_compare/`），同一组件组合（按钮/表单/表格/卡片/标签/Tab/进度/消息/对话框）逐一对比，pywebview 加载 Vite dev server 实测（顺带验证了开发期热重载架构）：

| 候选 | 视觉定位 | 实测要点 |
|------|---------|---------|
| Element Plus | 明亮稳重的蓝、成熟中后台 | 表格 hover 默认良好，交互完整，观感均衡 |
| Naive UI | 精致极简、细节动画细腻、主题定制强 | 手动表格无 hover（需数据驱动 n-data-table）；消息/对话框必须 provider + useMessage/useDialog 注入（架构约束） |
| Arco Design Vue | 字节出品、动画活泼、色彩丰富 | 按钮无 warning 预设（着色用 status="warning"）；风格更「个性」 |
| Ant Design Vue | 深科技蓝、官方企业级 | 与 Element 正面竞争，观感更「正式」 |

**决策（用户实测判定）：Element Plus。** 理由：观感最均衡（既现代又不花哨）、组件交互完整默认可用（表格 hover、消息提示开箱即用）、主流成熟生态大、与统计工具定位契合。

**过程中发现的三库实现差异**（迁移有参考价值）：Naive 消息/对话框需 provider 包裹；Arco 按钮着色用 status 属性；Ant/Element 消息为全局静态 API 开箱即用。

**前端技术选型至此全部落定：pywebview（WebView2）+ Vue 3 + Element Plus + ECharts。**
