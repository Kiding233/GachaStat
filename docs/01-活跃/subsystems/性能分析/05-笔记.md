## 2026-09-17 | 根因查明：是探针自己的 bug，不是环境限制

**触发：** 用户追问「不能查明失败真实原因吗，我可以配合你运行指令」。

**根因：`QApplication([])` 传空 argv 会让 QtWebEngine 初始化失败**（进程以 `0xC0000409` 终止），`QApplication(sys.argv)` 正常。`main.py` 用的正是 `sys.argv`，所以应用一直正常。

**六变体矩阵**（每变体独立子进程 + 25s 超时）：

## 2026-09-28 | 判据 2 改逐段底噪尺子，门控最终 PASS

**用户裁定：** 三选一里选最彻底的「逐段测底噪」。

| 段 | 该段噪声包络 | 实测效应 | 带子 |
|---|---|---|---|
| config_load | 2.9% | 1.044 | 10.0% |
| env_build | **18.5%** | 0.961 | **18.5%** |
| extract | 3.4% | 1.035 | 10.0% |
| pool_start | **10.1%** | 0.986 | **10.1%** |

±10% 套在 12 秒的「模拟」段上很宽松（该段同批底噪仅 ±2.6%），套在 0.2 秒的段上就太紧。**所以问题从来不是「10% 这个数太大或太小」，而是「同一个数套在所有段上」。**

## 2026-09-29 | 池启动优化落地；一处「推翻」被反推翻

**触发：** 接手被上下文超限卡死的上一会话（`ff072d0f`，9-16 至 9-28 累计 569 条消息），

### 一、`pool_start` 拆开：0.824 → 0.345 秒

**病因不是「进程池的开销」，是「每个 worker 重新导入主模块」。** Windows 用 spawn 起
worker，每个 worker 是全新解释器且**必须重新导入主模块**（`cli.py`）才能拿到 initializer；
而 `cli.py` 顶层原有 4 条重导入，其中任意一条都触发整个 `gacha_simulator.core` 加载
（冷进程实测 **0.204 s**），由 4 个 worker 各付一遍。

**定位手法（可复用）：** 把探针的 `__main__` 做成「轻」与「重」两版对照——
轻版 Pool 构造 0.280 s、重版（顶层 `import gacha_simulator.cli`）0.854 s、真实 CLI 0.824 s。
三者吻合，即锁定病因。**这是「对照实验优于读数分解」的一例**：不拆秒表，改一个自变量看差值。

把 4 条导入下沉到函数体后顶层只剩 `_version` / `paths`（合 0.026 s，与空解释器持平），
实测 **0.824 → 0.345 s（降 58%）**。残留的 0.345 s 是 worker 在 `_wk_init` 内导入 core 的
固有成本，那一段被「不预导入 core/service」的既有设计锁住（避开 Windows spawn 的页面文件
耗尽），不可动。

**等价性验证（用户要求的）**：`-n 200 -s 42 --output-format full` 固化基线，逐字段对照
**零差异**；全量测试改动前后各跑一次，**均为 1934 passed / 35 skipped**（改动前那份用
`git stash` 单文件暂存实测，不是推断）。

### 二、上一会话的内存结论，测错了对象

上一会话的 §12.2 宣布「父进程持有全部 n 份提取包」被推翻，依据是「实测父进程峰值 41 MB，
n 从 1000 涨到 20000 一点没动」。**我复核后判定该推翻不成立。**

原探针用 `_split_rss(os.getpid())` 取 `self`，而 `os.getpid()` 返回的是**探针进程**——
一个只起采样线程、不跑任何模拟的空壳。它的 `children()` 才是被测的 cli 进程树。于是：

- 「父进程 41 MB」测的是探针自己（恒定是必然的）；
- 「子进程 5430 MB」实为 **cli 主进程 + 全部 worker 的总和**，标签也是错的。

**按 pid 分项重测（n=2000/w=4）：cli 主进程 586.6 MB、workers 合计仅 210.6 MB。**
n 翻倍到 4000 → 主进程 1121.1 MB（**1.91x，近严格线性**），workers 只 1.33x。
**故规则 1/4 的原始理由成立**，不该被推翻；真实缺口是没把 `return_compact` / `on_result`
两个旋钮算进去。

**单变量对照确证归因**（n=2000/w=4，只换「父进程是否保留 n 份结果」）：

| 变体 | 峰值 | 保留份数 |
|---|---|---|
| A 现状（`on_result=None`，`return_compact` 默认 True）= CLI 姿势 | 588.1 MB | 2000 |
| B 加 `on_result` 流式 | 227.5 MB | 0 |
| C `return_compact=False` = GUI/WebUI 姿势 | 218.0 MB | 0 |

**主进程的 `results` 列表攒了 n 份完整 `CompactResult`，而 `cli.py` 只用它算 3 个标量。**
GUI/WebUI 早已改走 `extraction` 并置 `return_compact=False`，CLI 没跟上。

### 三、方法论：探针的测量对象必须自己核对

上一会话栽在「探针写坏」上一次（直接调 `_run_single` + 手搓 target_set，`strategy_params`
为空导致一张卡都没抽，量出的数不作数），这次是同一类问题的另一种形态：
**探针跑对了、数也真实，但量的是另一个进程。**

两处的共同点：**「我量的是谁」这一步没有被验证过。** 探针的输出看起来完全合理
（41 MB 恒定、随并发度不变），配合「父进程该是累积的大头」这个先验，反而更容易被采信。
故记一条：**探针的测量对象要在代码里显式写出并被复核**，尤其当结论是「推翻既有认知」时。
本次还顺手抓到同一族的第二个问题：`return_compact=False` 与 `on_result` 组合会让父进程
把每次模拟都误判为失败（`compact is None` 被当作失败），回调 0 次且无告警——
是「静默失效」的第 N 次复发形态。
